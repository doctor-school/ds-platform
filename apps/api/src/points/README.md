# `points` — 025 attention-points engine

Spec: `apps/docs/content/specs/features/025-attention-points-engine/` (design §1–§4, §6, §8, §9). Tables: `packages/db/src/schema/points-ledger.ts` + migrations `apps/api/drizzle/0058_points_ledger.sql` (ledger) `0059_points_rule_book.sql` (rule-book seed, `issuance` account, rule-version immutability) and `0060_points_engine.sql` (engine columns, fact journal, engine seed). Contracts: `packages/schemas/src/points/` (`points-ledger.schema.ts`, `rules.ts`, `points-account.schema.ts`).

## What ships (#3807 — the ledger core)

- `PointsLedgerService.resolvePersonAccount(personId)` — **the** account-resolution API (EARS-1). Opens the person's one `attention_points` account on first need; concurrent first needs converge on the unique (`subject_kind`, `subject_id`, `unit`). `resolveSystemAccount(code)` does the same for `issuance` / `reserve` / `sink` / `advance`.
- `PointsLedgerService.post(fact, tx?)` — **the** write entry point. Joins the caller's drizzle transaction when given (as a savepoint — a refusal rolls back only the fact; design §1), else opens its own. Refuses a fact dated more than one day ahead before touching the database (`points-occurred-at-future`, 422, EARS-27) → open every account the legs name in sorted key order, then lock the person accounts `FOR UPDATE` in id order (per-account serialisation without lock-order deadlocks, EARS-22) → insert the fact's `points_posting_keys` row; a conflict on `event_id` or dedupe key writes nothing and answers `{ status: "duplicate", postings }` (EARS-4) — even if the account has closed since → refuse a closed account (`points-account-closed`, EARS-31) → refuse a leg taking a person's available Pul below zero (`points-insufficient-pul`, EARS-22) → write the postings. System accounts are not locked: they carry no balance check, and locking `issuance` would serialise every accrual on the platform.
- `PointsLedgerService.close(personId, at)` — the personal-data-lifecycle seam (EARS-31): sets `closed_at` once; postings are untouched, no reserve is released and no obligation settled.
- `PointsLedgerService.post` also refuses a leg debiting Bre or Con from a person account unless it reverses a specific earlier posting (`points-bre-con-debit`, 422, EARS-12) — no penalty and no conversion between denominations can be written. The one-day future skew is the exported `POINTS_FUTURE_SKEW_MS`; `points-skew.spec.ts` pins it to the 0058 CHECK interval.
- Refusals are `PointsLedgerError` (RFC 7807 body via `toProblemDetails`; `PointsProblemFilter` writes it on the admin routes and hands every other exception to the shared 012 admin filter).

## What ships (#3808, #3838 — the rule engine)

Rules are data: a rule or setting is a version of one body schema, and a producer reports only what happened. Design: the 025 production amendment (A–J).

- Catalog and rule shape (code, `packages/schemas/src/points/`): `fact-types.ts` — the fact-type catalog `POINTS_FACT_TYPES` (lookup `getPointsFactType`, strict attribute parsing `pointsFactAttributesSchema`), the predicate signatures `POINTS_PREDICATES` and the forbidden-vocabulary check `findForbiddenVocabulary`, enforced over the whole catalog by `fact-types.spec.ts` (EARS-32); `condition.ts` — the condition AST (EARS-34); `rules.ts` — the one body schema `PointsRuleBodySchema` (`rule` | `setting` | `system`), per-id parsing `parsePointsRuleBody`, the settings (EARS-39), the retired 0059 ids and `POINTS_ENGINE_SEED`; `record.ts` — the `record` fact (no amount, rule or dedupe field), outcomes and trace. `rules-v1.ts` keeps the 0059 bodies only for the seed test.
- `PointsEngine.record(fact)` / `record(tx, fact)` (`engine/points-engine.service.ts`, EARS-33) — **the** entry point for every producer. Validates the fact against its catalog entry (`PointsFactRefusedError`, nothing written); a journaled `eventId` answers `duplicate` with the original applications (EARS-4). Otherwise, in a savepoint of the producer's transaction: candidates = the version of each rule active at `occurredAt` whose `trigger_fact_types` contain the type (`RuleBookService.candidatesFor`, GIN); predicate beneficiaries resolved, then every person account locked `FOR UPDATE` in ascending id; each `countPer` scope locked with `pg_advisory_xact_lock` in ascending key order, because a scope need not be a locked account (EARS-36, EARS-11); per candidate `active` → validity window → condition (`engine/condition.ts` with `engine/predicates.ts`; journal predicates include the fact itself, account reads see pre-effect state — EARS-34) → limits (`oncePer` dedupe key `<limit key>:<scope values>`, `countPer` per Europe/Moscow period `engine/period.ts`); exclusive groups (EARS-38); debits before credits, a debit needing `person.phoneVerified` (`points-phone-unverified`); one ledger fact `<eventId>#<ruleId>` per applied rule through `PointsLedgerService.post`; the journal row `points_facts` with the full trace in the same transaction (EARS-40). Outcome `applied` / `duplicate` / `no-effect`. `record(fact)` publishes `PointsCredited` after its own COMMIT; with a `tx` the producer must call `publishAfterCommit()` after its COMMIT and never after a rollback.
- Spend effects wait for #3810: publish refuses `reserve` / `settle` / `release`, a price-list `debit` and `concurrentOpen` (`engine/publish-check.ts`); for the seeded ones `record` throws on a `reserve` or price-list `debit` (fail closed) and traces `settle` / `release` `no-open-hold`. `item.*` predicates answer no-row values until the price list exists.
- `RuleBookService.publish` / `POST /v1/admin/points/rules/:ruleId/versions` (`PointsRulesAdminController`, `platform_admin`, live revalidation, amended EARS-25) — any admin slug or an existing id; `parsePointsRuleBody` then `checkRuleBody` (catalog trigger types, condition type check with `condition.`-prefixed paths, Pul only where the type earns Pul, `setting.effect.maxAmount`, limit scope fields on every trigger, at most one `oncePer`, a credit needs a limit or explicit `unlimited`); a retired 0059 id → 422 `points-rule-retired`; a past `effectiveFrom` → 422 `points-rule-effective-from-past`; a changed kind or invalid body → 422 `points-rule-parameters-invalid` with field paths. Stores the next version (with `kind` and `trigger_fact_types`) under a per-rule advisory lock in a request-audit-context transaction (`published_by` = the admin's user id), answers 201 `PublishedPointsRuleVersion` with stacking warnings. A publish never re-evaluates a journaled fact (EARS-42). No Idempotency-Key: a retried publish stores one more identical version.
- `PointsEventsPublisher` — the in-process typed publisher (apps/api has no event bus): `onCredited(subscriber)` / `publishCredited(event)`, after COMMIT only, at-most-once, a subscriber failure is logged and never reaches the producer. No subscriber is registered yet.
- Migration `0060_points_engine.sql` — `points_rule_versions.kind` + `trigger_fact_types` (GIN; both frozen by the replaced immutability function), the fact journal `points_facts` (append-only; erasure may re-point `person_id` under `app.points_erasure = 'on'`), the `countPer` postings index, and the design G seed at the epoch, each row numbered `max(version) + 1` for its id — no refusing guard (EARS-44; production pre-check #3850).

## What ships (#3813 — consumer read)

- `GET /v1/me/points` (`PointsMeController`, `doctor_guest` / `platform_admin`, fast-path) → `PointsAccount` (EARS-2): the caller's own account, the person being the session subject's live `users.id`. The route takes no person identifier; a `?personId=` naming another person is refused with 403. Unauthenticated → 401.
- `PointsLedgerService.readPersonAccount(personId)` folds the postings at read time with the pure `foldPointsAccount` (`points-balance.ts`): available per denomination = Σ credits − Σ debits of the person account; `pul.reserved` = the person's `reserve:balance` Pul of every `reserve:<registration>` fact with no `settle:` / `release:` fact yet; `advance` = the `reserve:advance` amounts of unreleased reserves, netted oldest first by the person's `obligation-settle:pul` postings (`open` = obligations not fully netted, `remaining` = what is owed). A person with no account yet reads the zero fold of an open account — the read opens no account (a read never writes). `status` is `closed` once `closed_at` is set (EARS-31).
- EARS-30: Pul is an integer with `pul.unit = "Pul"`; no field states «free» or money; `points.errors.spec.ts` sweeps every `points-*` problem detail for «бесплатно» / «баллы» / free.

## What ships (#3842 — posting history)

- `GET /v1/me/points/postings?cursor=&limit=` (`PointsMeController.postings`, same audience, fast-path, `Cache-Control: no-store`) → `PostingHistory` (EARS-46): every posting on the caller's own person account, newest first by (`occurred_at`, `id`). Same person resolution as the balance read — no person parameter, a foreign `?personId=` → 403, unauthenticated → 401; a person with no account reads `{ items: [], nextCursor: null }` and the read opens no account.
- Page size: `limit` defaults to **50**, bounded **1…100** (`POINTS_POSTING_HISTORY_LIMIT` in `@ds/schemas`). An out-of-range or non-integer `limit`, or a `cursor` this route did not issue, → 400 `points-history-query-invalid` (`PointsProblemFilter` on the route).
- Cursor: opaque base64url of the last item's keyset position (`points-history-cursor.ts`); `occurred_at` travels as Postgres's microsecond UTC text, so the keyset comparison `(occurred_at, id) < cursor` neither repeats nor skips postings sharing a timestamp (every leg of one fact shares `occurred_at`). `nextCursor` is null on the last page.
- Item: `postingId`, `occurredAt`, `denomination`, `amount` signed from the person's side (credit +, debit −), `action` (the fact type the engine wrote; null on a ledger posting no fact type produced), `contentRef` (the journaled fact's ref — the engine's ledger event id is `<fact event id>#<rule id>` — omitted when the fact has no ref or its ref is a person, e.g. `referral.attributed`), `ruleId`, `ruleVersion`, `reversesPostingId` on a compensating posting. No attribution column (`project_id`, `output_*`, `attributed_*`), counterparty account or fact subject is ever selected (`PointsLedgerService.readPersonPostings`).

## Invariants the database enforces

- Postings are immutable: a `BEFORE UPDATE OR DELETE` trigger refuses every row, and the same for `points_posting_keys` (EARS-27, EARS-4).
- `points_postings` is `PARTITION BY RANGE (occurred_at)`, monthly partitions 2026-01..2027-12 + DEFAULT, pg_partman from 2028-01; unique (`event_id`, `leg`, `occurred_at`); `rule_id` / `rule_version` NOT NULL with a composite FK to `points_rule_versions`; `amount > 0`; `occurred_at <= recorded_at + interval '1 day'` (a far-future posting would sit in DEFAULT and block partition creation); an insert trigger requires a denomination on `attention_points` postings and one unit per posting.
- A balance is a fold `Σ credits − Σ debits` per (account, denomination) — there is no balance column.

Read-side constraints on the reserve/advance writers (noted on #3810 and #3811): a reserve covered wholly by the advance writes no posting on the person account, so `foldPostings` cannot find it and `advance.remaining` under-reports until the writer gives it a person-attributable leg (or the fold re-grounds on the reserve rows); and `obligation-settle:pul` netting is global, applied oldest first, so a partially netted obligation whose reserve is later released re-applies its netting to younger obligations until settle postings name their reserve.
