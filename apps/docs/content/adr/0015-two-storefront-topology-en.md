# ADR-0015 — Two-storefront topology (doctor.school + academy.doctor.school on one platform) for DS Platform

**Date:** 2026-08-22
**Status:** Accepted
**Related to:** epic [#1430](https://github.com/doctor-school/ds-platform/issues/1430) (milestone «Doctor.School relaunch — two-site IA»), this ADR [#1432](https://github.com/doctor-school/ds-platform/issues/1432); discovery provenance — Plane `doctor-school` DSP-252 (discovery closed) and DSP-251 (wireframe R4 owner-approved); input package `apps/docs/content/specs/product/two-site-ia/`
**Inherits:** ADR-0001 §6 (IdP + session model), ADR-0002 (NestJS API + REST/OpenAPI + `@ds/api-client`), ADR-0003 (Postgres 17 + Drizzle + pgvector), ADR-0004 (Next.js 15 app-split + design system), ADR-0005 (React Native + Expo mobile), ADR-0012 (deployment topology v1)
**Sibling, in authoring:** ADR-0016 — core domain model (Issue [#1433](https://github.com/doctor-school/ds-platform/issues/1433)). Entities are named here only where the topology depends on them; their shape is decided there.

---

## Context

The Product Lead decided on 2026-08-22 to relaunch the product as **two public storefronts of one platform**:

- **`doctor.school`** — the doctor-facing storefront: specialty catalogue, schools, courses, modules and lessons, events (online and offline), attention points, documents and verification.
- **`academy.doctor.school`** — the **backstage**: projects of the Academy, catalogues of partners / projects / experts, the author and co-author workspaces, the partner (investor) workspace.

The discovery package fixes the boundaries this ADR must respect as one-way doors:

- **OWD-1** — one person = one account across both storefronts; roles (doctor, expert, speaker) are attributes, not separate logins.
- **OWD-5** — the Academy is a **separate public domain with its own audience**, but part of one ecosystem, not a separate product.
- **OWD-6** — **one platform, two fronts** (not two systems): person and school/product data are shared; the doctor has no access to the backstage.
- **OWD-7** — leaving GetCourse: content moves onto this platform, no GetCourse integration exists or will exist.
- **OWD-9** — a project is traceable across both storefronts and the whole ledger.
- **OWD-10** — the doctor sees the same lessons, events and one attention-points balance on the web storefront and in the mobile applications.
- **OWD-12** — Doctor.School stores copies of the doctor documents and is itself the issuer of the training documents.

The premise «one backend / one database» is stated in the input package as a premise **to be verified** (`README-ru.md` → stage 1). This ADR verifies it against the code that exists, then fixes the front-end topology, because the previously recorded host to application map no longer describes either the product or production:

- ADR-0004 §2 recorded `apps/promo` = `doctor.school` and `apps/portal` = `app.doctor.school`. In production since 2026-08-03 (Issue #1171) the portal is served at **`academy.doctor.school`**; `app.doctor.school` served a path-preserving 301 to it for 12 days and was then retired entirely (owner-approved 2026-08-15, Issue #1173) — it is a dead name, not a redirect.
- The doctor-facing storefront in the new picture is a **first-class product surface** with authenticated learning, a points ledger and document flows — not the marketing landing that `apps/promo` was scoped for.

---

## Decision

### 1. One backend, one database, one IdP — the OWD-6 premise holds

Both storefronts, the admin surfaces and the mobile applications are clients of **one** API, **one** database and **one** identity provider. No per-storefront backend, no per-storefront database, no per-storefront tenant.

Evidence from the code as it stands (not an aspiration):

| Layer    | Fact                                                                                                                                                                                                                                                                                               | Consequence                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| API      | `apps/api` is a single NestJS application (ADR-0002 §2/§4); the REST contract is generated once into `@ds/api-client` from the Zod SSOT in `packages/schemas`. There is no host-aware or tenant-aware routing anywhere in the application.                                                         | A second storefront is a new **client** of the same contract, not a fork.                                 |
| Database | One Postgres 17 instance with one Drizzle schema in `packages/db/src/schema/*.ts` (users, events, registrations, taxonomy, event-recordings, consent-records, audit-ledger, lifecycle, presence-beats, idempotency-keys, media-cleanup-jobs). No storefront or tenant discriminator column exists. | One person row, one registration row, one ledger — OWD-1, OWD-9 and OWD-10 are satisfied by construction. |
| Identity | One Zitadel instance at `id.doctor.school` (ADR-0001 §6); sessions are host-only cookies issued per front-end host, cross-host continuity via Zitadel and the first-party sign-in host `login.doctor.school` (§4).                                                                                 | One account spanning both hosts without a shared `.doctor.school` cookie.                                 |
| Delivery | ADR-0012 §1 — one `api-prod` plane and one `data-prod` plane.                                                                                                                                                                                                                                      | The second storefront adds a front-end container and a Caddy virtual host, nothing else.                  |

The alternatives (a backend, a database or an IdP per storefront) are rejected below, each against the one-way door it breaks.

### 2. Host to application map

```
apps/doctor/   # NEW — doctor.school            · the doctor-facing storefront (public + authenticated)
apps/portal/   # academy.doctor.school          · the Academy backstage (authenticated, role-gated)
apps/admin/    # admin.doctor.school            · Refine + 2FA, internal operations
apps/cms/      # cms.doctor.school              · Payload v3, editorial content
apps/login/    # NEW — login.doctor.school      · the sign-in host of both storefronts (§4)
```

- **`apps/doctor` is a new Next.js 15 application** built on the same `@ds/design-system`, `@ds/api-client` and `packages/schemas` as the rest. Public pages (specialty catalogue, school / course / lesson descriptions, event announcements, marketing landing) are statically generated or ISR; authenticated pages (module path, points, documents, tickets) are SSR with the host-only session cookie.
- **`apps/portal` serves `academy.doctor.school`** — the host it already serves in production. Its scope narrows to the backstage: projects, catalogues, author / co-author / partner workspaces.
- **`apps/promo` folds into `apps/doctor`.** The marketing landing becomes route segments of the doctor storefront (statically generated per route), so one host owns one information architecture and the doctor never crosses an application boundary between «read about the school» and «start the module». `apps/promo` is retired once its routes are served by `apps/doctor`; that retirement is a tracked deliverable of stage 3, not a silent deletion.
- **`apps/login` is a new, thin Next.js 15 application** on the sign-in host both storefront OIDC clients name as their login UI (§4). It mounts the same `@ds/auth-flow` sign-in, registration, verification and reset routes the storefronts mount, rendered with the originating storefront's host-config. It holds only the shared browser session; it has no product pages and no user content.
- **`apps/admin` and `apps/cms` are unchanged.** Their audiences, security perimeters and deploy cadence are unaffected by the storefront split.
- `apps/docs`, `apps/showcase` and `apps/academy-demo` are internal surfaces, out of scope here.

### 3. One application per storefront (the chosen shape)

The doctor storefront and the Academy backstage are **separate Next.js applications**, not one application routing on the `Host` header. Reasons, each tied to an existing decision:

1. **Audiences and information architectures do not overlap.** The doctor storefront is a learning product; the backstage is a workspace for experts and partners. Two applications keep separate deploys and perimeters, but the front-end _code_ is shared: every capability both storefronts render lives in one feature package (ADR-0013 §A1), and an application holds only its route files, its host config and its host-only pages.
2. **The authentication perimeters are per host anyway.** ADR-0001 §6 issues host-only `__Host-` cookies; a single application serving both hosts would still hold two independent session scopes, gaining nothing while making backstage code paths reachable on the doctor host through a routing mistake. OWD-6 («the doctor has no access to the backstage») deserves a build-time boundary, not a runtime host condition.
3. **Independent deploy cadence and isolated security perimeters** — the same rationale ADR-0004 §2 already applies to the existing app-split (ADR-0004 → Consequences).
4. **The doctor storefront is the web core of the mobile product.** Q-36 fixes the mobile applications as a cross-platform product over a web core; a storefront that is its own application shares route- and data-level primitives through `packages/*` without dragging backstage code into the mobile build graph.

### 4. Session and access across the two hosts

- **One account (OWD-1).** Zitadel is the single identity provider; a person authenticates once and is the same subject on both hosts.
- **Per-host session cookies.** The session cookie on the doctor host and the one on the academy host are separate by construction (`__Host-` cookies cannot be scoped to a parent domain). Each storefront serves the API under its own origin (a same-origin BFF proxy), so each session is a server-side record in the API's session store behind that host's `__Host-ds_session` cookie.
- **Cross-host sign-in: Zitadel is the authorization server, the sign-in host is ours.** Each storefront is a confidential OIDC client of Zitadel — one client per storefront per environment, authenticating at the token endpoint with `private_key_jwt`, PKCE `S256` required, exactly one registered `redirect_uri` (the storefront's fixed callback) and one `post_logout_redirect_uri`. Both URIs name the host the storefront is served on in that environment: in production the Academy client names `academy.doctor.school`, and the doctor client names `new.doctor.school` today and `doctor.school` from the relaunch (§7) — that move is a re-registration of the client's URIs, never a second or wildcard URI, and bare `doctor.school` is the legacy site until then. Both clients name the first-party **sign-in host** `login.doctor.school` as their login UI (Zitadel's per-application `login_version.login_v2.base_uri`; Zitadel sends the browser to `<base_uri>/login?authRequest=<id>`). Login V2 is selected per app; the instance flag `loginV2.required` stays false so each client's own `base_uri` is honoured. The sign-in host is a thin first-party application (`apps/login`, §2) that mounts the `@ds/auth-flow` forms; its server calls the API, and the API drives Zitadel's Session API v2 and OIDC service v2 as the sign-in does today. Code issuance, single use, PKCE verification, exact `redirect_uri` matching and client authentication stay Zitadel's. The flow:
  1. _Start (either storefront)._ A sign-in action calls the storefront server, which creates a **server-side transaction** through the API's internal transaction endpoint — the API generates and holds fresh `state` and `nonce` and the PKCE `code_verifier` and builds the authorize URL; the transaction holds the return path and a lifetime by kind — an **interactive** transaction (the sign-in, registration and reset entries) lives 60 minutes, a **silent** one (step 4) ≈60 s, and either is single-use. The storefront server keeps only the transaction's opaque id, in the host-only `__Host-ds_oidc_tx` cookie, and answers a top-level redirect to Zitadel's authorize endpoint on `id.doctor.school` with `state`, `nonce`, the `S256` challenge, `response_mode=query` and the fixed `redirect_uri`. The storefront's sign-in, registration and reset entries (`/login`, `/register`, `/reset`) all lead here and render no form on the storefront; the registration entry adds `prompt=create` (`PROMPT_CREATE`, `authorization.proto` field 6), so the sign-in host opens on the registration form. The interactive lifetime covers the longest flow that runs inside it. A Zitadel v2 auth request carries no lifetime of its own (Zitadel v4.17.3: `internal/query/auth_request_by_id.sql` selects it by id and instance alone, `internal/command/auth_request.go` `LinkSessionToAuthRequest` / `FailAuthRequest` check only its state, and `internal/query/projection/auth_request.go` deletes it only on success or failure), so the bound is ours: the longest code a person waits on inside the flow — the e-mail verification and password-reset codes, 3600 s (`VERIFY_EMAIL_CODE_LIFETIME_SECONDS`, `PASSWORD_RESET_CODE_LIFETIME_SECONDS`, `apps/api/src/mailer/code-emails.ts`); a password plus SMS-code sign-in fits well inside it. No person acts inside a silent transaction, so it stays short.
  2. _Sign-in host._ Zitadel redirects to `login.doctor.school/login?authRequest=<id>`. The sign-in host reads the request (`GET /v2/oidc/auth_requests/{id}`) and selects the **originating storefront's** `@ds/auth-flow` host-config by the request's OIDC `client_id`, from one fixed per-environment map: the Academy client → `ACADEMY_AUTH_FLOW`, the doctor client → `DOCTOR_AUTH_FLOW`. A client outside the map — the admin client included — is refused: the request is finalised with the OIDC error `access_denied` and no form renders. The sign-in host mounts the same `Login` / `Register` / `Reset` / `Verify` routes the storefronts mount today, so the registration field set (the doctor's optional promo field), the consents and their version, the registration and verification endpoints and payloads (`/v1/auth/register|verify` for the Academy, `/v1/storefront/doctor/register|verify` for the doctor storefront) and the brand panel copy and icons are exactly the originating storefront's; the sign-in form is identical on both. There is no second copy of any form and no sign-in-host variant of one — the host differences stay the registered host-config fields of `@ds/auth-flow` (ADR-0013 A1). When the browser holds a live sign-in-host session (`__Host-ds_login`) whose fingerprint matches, and the auth request asks for no fresh credential — no `prompt=login`, no `max_age` shorter than the time since the session's last credential check — it finalises at once with that session's Zitadel `sessionId` + `sessionToken` (`POST /v2/oidc/auth_requests/{id}`) — no form. Otherwise it shows our forms — password, e-mail code, SMS code, captcha, rate limits and anti-enumeration exactly as today, served on this host; the credential step creates the Zitadel session through the Session API v2 with an explicit `lifetime` (shared browser session below), the sign-in host sets `__Host-ds_login` in that same response and finalises with the new session. A registration ends the same way: its verification step — the step that signs a fresh registrant in today — creates the Zitadel session on the sign-in host, so a new person is signed in on both storefronts from the first sign-in. Zitadel then redirects to the storefront callback with the code.
  3. _Callback (storefront server)._ A server route that answers `GET` only and never renders a document. It redeems the code before it answers, through the API — the only holder of the storefront clients' credentials — presenting the transaction id from `__Host-ds_oidc_tx` with the callback's `state` and code; the API finds that transaction, checks `state` against it and spends it once, redeeming with the verifier it holds. The API calls Zitadel's token endpoint, checks `nonce`, and — only when the ID token's `sid` is the Zitadel session of a live sign-in-host record (requirement 8) — mints a **new** storefront session under a new `sid` linked to that Zitadel session id. The storefront sets `__Host-ds_session` and answers `303` to the stored return path with an explicit empty fragment (`Location: <path>#`); the code never reaches a rendered page. Where the person lands stays the storefront's decision: the stored return path, or, for a sign-in started with none, the storefront's own landing rules (the Academy's `/webinars`; the doctor storefront's specialty-aware `/` or `/events`, `landing.specialtyAware`). The sign-in host never chooses a landing. A callback whose `state` finds no live transaction — an interactive one past its 60 minutes, or one already used — mints nothing from it (requirement 3; its code stays unredeemable, the verifier lived only in that transaction) and leaves no error document. When the browser carries no check guard (step 4), it answers `303` into a fresh silent transaction with no return path and sets the guard, so a Zitadel session the sign-in host already holds for this browser is recovered and the person lands by the storefront's landing rules — only in this case is the return path lost. With the guard present, it answers `303` to `/` as a guest with the marker set.
  4. _The other storefront — a server-side silent check._ The storefront **server** resolves a signed-out request before anything renders, the same server-side pattern as the own-account hand-off (PR #2952: `apps/portal/middleware.ts`, `apps/doctor/proxy.ts` redirect before any render), so a signed-in person never sees a guest page first. A checkable request — a top-level document `GET` (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`) with no live storefront session, no marker cookie, no check guard and no silent transaction in flight — is answered by the storefront middleware / proxy with a top-level redirect into step 1 with `prompt=none` and the request's path and query as the return path (requirement 1, the one-shot `ds_guest=1` flag removed). Step 2 finalises it with the existing shared session, or — when there is none — with the OIDC error `login_required`. The callback then either mints the session (step 3), or, on `login_required` or any other OIDC error of a silent transaction, sets the marker `__Host-ds_guest` and answers `303` to the return path, which renders as a guest; either outcome also sets the check guard. The person sees the signed-in page or the guest page, never one after the other, and no form is shown.
     - _Marker._ `__Host-ds_guest` means «checked, signed out»: host-only, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `Max-Age` 10 minutes. Its value is its issue time and a server HMAC over it (a server-held key), no identifier; a marker whose HMAC does not verify or whose issue time is more than 10 minutes old is ignored, so a marker a script plants — without `HttpOnly`, with any lifetime — suppresses nothing. It is set by the callback of a silent transaction that ended without a session and by sign-out on that storefront, and deleted by every callback that mints a session. It only suppresses the automatic check: the storefront's sign-in entry ignores it, so a person who signed in on the other storefront within those 10 minutes passes the sign-in entry with no form (step 2 finalises with the live shared session), and the marker's expiry brings the automatic check back.
     - _Loop guard._ One check per navigation at most, by construction: every outcome of a silent callback — a minted session or the marker — also sets the one-shot check guard `__Host-ds_check` (host-only, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, 60 s). The middleware never starts a check while the guard, the marker or a live silent `__Host-ds_oidc_tx` is present, and the first document request that carries the guard deletes it. If that request resolves a session, it renders signed in; if it does not — the minted session refused on an ADR-0001 §6 fingerprint mismatch, a session-store miss, a dropped `__Host-ds_session` — it renders the guest page and sets the marker, never a second check. A client that keeps no cookies cannot hold the marker: when a silent transaction's callback arrives without its `__Host-ds_oidc_tx`, the callback burns the transaction (requirement 2 (d) when a code is present) and answers `303` to the return path with the one-shot query flag `ds_guest=1`; the middleware never checks a request carrying it, and the page's canonical URL omits it. Such a client makes one silent round trip per navigation, never a loop.
     - _Abandoned form._ Only a live **silent** transaction holds the check back; an **interactive** transaction never does. A checkable request that carries a live interactive `__Host-ds_oidc_tx` starts the silent check, which **replaces** it: the interactive transaction is deleted server-side and the cookie now names the silent one, so a form the person left never holds back the silent check for its 60 minutes. Replacing it is safe: single use and the login-CSRF binding are unchanged — each transaction is still used once and its callback still checks `state` against `__Host-ds_oidc_tx` — and a sign-in finished afterwards in the replaced form finds no transaction, so its callback mints nothing from it and follows step 3's expired-callback path. **Accepted, stated on purpose:** the replacement does not tell an abandoned form from a live one, so a registration or sign-in still in progress in another tab (a registrant waiting on the e-mail code) loses its transaction when a storefront page is opened as a document in a second tab; finished afterwards it loses its return path, and within the 60 s guard it lands on `/` signed out with the marker set, so it may render signed out until the marker expires (at most 10 minutes) or the person uses the sign-in entry, which passes with no form.
     - _Rate limits._ The silent path has its own per-IP bucket, separate from the password / code limiter (platform default 20 per 15 minutes, `apps/api/src/auth/rate-limit/rate-limit.types.ts:107`): a `scopedPerIpPer15Min` scope `oidc:silent-check`, keyed by the client IP the storefront or sign-in host server forwards, counting each silent-check start, each sign-in-host entry of a `prompt=none` auth request and each callback of a silent transaction, with a ceiling of 1200 per 15 minutes. It is sized for a clinic or hospital NAT: tens of browsers behind one address, three hits per check and one check per browser per 10-minute marker make a few hundred per 15 minutes, and the ceiling leaves several times that. Interactive auth limits are unchanged. A tripped silent limit never reaches the person as an error: a limited start answers the request with the guest page itself (HTTP 200, no redirect); a limited sign-in-host entry finalises the auth request with `login_required`; a limited callback of a silent transaction redeems nothing, deletes the transaction and ends as on `login_required` — marker, guard, `303` to the return path, rendered as a guest.
     - _Exempt requests._ The middleware starts no check for: any method other than `GET`; a request without the top-level-document fetch metadata above; a prefetch (`Sec-Purpose` / `Purpose: prefetch`) or a Next.js router request (`RSC`, `Next-Router-Prefetch`); the same-origin API / BFF routes (`/v1/*`); static assets (`/_next/*`, files with an extension, `favicon.ico`, `robots.txt`, sitemaps); `/.well-known/*` (the app-association files of §5); the storefront's own auth routes (sign-in, registration and reset entries, the callback, sign-out); and the health route.
     - _Crawlers and clients without fetch metadata._ A request whose User-Agent is on the maintained search-crawler list (Yandex, Google, Bing and the other engines the storefront is indexed by), or which carries no fetch metadata, gets the guest page directly with no redirect — the same page any signed-out visitor sees, so indexing sees no redirect and no content difference. The cost falls on browsers without fetch metadata: they get no automatic check and sign in through the sign-in entry (no form while a shared session is live).
     - _Caching._ The check redirect and every callback response carry `Cache-Control: no-store`; a page rendered for a session is `private, no-store`; a guest render of a public page keeps its static / ISR caching. The middleware / proxy decides before the page cache answers, so a cached guest page never reaches a request that is due a check.
- **Registration and reset live on the sign-in host too.** A registration finished on a storefront would end with a storefront session and no shared session — the fresh registrant signed in on that storefront only — and carrying it to the sign-in host would need a transferable ticket between hosts, the login-CSRF vector rejected below. So every flow that ends signed in — sign-in, registration with its verification, reset — runs on the sign-in host, with the originating storefront's host-config.
- **A direct visit to the sign-in host, or a stale auth request.** When the sign-in host first reads an auth request, it records the request's `client_id` in its server-side form state, keyed by the requirement-3 CSRF cookie. A request to `login.doctor.school` whose auth request Zitadel no longer returns (already handled) or that is malformed is answered with a redirect to the `/login` of the storefront that recorded client belongs to, from the same fixed per-environment map — never from a URL parameter — so an Academy person whose request went stale mid-form returns to the Academy. A request with no resolvable client — no auth request, a request this browser never opened, or any other path — is redirected to the doctor storefront's `/login`. That fallback is a deliberate lead decision (the owner's decision covers the direct visit; the doctor storefront is the primary audience): a per-environment setting, `https://new.doctor.school/login` in production today, following the storefront to `doctor.school` at the relaunch, never the legacy `doctor.school` site. Either entry starts step 1, so a browser that already holds a live shared session passes straight through to the storefront with no form.
- **One shared browser session per browser.** The sign-in host keeps exactly one record per browser behind `__Host-ds_login`, holding one Zitadel session: its id and session token, encrypted at rest (AES-256-GCM, key `SIGN_IN_RECORD_KEY`), and the ADR-0001 §6 client fingerprint (hash of UA + IP /24 + accept-language). The Zitadel session is created with an explicit `lifetime` of 30 days — the web session ceiling of ADR-0001 §6, the value the API's storefront sessions already carry (`SESSION_TTL_SECONDS`, `apps/api/src/auth/session/session.service.ts`) — so it expires on its own. The record lives no longer than that Zitadel session, expires after 7 days in which it finalised no authorize (idle timeout), and is deleted on sign-out; a storefront session minted from it expires no later than the Zitadel session, so silent sign-in never carries a person past 30 days from the credential step. A record whose fingerprint no longer matches is treated as signed out, exactly like a storefront session on fingerprint mismatch: it is deleted and its Zitadel session terminated. A live record answers every later authorize that asks for no fresh credential without a form. A fresh credential step in a browser that already holds a record — `prompt=login`, or the person signing in as another account — **replaces** it: the old Zitadel session is terminated, and with it every storefront session linked to it (one sign-out below); the new session takes the record and the cookie id is rotated. One browser never holds two shared sessions, and every storefront session of the browser is linked to the one it holds.
- **One sign-out on both storefronts.** Sign-out on either storefront is one server-side call: the API terminates the Zitadel session (`DELETE /v2/sessions/{id}`), deletes the sign-in-host record and revokes every storefront session linked to that Zitadel session id — synchronously, in its own session store — so the other storefront's next request resolves its cookie to no live session and renders signed out. Terminations that start elsewhere (the IdP console, «sign out on all devices») reach the storefronts through OIDC Back-Channel Logout: both clients register a `back_channel_logout_uri` on the API, which verifies the logout token (signature, `iss`, `aud`, the back-channel `events` claim, `sid`, no `nonce`) before it revokes by `sid`. Refresh-token reuse detected on any linked session — a refresh Zitadel refuses as `invalid_grant` — revokes the whole set the same way (ADR-0001 §6); any other refused refresh (an IdP outage, a locked person) ends only the presenting session. A password reset terminates every Zitadel session of that person and deletes their sign-in-host records, and the API revokes every storefront session linked to those sessions, as on sign-out. The platform offers no password change: a new password is set only through the reset, and any future password-change flow ends every session as the reset does. An automatic lockout (native Zitadel) ends every session of the person: Zitadel deletes their Zitadel sessions and refuses their refresh, so each linked storefront session ends at its next refresh; the platform adds no revocation of its own. Storefront sessions minted before the storefronts move to the sign-in host are linked to no shared session; the release that moves them revokes all of those sessions once, inside the 02:00–06:00 MSK window (one forced sign-in, owner-accepted on #3006), so the «0» of the one-sign-out metric holds from that release.
- **Admin is outside the mechanism.** `admin.doctor.school` keeps its own TOTP-gated session (feature 011); its OIDC client does not name the sign-in host, the sign-in host refuses its auth requests, an admin sign-in never creates a sign-in-host session, and a sign-in-host session never creates an admin session.
- **Binding security requirements** (OAuth 2.0 Security BCP — RFC 9700; OIDC Core 1.0; OIDC Back-Channel Logout 1.0). Every implementation PR carries a named test for each:
  1. _Open redirect / code exfiltration_ — each storefront client registers exactly one `redirect_uri` (its fixed callback) and one `post_logout_redirect_uri` per environment, and Zitadel matches them **exactly** — no wildcard, prefix or look-alike (RFC 9700 §2.1, §4.1, §4.11). The page the person started on never enters a redirect URI: it is a same-origin relative path stored in the server-side transaction, accepted only when it starts with `/`, not `//` or `/\`, and carries no scheme or control character, otherwise `/`. It is the path and query — the fragment never reaches the server (requirement 2 (c)) — capped at 2048 characters: a longer one is cut to its path, and to `/` when the path alone is longer. Tests: a foreign or look-alike `redirect_uri` gets no code; `//evil.example`, `https://evil.example` and `/\evil.example` return paths land on `/`; a return path with a query lands with its query; a 3000-character return path lands on its path.
  2. _Code theft and replay, XSS on a storefront included_ — the code is Zitadel's: single use, bound to its client, its `redirect_uri` and the `S256` challenge of a verifier the API generated and holds server-side; redeeming it needs the storefront client's `private_key_jwt` credential, which only the API holds, through an API redeem endpoint reachable only from the storefront servers on the internal network — the public `api.doctor.school` virtual host and the same-origin BFF proxies do not route it (RFC 9700 §2.1.1, §4.5). An XSS on a storefront that runs an authorize in the victim's browser with an attacker-prepared `state` and challenge gets no usable code: (a) the sign-in host's `/login` entry and credential pages and the storefront callback accept only top-level navigations (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`); the sign-in host answers no cross-origin credentialed request — it sends no CORS headers at all — and the form posts are same-origin `POST`s (`Sec-Fetch-Site: same-origin`) under the requirement-3 CSRF token and `Origin` check; every sign-in-host response sends `frame-ancestors 'none'` and `Cross-Origin-Opener-Policy: same-origin`, so no frame runs the flow; (b) the storefronts' own authorize requests always carry `response_mode=query`, but Zitadel honours a caller-chosen `response_mode` (`fragment`, `form_post`) for the code flow, the v2 auth request the sign-in host reads does not expose it (`authorization.proto` fields 1–10) and the OIDC application has no response-mode restriction (`application/v2/oidc.proto`: response and grant types only, Zitadel v4.17.3), so a forged mode is neutralised at the callback; (c) the callback is a server route that never renders a document: it answers `GET` only, redeems the code — or burns it, (d) — before it answers, and every response it gives, refusals included, is a `303` whose `Location` carries an explicit empty fragment (`#`), so a fragment the browser carried in (`response_mode=fragment`) is dropped instead of inherited by the landing page, and it refuses `POST` (`response_mode=form_post`) with that same `303`, reading no body — the code is never in the URL or body of a committed same-origin document a script could read; (d) a callback whose `state` belongs to another browser's transaction still redeems the code with that transaction's server-held verifier, discards the tokens, burns the transaction and writes a security audit event — the code is spent before the attacker can present it. Tests: a replayed, expired, verifier-less or foreign-client code is refused; the XSS scenario — attacker transaction, authorize in the victim's browser, the attacker presenting the code — ends with no session for the attacker; an authorize with `response_mode=fragment` leaves no readable code on any landing page; a `response_mode=form_post` callback is refused and creates no session.
  3. _Login CSRF_ — `state` and `nonce` (OIDC Core §3.1.2.1) are bound to the initiating storefront transaction, and a callback with no matching transaction is refused (RFC 9700 §4.7): nothing is minted from it, and the browser recovers only through a fresh silent transaction of its own (step 3). The shared browser session is created only from a credential the person entered **in that browser on the sign-in host**: the forms post to the sign-in host's own server with a CSRF token bound to a pre-existing `__Host-` cookie of that host and an `Origin` check, and no ticket, URL parameter or header ever carries a session into a browser. Tests: an unsolicited callback is refused; a registration whose e-mail-code step takes longer than 60 s ends signed in on the stored return path; a callback for an interactive transaction past its 60 minutes mints no session from it and, with a live shared session, ends signed in by the landing rules through the silent recovery; a cross-site post of an attacker's credentials to the sign-in host creates no session; no endpoint adopts a session from a request parameter.
  4. _Cookie theft_ — `__Host-ds_login` on the sign-in host, `__Host-ds_oidc_tx` and `__Host-ds_session` on each storefront: host-only, `HttpOnly`, `Secure`, `SameSite=Lax`, never `Domain=.doctor.school`. The sign-in host serves no user content and a strict nonce-based CSP. A test asserts the attributes.
  5. _Session fixation_ — every storefront callback mints a fresh `sid`, the sign-in host rotates its cookie id on every credential step, and neither adopts a presented session id.
  6. _Complete sign-out_ — sign-out terminates the Zitadel session, the sign-in-host record and every storefront session linked to it server-side, not only a cookie delete. Tests: sign out on host 1 with host 2 open, and host 2's next request is signed out; two credential sign-ins in one browser followed by one sign-out leave no live session on either storefront; an unsigned or foreign-audience logout token revokes nothing.
  7. _Admin isolation and the client map_ — a storefront sign-in does not authenticate `admin.doctor.school`, and the reverse; the sign-in host refuses an admin auth request. The host-config is selected only by the auth request's `client_id` from the fixed map, never from a URL parameter, header or cookie. Tests: an admin or unknown-client auth request is finalised with `access_denied` and renders no form; each storefront client renders its own registration fields, consents and brand panel and posts to its own registration and verification endpoints.
  8. _No weaker factor_ — every credential check runs unchanged on the same API endpoints, captcha and SMS budget included: the sign-in host moves where the forms render, not what they check, and the silent path only reuses a Zitadel session a credential step already checked in that same browser. Only our sign-in host finalises a storefront auth request: Zitadel sends storefront clients only to our `base_uri`, and the redeem accepts a code only when the ID token's `sid` is the Zitadel session of a live sign-in-host record; a code finalised by any other login UI — Zitadel's own Login V2 on `id.doctor.school`, still served for the console — is refused at redeem and its tokens discarded. Test: a storefront auth request finalised through the hosted login yields no storefront session. Reviewed explicitly.
  9. _Enumeration-safe and rate-limited_ — the sign-in-host forms keep the existing anti-enumeration behaviour and per-IP / per-user limits, with the client IP forwarded by the sign-in host server as the storefront BFFs forward it today; the silent-check start, login-entry, callback, redeem and back-channel endpoints take no identifier and are rate-limited; the silent path uses its own NAT-sized bucket (step 4), and a limited silent request ends as a guest render, never an error document.
  10. _Shared-session strength_ — `__Host-ds_login` carries at least the protection of a storefront session (ADR-0001 §6): the record stores the client fingerprint and checks it on every use (silent finalisation included), and a mismatch deletes the record and terminates its Zitadel session; the Zitadel session carries an explicit 30-day `lifetime` (`CreateSessionRequest.lifetime` — without it a Session API v2 session never expires, `session/v2/session_service.proto`, Zitadel v4.17.3), the record a 7-day idle timeout, and a storefront session minted from it expires no later than the Zitadel session. Tests: a `__Host-ds_login` presented from another fingerprint ends a `prompt=none` authorize in `login_required` and mints no storefront session; after the lifetime expires a `prompt=none` authorize ends in `login_required`; an idle-expired record mints nothing.
  11. _Fresh authentication and credential events_ — the sign-in host honours `prompt=login` and `max_age` from the auth request (`authorization.proto` fields 6 and 9): either one forces the credential form, measured against the session's last credential check, and the fresh credential step replaces the record; `prompt=none` with no usable record ends in `login_required`. A password reset terminates every Zitadel session of the person and deletes their sign-in-host records, which ends every linked storefront session (one sign-out); the platform offers no password change, and any future password-change flow ends every session as the reset does. An automatic lockout ends every session of the person inside Zitadel, which refuses their refresh, so each linked storefront session ends at its next refresh. Tests: `prompt=login` with a live record shows the form; a `max_age` shorter than the session's age shows the form; after a password reset the other storefront's next request is signed out and its silent check ends in `login_required`; against the real IdP a lock deletes every Zitadel session of the person and their refresh is refused.
  12. _Silent check without a flash or a loop_ — the step-4 check runs on the storefront server before any render, under the marker, loop-guard, rate-limit, exemption, crawler and caching rules of step 4; its return path is held to requirement 1. Tests: a signed-out document navigation in a browser with a live shared session gets a redirect as its first response and ends on the signed-in page; with no shared session it ends on the guest page with `__Host-ds_guest` set, and the next navigation starts no check; a client that keeps no cookies makes one round trip and lands on `ds_guest=1`, never a second; a crawler User-Agent, a request without fetch metadata, a non-`GET`, a prefetch or router request, `/v1/*`, a static asset, `/.well-known/*` and the health route are never redirected; the sign-in entry with a marker present and a live shared session passes with no form; a callback that mints a session deletes the marker; a minted session refused on the next request (fingerprint mismatch) renders the guest page with no second redirect; with the silent limit tripped, a public page answers HTTP 200 with the guest render and no redirect, and a limited sign-in-host entry or silent callback ends on the guest page with the marker set; a marker with a bad HMAC or an issue time older than 10 minutes is ignored; the check redirect and callback responses carry `Cache-Control: no-store`.
- **The host is not the authorization boundary.** Roles and organisation memberships are attributes of the person (OWD-1, OWD-8); the API authorizes every request against those attributes regardless of which storefront issued it. The academy host additionally refuses to render a backstage surface for a subject with no backstage attribute — defence in depth on top of the API decision, never a substitute for it.
- **The doctor sees exactly one trace of the Academy** — the single entry point recorded in the input package (REQ-24); no backstage navigation is reachable from the doctor storefront.

## Rejected alternatives

### A backend per storefront

Two APIs over one database duplicate every contract, guard and migration, and give the doctor storefront and the backstage two places to disagree about the same person. Over separate databases they break OWD-1 (one account), OWD-9 (a project traceable across both storefronts) and OWD-10 (one points balance) outright.

### A database per storefront

Both storefronts read and write the same person, project, school and ledger rows. Splitting them creates a synchronisation problem between two products that OWD-6 explicitly says are not two products, and turns «one balance everywhere» (OWD-10) into an integration task instead of a property.

### A separate IdP or a separate identity tenant per storefront

It reintroduces «one person, two logins», which OWD-1 closes as a one-way door. Roles are attributes of a single subject; the same person is legitimately a doctor and an expert.

### One Next.js application serving both hosts by host-based routing

It buys no session sharing (host-only cookies are per host regardless — ADR-0001 §6), couples the deploy cadence of two audiences, and turns the OWD-6 backstage boundary into a runtime routing condition instead of a build-time separation.

### Zitadel's hosted login holding the shared browser session

The IdP-native shape in its default form — Zitadel's own login app on `id.doctor.school` takes the credential, holds the browser session and answers a storefront's `prompt=none` — needs no first-party login UI at all. It does not fit our sign-in on the Zitadel we run (`ghcr.io/zitadel/zitadel` and `zitadel-login` `v4.17.3`, `infra/deploy/compose/api-prod/compose.yml`):

- **It drops our forms.** The sign-in would move onto Zitadel's login app, losing the headless first-party forms of ADR-0001 §2 and the captcha, SMS toll-fraud budget, anti-enumeration and per-IP / per-user limits our API applies there; a forked login app that keeps them is our code in a vendored application pinned in lockstep with the IdP core.
- **Its silent answer is not an OIDC answer.** Zitadel's Login V2 answers `prompt=none` only from its own `sessions` cookie on the login host, and with no session it returns an HTTP 400 «No active session found» page (`apps/login/src/lib/server/flow-initiation.ts` at tag `v4.17.3`, the `Prompt.NONE` branch), not an OIDC `login_required` redirect back to the storefront — a signed-out visitor would land on an error page instead of staying on the storefront.
- **The headless sign-in leaves no browser session anywhere.** Today the API authenticates on our forms, starts the authorize request **server-to-server** with `prompt=none` and links the checked session to it (`apps/api/src/auth/idp/zitadel.idp.ts`, `exchangeSessionForTokens`); the browser never visits a login host, so a shared browser session needs a login UI the browser does visit — which is why the chosen shape moves our forms onto the sign-in host instead.

### A first-party shared sign-in point on `api.doctor.school`

Our API would issue its own cross-host authorization codes against a marker cookie on `api.doctor.school`, with the sign-in staying on each storefront. It loses on the evidence, because Zitadel `v4.17.3` already carries the chosen shape: each OIDC application can name its own login UI (`login_version.login_v2.base_uri` — `proto/zitadel/application/v2/oidc.proto` field `login_version`, `proto/zitadel/application/v2/login.proto`; `internal/api/oidc/client_converter.go`, `Client.LoginURL`, sends the browser to `<base_uri>/login?authRequest=<id>`; «The version and the optional custom URI for the available login UI is configurable under the application settings» — [zitadel.com/docs/guides/integrate/login-ui/oidc-standard](https://zitadel.com/docs/guides/integrate/login-ui/oidc-standard)), and that UI finalises any auth request with an existing session or with an OIDC error (`CreateCallback`, `POST /v2/oidc/auth_requests/{id}` with `session { session_id, session_token }` or `error { ERROR_REASON_LOGIN_REQUIRED }` — `proto/zitadel/oidc/v2/oidc_service.proto`, `proto/zitadel/oidc/v2/authorization.proto`; Zitadel's own Login V2 finalises `prompt=none` exactly this way from its cookie). The shared point would therefore rebuild in first-party code what Zitadel already enforces — code issuance, single use, PKCE, exact `redirect_uri` matching, client authentication — and, because the credential would be entered on a storefront while the shared marker lives on another host, it needs a transferable ticket between the two hosts: a login-CSRF vector (an attacker's ticket delivered to a victim's browser) that the chosen shape does not have, since there the credential is entered on the host that holds the shared session.

### The sign-in host on `id.doctor.school` or on `api.doctor.school`

On `id.doctor.school` our forms would share an origin with the Zitadel Console and Zitadel's login app, so an XSS in our sign-in pages would reach the IdP administration session. On `api.doctor.school` they would share an origin with the API that answers the storefront BFFs and the realtime endpoints, widening an XSS on a form page into the API origin. A dedicated host keeps the shared browser session in an origin that carries nothing else.

### A shared session cookie on `.doctor.school`

Rejected by ADR-0001 §6: a cookie spanning trust zones turns one XSS or one subdomain takeover anywhere under `doctor.school` into a session theft on every host, the admin host included.

### Growing `apps/promo` into the doctor storefront

Rejected as a framing, adopted as a migration. `apps/promo` is scoped as an SSG marketing surface with no session, no authenticated data fetching and no product design surface for learning; the doctor storefront is a full authenticated product. The new application `apps/doctor` is created for that scope and **absorbs the promo routes** (§2), rather than stretching the promo application to carry sessions, a points ledger and document flows.

## Consequences

### Positive

- The «one backend / one database» premise is verified against the code rather than assumed: OWD-1, OWD-9 and OWD-10 hold by construction, with no synchronisation machinery to build.
- The second storefront costs one front-end container and one Caddy virtual host — the ADR-0012 cluster shape and the ADR-0002 API contract are untouched.
- The backstage boundary of OWD-6 is a build-time separation (a different application) plus an API authorization decision, not a runtime host check.
- The doctor storefront is the web core the mobile product needs (Q-36), sharing schemas, client and design system through `packages/*`.
- The host map in the ADR corpus now matches production (`academy.doctor.school` = the portal), so the next session reads facts instead of drift.

### Negative

- One more Next.js application to build, deploy and keep visually consistent; `apps/promo` must be migrated and retired rather than left standing (tracked at stage 3).
- Two storefronts mean two design surfaces to keep in parity with `design-source/`; a shared design system reduces but does not remove the cost.
- Cross-host continuity adds a first-party sign-in host: one more application (`apps/login`), container and Caddy virtual host. Zitadel keeps code issuance, PKCE, exact redirect matching and client authentication; our code owns the sign-in-host session record, the client → host-config map, the server-side silent check, the callback and redeem path and the back-channel logout receiver, each held to the twelve requirements of §4 and a dedicated security review per implementation PR.
- Every sign-in, registration and reset happens on `login.doctor.school`: the person leaves the storefront for the sign-in host and comes back through `id.doctor.school`. A signed-out document navigation with no marker costs one silent top-level round trip through `id.doctor.school` and the sign-in host before it renders, so a guest's first page view on a storefront — and one every 10 minutes after — depends on those two hosts answering. The release that moves the storefronts onto the sign-in host signs every storefront session out once, in the 02:00–06:00 MSK window.
- Browsers that send no fetch metadata get no automatic recognition on the other storefront; their sign-in entry still passes without a form while a shared session is live.
- Video, points and document capabilities are named as additions, not built: each is a tracked deliverable with its own cost, and none of them is a stack change.
