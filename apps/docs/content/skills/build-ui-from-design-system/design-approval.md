## Design-approval gate (user-facing surfaces)

The new _look_ of a doctor- or sponsor-facing surface is the owner's taste decision; UX mechanics, admin-kit screens and plain fields in an existing form are the lead's (AGENTS.md §7). Two non-bypassable check-ins wrap the procedure; for a `user-facing` task they gate implementation (`run-task-lifecycle` step 2 — Stage A precedes UI code; isolation and a discovery claim may happen first). The gate's surface set is **every user-visible render, not just screens**: notification emails and SMS templates (incl. IdP-rendered message texts, e.g. Zitadel's verification email) pass the same Stage-A/Stage-B check-ins — a vendor's bundled default copy shipped on a user-visible channel is a silent Stage-A bypass (#869).

**Screen composition is settled upstream (ADR-0014).** When a feature came through `do-product-discovery`, its surface LAYOUT was already picked by the owner on the Claude Design mockup (`author-design-mockup`) — build that arrangement. This gate's Stage A below remains the **element-class** pick (a class not yet in the constitution); a feature with no prior discovery mockup composes its layout here directly.

**Stage A — before any UI code (after step 5).**

- **Admin screens: approved-non-canvas by default (#3487).** An `apps/admin` section composed only from the approved admin kit — `AdminDataList` lists, full-page forms, relationship panels (`feature-012-relationship-editors-v1`), lifecycle/publish actions with the impact dialog (`feature-012-publish-lifecycle-v1`) — takes `ui-source-kind: approved-non-canvas` with no owner canvas ask. The lead records the section's states list as a comment on its Issue; that comment, linking the standing decision #3487, is the entry's `approvalProvenance`. The `tools/lint/ui-approved-sources.json` entry lands in its own PR before the implementation PR (the guard rejects a source the implementation PR adds). The owner is asked only about an element the kit lacks (e.g. a rich-text editor, 048), and only about that element; the bespoke gate of `SKILL.md` still applies to it, and its provenance is that owner decision — the lead's states list never covers it ([parity-evidence](./parity-evidence.md) → `approved-non-canvas`).
- **Brand SoT first.** Read `packages/design-system/tokens/primitive.json` (Pantone annotations name the registered brand anchors, e.g. `blue.700 #114D9E` = Pantone Dark Blue C) + the brandbook **before** assembling the package — it avoids wasted rounds.
- **Claude Design rules: read [`operate-claude-design`](../operate-claude-design/SKILL.md) first.** It is the single home of what lives in the design system «Doctor.School Design System» (published from `@ds/design-system`), the project and the prompt, the canvas inventory, the English prompt template (delta only — no token or design-system restatement, owner correction 2026-07-13, #770) and prompt provenance (an Issue comment, never a repo file).
- **Prepare the prompt, then trigger the owner.** The look pick happens in **claude.ai/design** (the Claude Design app), not in coding-agent chat prose or a wireframe — write the prompt from that skill's template and **explicitly trigger** the owner to run the taste-work there. For the element-class Stage A its «Content and host differences» and «Interactions» sections carry the feature's content contract (the fixed surface content set, IA/flows, the relevant `US-N` stories) and a «Switches» entry carries the 2–3 researched direction options as the values of one switch (the registry shortlist, **informed by the design constitution and `research-ui-element` visual-direction audit** — visual direction + the interaction floor: hover/focus/cursor/reduced-motion). Research (web-first: GOV.UK · Primer · Polaris · Carbon · React-Aria · NN/g · Baymard) comes **before** the prompt; a "research-backed standard" that only cites sources without an owner-facing pick does **not** satisfy Stage A. The owner's pick in claude.ai/design **is** the Stage-A artifact — a text `AskUserQuestion` of colour/layout options is not a valid look proposal.
- **Stage-A packaging.** Before any option set reaches the owner: drop every option the owner's stated criteria already rule out (≤1 left ⇒ present it as the default with a veto line); one label per option end-to-end (question = filename = caption); one desktop + mobile pair per option; each option opens with its provenance (registry · adoption unit · licence · net-new deps · what we configure vs write).
- **Canvas-derived options state their delta from the vendored canvas render** (e.g. a contrast-forced colour change), so a divergence never first surfaces at Stage B.
- **Restate ambiguous feedback** (a metaphor) in one line pointing at the exact element before re-rendering.
- **Read the full record first.** On resume read the whole Issue thread (`gh issue view <N> -c`) and copy every recorded design decision into the checklist; a handoff assertion alone is unverified — ask again only when the decision is absent, ambiguous or its scope changed.
- **No inversion, no silent inheritance.** Record the pick as an artifact (Issue comment / `AskUserQuestion` answer) **before** engineering — never surface the design last as a finished green PR. Every inherited template default (column side, logo, form position) is an explicit kept-or-changed choice.
- **Behavioral-change gate.** A change a doctor or sponsor would notice in what the product does — a feature removed, a different default, a change to what is saved — is its own owner-decision line **before** implementation, and the Stage-B request lists it in an explicit «поведенческие изменения» line, never only in the final summary. UX mechanics (focus, validation timing, empty/loading states, control choice within the kit) are the lead's call: decide, record, proceed.
- **DS-doc surfaces** (catalogue / showcase / viewer): research the standard doc pattern first (Storybook · Carbon · Atlassian: realistic-but-neutral render **+** slots/props table **+** state matrix); don't invent a rendering or swing between product-mirror and raw-prop-name extremes.
- **Reopened / Nth attempt:** before authoring any option, read the prior attempts' logs/PRs and write "what was rejected + the unit's purpose"; "research" means WebFetch-ing real reference pages, not snippet assertions.

**Stage B — before live-verify / merge (around step 9).** **This is the canonical Stage-B procedure** (AGENTS.md §6 is the hard rule; dev-stand docs supply mechanics). It applies only to a difference the user will see or experience — no render surface ⇒ `Stage-B: N/A — no render surface`, no owner slot (a runtime change in a Stage-check class — auth/session, IdP, email/SMS code, captcha — still needs the agent's recorded `Stage-check: PASS` on its PR slot); an invisible UI change ⇒ green CI e2e + before/after captures, no slot (`.claude/rules/change-tiers.md` → Stage-B and stands). The route follows the tier of the PR's runtime files:

- **Ship** — the owner decides in chat; no stand, no captures, no live URL. Record `Stage-B: GO — <what was decided>` with `Stage-B-head` (the current head), `Stage-B-recorded-at`, `Stage-B-owner-quote` and `Stage-B-source` (format under _Recorded Stage-B evidence_ below).
- **Show** — the lead first drives the change in the running app (accept + reject paths, dependent states, error language; AGENTS.md §6); the PR screenshots record that drive and never stand in for it. Then the owner gives the GO on those screenshots; no staging slot. Record the common fields plus `Stage-B-evidence: <https PR capture URL>` in place of `Stage-B-live-url`, and the Stage-B request names what was driven and how accept and reject behaved.
- **Ask** — the full stand procedure below.

Every GO, any tier:

- **A GO is an unconditional acceptance.** A reply that lists findings and ends «остальное ок» is a findings list, not a GO: fix the findings (or move them to an Issue the owner agrees to), re-capture, send a new request (#3454).
- **The pre-GO drive is exploratory, not the scripted path.** Before any GO ask the lead sweeps the surface as an operator — every transition from every state, repeat and out-of-order clicks, form saves interleaved with transitions, each refusal message cleared by the next success — and fixes what it finds first — the owner's GO is acceptance, not QA; a green `e2e-stage` run is not the drive (#1705, #3265).
- **The lead views every capture whole before the ask.** Open each linked capture and check the whole frame (cards, headers, clipping, empty boxes), not only the changed element; a reviewer's «no mismatch» is not this check (#2869).

The rest of this section is the Ask procedure for a visible difference. Stage A never substitutes for the live verdict: the owner re-confirms the rendered result on the running stand, which stays **up** until verdict; an unanswered approval question **BLOCKS merge** (never screenshot-only or after-the-fact).

- **Behavioral-only lead self-cert (narrow carve-out).** Only with **no new/changed visual surface** and explicit owner autonomous-merge authorization; never bypass a pending design question. On a PR without environment-sensitive paths (`.claude/rules/change-tiers.md` → Enforcement) record `Stage-B: N/A (no visual surface) — lead-certified` with green CI e2e on the head plus main-vs-head captures of every touched screen as `Stage-B-evidence`. A PR with environment-sensitive paths needs the lead's live slot run instead: record `Stage-B: N/A (no visual surface) — lead-certified; harness: <command>; run UTC: <timestamp>; report: <Issue/PR artifact URL>` and put complete owner-readable stdout and tested SHA at that URL. Webinar presence/chat uses `pnpm loadtest:room:verify`, not a build/unit/e2e summary.
- **Decision echo (when re-touching a decided surface).** The Stage-B ask MUST quote the prior decision verbatim with Issue/PR and its exact scope; never reduce it to a slogan. Any drift is visible in the ask, not discovered by the owner (#891: an IdP-email-only constraint was over-generalized until scope was re-checked).
- **Serve the configured production build.** Inspect the app's `next.config` before choosing its entrypoint. Portal and Doctor use `output: "standalone"`: build the app and its workspace dependencies with the task's `API_PROXY_TARGET` set at build time; copy `.next/static` and `public` into `.next/standalone/apps/<app>/.next/static` and `.next/standalone/apps/<app>/public`, then run `node apps/<app>/server.js` with cwd `.next/standalone`. Resolve host/ports/env from the local recipe; set the same task API target at runtime. Follow that recipe's persistent process launcher for the active OS and record cwd, PID and logs. API runs its compiled `dist/main.js`. The local owner-review stand is distinct from production deployment; `next dev` is only for the agent's iteration loop.
- **Deliver a LIVE, openable URL — on the STAGING SLOT, not on localhost.** The owner-facing stand is a per-PR slot on the staging box: `pnpm stage:slot up pr-<N> --ref <40-char sha>`, reachable at `https://<app>-pr-<N>.stage.doctor.school` behind the stand's basic-auth pair. Hand over the URL, the basic-auth credentials and the click-path for stateful steps. A screenshot is a supplement, never a substitute. Operator contract, prerequisites and lifecycle: `tools/staging/README.md` → «Stage-B: the owner-facing stand».
  - **Why not the local stand.** A `localhost` URL lives only as long as the lead's machine and session, has no HTTPS and no real IdP, and cannot be opened from the owner's phone. The local stand (`pnpm dev:ports`, `.claude/rules/dev-stand.md`) is the AGENT's own iteration and pre-Stage-B drive — it is never the surface the owner is asked to judge.
  - **The one fallback, declared out loud.** If the staging box is unreachable, a local URL is allowed only when the Stage-B ask itself states that it is a local stand and why the slot could not be raised. A silent localhost handback is a process failure, not a shortcut.
- **URL first.** The handoff's first line is the live review URL (`🔗 https://…`); screenshots follow as eyes-on artifacts, never lead or substitute for it.
- **The stand is lead-owned, its lifetime IS the verdict, and the ask is an ARTIFACT.** The lead raises the slot at Stage-B **together with a Stage-B request comment on the PR**, and sends the owner the same message in chat; the handoff prompt only POINTS at that comment, it is never the ask itself. No request comment ⇒ the slot must not be standing. The slot then stays up until the owner answers; the closeout tail tears it down (`pnpm stage:slot down pr-<N>`) alongside the worktree. A subagent supplies the ephemeral build/proof and the relaunch recipe only — subagent-held processes are reaped on return, so **never hand off a subagent-served URL** (#705). No timer, no sweeper and no clock ever gc's a slot that is waiting on a verdict. If the owner DEFERS acceptance behind a prerequisite, the slot comes down now and the PR records «re-raise after X»; an active findings loop keeps it up; rework in another session means down now and a re-raise on the new head with a NEW request. `pnpm bootstrap` (`## Stage slots`) flags every live slot whose request is missing or pins an older head.

  The **Stage-B request comment** — one comment whose FIRST non-empty line is the `## Stage-B request` heading (a preamble above it makes the comment invisible to `pnpm bootstrap`), this shape, one `<host>:` line per app in scope. Name where the sign-in credential lives, never the credential:

  ```text
  ## Stage-B request
  slot: pr-<N>
  head: <40-char head SHA>
  academy: https://academy-pr-<N>.stage.doctor.school
  doctor: https://doctor-pr-<N>.stage.doctor.school
  sign-in: <role, e.g. doctor with a specialty> — credential in <where it lives>
  walk: <step>; <step>; <step>
  asked-in-chat: <YYYY-MM-DD>
  ```

- **Press states are driven before the request.** Capture a driven `:active`/press state of every interactive element on a non-default surface, both themes (live pointer or `CSS.forcePseudoState`, one CDP session — memory `reference_cdp_forced_pseudo_state_isolation`); reasoning from markup is not verification. A round that fixes a state carries a captured BEFORE≠AFTER pair of that state, judged against rest and hover.
- **Walk links come from the stand DB.** Query the stand for the titles and ids the walk names and give direct links; never a nav label, title or slug from an earlier request (#2358).
- **An anomaly seen is re-observed, never explained away.** Anything odd in the pre-request pass is reproduced live before the request; an inference («момент загрузки») is not an observation.
- **Operator comprehension is part of the drive.** For every new form field and nav entry the verifier states what an operator would enter or expect from the rendered label + hint alone; a field whose meaning is not derivable, or a nav label that opens something else, is a FAIL even when the round-trip passes.
- **Representative stand data first** — within the session's own branch DB only (`ds_dev_<N>`: `dev:db:drop <N>` + `dev:db:branch <N>`, or realistic RU rows seeded there); the shared stand DB is seeded, never purged (`dev-stand.md` → Shared-stand discipline). E2e fixtures for user-visible text use realistic values.
- **Drive every handed URL logged-in first** — copied from the route tree (`apps/portal/app/**/page.tsx`), never guessed, and driven end-to-end in a logged-in session without unexpected redirects; a port-200 probe is liveness, not a handoff check.
- **The request is invalid unless it carries all three:** (a) URL + credentials for every surface and auxiliary service the walk touches (Mailpit/OTP UI, …), each resolved from `.env.local` / `dev:status` and curl-probed by the lead first — docker-stand services live on the recipe host, never assumed `localhost`; (b) a «changed on purpose» list of every visible removal/replacement since the previous round or the canvas; (c) a product variant choice on a user-visible element put as an explicit question, never chosen silently. The stop-state records the port pair and the relaunch recipe (worktree, env, ports).
- **Retain the task's owner-review stand until the verdict, then close its resources.** Before handback or worktree teardown, read the task's recorded owner-review obligation and latest verdict. A test-only PR or a PR-level N/A marker does not cancel a promised task-level acceptance stand. While acceptance is pending, the lead keeps the compiled stand alive and verifies each handed-back URL, with PID/worktree/branch DB and relaunch recipe recorded in the task. Preserve or relocate that stand before canonical branch teardown. After an explicit acceptance, record the verdict and autonomously finish the resource tail before the completion report: archive task evidence, run canonical worktree teardown and drop only task-owned branch databases when no retained task needs them. Verify owned listeners/worktree/task stash are gone; preserve foreign resources. No extra cleanup permission is needed within the already-authorized task scope.
- **Batched-gate carve-out (the only deferral).** When the owner's approved epic decomposition designates a dedicated **batched Stage-B gate Issue** (e.g. an epic's final «Stage-B approval» child), user-facing child PRs MAY merge on Mode-a + green CI with the owner's live Stage-B run at that gate Issue (stands stay up) — but each such PR MUST name the deferral in its body (`Stage-B: batched at #<gate>`); a silent deferral is still a violation. The deterministic pre-merge check is the `stage-b` guard (#692): `pnpm pr:preflight <N> --pre-merge` fails unless a `Stage-B: GO` / `Stage-B: batched at #<gate>` is recorded (`.claude/rules/repo-conventions.md`); the same sweep also runs the deterministic CI merge gate `pnpm merge:gate <N>` (#836). **The batch is BOUNDED:** the deferral expires at the first NEW operator/admin SECTION (not merely a new field on an existing screen) — the accumulated surface then gets a live owner pass before any further batching — and the gate Issue maintains the running list of deferred surfaces, so the batch stays a visible artifact, never a habit. Precedent: 012→017 admin surfaces shipped under batched/self-cert Stage-B and met the owner only in aggregate at slice 017 (2026-08-27) — rejected wholesale, redesign #1578.
- **Brand-asset preflight.** Enumerate logo/mark variants by **opening each asset** (`Read` the image), never judging by filename (#237). Use the clean white/mono variant directly on a coloured surface; a CSS invert filter or a `bg-card` chip is a banned hack (last resort only if no clean variant exists — then request it). **Assets are SVG (logos/icons) / WEBP (raster); PNG/JPG is a hygiene defect** (ADR-0013 §8). Exactly one logo per viewport.
- **On non-specific sign-off** ("fix the details"): apply the polish you already self-identified and re-present ONE updated view — don't re-query.

A user-facing surface entering implementation with no recorded owner design sign-off is the banned shortcut.

## Recorded Stage-B evidence (#1920)

Every affirmative record keeps its canonical marker and binds the exact reviewed head:

```text
Stage-B: GO
Stage-B-head: <40hex current PR head>
Stage-B-recorded-at: <ISO UTC>
Stage-B-owner-quote: <verbatim owner decision, no placeholder>
Stage-B-source: <https decision URL OR owner-relay:<session-id>#<message-id>>
Stage-B-live-url: <http(s) live stand URL>
```

The owner relay is auditable attribution, not cryptographic identity proof. A pure rebase carries the record: with no merge commit above `origin/main` and `git range-diff origin/main <recorded head> <head>` all `=`, the pre-merge guard accepts it and prints an audit line — the same probe as the Mode-a carry-over (#1865, #2373). A delta since the recorded head (net of `main`) made only of non-runtime files — tests, changesets, `.github/ui-evidence/**`, docs, `.feature` — carries it too, and the guard prints the carried files. A slot-report lead certification stays pinned by its `Stage-B-report-sha`. A runtime-file delta needs a fresh Stage-B record; when the original owner approval still applies, rebind it with recorded applicability evidence rather than asking the owner twice. The latest timestamped decision (recorded UTC plus native timestamps) wins; newer HOLD/NO/REVOKED/pending blocks. Failed or missing evidence reads block. A fetched decision source must contain the exact quote; a linked verification report must contain the complete recorded stdout and tested SHA. Never manufacture approval from the GitHub login of an agent-posted comment.

Every `Stage-B: N/A (no visual surface) — lead-certified` marker requires the common head/date/quote/source fields above (a real owner quote with its source, never a line copied from an instruction file) plus `Stage-B-authorization: autonomous-merge` and `Stage-B-visual-change: none`. On a PR without environment-sensitive paths that is the whole slot-free proof together with `Stage-B-evidence: <https URL>` (main-vs-head captures of every touched screen) and the green required CI e2e check on the current head. A PR with environment-sensitive paths instead carries the slot report: the `; harness: <command>; run UTC: <ISO>; report: <https Issue/PR artifact URL>` marker suffix, `Stage-B-live-verified: yes`, `Stage-B-report-stdout: <complete stdout>` and `Stage-B-report-sha: <head>`; keep complete owner-readable stdout at the report artifact — a summary of unit tests is not live verification.

For a verified **Ship** PR (`change-tier` resolves to ship) the pre-merge guard accepts a GO without `Stage-B-live-url` — it approves wording, not a stand; `Stage-B-head` stays pinned to the current head (a pure rebase carries it) and recorded-at, owner-quote and source stay required. For a verified **Show** PR a GO may carry `Stage-B-evidence: <https URL>` (a PR capture) in place of `Stage-B-live-url`; the head pin stays. A declaration below its minimum tier gets the Ask rules here and is refused by the `change-tier` guard.

For a **copy-only** PR — only user-visible strings or their formatting inputs change, certified by the latest head-pinned Mode (a) review as `render-delta: copy-only` for the body's `ui-parity: N/A (copy-only) — <reason>` ([parity-evidence.md](parity-evidence.md)) — no stand is raised: the owner decides the wording in chat, and `Stage-B: GO` carries the common head/date/quote/source fields with that decision as quote and source, `Stage-B-live-url` omitted. Without that certification a GO still requires the live URL.

For `Stage-B: batched at #<gate>` also record common head/date/quote/source fields and `Stage-B-surfaces: <comma-separated touched paths>`. The gate Issue must record `Stage-B-batch-approved: yes`, the owner-quote/source fields, `Stage-B-deferred-prs: #N,...`, matching `Stage-B-surfaces:` and `Stage-B-new-section: no`. A new operator/admin section expires deferral and needs a fresh GO. Neither a bare marker nor an agent-created gate authorizes a batch.
