# 003 — User authentication (Requirements)

## Production amendment — login email delivery (2026-09-11, #2171 / #2145)

This amendment overrides only the native login-email delivery statements in Outcomes, Scope, Constraints and EARS-6/29; the running-production baseline is retained below. The owner approved the narrow remaining-login fix through the existing mailer, without redesign or provider-chain work. The four existing BFF email families are outside this increment; #2144 and the broader #2145 acceptance remain open.

For EARS-6, the system shall obtain the verified-account login OTP through Session API `challenges.otpEmail.returnCode: {}`, suppress native delivery, and send the returned code through the existing BFF mailer and shared layout under EARS-29/30. Zitadel remains the sole generation, expiry, attempt-counting, verification and session authority. The login code is eight digits and valid for 300 seconds; the email shall state «Код действует 5 минут» and direct entry in the already-open requesting tab, with no button, anchor or navigation URL in HTML or plain text. Returned codes remain server-only and unpersisted. Missing returned code/session data or delivery failure shall preserve the enumeration-safe response; SMS and unverified-account recovery are unchanged.

The existing delivery route is reused without provider configuration or failover changes. Verify only the changed login path and its error handling, including installed return-code support, no native duplicate, normal session completion and the rendered email; retain the applicable live Stage-B owner gate. Design mechanics and exact copy: design production amendment.

The earlier authentication slices remain shipped. The Postbox transport revision (EARS-31/32, #2115) is specified here; runtime implementation and controlled activation remain open under #1059. Microsoft delivery evidence remains open under #1120.

## Production amendment — staff accounts are users, not participants (2026-09-30, #2456)

This amendment overrides only the `doctor_guest`-only account statements in Scope and EARS-26/27/28 (and design §4/§12); the running-production baseline is retained below. Owner decision on #2456: a staff account is a signed-in user of the storefronts, not an event participant.

- **Account endpoints (EARS-27/28).** `GET /v1/me/profile` and `GET`/`PUT /v1/me/display-name` (006 EARS-16) admit `platform_admin` as well as `doctor_guest` — still `access: authenticated`, `auth_check: fast-path`, self-only by the session `sub`. A staff session renders its own `/account` surface on both storefronts and signs out from it (EARS-10). A principal holding only `event-registrar` stays refused (044 EARS-19); a registrar who is also a site user holds `doctor_guest`.
- **Staff marker (EARS-26).** On every authenticated request, the session auth hooks (storefront and admin) shall set the `users.role` mirror column to the first staff role the session's project-roles claim carries, in the order `platform_admin`, `event-registrar`, `legacy_admin`, `pd_officer`, else to `doctor_guest`. The column is written only when the value changes, and a freshly healed row is marked in the same pass. The IdP claim stays the authority: the webhook/sweep upsert never overwrites `role`. The write is fail-soft like the heal. It belongs to the session layer, so the EARS-27 handler itself still performs no write.
- **Participants exclude staff.** Participant reads count only accounts whose mirror row carries `doctor_guest`: the storefront sign-up count, the roster read model, the registrar roster page (rows and total), the live room population with its expiry, and derived presence minutes (006). Per-user reads (the caller's own events and participant card) are unchanged.
- **Onboarding.** Staff grants carry `doctor_guest` plus the staff role (admin onboarding runbook, step 5). A staff member's mirror row reads `doctor_guest`, and so still counts, until their next signed-in request after the grant.

Verification: `apps/api/test/me/profile.e2e-spec.ts` (`EARS-27`, `EARS-16` and `EARS-26` staff cases), `apps/api/src/auth/mirror-self-heal.service.spec.ts` and `apps/api/src/auth/staff-role.spec.ts` (`EARS-26`), `apps/api/test/registration/staff-not-participants.e2e-spec.ts` (`EARS-26`). The staff `/account` render is a live-stand Playwright tier on both storefronts plus the Stage-B owner gate.

## Production amendment — one email code (2026-10-02, #2552 / #2553)

This amendment overrides: the sentence «The login code is eight digits…» of the 2026-09-11 amendment above; EARS-3 (verification ends in a session); EARS-6 and EARS-7 (code format only — the SMS-OTP login flow and its toll-fraud guard are unchanged); EARS-22 (the «fixed-length numeric OTP» mask); EARS-23 (account-exists notice without a code); EARS-24 (existence-agnostic `/verify` with co-equal Sign in / Reset); EARS-25 (resend issues only for an unverified registrant); EARS-29 («Preserve each Zitadel generator's format»); EARS-34 (verify-then-sign-in out-of-band); EARS-39 (cold-step password replay and `/login` routing); the Invariants lines on enumeration and on code transit; the Verification rows 6, 23, 24, 25, 29, 34 and 39, and the «masked address» of row 40 (row 7 keeps its SMS-login and toll-fraud scope with the new code format). It adds EARS-41…43. The running-production baseline is retained below. Design mechanics: design production amendment of the same date.

Production incident 2026-10-02: a congress-created account (044 EARS-4, no credential, email unverified) asked for a sign-in code, received the six-character verification code (EARS-34) and typed it into the eight-cell login step — «Код не подошёл», a loop with no exit; re-registration onto that account received a code-free notice (EARS-23/24), a second dead end. Owner decisions on epic #2552, chat 2026-10-02: «вход по коду это то же самое, что и подтверждение кодом в процессе регистрации - это очень удобно. Пользователю меньше вариантов запутаться.»; «мы же это уже решили в auth-flow. 8 ячеек просочились по ошибке! Мы уже согласовали 6!»; code-only mails with no links; one code screen for sign-in and registration with a way back to fix a mistyped address; re-registration onto an existing account: a password already set stays untouched, a missing one is set from the entered value, the profile fills only empty fields, «already registered, password unchanged» appears only in the mail, with no post-login notice; «надо всё привести к единообразию на обеих фронтах и к согласованию с макетами, то есть убрать ненужный шаг с 8 ячейками из макета и кода.»

**Lead security decision (2026-10-02, disclosed to the owner): a password set before the address was ever verified is not trusted.** Registration (EARS-1) creates the account with its password before any code is entered, so anyone can register someone else's address with a password of their own; that account stays unverified until the mailbox owner proves the address. If that password survived the owner's first code, the squatter would hold a working password on the owner's now-verified account (pre-account-takeover). The owner's «a password already set stays untouched» therefore applies to passwords set while the address was verified; a password set before the first verification is replaced or invalidated at the first accepted code (EARS-41).

- **One code kind (EARS-6, EARS-7, EARS-29 amended).** Every one-time code the system mails or texts — registration verification, its resend, login by email or SMS, password reset — shall be **six digits (0–9)**, generated, expired and checked by Zitadel (owner decision 2026-10-06, #2636). The Zitadel secret generators `VERIFY_EMAIL_CODE`, `PASSWORD_RESET_CODE`, `OTP_EMAIL` and `OTP_SMS` are converged to length 6, digits only — no letters, no symbols — as a provisioned, idempotent setting read back on every production deploy. Each generator keeps its own lifetime; the mail states the lifetime of the code it carries. The BFF accepts a submitted code only as six digits (surrounding whitespace trimmed); anything else is the generic failure (EARS-16). The client field accepts digits only and auto-submits on the sixth digit (EARS-22 amended). A code with letters issued before the change reached production is refused afterwards; the user requests a new one. SMS-OTP login (EARS-7) and its toll-fraud guard (EARS-14) are otherwise unchanged.
- **EARS-41 — one code submission.** WHEN a user submits an identifier and a six-digit code from any code step — login by code, registration, re-registration — THE SYSTEM SHALL decide on the server, by account state, which Zitadel check applies, never on a client hint: for an account whose email is verified, the Zitadel `otp_email` (or `otp_sms`) session check of the armed login challenge; for an account whose email is unverified, the Zitadel email verification check, which on success flips `email_verified` on the IdP and the mirror and appends one terminal `auth.account.verified` (channel `email`) ledger row exactly as EARS-3, and then establishes the session through a Zitadel `otp_email` challenge the BFF arms with `returnCode: {}` (no delivery) and completes at once with the returned code (design amendment). At that first accepted code of an unverified account, any password the account holds is pre-verification and SHALL NOT survive: on the registration or re-registration path the password the code step submits **replaces** it (or is set, if there is none); on the login-by-code path, or a registration step whose in-tab password is gone, it is **invalidated** and the account becomes code-only until its owner sets a password through reset (EARS-11/12). In both cases every session the account held before the code is revoked, as on reset (EARS-12). On success either branch establishes the BFF session (EARS-8) and honours the return target. A wrong, expired or already-used code, an unknown identifier and an account in any state shall return the same generic failure with status, body and timing within the EARS-16 budget; EARS-13 rate limits apply to every branch, in addition to Zitadel's own attempt counting where it applies. The BFF never generates or checks a code.
- **EARS-34 amended — login-code request.** WHEN a user requests an email login code for an identifier, THE SYSTEM SHALL keep the response byte-identical across verified, unverified and unknown identifiers (EARS-16) and SHALL, fire-and-forget: for a verified account arm the `otp_email` challenge and mail its code; for an unverified account issue the Zitadel verification code (Zitadel cannot arm `otp_email` for an unverified address) and mail it in the **same** sign-in code mail — the user sees no difference — after which entering it signs them in through EARS-41; for an unknown identifier do nothing. Ledger and no-write rules of the baseline EARS-34 are unchanged.
- **EARS-23 amended — re-registration onto an existing account.** WHEN a registration request targets an already-registered email, THE SYSTEM SHALL keep the response, status and timing identical to the never-registered case (EARS-16) and SHALL send the owner, fire-and-forget and throttled per address by the existing HMAC-keyed Redis marker, a **code mail** with no link: the code is the one EARS-34 would issue for that account state, and the copy says the address is already registered, plus — for a **verified** account with a password — «Ваш пароль не изменился», and for any other account that the password typed at registration will be saved once the code is entered. Entering the code on the registration's code step signs the owner in through EARS-41. Only after the code is accepted, the registration values the code step submits with it shall be applied: on a **verified** account the submitted password is set when the account has no password and ignored when it has one; on an **unverified** account it replaces any pre-verification password (EARS-41); submitted profile fields fill only fields that are empty and never overwrite. Before an accepted code nothing is written to the existing account — no password, profile, consent or `auth.register` row, as in the baseline. The platform consent ticked on the re-registration form is likewise applied only after the code is accepted, and only to an account that holds no platform consent yet (for example a congress-created one): it is recorded then as on a fresh registration (EARS-1); an existing consent is never overwritten and no second consent row is written. No post-login notice is shown; the return target is honoured.
- **EARS-24 amended — the registration code step.** The `/verify` step of both storefronts shall be the one code step (EARS-42) for a new and an already-registered address alike, never branching on existence: the address exactly as typed, six cells, resend with cooldown, and «← Изменить почту» back to the registration form with its entered fields preserved in the same tab. The co-equal «Уже регистрировались? Войти / Сбросить пароль» block is removed.
- **EARS-25 amended — resend.** WHEN a visitor requests a resend from any code step, THE SYSTEM SHALL re-issue, enumeration-safely, the code that fits the account state (EARS-34) — the verification code for an unverified account, the login code for a verified one — for any existing account, and do nothing for an unknown identifier; response, status and timing stay identical across all three (EARS-16), an `otp.sent` ledger row is written only when a code is issued, no `users`/consent row is written, and rate limits (EARS-13) and bot protection (EARS-17) are unchanged.
- **EARS-39 amended — no password replay.** The session after a registration code comes from the code (EARS-41), so the post-verify password replay (#175) and the cold-step routing to `/login` are retired. The registration password stays only in volatile memory of the requesting tab until it is submitted with the code. A cold step (hard reload, restored tab, expired hold) still signs in by the code, but it submits no password, so the account's pre-verification password is invalidated (EARS-41) — the server cannot tell the registrant's own unverified password from a squatter's — and the owner sets a password later through reset (EARS-11/12). A refused code keeps the user on the step with the generic error.
- **EARS-42 — one code step UI.** Login by code, registration and re-registration on both storefronts shall use one code step from `@ds/auth-flow`: heading «Проверьте почту» (SMS: «Проверьте телефон»), «Мы отправили код на <address>», six cells, resend with cooldown, and a back link — «← Изменить почту» in registration, «← Изменить способ» in login. The address is the email or phone exactly as the visitor typed it, never masked (owner decision 2026-10-05, #2607) — on this step, the reset «Новый пароль» step and every resend note; the enumeration-safe responses (EARS-16) and PD masking in logs (EARS-18) are unchanged. No eight-cell step exists on any host. Exact strings come from the owner-approved `auth` canvas redraw (#2554), which adds the code-sent state; this clause names the elements, not the final copy.
- **EARS-43 — code-method entry and the method switch.** WHEN `/login` is opened with `?method=code`, THE SYSTEM SHALL open the email-code method directly on both storefronts, keeping a same-origin `returnTo`; a plain `/login?method=code&returnTo=/account/congress` on the doctor origin stays the general entry (for example from an instruction page: the visitor types the email and requests the code), while the congress site's personal «Войти в кабинет» button after a sign-up now carries a hand-off reference (EARS-44, 044 EARS-39; 046 amendment) — both entries stay (owner decision 2026-10-06, #2626). WHEN the visitor switches between the sign-in methods «Пароль» and «По коду», in either direction, THE SYSTEM SHALL keep the email or phone already typed in the identifier field on both storefronts; a carried phone number opens «По коду» on the phone channel where the storefront serves it, any other value on email; the password and any error message are not carried (owner decision 2026-10-06, #2615).

**Invariants (amended).** Register, login-code request, resend and code submission are indistinguishable between existing and unknown identifiers and between verified and unverified accounts (status, body, timing ≤ 50 ms); per-account routing happens only in the mailbox. A Zitadel-returned code transits the BFF only as the value of an outbound mail or, in EARS-41, as the in-flight value handed straight back to Zitadel to complete the session it armed — never logged, persisted, or returned (EARS-30). An **existing** account's state — password, profile, verification — never changes before a code is accepted (a fresh registration still creates its account under EARS-1). No password set before the address was first verified survives that first verification.

**Docs outside the triplets that the implementation rewrites when it ships:** the glossary `enumeration-resistance` term (account-exists notice) — #2556; the 046 PRD journey 1, the 046 frontmatter description and the 046 design «Letters» link-origin paragraph (the confirmation-letter link) — #2557.

## Production amendment — congress hand-off to the code step (2026-10-06, #2626)

This amendment rewrites the congress sentence of EARS-43 inline (above; the site button never shipped, so no baseline text is kept) and adds EARS-44; the rest of the running-production baseline is retained. Owner decision 2026-10-06 (#2626, lead chat): no links in letters; a visitor who has just filled the Congress registration form (044) and presses «Войти в кабинет» lands directly on the code step with the code already sent — «Если он сразу нажал, то всё предзаполнится автоматом. Если с общей страницы инструкции позже, то сам введёт почту - это норм.» Mechanism (lead decision, design «Congress hand-off»): the accepted sign-up returns an opaque random reference backed by server-side state (044 EARS-39); `/login` redeems it.

- **EARS-44 — hand-off redemption.** WHEN `/login` is opened with `?method=code&handoff=<ref>` on either storefront, THE SYSTEM SHALL call `POST /v1/auth/login/otp/handoff {ref}` once per page load and, for a live reference (known by its SHA-256 hash, within 24 h of the sign-up, fewer than 3 redemptions so far), issue the login code exactly as EARS-34 does for that account state (verified → `otp_email` code; unverified → the verification code in the same mail) and open straight on the EARS-42 code step («Мы отправили код на <address>», the address returned by the endpoint), with resend and «← Изменить способ» as usual; it SHALL then remove `handoff` from the address bar (history replace) right after reading it, so a reload does not send again and the reference does not stay in history. The reference allows up to 3 redemptions (page loads) within its 24 h; each sends a code and counts as a code request under EARS-13 (per account and per IP), and a redemption the per-account EARS-13 limit refuses still consumes one of the three (the per-IP limit refuses before the reference is read and consumes none); the endpoint carries no captcha (bot protection was passed on the sign-up form) and its response timing is equalized. A 4th redemption, an expired, unknown or malformed reference SHALL get the one identical fallback response (no mail) and `/login` SHALL fall back silently to the EARS-43 state («По коду» preselected, empty field) — never an error page, never a hint whether an address has an account. WHEN an EARS-13 limit refuses a redemption, THE SYSTEM SHALL answer with the same generic throttled response as any code request (no `{address}`, no mail) and the page SHALL show the EARS-43 state with that EARS-13 generic throttled message. WHEN the browser already holds a doctor session, `/login` with a well-formed `handoff` SHALL still mount the door (the signed-in redirect off `/login` does not apply to it; a malformed `handoff` is redirected as before) and the redemption SHALL compare the reference's account with that session: for a live reference naming the session's own account THE SYSTEM SHALL answer `already_signed_in`, send no code and count no redemption, and `/login` SHALL go straight to the carried `returnTo` (validated exactly as after a sign-in; otherwise the landing); for a live reference naming another account the redemption is the one above (the code goes to the reference's account, the EARS-42 code step renders, no new screen or copy), and a correct code SHALL replace the existing session — the prior session is revoked and the browser holds only the reference account's session; a refused reference SHALL get the one fallback response and a signed-in visitor SHALL be sent to the landing instead of the form. `already_signed_in` is reachable only by a holder of a live reference who is already signed in as its account, so it discloses nothing to anyone else.
- **Out of scope.** Links in letters; any link that sends a code to an email written in the URL (it would bypass the captcha and let anyone flood an address).
- **Constraint.** The reference is 32 random bytes (base64url); the API keeps only `SHA-256(ref)` → `{accountId, identifier, redemptions}` in Redis, TTL 24 h from the sign-up, where `identifier` is the address exactly as typed in the sign-up form. There is no signing secret and no new env key; redemption state lives only in Redis.

**Invariants (added).** The reference carries no data (no account id, time or ordering); the server maps its hash to the account, so nothing decodes and no existence or age signal leaks. The hand-off endpoint reveals nothing about account existence for anything but a live reference: a missing, malformed, expired, unknown or exhausted reference gets one response, identical in status, body and timing; the address returned on redemption is returned only for a live reference, and it is the address exactly as typed in the sign-up form (the EARS-42 «Мы отправили код на <address>»), never the account's stored spelling — an existing account keeps the letter case it was first registered with, so returning it would tell an existing address from a new one. EARS-16 and EARS-13 are unchanged — each redemption is one more code request under them, and the sign-up that mints the reference already ensures an account for every accepted address (044 EARS-7), so a reference exists identically for new and existing addresses. **Leak controls (SHALL).** The reference SHALL never be logged or persisted in clear (EARS-18 redaction applies to the `handoff` query and body); `/login` responses SHALL carry `Referrer-Policy: no-referrer`; the page SHALL strip `handoff` from the address bar by history replace right after reading it. A leaked live link discloses the address and can send at most 3 codes to it within 24 h; the code itself goes only to the mailbox.

## Production amendment — auth rate limit behind one shared address (2026-10-07, #2684)

This amendment overrides the per-IP clause of EARS-13 (below); the per-user (10 / 15 min) and per-ASN (100 / h) clauses, the per-user forgive-on-success and the generic throttled response are retained. Production incident: doctors signing in by code from one hospital address received the generic throttled response after about ten sign-ins, because every code sign-in spent two units (request + submission) of one shared 20 / 15 min per-IP window. Shared public addresses (hospital, congress hall, carrier CGNAT) are a real usage shape — the congress intake is already sized for it (044 EARS-1, 60 / 15 min). Lead decision 2026-10-07 (owner-delegated).

- **EARS-13 amended — the per-IP window splits by door.** The per-IP window is held separately for two kinds of auth door. (1) **Verification doors** — password login, code login (`login/otp`), registration `verify`, `password/reset/complete`: WHEN a request through a verification door succeeds, THE SYSTEM SHALL give back the one per-IP unit that request consumed — its own unit only, never clearing the window — so this window counts failed verifications, 20 / 15 min per IP; a success interleaved between failures does not reduce the failures already counted. (2) **Sending doors** — code request (`login/otp/request`), `register` (both storefronts), resend, the `password/reset` request, the sign-in hand-off redemption: each request consumes one unit of the sending doors' own per-IP window, 60 / 15 min per IP, which a verification success never gives back. The per-user window, the per-ASN window (shared by both doors), captcha (EARS-17) and the SMS budget (EARS-14) remain the per-target and anti-bot controls. The ops per-IP override (`RATE_LIMIT_PER_IP_15MIN`) moves both per-IP windows.

## Outcomes

- A net-new visitor can self-register on the doctor portal and obtain a backend identity in the `doctor_guest` role (ADR-0001 §1), authenticated against **Zitadel as the IdP** (ADR-0001 §8).
- Credentials, sessions, tokens, OTP delivery, and password storage are **owned by Zitadel** and consumed through its Session / User v2 API — `apps/api` never reimplements an auth primitive (see Constraints and design §2).
- The doctor portal presents **headless inline forms on its own origin** (ADR-0001 §2 — Variant B; no redirect to an IdP-hosted login app). The browser holds only a `__Host-` session cookie; access/refresh tokens never reach client JavaScript (BFF pattern, design §3).
- Every authenticated principal produced by this feature is a `doctor_guest` mirror row in the backend (`users`), keyed by UUID. **Email is the primary registration identifier** (every registrant has an email); phone is a secondary identifier added/verified after registration. The mirror invariant `phone OR email NOT NULL` (ADR-0001 §3) therefore always holds via the email column. Rationale: Zitadel cannot create a login-capable human user without an email — the constraint is invariant across `AddHumanUser` v1/v2 and the newer `CreateUser` `/v2/users/new` (confirmed in `main`, proto `email … [(validate.rules).message.required = true]`), so a phone-only registration is unbuildable on this IdP (GH #202).
- Per-purpose, versioned **consent is captured at registration** before any personal-data (PD) row is created (ADR-0009).
- The mandatory v1 **security baseline** (ADR-0001 §7) — rate limiting, account lockout, enumeration resistance, SMS toll-fraud circuit-breaker, CAPTCHA — is enforced on the auth surface.

## Scope

**In:**

- Self-service registration on the portal with **email + password** (email is the primary registration identifier — Zitadel hard-requires an email on human-user creation, GH #202).
- **Email verification** (Zitadel email OTP code, delivered code-only by the BFF mailer per EARS-29) at registration. Phone verification is a post-registration secondary-identifier concern (future), not a registration step.
- **Password login** by email or phone (phone is a valid login identifier once attached to the account).
- **Passwordless email login via OTP code** (Zitadel `otp_email`; the user types the code — _not_ a magic link, see Out).
- **Phone login via SMS-OTP** (Zitadel `otp_sms`).
- **BFF session establishment**: `apps/api` completes the OIDC exchange against the Zitadel session, stores the rotating refresh token server-side in Redis, and sets a per-origin `__Host-` session cookie (ADR-0001 §6).
- **Token refresh / rotation** (opaque, single-use; refresh-reuse invalidates the chain — ADR-0001 §6, §7).
- **Logout** (server-side session DELETE → cookie cleared).
- **Password reset** (Zitadel forgot-password code flow): initiate + complete.
- **Own-mailer code-only delivery of the verify/reset codes (GH #910/#872 increment).** The email-verify (EARS-1/25) and password-reset (EARS-11) send hops obtain the one-time code from Zitadel via `returnCode` (Zitadel sends no email) and deliver it as a branded, Russian, code-only email through the BFF `MailerModule` (`apps/api/src/mailer/`), over a **Postbox-primary → explicitly enabled optional Resend failover** transport chain with per-failure observability, a log/egress scrub on the transiting code, and a documented throughput ramp (EARS-29–32, design §14).
- **Backend user-mirror** of the `doctor_guest` user, created/updated from a Zitadel Action webhook, with a minimal reconciliation sweep and a read-path self-heal for an orphaned session (EARS-26).
- **Consent capture** at registration via the ADR-0009 mechanism (records the per-purpose consent versions the registrant accepted).
- **Security baseline** (ADR-0001 §7): rate limits (per-user / per-IP / per-ASN), account lockout (native Zitadel lockout policy + our notification email), enumeration-resistant responses, SMS toll-fraud per-phone/IP/ASN limits + a global daily SMS-budget circuit-breaker.
- **Bot-protection bootstrap.** 003 is the platform's first consumer of bot-protection, so it bootstraps the mechanism behind a `BotProtection` provider interface — a Yandex SmartCaptcha adapter (server-side token verification in `apps/api`) + the widget on the portal auth forms. The provider stays swappable per ADR-0001 open-q #7; 003 owns the policy of _where_ it applies (EARS-17).
- **Auth audit events** written to `audit_ledger` (this section is the "spec §7.3" forward-referenced from ADR-0001 §7, §10).
- **Password friction reduction (GH #1331 increment).** A creation-password policy of **minimum length only** — ≥ 8 characters, **no** character-class requirement — owned **explicitly** by the IdP complexity policy (provisioning becomes the managed owner of that policy instead of inheriting the provider default) and mirrored by a single `@ds/schemas` SSOT constant; the one rule shown on the password step **before** submission and never swapped out by the error; a **show-password** toggle on every password-creation field; and honest verification-step exits when no session results (EARS-36–39, design §15).
- **Account profile v1 (GH #770 increment).** A session-scoped **profile self-read** `GET /v1/me/profile` over the existing `users` mirror (read-only — no writes, no new columns), and the **`/account` profile surface** that renders it on **both storefront hosts** — the Academy portal and `doctor.school` — through one shared account-profile block, each host supplying only its copy, transport and route table (the doctor host projects this surface until feature 022 replaces it): avatar initials + inline-editable display name (via the existing `PUT /v1/me/display-name`), email with verified state, phone row, a change-password handoff to the existing `/reset` flow, a link to «Мои события», and sign-out (EARS-27/28, design §12). The events link is the ONE element a host projection may omit rather than fake: a host that has not shipped `/account/events` hides the row instead of linking into a 404 (017 EARS-3 honest-empty), which is the carve-out the doctor storefront ships in #1958.

**Explicitly out** (each is a documented seam consumed by a later vertical — design §7):

- **Legacy-doctor reactivation** (the ~10k Directual hard cutover, hash-compat vs forced reset, first-login flow). Stays an operational artifact + later spec per ADR-0001 §9. 003 only exposes the primitives it will reuse (email-OTP, SMS-OTP, consent capture, mirror sync).
- **MFA enrollment / enforcement.** `doctor_guest` carries no MFA mandate (ADR-0001 §4). 003 ships the `mfa` claim in the session (ADR-0001 §1) and a documented `role → mfa_required` policy seam, but builds **no** TOTP enrollment/verification and populates the policy with **no** elevated roles. The first vertical with a mandatory-MFA role (admin/ops → `platform_admin`; v2 `expert` etc.) builds the mechanism.
- **Magic-link** (clickable login URL). Superseded for v1 by native email-OTP. A thin transport over the native one-time secret + the ADR-0001 §8 security review remains a seam.
- **Authentication of `platform_admin` / `legacy_admin`.** Those are provisioned/ops principals (admin-console vertical) or cutover-owned (ADR-0001 §9), not self-registration outputs.
- **Mobile auth** (device-id-bound refresh, Keychain/Keystore, biometric unlock, native OAuth hop — ADR-0001 §6, ADR-0005). Separate iteration over the same backend primitives.
- **Social OAuth** (VK ID / Yandex ID / Telegram) — v2 per ADR-0001 §5; **account linking** — ADR-0001 §6.2.
- **Step-up authentication** for high-risk actions (ADR-0001 §10) — no high-risk `doctor_guest` endpoints exist yet.
- Full **consent subsystem** (withdrawal, version migration, consent audit) — owned by the ADR-0009 vertical; 003 only captures at registration.
- WebAuthn / Passkeys, HIBP pwned-password check, anomaly/impossible-travel detection — deferred per ADR-0001 deferred-gaps table.
- **PD-lifecycle actions on the profile surface** (152-ФЗ personal-data export / deletion / consent withdrawal). No backend for these exists — the ADR-0009 vertical owns them; they are tracked as a separate follow-up Issue, **not** silently implied by `/account` (F-22: no untracked seam).
- **MFA management from `/account`** (enroll / disable / factor list) — follows the MFA seam above; the v1 profile surface shows no MFA controls.
- **Phone editing from `/account`** (attach / change / verify a phone) — the post-registration secondary-identifier increment (EARS-2/4); v1 renders the phone read-only.
- **Login email-OTP rendering migration.** The EARS-6 email remains generated, rendered and sent by Zitadel (`verifyemailotp`, #878). Its SMTP relay changes to Postbox through the shared `IDP_SMTP_REAL_*` configuration and existing reconcile; the BFF failover chain does not cover this native send. Moving generation/rendering/delivery into the BFF is outside #1059.
- **Forced rotation / re-validation of existing passwords** under the relaxed policy (EARS-36). The policy governs password **creation** (register, reset-complete); login keeps its permissive shape guard so every credential predating the change still authenticates. No mass reset, no "your password no longer conforms" prompt.
- **Compromised-password (HIBP k-anonymity) check.** The honest residual of the length-only policy — a long, weak, breached passphrase passes. Deferred per ADR-0001's deferred-gaps table (DSO-26); the compensating controls that carry the risk meanwhile are the shipped EARS-13 rate limits, EARS-15 lockout, and EARS-16 enumeration resistance. Named here, not silently implied (F-22).
- **Passwordless registration** (email + consent only, password set later) and any change to the login-side identifier/OTP surfaces — a separate product decision, not part of this increment.
- **Bulk / marketing email.** Newsletters (Unisender classic / GetCourse flows) stay as-is; the §14 transport chain governs the platform's transactional sends only (#872 scope fence).

## Constraints

- **SMTP provider coordination (#2116, design §14.5).** Existing provisioning, runtime reconciliation and BFF configuration share `IDP_SMTP_REAL_PROVIDER` and provider-scoped identities. Preserve flag synchronization, nonproduction intercept and SMS behavior. Canonical deployment checks native readback before replacement and again after the new application starts; the transition is not atomic because the old application may still use or reselect mail.ru. Failed activation restores the coherent prior BFF environment and retained native ID, with real native/BFF receipt proof.

- **IdP boundary (hard).** Credential verification, session lifecycle, token issuance/rotation, JWKS/OIDC, one-time-code **generation / validation / expiry / attempt-counting**, password storage, and account-lockout counting are **native Zitadel** features — consumed via the Session / User v2 API, never reimplemented in `apps/api`. Code **delivery** is split deliberately: SMS-OTP and the login email-OTP stay Zitadel-sent, while the email-verify and password-reset codes are obtained via `returnCode` and delivered by the BFF mailer (EARS-29, design §14) — the BFF transports the code; it never generates or checks one. The native-vs-custom split is fixed in design §2 (table). AGPL §13 discipline applies: integrate via API/Actions/config only; **do not patch Zitadel source** (ADR-0001 §8).
- **UI model = Variant B (headless inline).** Forms live on the portal origin; the BFF brokers Zitadel calls. No IdP-hosted login app, no auth-subdomain redirect for credentials (ADR-0001 §2). Zitadel Login v2 was considered and rejected for v1 (design §8 — recorded so it is not re-litigated).
- **No hardcoded origin.** The portal origin / cookie domain are read from configuration, never hardcoded in code or spec (mirrors AGENTS.md §9.1). `__Host-` cookies are origin-bound by construction.
- **Tokens** (ADR-0001 §6): access JWT 15 min (RS256/ES256); refresh opaque, rotating, single-use, 30 d web; refresh stored server-side in Redis on the BFF; `__Host-` cookie HttpOnly + Secure + SameSite=Lax, per-app origin (no cross-subdomain shared cookie). JWT claims minimal: `sub, roles[], mfa, sid, iat, exp, jti` — no `permissions[]`.
- **Identifiers** (ADR-0001 §3): UUID is the sole FK key; `phone` and `email` both unique, both login methods; CHECK `phone OR email NOT NULL`.
- **Consent before PD** (ADR-0009): no PD-bearing `users` row is committed before the registrant's per-purpose consent versions are recorded.
- **Pinned Zitadel version.** The deployed Zitadel must be a release patched against the known login-UI enumeration bypasses — CVE-2024-41952 ("ignore unknown usernames" flag not honoured), CVE-2025-57770 ("select account" page), and CVE-2026-23511 (password-reset endpoints + Login UI V2) — i.e. **≥ 4.9.1 (v4) or ≥ 3.4.6 (v3)**. Pinning a patched version is part of the Definition of Done; our rate-limit + enumeration-resistant responses are the defense-in-depth backstop (ADR-0001 §7).
- **Stack** (ADR-0002): Node 22 LTS, TS strict, ESM-only; NestJS 11 + Fastify + `nestjs-zod`; schema SSOT in `packages/schemas/`; URI versioning `/v1/...`; Vitest + supertest. Service-dependent tests `skipIf` their dependency env (`DATABASE_URL`, `IDP_ISSUER`) is absent, so they do not redden `main` in the shared CI unit job.
- **Audit** (ADR-0003 §6): auth events are appended to `audit_ledger` (append-only, 3-year retention); PD is masked in logs.

The auth vertical is the platform's first real aggregate cluster (unlike the query-only 001/002). Ownership is split across the IdP boundary: **Zitadel** owns credential/session/token state; **`apps/api`** owns the domain mirror, consent, RBAC role grant, audit, and the abuse-prevention guards.

### Read models

- **`UserMirror`** — backend `users` row: `id` (UUID PK), `zitadel_sub`, `email?`, `phone?`, `email_verified`, `phone_verified`, `role = doctor_guest`, timestamps. Invariant `phone OR email NOT NULL`.

- **On `UserRegistered`** → record `ConsentCaptured`, grant `doctor_guest`, upsert `UserMirror` (`MirrorSynced`). PD activation gated on consent.

## EARS requirements

> **Numbering convention:** flat (`EARS-1`, `EARS-2`, …) per ADR-0006 §4. EARS-1…12 are the functional handlers (each becomes a child Issue); EARS-13…22 are cross-cutting ubiquitous / unwanted-behavior requirements enforced across the surface. The `ears-tests` CI guard is content-match WARN in Phase 0.

**Registration & verification**

- **EARS-1:** When a visitor submits the registration form with a valid email and a policy-conforming password, the system shall create a Zitadel user, record the accepted per-purpose consent versions (ADR-0009), upsert a `doctor_guest` `UserMirror` row, trigger an email verification code (obtained and delivered per EARS-29), and respond without disclosing whether the email pre-existed (enumeration-resistant, EARS-16).
- **EARS-2:** Email is the **primary registration identifier** (per EARS-1); phone is a **post-registration secondary identifier** (added/verified after the account exists), **not** a registration channel. There is no phone-only registration — Zitadel cannot create a login-capable human without an email (invariant across `AddHumanUser` v1/v2 and `CreateUser` `/v2/users/new`, confirmed in `main`; GH #202). Phone as a _login_ identifier (EARS-5) and SMS-OTP login (EARS-7) are unaffected — they operate on an already-attached, verified phone. (The post-registration "attach + verify a secondary phone" surface is a future increment, not built here.)
- **EARS-3:** When a registrant submits the email verification code, the system shall verify it via Zitadel `otp_email`, mark `email_verified` on the mirror, and emit one terminal `auth.account.verified` (channel `email`) row to `audit_ledger`; an invalid/expired code shall return a generic failure, emit no terminal row, and count against the OTP attempt limit.
- **EARS-4:** Registration verification is **email-only** (EARS-3). Phone verification (`phone_verified` via Zitadel `otp_sms`) is a post-registration secondary-identifier concern (future), not a registration step — there is no phone to verify _at registration_ because registration is email-primary (EARS-2). The verify port/handler still distinguishes channels for the future secondary-phone path; the SMS-OTP _login_ code path (EARS-7) is unaffected.

**Login**

- **EARS-5:** When a user submits identifier (email or phone) + password, the system shall create a Zitadel session with a password check; on success it shall establish a BFF session (EARS-8); on failure it shall return an enumeration-resistant generic error and increment the lockout counter.
- **EARS-6:** When a user requests an email login code and then submits it, the system shall verify it via Zitadel `otp_email` and, on success, establish a BFF session (EARS-8). (This is the v1 passwordless email path; no magic link.)
- **EARS-7:** When a user requests an SMS login code and then submits it, the system shall verify it via Zitadel `otp_sms` and, on success, establish a BFF session (EARS-8), subject to the SMS toll-fraud guard (EARS-14).
- **EARS-8:** When a Zitadel session has passed its required check, the system shall complete the OIDC exchange, store the rotating refresh token server-side in Redis, mint the access JWT (claims `sub, roles[], mfa, sid, iat, exp, jti`), and set a per-origin `__Host-` HttpOnly+Secure+SameSite=Lax session cookie; the browser shall never receive a token in a response body.

**Session**

- **EARS-9:** When a client presents a valid session cookie whose access token is expired, the system shall rotate the refresh token single-use and issue a new access token; if a refresh token is replayed after rotation, the system shall invalidate the entire chain, revoke the session, and emit `RefreshReuseDetected` (ADR-0001 §6/§7, RFC 6819).
- **EARS-10:** When an authenticated user requests logout, the system shall DELETE the server-side session (invalidating its refresh chain), clear the `__Host-` cookie, and emit `SessionRevoked`.

**Password reset**

- **EARS-11:** When a user requests a password reset for an identifier, the system shall trigger the Zitadel forgot-password code flow — the code obtained via `returnCode` and delivered code-only by the BFF mailer (EARS-29) — and respond enumeration-resistantly regardless of whether the identifier exists (ADR-0001 §7; backstops the Zitadel reset-flow enumeration advisory).
- **EARS-12:** When a user submits a valid reset code and a policy-conforming new password, the system shall set the new password via Zitadel, revoke all of that user's existing sessions, emit `PasswordResetCompleted`, and establish a new authenticated session for the subject (auto-login — setting the `__Host-` session cookie, with no token in the response body per EARS-8).

**Cross-cutting (ubiquitous / unwanted-behavior)**

- **EARS-13:** The system shall rate-limit auth endpoints per ADR-0001 §7 — per-user (10 / 15 min), per-IP (20 / 15 min), per-ASN (100 / h) — returning a generic throttled response without revealing account existence; a successful login — by password or by code (EARS-6/7/41, every door that establishes the session from a code) — or password-reset-complete clears (forgives) the per-user window for that identifier (the per-IP / per-ASN windows are not forgiven).
- **EARS-14:** While issuing SMS (verification or login OTP), the system shall enforce per-phone (3/h), per-IP (10/h), per-ASN (100/h) limits and a global daily SMS-budget circuit-breaker (≤ 2000/day), refusing further sends when any threshold is exceeded.
- **EARS-15:** When a user reaches 10 failed password attempts within 30 min, the system shall soft-lock the account (native Zitadel lockout policy) and send a notification email; the account unlocks per policy.
- **EARS-16:** The system shall return idempotent, enumeration-resistant responses on register / login / reset with a timing delta ≤ 50 ms between the existing-account and unknown-account paths (ADR-0001 §7).
- **EARS-17:** When a visitor initiates an abuse-prone unauthenticated action, the portal shall execute Yandex SmartCaptcha through the provider's native **invisible, on-demand** flow and shall resume the pending action exactly once with a **fresh, single-use** token; no permanent checkbox shall occupy an auth form, and provider challenge UI shall appear only when Yandex requires it. Registration, an initial email/SMS login-code request, an initial password-reset request, and **every** verification/login/reset resend are protected this way. Password login shall start without CAPTCHA; only the stable backend `BOT_PROTECTION_REQUIRED` outcome after the failed-login threshold shall execute a fresh challenge and retry the original login values exactly once. Email-verification-code confirmation, login-OTP confirmation, and password-reset completion shall never request CAPTCHA. The widget shall use the portal's resolved light/dark theme initially and follow live theme changes. Every expiry, rejection, script/network failure, or dismissed incomplete challenge shall terminate and reset that attempt, preserve entered form data, and show truthful localized CAPTCHA-specific feedback; a successful later solve shall clear only that feedback, and neither a token nor a provider callback may replay an action.
- **EARS-18:** The system shall append every auth event — `auth.{register, account.verified, login.succeeded, login.failed, logout, token.refresh, token.reuse_detected, password.reset.requested, password.reset.completed, otp.sent, otp.verified, otp.failed, lockout, consent.captured}` — to `audit_ledger` (ADR-0003 §6) with PD masked.
- **EARS-19:** When Zitadel emits a user create/update Action webhook, the system shall upsert the corresponding `UserMirror` row, ensure the `doctor_guest` role grant, and reconcile divergence on a periodic sweep (eventual consistency, ADR-0001 Consequences).
- **EARS-20:** When a registration is processed, the system shall record the registrant's accepted per-purpose consent versions (ADR-0009) and shall refuse to activate the PD-bearing mirror row if consent is absent.
- **EARS-21:** The portal auth UI shall render in **Russian (primary)** with **no hardcoded user-facing strings** — all copy (labels, descriptions, buttons, placeholders, the consent line, and error messages) sourced from a typed message catalog over an i18n-ready structure, so a future locale can be added without re-touching components; **RU-only ships now with no user-facing language switcher** (the i18n infrastructure is present for a later locale). (Design §8.1.)
- **EARS-22:** Each portal user-input field shall apply the client-side validation rule and input mask relevant to its data type — email shape, E.164 phone with mask, fixed-length numeric OTP, password policy — before submit, surfacing obviously-malformed input with localized (RU) copy from the message catalog (EARS-21); this is a UX affordance only — the BFF/IdP remains the credential authority (Constraints) and the request schemas stay loose, so a field that declares no relevant rule states "none" with a one-line reason. (Defects #192 (`/login` identifier) and #196 (`/reset` identifier) motivate this; enforcement — semantic field primitives + an ESLint gate — is tracked in #197. Design §8.2.)
- **EARS-23:** When a registration request targets an **already-registered** email, the system shall send an _account-exists notice_ email to that address — a single “Войти” action to the configured portal /login route (no password-reset link) carrying **no** verification code, login code, token, or new account/PD — so the legitimate owner is never stranded, while the API response, status, and timing stay **identical** to the never-registered case (EARS-16). The notice send is **fire-and-forget** (off the response path, so SMTP latency cannot leak as a timing oracle) and **throttled per-address** (an ephemeral, HMAC-keyed Redis marker with a short TTL — never a persistent, queryable per-email record), so the registration form cannot be turned into an inbox-flooding tool; a send failure is logged only and never alters the response. The already-existed branch still creates no account, writes no `users`/consent row, and appends no `auth.register` ledger entry. The BFF gains its own transactional-email channel (`MailerModule`), **distinct** from Zitadel's identity-credential notifications (codes / OTP / reset). (Defect #207. Design §4.)
- **EARS-24:** The post-registration confirmation screen (`/verify`, the one confirmation route of both storefronts, reached by the registration door's hop with the address and the return target in the query) shall present a **single, existence-agnostic** view that serves the new and the already-registered visitor without the client ever learning which it is: it frames the step as "check your email" and offers, as co-equal affordances, **(a)** entering the email code (the new registrant's path — unchanged auto-submit + post-verify auto-login, #175/#194) and **(b)** prominent **Sign in** / **Reset password** actions (the already-registered owner's path). The screen shall never branch on account existence — the BFF deliberately does not disclose it (EARS-16) — and the existing owner's correct path is also delivered privately in the EARS-23 notice email. Copy is sourced from the message catalog (EARS-21). (Resolves the duplicate-registration dead-end where an existing user was routed to an imperative "enter your code" screen for a code that never arrives; defect #207. Design §8.3.)
- **EARS-25:** When a visitor on the existence-agnostic `/verify` screen (EARS-24) requests that the registration email verification code be **re-sent**, the system shall re-trigger the Zitadel `otp_email` verification code for that identifier (re-issued via `returnCode` and delivered per EARS-29) and respond **enumeration-resistantly** regardless of whether the identifier exists or is already verified (mirroring EARS-11/EARS-16) — a code is re-issued only for an existing, unverified registrant, while the response, status, and timing stay identical to the unknown / already-verified case. The resend resolves the identifier → Zitadel `sub` without disclosing existence (the same enumeration-safe wrapper as `RequestPasswordReset`/`RequestEmailOtp`) and is subject to the EARS-13 rate limits; it creates no `users`/consent row and appends an `otp.sent` ledger row only when a code is actually issued. (The new registrant whose first code did not arrive can re-request it without re-typing the password; the already-registered owner's co-equal Sign in / Reset password affordances and the EARS-23 notice email are unaffected. Design §4.)
- **EARS-40:** When `/verify` is opened with no address — no same-tab `?email=` query (the verification mail is link-free, EARS-29, so the query is the only carrier) — the system shall send the visitor to `/register` before the verification step is shown, replacing the address-less `/verify` in history and carrying the return target (`returnTo`, the EARS-2 context) onward when a same-origin one is present; the verification step is never shown without an address to name, so it has no generic-identifier description, no address-less submit and no address-less resend. The route renders nothing on such an arrival — no step and no page frame (design §8.3). The `?email=` entry renders the step as before. Owner decision 2026-09-28 (GH #2394). The verification canvas's address-less error state («Не удалось определить аккаунт…», the `ошибка` tab of the «Подтверждение» frame) is retired by this clause and removed from the canvas under GH #2403. (Design §8.3.)

- **EARS-26:** When an authenticated request's session subject resolves (a valid IdP session) but no `users` mirror row exists for its `zitadel_sub` — a webhook miss/lag the sweep has not yet closed, or a mirror row lost while IdP sessions for that sub stay alive — the system shall lazily re-materialize the mirror row from the IdP **before the handler runs**, performing the same idempotent upsert + `doctor_guest` re-grant the EARS-19 webhook/sweep perform, and serve the request as normal, so the orphaned-session state can never bounce authenticated surfaces into the silent `/login` → `/account` redirect carousel. A sub the IdP no longer knows (or an identifier-less machine account, not a `doctor_guest` mirror candidate) heals nothing, and the mirror-backed handler keeps its fail-closed generic 401; responses to genuinely unauthenticated callers (EARS-16) are unchanged. (GH #709 — the third mirror-sync layer: webhook primary, sweep backstop, read-path self-heal lazy. Design §4.)

**Own-mailer code delivery (GH #910 / #872)**

- **EARS-29:** When the system triggers an email verification code (the EARS-1 registration cascade or the EARS-25 resend) or a password-reset code (EARS-11), it shall obtain the one-time code from Zitadel via the **`returnCode`** delivery variant — Zitadel generates, stores, expires, attempt-counts, and verifies the code but sends no email — and shall compose and dispatch the branded, Russian, **code-only** email through the BFF `MailerModule` (`apps/api/src/mailer/`, design §14): the code leads the subject and appears in the body as one unbroken enlarged token with an explicit expiry line, and the mail carries **no link or button of any kind** (the owner-picked Notion/Slack-style artifact, design §13.3/§13.4). Code verification stays Zitadel-native (EARS-3/12) — the BFF transports the code; it never generates or checks one. The existing layout is reused across transactional kinds without changing its visual values (design §13.5, #2171). HTML and plain text shall carry the same instructions, code, expiry and permitted actions. Every code-mail block, including the footer, shall be free of navigation URLs as well as links/buttons; the instruction shall direct entry in the already-open requesting tab. Registration and unverified-account login shall use trigger-appropriate copy. Preserve each Zitadel generator’s format and lifetime; verified-login delivery migration remains owned by #2145, not this layout change.
- **EARS-30:** While a Zitadel-returned one-time code transits the BFF (EARS-29), the system shall hold it in memory only for the duration of the in-flight send and shall never write it to logs, traces, error reports, provider-response echoes, or `audit_ledger` rows (a testable egress/log scrub over every send outcome — success, failover, and total failure); no persistence of the code exists beyond the send.
- **EARS-31:** When the BFF mailer dispatches in real mode, it shall use the explicitly selected SMTP primary, with **Postbox for all recipient domains** as the target topology; explicit mail.ru configuration remains supported for deployment before activation. Resend shall remain dormant unless both its failover enable switch and valid credentials are supplied; credentials alone shall never select or promote a provider. Missing, unknown or inconsistent real-mode configuration shall fail loudly without sending to Mailpit or another provider; Mailpit is used only in explicitly selected intercept mode. Each attempt shall terminate within the bounded deadlines and cancellation contract in design §14.3. A definite pre-acceptance rejection may switch once to the explicitly enabled fallback, with no same-channel retry. An uncertain acceptance outcome shall terminate without automatic failover. A provider acceptance (SMTP final 2xx / HTTP 2xx) shall mean **accepted**, never proven delivered or placed in Inbox; no automatic failover occurs after acceptance. Exhausting eligible channels or a deadline shall fail closed internally, with sanitized diagnostics (EARS-30/32) and the unchanged enumeration-safe API response (EARS-16). (#1059; design §14.)
- **EARS-32:** The system shall surface every BFF mailer failover, configuration error, timeout and relay failure as a structured log and metric labelled with the **actual configured provider** and sanitized response/error code, with the existing GlitchTip failure reporting. It shall distinguish primary acceptance, fallback acceptance, uncertain outcome and total failure, without representing SMTP acceptance as mailbox delivery. Diagnostics shall contain no credentials, recipient address, subject, body or one-time code (EARS-30). Native Zitadel SMTP delivery remains separately observable; its failures shall not be represented as covered by BFF failover. (#1059/#1120; design §14.)
- **EARS-33:** When the BFF dispatches a transactional email or SMS and the synthetic-send suppression toggle is on (`LOADTEST_SUPPRESS_SYNTHETIC`, default **off** → the seam is fully inert), the system shall drop — **before** the relay/provider call — any send addressed to a synthetic-tagged recipient (a reserved recipient-domain suffix, default `@loadtest.invalid`, parameterized by `LOADTEST_SYNTHETIC_DOMAIN`; the SMS path uses the analogous reserved-recipient match) and count it on a loud per-suppression metric + log line (the transport is never contacted, so **zero** real send leaves the box), while every send to an **untagged** recipient proceeds unchanged. With the toggle **off**, all sends — tagged or not — proceed normally. The seam sits at the **same single mailer/SMS send point** as EARS-29/31, matched by recipient only and **after** the identical request-shape pipeline the load test must exercise (enumeration-safe wrapper, `register-notice-throttle`, artifact composition — the campaign measures the real pipeline minus the relay hop); it never flips the global `EMAIL_DELIVERY_MODE`/`SMS_DELIVERY_MODE`. The three-state matrix is **fail-closed on the toggle** — off → normal (every case); on + tagged → suppressed + counted; on + untagged → normal — so a missing/false toggle can never suppress a real user's mail. Backend-only (no UI trigger anywhere; verified by Vitest unit/e2e alone). (Load-test #873 phase-2 prerequisite — synthetic auth-burst sends never reach real channels or burn sender reputation or provider quota; #1068 blocks #873. Design §14.8.)

**Account profile v1 (GH #770)**

- **EARS-27:** When an authenticated user requests `GET /v1/me/profile`, the system shall return the session subject's **own** identity fields from the `users` mirror — `{ email: string, emailVerified: boolean, phone: string|null, phoneVerified: boolean|null, displayName: string|null }` — performing no writes; the read is strictly session-scoped (self-only — no parameterized lookup of another subject exists on this route). An unauthenticated request shall receive the same generic auth outcome as the other `/v1/me/*` reads (the fail-closed generic 401, EARS-16-consistent; an orphaned-session subject heals per EARS-26 like any other mirror-backed read). (Design §12.)
- **EARS-28:** When an authenticated user opens the portal `/account` page, the portal shall render a profile surface composed of: avatar initials + the display name with **inline edit** (persisted via the existing `PUT /v1/me/display-name`), the email with its verified state, a phone row that renders an explicit «не указан» state when no phone is attached (read-only — no phone editing, Scope), a **change-password action that hands off to the existing `/reset` flow** (no in-page password form and no new backend), a link to «Мои события» (`/account/events`), and sign-out (EARS-10). The surface shall **not** render raw session claims — no `sub`, no roles array, no raw `mfa` boolean — replacing the prior claims dump entirely. Copy comes from the message catalog (EARS-21); field validation follows EARS-22. The visual design is canvas-driven (Stage-A pick in claude.ai/design, vendored into `design-source/` before implementation) — this clause pins **behavior**, not pixels. (Design §12.)

**Enumeration-safe recovery for unverified accounts (GH #1131)**

- **EARS-34:** When a user requests an email login code (EARS-6) for an identifier that resolves to an **existing but email-unverified** account, the system shall keep the synchronous API response **byte-identical** — body, status, and timing (within the EARS-16 ≤ 50 ms budget) — to the verified-account and the nonexistent-identifier cases, and shall, **out-of-band** via the BFF branded mailer (EARS-29; fire-and-forget off the response path, mirroring EARS-23), send a **verification email** (the verify-to-sign-in artifact — the branded, Russian, code-only verification code, EARS-25/29) **instead of** arming the Zitadel `otp_email` login challenge, which cannot complete for an unverified account. Existence and verification state are therefore never disclosed by the response (the login form is not an oracle, EARS-16); the account owner's correct next step — verify the email, then sign in — travels **only in the mailbox** (OWASP side-channel-free recovery). The branch resolves the identifier → Zitadel `sub` without disclosing existence (the same enumeration-safe wrapper as EARS-6/11/25), is subject to the EARS-13 rate limits and the EARS-17 bot-protection surface, creates no `users`/consent row, and appends an `otp.sent` ledger row (EARS-18) only when a verification code is actually issued. A **verified** account still arms the `otp_email` login challenge unchanged (EARS-6); a **nonexistent** identifier remains a silent, uniform no-op (no "unknown recipient" notice mail in this iteration). No Zitadel-side behavior change (the login-OTP challenge arming stays native). (Resolves the login-by-email-code silent dead-end where an unverified account requested a code that, by Zitadel design, is never sent — GH #1131. Design §4/§6.)
- **EARS-35:** When an email-based password reset **completes** successfully — a valid reset code proven together with a policy-conforming new password (EARS-12) — the system shall mark the account's email **verified** in the IdP (`email_verified` set via Zitadel, mirrored onto `UserMirror`), because a proven reset code is itself proof the subject controls the mailbox (proof-of-mailbox-ownership). **No account state is mutated before a valid token** (OWASP): a bad/expired code or an unknown identifier changes nothing and stays the generic, enumeration-safe outcome (EARS-16). This closes the **stuck-unverified** state through the existing recovery path — an owner who never verified at registration but proves mailbox ownership via reset is no longer barred from the verified-only login-code path (EARS-6/EARS-34) — without adding a new mutation surface. The verification flip emits the terminal `auth.account.verified` (channel `email`) ledger row (EARS-3/18) exactly as the registration-verify path does, and is idempotent (an already-verified account → no-op flip). (GH #1131. Design §4.)

**Password friction — length-only policy, visible rule, reveal toggle (GH #1331)**

- **EARS-36:** The creation-password policy shall be **minimum length only** — at least **8 characters**, with **no** upper-case, lower-case, digit, or symbol requirement and no other composition rule — and it shall be **explicitly configured in the IdP** (the Zitadel instance password-complexity policy: `minLength = 8`, every character-class flag `false`), set idempotently by provisioning so the policy is a **managed, versioned artifact** and never an inherited provider default. `@ds/schemas` shall mirror that policy from a **single SSOT constant** consumed by both the API DTO contract and the portal's client-side pre-validation (EARS-22), so the rule exists in exactly one place in the codebase and cannot drift between the API and the portal. The policy governs password **creation** only — registration (EARS-1) and reset-complete (EARS-12); the login guard stays permissive (shape only) so credentials created under the previous policy keep working, and no existing password is invalidated, rotated, or re-validated. A residual rejection by an IdP configured stricter than the mirrored baseline shall remain the generic, enumeration-safe **422** (never a 500, never an existence oracle — EARS-16). (Owner decision 2026-08-20: maximally reduce the barrier to entry — length is sufficient, character-class requirements are removed. GH #1331. Design §15.)
- **EARS-37:** The registration password step shall present the password requirement — the **single** rule «Не менее 8 символов» — **before** submission, from the moment the field is rendered, and on a validation error shall show the error **in place of** the hint, through the **one** shared message slot of the password field (ADR-0013 §7) — hint or error, never both. The error copy shall state the **same single rule** as the hint (no requirement is named in the error that is not already named in the hint, and vice versa), and shall be sourced from the message catalog (EARS-21), so the swap never costs the user the rule they still need. Because the policy is length-only (EARS-36) there is exactly one rule to show — no per-requirement checklist, no strength meter, and no sequential reveal of a second requirement after the first is satisfied. (GH #1331. Design §15.)
- **EARS-38:** Every field where the user **creates or enters a password** — registration (EARS-1), reset-complete (EARS-12), and password login (EARS-5) — shall carry a **show-password toggle** that switches the field between masked and plain rendering. The control shall default to **masked**, be reachable and operable by keyboard, expose its state to assistive technology with localized labels from the message catalog (EARS-21), preserve the caret/entered value across a toggle, and never persist the revealed state across a page load or another field. Revealing shall change nothing but the rendering — no value is copied, logged, submitted, or stored anywhere as a side effect. (Owner-mandated 2026-08-20: «Кнопку "Показать пароль" надо обязательно добавить». GH #1331. Design §15.)
- **EARS-39:** When a registrant confirms the email without a signed-in session resulting from it, the verification step shall exit honestly: (a) a **cold** step — the in-memory password held for the #175 auto-login replay is absent (a hard reload, a restored tab, or an expired hold) — shall, on a successful verification, route them to `/login` carrying the return target onward (EARS-2 context), where they sign in with the password they just created (EARS-21); (b) an auto-login replay the IdP **refuses or that throws** shall keep them on the **verification** step with the generic EARS-16 error and no routing. The held password's security envelope is unchanged (design §4): it stays in volatile client memory only, is never written to the URL, storage, or a cookie, and is not persisted to survive the reload. Owner decision 2026-09-15 (tech spec `2026-09-15-auth-flow-wave-1-entry-gate-en.md` §5 Q2); the alternative of keeping a cold step on `/verify` with sign-in copy (GH #1394) was rejected. (GH #1331. Design §15.)

## Invariants

- Every `UserMirror` row satisfies `phone OR email NOT NULL` and carries exactly one `zitadel_sub`. Since registration is email-primary (EARS-1/2; Zitadel hard-requires email, GH #202), every registered row carries an email, so the invariant always holds via the email column; phone is the optional secondary identifier.
- No PD-bearing `users` row is committed without a corresponding `ConsentCaptured` record (EARS-20).
- A refresh token is valid for exactly one rotation; any reuse invalidates the chain (EARS-9).
- No access or refresh token ever appears in a client-readable response body or in non-`__Host-` storage (EARS-8).
- Register / login / reset / verify-code-resend / login-email-code responses are indistinguishable (status + body + timing ≤ 50 ms) between existing and unknown identifiers (EARS-16). A registration on an already-registered email triggers no account/consent/ledger write; any owner-directed account-exists notice is delivered out-of-band by email (EARS-23), never via the API response, and the post-register screen is existence-agnostic (EARS-24). A verification-code resend (EARS-25) re-issues a code only for an existing, unverified registrant and writes an `otp.sent` ledger row only then, so neither the response nor the ledger discloses existence. A login-email-code request for an existing-**unverified** account (EARS-34) returns the identical response and delivers the verify-to-sign-in path out-of-band by email, never via the API response; a successfully completed password reset marks the email verified (EARS-35) as proof-of-mailbox-ownership, and no state is mutated before a valid reset token is proven.
- Every state-changing auth command emits exactly one terminal `audit_ledger` entry (EARS-18).
- `apps/api` contains no password hashing, no token signing, and no OTP generation — all delegated to Zitadel (Constraints, design §2). A Zitadel-issued verify/reset code transits the BFF solely as the value embedded in the outbound mail (EARS-29): never logged, never persisted, never in an API response or audit row (EARS-30), and a mailer send counts as accepted only on a final provider 2xx, which does not prove mailbox delivery (EARS-31).
- The session JWT carries the `mfa` claim even though no `doctor_guest` flow requires MFA (seam for future enforcement).
- The creation-password rule exists in exactly **two** authorities and nowhere else: the explicitly-provisioned IdP complexity policy (the credential authority) and the single `@ds/schemas` SSOT constant that mirrors it (EARS-36). No portal component, message string, or API handler restates a composition rule the policy does not contain, and no shipped surface asks for a character class (EARS-37). A password value is never persisted, logged, or stored by the portal — revealing it (EARS-38) or reloading the verify step (EARS-39) changes nothing about that.
- `GET /v1/me/profile` performs no write on any path (EARS-27), and no product surface renders raw session claims (`sub`, roles array, raw `mfa`) — the `/account` profile surface shows only product-shaped identity fields (EARS-28).

## Dependencies & sequencing

- **Frontend scaffold (first consumer).** The Variant-B auth forms live in `apps/portal`, built from `packages/design-system` — **both are currently stubs** (only `package.json`). 003's frontend work graduates them: scaffold `apps/portal` (Tailwind 4 + shadcn/ui, ADR-0004 §5–7) and graduate `packages/design-system` with the design tokens (theme CSS variables incl. `--radius`) + only the auth-form component set the forms need (Input, Button, Form, Label, OTP input, Card), per the incremental stub-graduation pattern of 001/002. Sequenced before the form-facing EARS; the full design system grows with later verticals.
- **Endpoint-authorization matrix (ADR-0001 design §2.5 — "mandatory artifact" + CI gate `tools/lint-endpoint-authz`).** This infrastructure does **not yet exist** in `tools/`. 003 introduces the first real classified endpoints (public: register / login / reset / verify; `doctor_guest`-protected: logout / refresh / session). 003 therefore either bootstraps the minimal endpoint-authz metadata convention + lint, or it is gated on a preceding engineering-task that does. **Decision for the lead agent before child-Issue planning.**
- **Consent mechanism (ADR-0009).** EARS-20 needs a capture API. If the ADR-0009 capture primitive is not yet implemented, 003 builds the minimal registration-time capture (record accepted versions) and leaves withdrawal/version-migration to the ADR-0009 vertical.
- **Dev-stand Zitadel + Mailpit + Redis.** Integration tests run against the dev-stand `idp`, `mailpit`, and Redis services (AGENTS.md §9); endpoints/ports are read from `.env.local`.
- **Password-friction increment → four implementation slices (GH #1331).** The EARS-36–39 clauses ship as their own Issues, opened after this spec increment is on `main` (SDD): **(1) EARS-36 policy SSOT** — the idempotent IdP complexity-policy converge step in `infra/dev-stand/idp/provision.sh` (+ the prod instance) and the `@ds/schemas` constant it mirrors, with the login guard left permissive; **(2) EARS-37 requirement presentation** — the single-rule hint plus the matching error copy in the catalog, both on the shared `FormMessage` slot of the password field; **(3) EARS-38 show-password toggle** — the `@ds/design-system` `PasswordField` primitive, consumed by register / reset / login; **(4) EARS-39 verification exits** — the cold-step and refused-replay exits of the verification step, shared by both hosts. Slice 1 is sequenced **first** (the IdP is the credential authority; a relaxed schema in front of a strict instance would surface as the 422 residual), slices 2–4 are independent of each other. Slices 2–4 are `user-facing` and carry the Stage-A/Stage-B design gate; slice 1 is backend-only.
- **Decision-debt → ADR-0001 revision (separate adr-revision task).** Three research findings touch ADR-0001 and are recorded in design §9 for a follow-up revision — not changed inside this spec-authoring: §8 (magic-link wording now that native email-OTP exists), §7 (Zitadel enumeration/lockout CVEs + patched-version pin), §2 (Login v2 considered & rejected).

- **Postbox sequencing (#1059, spec revision #2115).** Merge this contract before runtime implementation. The implementation includes the BFF transport/config/observability and native Zitadel SMTP reconcile with stable identities per provider: the existing `real transactional sender` remains unchanged for mail.ru, while Postbox uses one separate `real transactional sender:postbox` profile. Preparation creates and verifies the inactive profile before controlled activation; rollback reactivates the retained original ID and restores the coherent BFF selection. Existing-profile metadata/password updates and projection replay/reset are excluded. Public metadata cannot prove stored-password equality, and an old-ID test reads a different model from actual native delivery; verify a real native notification on activation and rollback (design ?14.5). The migration choice and applicable release approval are recorded before production writes; no new Yandex account/key or email template is introduced. Controlled activation, secret wiring, rollback, native login-OTP and verify/reset received-artifact checks belong to release blocker #2116 under #1059. The default Postbox quota (200/day, 1/s) does not meet the ≥5,000/day ramp target; approved quota and measured headroom are required before that ramp. Microsoft sender-auth/Inbox proof remains #1120 (support NN500565): code preparation need not await support, but TrustedSenderList-assisted Inbox placement is not a pass. Asynchronous provider delivery-event ingestion is outside this revision; any such pipeline requires a separately scoped contract under #1059 before implementation, and no delivered-status API or automatic post-acceptance resend is promised.
