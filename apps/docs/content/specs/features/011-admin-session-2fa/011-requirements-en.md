# 011 — Admin session hardening: dedicated `__Host-ds_admin_session` + mandatory TOTP (Requirements)

> Initiative: GitHub Issue [#718](https://github.com/doctor-school/ds-platform/issues/718), carrying the implementation half of decision-debt [#663](https://github.com/doctor-school/ds-platform/issues/663) (surfaced by the #595 Mode-a review of PR #660). **Required before the 2026 Q3 pilot.**
>
> **No `011-product.md` PRD exists, and none is required.** This is internal-admin security hardening with no external product audience: the surface is used by the Tech Lead and the small trusted `platform_admin` operator group, the deliverable is a security posture mandated by ADR-0001 §4 rather than a user job to be discovered, and the single genuine product fork (how an admin gets their first factor) was settled directly with the product owner on 2026-08-07 — recorded verbatim in **Prior decisions → PD-1**. EARS clauses therefore carry no `realizes: US-N` backlinks (ADR-0014 §2 applies to PRD-derived specs).

## Outcomes

- **The admin surface has its own credential.** A `platform_admin` authenticating at the admin origin receives a **dedicated `__Host-ds_admin_session`** cookie — host-only, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/` — and the admin API accepts **only** that cookie. A stolen or CSRF-replayed doctor-portal session can no longer reach an admin command, closing the wave-1 posture ADR-0004 design §3.2 accepted as temporary.
- **Every admin session is MFA-verified.** No `platform_admin` reaches any admin surface without having proved possession of a TOTP factor **in that login**. The `mfa` claim on an admin session is `true` by construction, not by hope.
- **An admin enrols themselves, in the admin app, with no operator hand-holding.** A `platform_admin` whose account carries no TOTP factor is forced into an enrollment screen (QR + manual secret + verify-code) before any admin surface renders — and that same screen is the bootstrap path for the admins who exist today (PD-1). There is no out-of-band cutover mailing, no support ticket, no manual IdP console step in the happy path.
- **The 003 policy seam gets its first tenant.** `role → mfa_required` — shipped in 003 as a documented no-op seam with no elevated roles — is populated with `platform_admin`, and the check runs immediately after primary auth. 011 is the "first vertical with a mandatory-MFA role builds the mechanism" that 003 named.
- **The MFA capability is provisioned as code, not clicked into a console.** TOTP as an allowed second factor, and the login-policy check lifetimes that make the factor re-verify per login, are declared in the dev-stand provisioning and carry a stated prod-parity obligation — so dev, stand, and prod cannot silently diverge on a security control.
- **The admin-session and MFA lifecycle is auditable.** Enrollment, challenge success/failure, lockout, and admin-session establishment/refusal each append a terminal `audit_ledger` row under the ADR-0001 design §7.3 taxonomy — an admin login is reconstructable after the fact.
- **Nothing about the doctor portal changes.** `__Host-ds_session`, the 003 login flows, and `doctor_guest` behaviour are untouched; 011 adds a second, stricter tier beside them.

## Lead authoring decisions

Two questions the initiative did not settle and the owner fork did not cover. Each is settled here as a **lead decision (2026-08-07)**, carried inline on the requirement it shapes, and vetoable at spec review.

- **LD-1 — A successful enrollment verify completes that login; no forced re-login.** ADR-0001 design §8.5 step 4 terminates the enrollment session and demands a fresh MFA login. That step exists because the §8.5 vehicle is a **magic-link** session — a link in an inbox is a weaker primary credential than a password, so the elevated enrollment session must not be reused. 011's vehicle is a **completed password authentication** (PD-1), and the enrollment verify **is** a successful TOTP verification of the factor just registered — both factors have therefore been presented in this login. Forcing an immediate second full login would add friction that proves nothing. The system upgrades the pending authentication in place and issues the full admin session with `mfa = true` (EARS-5). The §8.5 invariant that matters — _the UI does not allow continuing without enrollment_ — is kept intact (EARS-4).
- **LD-2 — Factor recovery is an operator action, not a self-serve flow, in this slice.** A lost authenticator locks a `platform_admin` out of a **live medical platform**, so the recovery path must exist and be written down — but self-serve recovery codes are their own vertical (generation, one-time display, secure storage guidance, redemption, regeneration, audit) and would double this slice. In 011 the recovery path is an **explicit operator action**, and that action runs **through our API, not through the IdP console**: the Tech Lead — the single CODEOWNERS owner in Phase 0 (ADR-0008 §2.7) — calls the `platform_admin`-only factor-removal endpoint of **EARS-13**, after which the target admin's next login hits the forced-enrollment screen (EARS-4) and re-enrols. **Why an endpoint rather than the console:** a console-side removal is never observed by `apps/api`, so the `auth.mfa.reset` row EARS-9 mandates would never be written — an unbuildable criterion. Worse, stripping another admin's second factor is the single most sensitive admin action in this spec, and ADR-0001 §7/§10 already classify "MFA change" and "admin user-management writes" as elevated actions demanding **fresh MFA**; leaving it outside the API would make an ADR-mandated control unreachable rather than deferred. **How that freshness is proven matters, because the general mechanism does not exist:** `StepUpGuard`, the `acr=mfa-fresh` claim and the 30-minute elevated session are an ADR-0001 §10 _decision_ that was never built here (`stepUp` is matrix metadata only, read by no guard). EARS-13 therefore proves freshness **route-locally** — the caller supplies their own current TOTP code with the request — which satisfies §10's policy intent for this route without claiming machinery that is absent. The runbook documents **this endpoint**. **Self-serve recovery codes are named in Out of scope** as a tracked follow-up, not a silent gap — only the _vehicle_ of the interim path is settled here; the decision that recovery is an operator action stands.

  **Operator-population precondition, and the BREAK-GLASS exception below it.** The EARS-13 endpoint presumes **≥2 enrolled `platform_admin` operators**: the caller must prove fresh possession of their _own_ factor and cannot remove their own last one — so with a single operator there is nobody who can run it. That is today's Phase-0 reality (AGENTS.md §7 records the Tech Lead as the single CODEOWNERS owner), and pretending otherwise would convert an unauditable recovery path into a nonexistent one. So: **while fewer than two `platform_admin` operators hold an enrolled factor, factor loss triggers the named BREAK-GLASS path** — the Tech Lead removes the factor through the **IdP admin API** following the module runbook, and the _same runbook step_ appends the compensating **`auth.mfa.reset`** row through a dedicated ops script, so the ledger stays complete rather than silently missing the most sensitive event in the system, plus a **mandatory post-action note on the tracking Issue**. Break-glass is a **documented exception with a compensating audit path and a stated precondition** — not a silent bypass, and not a licence to skip the endpoint once a second operator exists. The precondition is verifiable before the slice ships: count the enrolled operators.

## Scope

**In:**

- **Dedicated admin session cookie (issuance).** On a completed admin authentication at the admin origin, the API issues `__Host-ds_admin_session` — host-only (no `Domain`), `Path=/`, `HttpOnly`, `Secure`, `SameSite=Strict` — carrying only an opaque server-side session reference, never a token (EARS-1).
- **Dedicated admin session cookie (validation + separation).** The admin session hook accepts **only** `__Host-ds_admin_session` on admin routes; `__Host-ds_session` presented to an admin route is refused as unauthenticated, and vice versa. Admin logout clears the admin cookie and terminates its server-side record without touching the portal session (EARS-2).
- **`role → mfa_required` policy populated.** The 003 policy seam is populated with `platform_admin` and evaluated immediately after primary auth; a role in the policy cannot obtain a full admin session without a satisfied second factor (EARS-3).
- **Forced-enrollment gate.** A `platform_admin` who completes primary auth with **no** registered TOTP factor is put into the `mfa_pending_enrollment` state and can reach **only** the enrollment screen and its two endpoints — every other admin surface and admin API route is refused for that pending state (EARS-4).
- **Self-serve TOTP enrollment screen (admin app).** QR code + the manually-transcribable secret + a verify-code field; a correct code registers the factor, emits `auth.mfa.enrolled`, and completes the login in place (LD-1). This is also the bootstrap for existing admins (PD-1) (EARS-5).
- **TOTP challenge on every subsequent admin login.** After primary auth, an enrolled `platform_admin` is presented a TOTP challenge screen; only a correct code yields the admin session (EARS-6).
- **Failed-code handling: rate limit, lockout, uniform errors.** Verification attempts are rate-limited and lockout-bounded per ADR-0001 §7; failures return a single uniform message that distinguishes neither "wrong code" from "no such factor" nor a locked from an unlocked account, with the §7 timing-delta discipline (EARS-7).
- **Zitadel TOTP enablement as provisioned configuration.** TOTP registered as an allowed second factor on the login policy, with the `secondFactorCheckLifetime` / `multiFactorCheckLifetime` / `mfaInitSkipLifetime` knobs set so a factor check does **not** survive across logins and enrollment cannot be skipped; declared in `infra/dev-stand/idp/provision.sh` and carrying a stated prod-parity obligation (EARS-8).
- **Operator factor removal as an audited endpoint with a route-local fresh-possession proof.** A `platform_admin`-only endpoint that removes another admin's TOTP factor, on the high-stakes introspection tier, requiring the **caller's own current TOTP code in the request** — verified at call time against the caller's registered factor. This realises the ADR-0001 §10 policy intent ("an MFA change is an elevated action and needs fresh MFA") for this one route **without** the general step-up mechanism, which is unbuilt. It emits the canonical `auth.mfa.reset` row and returns the target to forced enrollment. Vehicle of the LD-2 interim recovery path, subject to its operator-population precondition (EARS-13).
- **Audit trail with an explicit canonical mapping.** Every admin-session/MFA lifecycle event maps to a **canonical ADR-0001 design §7.3 `<class>.<event>` wire id** through the mapping table in Event Model → Events — no invented ids — with an `admin` **tier discriminator** so admin rows never blend into the portal's `auth.session.*` rows, each a terminal `audit_ledger` row, PD-masked (EARS-9).
- **Session-profile conformance for the new tier.** Fingerprint binding, TTL, server-side Redis storage, rotation, force-logout, and CSRF double-submit apply to `__Host-ds_admin_session` exactly as ADR-0001 §6 / design §7.1 specify — the new cookie is not a new session model (EARS-10).
- **Endpoint-authz classification.** Every admin route requires `platform_admin` **and** an MFA-verified admin session; the matrix rows carry the raised floor, and a role-only session is refused (EARS-11).
- **Admin UI discipline for the two new screens.** RU copy from the typed message catalog (no hardcoded strings), the `build-ui-from-design-system` adopt-before-bespoke gate with a **Stage-A design proposal approved by the product owner before implementation** and a **Stage-B live re-confirmation before merge**, ADR-0013 token discipline, and keyboard/screen-reader accessibility on the code fields (EARS-12).

**Explicitly out** (each a named deferral, not a silent default):

- **Self-serve MFA recovery codes.** Recovery in 011 is the operator action of LD-2, delivered as the EARS-13 endpoint (documented runbook + `auth.mfa.reset` audit row). Generation/one-time display/redemption/regeneration of recovery codes is a **tracked follow-up Issue**, opened by `open-ears-issues` step 3a against this Scope line — not a code comment.
- **SMS second factor for `moderator` / `support`.** ADR-0001 §4 accepts SMS for those roles in v1 and upgrades them to TOTP in v2; neither role exists as a populated `mfa_required` tenant yet. 011 populates the policy with `platform_admin` **only**. The policy structure stays a `role → requirement` map so adding a role later is a data change, not a reshape.
- **MFA for `expert` / `clinic_admin` / `investor`.** Also ADR-0001 §4 mandated, also not yet reachable roles. Same policy-map extension point.
- **The general step-up mechanism (`StepUpGuard`, the `acr=mfa-fresh` claim, the 30-minute elevated session, the `401 step_up_required` contract).** ADR-0001 §10 decided it; **it has never been built** — `stepUp` is matrix metadata only, no guard consumes it, and no route declares it. 011 does not build it, does not design it, and does not sweep the 007 admin routes onto it; raising the base admin session floor to MFA-verified remains the whole of 011's session work. EARS-13 meets §10's _policy intent_ for its one route by a **route-local** means (the caller's own current TOTP code in the request) and deliberately does **not** set `stepUp` matrix metadata: that column advertises the general mechanism, and a row there with no guard behind it is a fail-open claim — the endpoint-authz matrix would promise a protection nothing enforces.
- **Graduating EARS-13 onto the general step-up mechanism — a tracked deferral.** When the step-up vertical lands (guard, `acr=mfa-fresh` claim, elevated-session TTL, the `401 step_up_required` contract), the factor-removal route moves onto it: the route-local code check is replaced by `stepUp: true` metadata plus guard enforcement. This is a **named follow-up Issue** for `open-ears-issues` step 3a against this Scope line — not a code comment and not an assumption that someone will notice.
- **Other apps' cookies.** `__Host-ds_cms_session`, `__Host-ds_promo_session`, `__Host-ds_docs_session` (ADR-0004 design §3.2) are untouched. So is the portal's `__Host-ds_session`.
- **The `legacy_admin` Directual-cutover flow (ADR-0001 design §8.5).** The magic-link elevated-session bootstrap solves a population 011 does not have (PD-1). It stays available, unimplemented, for the cutover slice that needs it.
- **Cross-app SSO / OIDC silent re-auth for admin.** ADR-0004 design §3.2.1's `prompt=none` continuity is deliberately **not** extended to the admin origin — a `SameSite=Strict`, MFA-gated tier that silently re-materialises from another app's session would undo the separation this spec exists to create.
- **Passkeys / WebAuthn as an alternative factor.** ADR-0001 §4 fixes TOTP for `platform_admin` in v1.
- **Per-admin session management UI** (list/revoke my sessions). Force-logout exists server-side (EARS-10); a surface for it is not in this slice.
- **Cerbos policy migration.** Admin authorization stays the role fast-path check it is today; moving admin authz into Cerbos is unrelated to session hardening.

## Constraints

- **The admin cookie is the only admin credential — separation is enforced, not conventional.** `__Host-ds_admin_session` is issued only at the admin origin and accepted only on admin routes; `__Host-ds_session` is never accepted there. Because the admin app reaches the API same-origin through its `/v1/*` proxy, "the browser happens to send the portal cookie" must be an explicit **refusal**, not an accidental success (EARS-2). This is the exact wave-1 weakness ADR-0004 design §3.2 recorded.
- **`SameSite=Strict`, and its cost is accepted deliberately.** Strict suppresses the cookie on every cross-site navigation into the admin origin — a link from an email or chat lands the operator on the login screen rather than in the app. For an admin console used by a handful of operators who navigate by bookmark this is the correct trade (ADR-0004 design §3.2.1 names `strict` for admin/cms); the login screen must therefore recover gracefully and return the operator to their intended route.
- **MFA is mandated by the role policy in our backend, not by an org-wide IdP switch.** Zitadel login policies are **organization-scoped**, not role-scoped: an org-wide `forceMfa` would impose TOTP on every doctor. So Zitadel supplies the **capability** (TOTP as an allowed second factor + check lifetimes, EARS-8) and our `role → mfa_required` policy supplies the **mandate** (EARS-3). Losing sight of this split would either lock out doctors or leave admin MFA unenforced.
- **The pending-auth state is not a session.** Between primary auth and a satisfied second factor the principal holds a short-lived, host-only, `SameSite=Strict` **pending-auth** reference that grants access to nothing except the enrollment/challenge endpoints. It is stored server-side, is single-purpose, expires in minutes, and is never accepted by the admin session hook. A pending reference that could reach an admin route would defeat the entire spec.
- **No new auth primitive.** 011 composes the shipped 003 BFF-over-Zitadel machinery (session establish/validate, `mfa` claim derivation from `amr`, Redis session store, fingerprint binding) and the ADR-0001 §6 profile. It introduces no new token type, no new credential store, and no second identity source.
- **The fake IdP is never more permissive than the real one.** The TOTP register/verify seam is added to the `IdpPort` and implemented by **both** the Zitadel adapter and the in-repo fake; the fake rejects every code the real adapter rejects (wrong code, unregistered factor, replayed code, expired window). A fake that accepts any 6 digits would make the entire EARS-5/6/7 suite vacuous.
- **Admin mutations remain the high-stakes tier.** ADR-0001 §2.5/§8 introspection-path validation for admin mutations is unchanged; MFA raises the session floor and does not substitute for it.
- **Secrets never leave the enrollment exchange.** The TOTP secret / provisioning URI is returned exactly once, to the authenticated pending principal, over the enrollment-start response — never logged, never in an audit row, never re-readable after the factor is registered. PD masking per ADR-0001 §7 applies to every audit field.
- **No hardcoded origin, endpoint, or issuer.** The admin origin, IdP issuer, and Redis endpoint come from configuration (`.env.local` on the stand, deploy config in prod), never from a literal in code or spec (AGENTS.md §9).
- **Stack** (ADR-0002 / ADR-0004): the auth endpoints are NestJS + `nestjs-zod` with DTOs in `packages/schemas/`, URI-versioned `/v1/...`, tested with Vitest + supertest; the two screens are built in the Refine admin app (`apps/admin`), client-side. Service-dependent tests `skipIf` their dependency env (`DATABASE_URL`, `IDP_ISSUER`, `REDIS_URL`) is absent.

## Prior decisions

- **PD-1 — Owner-settled product fork (2026-08-07): self-serve enrollment in the admin app.** _A `platform_admin` login without enrolled MFA is forced into a TOTP-enrollment screen (QR + verify code) before reaching any admin surface; thereafter every admin login requires password + TOTP code. Bootstrap for existing admins is the same forced-enrollment screen at their next login._ **Rationale for not using the ADR-0001 design §8.5 magic-link elevated-session flow:** §8.5 solves the **Directual-cutover** case — legacy admins who have _no password in the new system_ and therefore need an out-of-band credential just to reach an enrollment screen. Our admins do not have that problem: they already password-login into the Zitadel-backed 003 auth, so a completed password authentication is available as the enrollment gateway. Introducing an emailed magic link would **weaken** the bootstrap (an inbox becomes a path to an admin factor) while solving nothing. §8.5 remains the correct flow for `legacy_admin` at cutover and is untouched. What 011 **does** inherit from §8.5: the canonical audit-event ids (`auth.mfa.enrolled`, `auth.lockout.triggered`) and the invariant that the UI does not allow continuing without enrollment.
- **ADR-0001 §4** — MFA **TOTP is mandatory for `platform_admin`**. The method is ADR-fixed; 011 does not re-open "which factor" and does not evaluate passkeys/SMS for this role.
- **ADR-0001 §6** — Per-app **host-only** cookies; a shared cross-subdomain cookie is rejected because same-origin XSS or subdomain takeover would compromise the admin session and bypass fingerprint/CSRF mitigations. 011 makes the admin app compliant with this decision — it is the app that was still borrowing the portal's cookie.
- **ADR-0001 §7** — Rate limiting, account lockout (10 failed / 30 min → soft-lock + email), enumeration-safe uniform responses with ≤50 ms timing delta, CSRF double-submit, and the strictest CSP profile for `admin.doctor.school`. EARS-7 applies this baseline to the TOTP verification endpoints rather than inventing thresholds.
- **ADR-0001 §2.5/§8** — Admin mutations are the high-stakes tier and ride IdP introspection; Zitadel is the IdP and must stay on a CVE-patched release (≥ 4.9.1 / ≥ 3.4.6).
- **ADR-0001 §10** — Step-up `acr=mfa-fresh`, TTL 30 min, `StepUpGuard`, the `401 step_up_required` contract. **Decided in the ADR, not built in the code**: verified against the tree at authoring time, `stepUp` appears only as endpoint-authz matrix metadata (`apps/api/src/authz/authz.types.ts`, rendered as a column by `authz.matrix.ts`), no guard reads it, no `acr` or `mfa_fresh_at` check exists in `apps/api`, and no route declares it. 011 raises the _entry_ floor and, for the single route where §10's policy intent is unavoidable (EARS-13), satisfies that intent **route-locally** rather than pretending the mechanism is there. The general mechanism stays unbuilt and out of scope, with the graduation tracked.
- **ADR-0001 design §7.1** — The session parameters table (access JWT 15 min, refresh opaque rotating single-use 30 d web, Redis server-side store, fingerprint binding, `acr=mfa-fresh` TTL 30 min). `__Host-ds_admin_session` conforms to this table; it is a second cookie, not a second session model (EARS-10).
- **ADR-0001 design §7.3** — The `<class>.<event>` auth audit taxonomy. The 011 events register under it with canonical wire ids (EARS-9).
- **ADR-0001 design §8.5** — Reused for event names + the no-continue-without-enrollment invariant; **not** reused as the bootstrap vehicle (PD-1).
- **ADR-0004 design §3.2** — The staged admin session model. Wave 1 (007, through the 2026-07-17 webinar) rides `__Host-ds_session`; **this spec is the named pre-pilot hardening trigger** the ADR links to #718. On merge, the admin row of the §3.2 topology list stops describing a staged compromise and describes the shipped target model.
- **ADR-0004 design §3.2.1** — Per-app cookie pattern with `sameSite: 'strict'` for admin/cms and CSRF double-submit on state-changing endpoints. 011 implements the admin row of that pattern; it deliberately does **not** adopt §3.2.1's `prompt=none` silent re-auth for admin (Scope → Out).
- **ADR-0002 §3** — nestjs-zod, URI versioning, Vitest + supertest, `packages/schemas/` DTO SSOT.
- **ADR-0003 §6** — `audit_ledger` as the append-only sink.
- **ADR-0006 §4** — Triplet structure + flat EARS numbering.
- **ADR-0013 + skill `build-ui-from-design-system`** — Adopt-before-bespoke and token discipline for the enrollment/challenge screens; the Stage-A/Stage-B design-approval gate applies because this is a `user-facing` surface (EARS-12).
- **Spec 003 (`003-requirements-en.md` → Scope → Out; `003-design.md` §Seams)** — _"003 ships the `mfa` claim in the session and a documented `role → mfa_required` policy seam, but builds no TOTP enrollment/verification and populates the policy with no elevated roles. The first vertical with a mandatory-MFA role (admin/ops → `platform_admin`) builds the mechanism."_ 011 **is** that vertical. The seam sits right after the primary-auth step and is a no-op today; EARS-3 flips it.
- **Spec 007 (`007-requirements-en.md` EARS-8, `007-design.md` §7)** — The admin commands are `authenticated` / `platform_admin` / `fast-path` and explicitly record the staged session posture with a forward reference to #718. 011 raises the floor those rows sit on (EARS-11); no 007 command changes shape.

### Step-0 delta note — what the legacy system did

The legacy Doctor.School admin is a **Bubble `page_admin`** page driven by **Directual** scenarios: external SaaS, no in-repo code, email+password only, **no MFA**, and **no session separation** between the admin page and the rest of the product. There is no legacy mechanism to mine, mirror, or migrate — 011 is a net-new control, and the delta against legacy is "from none to mandatory". Recorded so a later reader does not go looking for prior art that does not exist.

## Event Model

011 is a **security-tier vertical** on the authentication write path. It owns the admin session's issuance/validation and the TOTP factor lifecycle. It **consumes** the shipped 003 primary-auth machinery (Zitadel session establish, claim derivation, Redis session store, fingerprint binding) and the `ROLES` model; it **produces** an MFA-verified admin principal that every admin feature (007 today, later admin verticals) sits on. It owns **no** product data.

### Commands (handled by `apps/api`, admin origin)

- `StartAdminLogin(credentials)` — primary password authentication for the admin origin. On success it does **not** issue an admin session; it creates a short-lived server-side **pending-auth** record and returns the required next step: `mfa_enrollment_required` (no factor registered) or `mfa_challenge_required` (factor registered). Emits `AdminPrimaryAuthSucceeded` / `AdminPrimaryAuthFailed`.
- `StartMfaEnrollment()` — for a pending principal in `mfa_pending_enrollment`: registers a provisional TOTP factor at the IdP and returns the provisioning URI + QR payload + transcribable secret **once**. Emits nothing durable (the factor is not yet confirmed).
- `VerifyMfaEnrollment(code)` — verifies the first code against the provisional factor; on success the factor becomes registered, the pending-auth record is upgraded **in place** to a full admin session with `mfa = true` (LD-1), and `__Host-ds_admin_session` is set. Emits `MfaEnrolled` + `AdminSessionEstablished`.
- `VerifyMfaChallenge(code)` — verifies a TOTP code for an enrolled pending principal; on success issues the admin session. Emits `MfaChallengeSucceeded` + `AdminSessionEstablished`, or `MfaChallengeFailed` (and `LockoutTriggered` at the §7 threshold).
- `EndAdminSession()` — clears `__Host-ds_admin_session` and deletes its server-side record + IdP session; leaves any portal session alone. Emits `AdminSessionEnded`.
- `RemoveMfaFactor(userId, callerTotpCode)` — the LD-2 operator recovery action, handled by `apps/api` on the admin origin: a `platform_admin`-only, high-stakes (introspection-validated) command that removes the target admin's registered TOTP factor, admitted only on the **caller's own current TOTP code** carried in the request (route-local fresh-possession proof; no `stepUp` metadata, no guard dependency). The target's next login re-enters forced enrollment (EARS-4). Emits `MfaFactorRemoved` (EARS-13).

### Events — canonical wire-id mapping (all terminal `audit_ledger` rows, ADR-0003 §6)

**This table is normative.** Every 011 domain event maps to a **canonical ADR-0001 design §7.3 `<class>.<event>` wire id** — 011 invents no ids and defines no parallel taxonomy. The internal PascalCase domain-event name is reconciled to the wire id in the single shipped mapper `apps/api/src/auth/session/auth-audit.ledger.ts` (`toLedgerRow`), which already emits exactly this form; 011 extends that switch rather than adding a second source.

**Tier discriminator.** The admin tier and the doctor portal share the canonical `auth.session.*` and `auth.login.*` classes, so every row 011 writes carries **`tier: "admin"`** in the ledger row's `metadata` — the §7.3 idiom of a discriminating field (as `method` discriminates `auth.mfa.*` and `reason` discriminates `auth.session.terminated`), not a new class. Without it an admin-session forensic query silently returns portal rows. The discriminator is the **presence of `tier: "admin"`** — which is all the separability assertion needs. 011 does **not** claim portal rows already carry a tier: the shipped `toLedgerRow` writes none, and back-filling `tier: "portal"` onto 003's write path is owned by no clause here and is deliberately not implied.

### Read models

- **`AdminAuthState`** — what the admin app renders its auth flow from: **the state enum and nothing else** — `unauthenticated | mfa_pending_enrollment | mfa_pending_challenge | active`. It carries **no** remaining-attempt budget, **no** lock state, no factor id, no secret, and no raw session claims. **Why the budget/lock indicators were removed:** the caller reading this model is a principal who has already passed primary auth — precisely the stolen-password attacker the second factor exists to stop. Exposing lock or attempt state would hand that attacker, through a second endpoint, the very oracle EARS-7 spends a clause denying: a uniform verify response is worthless if a neighbouring read discloses that the account is locked (and therefore that it exists, holds `platform_admin`, and is under attack). The two surfaces are held to **one** disclosure rule, and Verification row 7 tests the state endpoint alongside the verify endpoints.
- **`AdminEnrollmentOffer`** — the one-time enrollment payload: provisioning URI, QR payload, transcribable secret, issuer/account labels. Returned exactly once, to the pending principal only.
- **`AdminSessionPrincipal`** (internal) — the validated admin principal for downstream guards: `sub`, `roles[]`, `mfa`, `sid`, fingerprint reference. This is what every admin route resolves; a request that cannot produce it is refused.

### Policies

- **On primary auth success at the admin origin** → evaluate `role → mfa_required`; a role in the policy **never** receives an admin session directly — it receives a pending-auth reference plus the required next step (EARS-3).
- **On `mfa_pending_enrollment`** → admit **only** the enrollment screen and its two endpoints; refuse every other admin surface and route (EARS-4).
- **On a successful enrollment verify** → register the factor, emit `auth.mfa.enrolled`, upgrade in place to a full admin session (LD-1, EARS-5).
- **On a successful challenge verify** → issue the admin session with `mfa = true` (EARS-6).
- **On a failed verify** → count against the §7 per-user/per-IP budgets, return the uniform failure, and at threshold soft-lock + notify (EARS-7).
- **On every admin route** → resolve `AdminSessionPrincipal` from `__Host-ds_admin_session` only, re-check fingerprint + `platform_admin` + `mfa = true`, and refuse otherwise with an audit row (EARS-2, EARS-10, EARS-11).
- **On logout / force-logout** → delete the server-side record and the IdP session, clear the cookie, leave the portal session untouched (EARS-2, EARS-10).

## EARS requirements

> **Numbering convention:** flat (`EARS-1` … `EARS-13`) per ADR-0006 §4. EARS-1…9 and EARS-13 are functional handlers (each becomes a child Issue); EARS-10…12 are cross-cutting ubiquitous / unwanted-behaviour requirements enforced across the surface. **No `realizes:` backlinks** — this spec has no `NNN-product.md` PRD (see the header note and PD-1).

**The dedicated admin session**

- **EARS-1** — When a `platform_admin` completes an admin authentication at the admin origin (primary auth **plus** a satisfied second factor), the system shall issue a **dedicated `__Host-ds_admin_session` cookie** — no `Domain` attribute, `Path=/`, `HttpOnly`, `Secure`, `SameSite=Strict` — whose value is an **opaque server-side session reference** and never a token or claim payload; the response shall carry no token in its body, and the doctor-portal cookie `__Host-ds_session` shall be neither set nor modified by this flow.
- **EARS-2** — The admin API shall authenticate admin routes **exclusively** via `__Host-ds_admin_session`: a request presenting only `__Host-ds_session` — including the same-origin case where the browser attaches it through the admin `/v1/*` proxy — shall be refused as unauthenticated with an `auth.session.rejected` audit row, and a request presenting only `__Host-ds_admin_session` to a portal route shall likewise be refused; admin logout shall delete the admin session record and clear only the admin cookie, leaving any concurrent portal session valid.

**Mandatory MFA for `platform_admin`**

- **EARS-3** — The system shall populate the 003 `role → mfa_required` policy with **`platform_admin`** and evaluate it **immediately after** primary authentication: when the authenticated principal holds a role present in the policy, the system shall **not** issue an admin session on primary auth alone, but shall create a short-lived server-side **pending-auth** record and return the required next step (`mfa_enrollment_required` when no TOTP factor is registered, `mfa_challenge_required` when one is); the pending-auth reference shall grant access to **no** admin route other than the enrollment/challenge endpoints and shall never be accepted by the admin session hook. The policy shall remain a `role → requirement` map so that adding a further role is a data change, not a reshape.
- **EARS-4** — While a `platform_admin` principal is in the `mfa_pending_enrollment` state, the admin app shall render **only** the TOTP-enrollment screen — no dashboard, no navigation to any admin resource, no partial admin data — and the API shall refuse every admin route except the enrollment start/verify endpoints; the state shall not be dismissible, skippable, or bypassable by direct URL entry, and the operator shall not be able to continue into the product without completing enrollment (ADR-0001 design §8.5 invariant, PD-1).
- **EARS-5** — When a `platform_admin` in `mfa_pending_enrollment` opens the enrollment screen, the system shall register a provisional TOTP factor and present **once** a scannable QR code, the same secret in **manually transcribable** form (for authenticator apps that cannot scan), and a verify-code field; and when the operator submits a **correct** code, the system shall confirm the factor as registered, append an **`auth.mfa.enrolled`** audit row (never containing the secret), and — because primary auth and a TOTP verification have both been satisfied in this login (**LD-1**) — **upgrade the pending-auth record in place** to a full admin session with `mfa = true`, issuing `__Host-ds_admin_session` per EARS-1 **without** requiring a second full login. This same screen shall be the bootstrap path for admins who already exist (PD-1). An incorrect code shall leave the operator on the enrollment screen with the factor unconfirmed, subject to EARS-7.
- **EARS-6** — When an **enrolled** `platform_admin` completes primary authentication at the admin origin, the system shall present a **TOTP challenge** and shall issue the admin session **only** on a correct, unexpired, not-previously-used code; a code accepted once shall not be accepted again within its validity window, and no admin surface or admin API route shall be reachable between primary auth and a satisfied challenge.
- **EARS-7** — When a TOTP verification (enrollment or challenge) fails, the system shall count the attempt against the ADR-0001 §7 per-user (10 / 15 min) and per-IP (20 / 15 min) budgets, append an `auth.mfa.failure` audit row, and return a **single uniform failure** that discriminates neither a wrong code from an unregistered factor nor a locked from an unlocked account, honouring the §7 ≤50 ms timing-delta discipline; on crossing the §7 lockout threshold (10 failed attempts / 30 min) the system shall **soft-lock** the account, append an `auth.lockout.triggered` row, and send the §7 notification — and a locked account shall be refused an admin session even when a subsequently correct code is presented.
- **EARS-8** — The system shall enable TOTP as an allowed second factor on the IdP **as provisioned configuration, not as a manual console action**: the login policy shall register the OTP second factor and set `secondFactorCheckLifetime` / `multiFactorCheckLifetime` short enough that a factor check does **not** survive across logins, and `mfaInitSkipLifetime` such that enrollment cannot be skipped; the settings shall be declared in the dev-stand provisioning (`infra/dev-stand/idp/provision.sh`) so a freshly provisioned stand is MFA-capable with no hand steps, and the corresponding **production-parity obligation** shall be recorded in the deploy documentation. Because IdP login policies are organisation-scoped rather than role-scoped, the org-wide `forceMfa` switch shall **not** be used — the role-scoped mandate is EARS-3, and enabling it org-wide would impose TOTP on every `doctor_guest`.
- **EARS-9** — The system shall append exactly one terminal `audit_ledger` row (ADR-0003 §6) per admin-session/MFA lifecycle event, using **exactly the canonical ADR-0001 design §7.3 wire id its domain event maps to in the Event Model → Events mapping table** (`auth.login.success` / `auth.login.failure` / `auth.mfa.enrolled` / `auth.mfa.used` / `auth.mfa.failure` / `auth.mfa.reset` / `auth.lockout.triggered` / `auth.session.created` / `auth.session.terminated` / `auth.session.rejected`) — no invented id and no parallel taxonomy — emitted through the single shipped mapper `auth-audit.ledger.ts` so no second source can drift; every such row shall carry **`tier: "admin"`** so admin rows are distinguishable from the portal's rows on the shared `auth.session.*` / `auth.login.*` classes, plus the actor, timestamp, IP, and user-agent. **`auth.session.rejected` shall additionally be registered upstream** — a forward-reference line in ADR-0001 design §7.3 naming this spec, landed in the same slice, per the repo's established registration form. **No** row shall ever contain the TOTP secret, provisioning URI, or a submitted code, and PD fields shall be masked per ADR-0001 §7.

**Operator factor recovery**

- **EARS-13** — When a `platform_admin` operator invokes the factor-removal command against a **different** admin account **and supplies their own current TOTP code in the request**, the system shall verify that code against the **caller's** registered factor at call time, remove the target account's registered TOTP factor, and append an **`auth.mfa.reset`** row carrying the acting operator in the canonical `by_admin` field, after which the target's next login shall re-enter the forced-enrollment state of EARS-4. A missing, wrong, expired, or replayed caller code shall refuse the removal under the **same uniform-failure and rate-limit discipline as EARS-7** — no distinct error, no separate attempt budget. The endpoint shall be classified `access: authenticated`, `required_roles: platform_admin` and shall ride the **high-stakes introspection** validation tier (ADR-0001 §2.5/§8).

  This caller-code requirement **realises the ADR-0001 §10 policy intent** — an MFA change is an elevated action and demands fresh MFA — **for this one route, by route-local means**. The general step-up mechanism (`StepUpGuard`, the `acr=mfa-fresh` claim, the 30-minute elevated session, the `401 step_up_required` contract) **is unbuilt in this repo and is not built here**; accordingly the route shall **not** declare `stepUp` matrix metadata, because that column advertises the general mechanism and a row behind no guard would make the generated endpoint-authz matrix promise a protection nothing enforces. Moving this route onto the general mechanism when its vertical lands is a tracked deferral (Scope → Out).

  Removal of the caller's **own** last factor shall be refused through this endpoint, so an operator cannot strip the control from themselves and re-enter enrollment unchallenged. **Operational precondition:** this path presumes **≥2 enrolled `platform_admin` operators** — with fewer, no caller can satisfy it, and the named BREAK-GLASS exception of LD-2 applies instead.

**Cross-cutting (ubiquitous / unwanted behaviour)**

- **EARS-10** — The `__Host-ds_admin_session` tier shall conform to the ADR-0001 §6 / design §7.1 session profile in full: the session record stored **server-side in Redis**, bound to a stable client **fingerprint** (hash of UA + IP /24 + accept-language) that is re-checked on every request and invalidates the session on mismatch, honouring the specified TTL and refresh rotation, revocable by force-logout, and protected by **CSRF double-submit** on every state-changing admin endpoint (ADR-0004 design §3.2.1). The admin tier shall introduce **no** new session model, token type, or credential store — it is a second cookie over the shipped 003 machinery.
- **EARS-11** — Every admin API route shall be classified in the endpoint-authz matrix as **`access: authenticated`, `required_roles: platform_admin`** with the additional requirement that the resolved admin principal carries **`mfa = true`**; a session that carries the `platform_admin` role but **not** a verified second factor shall be **refused** on every admin route (never silently downgraded, never partially served), and the existing 007 admin commands and reads shall keep their shape and their high-stakes introspection posture (ADR-0001 §2.5/§8) while sitting on this raised floor.
- **EARS-12** — The enrollment and challenge screens shall be delivered **in this slice alongside their backend** (F-22): built through the `build-ui-from-design-system` adopt-before-bespoke gate with a **Stage-A design proposal approved by the product owner before implementation** and a **Stage-B live re-confirmation on the running stand before merge**; all copy shall resolve from the typed RU message catalog of the admin app (`apps/admin/messages/ru.json`, established by 007 EARS-10 and enforced by the `local/no-hardcoded-display-string` ESLint rule scoped to `apps/admin/app/**` + `apps/admin/components/**`) with **no hardcoded user-facing strings** — including the uniform failure message of EARS-7 and the recovery guidance pointing at the LD-2 operator path; ADR-0013 token discipline (no arbitrary Tailwind values) shall hold for any bespoke styling; and the code-entry fields shall be keyboard-operable and screen-reader-labelled, with the secret transcribable by selection (never image-only) and the QR carrying a text alternative.

## Invariants

- An admin API route is reachable **only** with `__Host-ds_admin_session`; `__Host-ds_session` never authenticates an admin route, and the admin cookie never authenticates a portal route (EARS-1, EARS-2).
- Every established admin session carries `mfa = true`. There is **no** code path that issues an admin session on primary authentication alone (EARS-3, EARS-5, EARS-6, EARS-11).
- A pending-auth reference is not a session: it reaches the enrollment/challenge endpoints and nothing else, is server-side, is short-lived, and is never accepted by the admin session hook (EARS-3, EARS-4).
- A `platform_admin` with no registered factor sees exactly one screen — enrollment — and no admin data of any kind until the factor is verified (EARS-4).
- The TOTP secret is presented exactly once, to the authenticated pending principal, and never appears in a log, an audit row, or any later response (EARS-5, EARS-9).
- A TOTP code is single-use within its validity window (EARS-6).
- A failed verification is indistinguishable from every other failed verification, in body and in timing (EARS-7).
- **No surface reachable by a merely primary-authenticated principal discloses lock state, attempt budget, or account existence** — the uniform-failure rule binds `AdminAuthState` exactly as it binds the verify responses; one disclosure rule, not two (EARS-7, Read models).
- A soft-locked account cannot obtain an admin session, correct code or not, until the lock expires or is lifted (EARS-7).
- The IdP's org-wide `forceMfa` is never enabled; the mandate lives in the role policy (EARS-3, EARS-8).
- Every admin-session/MFA lifecycle event appends exactly one terminal `audit_ledger` row under its **canonical §7.3 wire id** from the Event Model mapping table, carrying `tier: "admin"`, PD-masked and secret-free (EARS-9).
- Factor removal happens **only** through the audited EARS-13 endpoint, **or** through the single named BREAK-GLASS exception of LD-2 while fewer than two `platform_admin` operators hold an enrolled factor. There is no third path, and never an _unobserved_ one: break-glass carries a compensating `auth.mfa.reset` row written by the runbook's ops script plus a post-action note on the tracking Issue, so every factor removal — API or break-glass — leaves a ledger row with a recorded acting operator (EARS-13, LD-2).
- An operator cannot remove their **own last factor through the API** (EARS-13); the only way a sole operator's factor is removed is the LD-2 break-glass path, under its stated precondition and with its compensating audit row.
- The doctor portal's session behaviour is byte-for-byte unchanged by this feature (EARS-1, EARS-2).

## Dependencies & sequencing

- **Feature 003 (user authentication) — shipped, and the direct upstream.** 011 composes 003's BFF-over-Zitadel session establish/validate, the `mfa` claim derived from `amr`, the Redis session store, and the fingerprint hook. The `role → mfa_required` seam 003 shipped as a documented no-op is exactly what EARS-3 populates. 011 adds **no** new auth primitive.
- **Feature 007 (minimal event admin) — shipped, and the surface being hardened.** 007's commands and reads keep their shape; only the floor they sit on rises (EARS-11). 007's own spec text already forward-references #718 as the pre-pilot hardening, so landing 011 resolves that forward reference rather than contradicting it.
- **Zitadel TOTP capability (dev stand + prod).** EARS-8's provisioning is a **prerequisite** for the EARS-5/6/7 e2e suites: the login-policy knobs exist in `infra/dev-stand/idp/provision.sh` today but are unset, and no TOTP/multifactor configuration is enabled anywhere. Sequence EARS-8 before the enrollment/challenge handlers; wire the `blocked_by` edge accordingly (`open-ears-issues` step 4). **Prod parity is a deploy-time obligation, not a code change** — an admin that can enroll on the stand and not in prod is a shipped outage.
- **The `IdpPort` TOTP seam + fake.** The port (`apps/api/src/auth/idp/idp.types.ts`) gains TOTP register/verify; **both** the Zitadel adapter and the in-repo fake implement it, the fake no more permissive than the real one (Constraints). This is a single change landing with EARS-5, consumed by EARS-6/7.
- **`packages/schemas/` DTOs.** The admin-auth request/response DTOs (`AdminAuthState`, `AdminEnrollmentOffer`, the verify payloads) are Zod schemas in the SSOT package, shared by the API and the Refine admin app through the generated SDK (ADR-0002 §3). The `mfa` claim shape in `auth.schema.ts` is reused, not redefined.
- **Design approval (Stage A) gates implementation of the screens.** Per AGENTS.md §6 and the `build-ui-from-design-system` skill, the enrollment + challenge screens need an owner-approved Stage-A proposal **before** they are built, and a Stage-B live re-confirmation **before** the PR merges. There is no admin canvas (the Stage-A gap recorded in 007), so the proposal starts from stock Refine + the approved registry whitelist.
- **Dev-stand Postgres + Zitadel + Redis.** The e2e suites run against the stand (`DATABASE_URL`, `IDP_ISSUER`, `REDIS_URL`), `skipIf` absent, endpoints read from `.env.local` and never hardcoded (`.claude/rules/dev-stand.md`).
- **Pilot deadline (2026 Q3).** #718 is a **pre-pilot** requirement: admin commands are the high-stakes tier, and the pilot is the point at which the admin surface stops being operated exclusively by its authors. The slice is deliberately not rushed into a live-event window (#718 Notes).
- **Step-up (`StepUpGuard` / `acr=mfa-fresh`) — NOT built, and therefore not depended on.** Verified against the tree: `stepUp` is endpoint-authz matrix metadata only (`apps/api/src/authz/authz.types.ts`, whose own comment defers the mechanism to the ADR; rendered as a column by `authz.matrix.ts`); no guard consumes it, no `acr` / `mfa_fresh_at` check exists anywhere in `apps/api`, and no route declares it. **011 therefore has no step-up dependency and no `blocked_by` edge on one:** EARS-13 carries its own route-local fresh-possession proof (the caller's current TOTP code), which reuses the EARS-5/6 verification path this slice already builds. Building the general mechanism is a separate vertical; the graduation of this route onto it is the tracked deferral named in Scope → Out.
- **Upstream taxonomy write-back.** `auth.session.rejected` needs its forward-reference line in ADR-0001 design §7.3 landed in the same slice as EARS-9 — a docs edit outside this spec directory, carried on the audit child Issue.
- **Follow-up opened from this spec.** Self-serve MFA recovery codes (Scope → Out) — a tracked Issue with a real done-criterion, opened by `open-ears-issues` step 3a. LD-2's operator recovery path is the interim, delivered as the EARS-13 endpoint and documented in the module runbook rather than left as a code comment.
