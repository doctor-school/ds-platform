# 011 — Усиление админской сессии: выделенная `__Host-ds_admin_session` + обязательный TOTP (Требования)

> Инициатива: GitHub Issue [#718](https://github.com/doctor-school/ds-platform/issues/718), несущий реализационную половину decision-debt [#663](https://github.com/doctor-school/ds-platform/issues/663) (выявлен Mode-a ревью #595 по PR #660). **Требуется до пилота 2026 Q3.**
>
> **PRD `011-product.md` не существует, и он не требуется.** Это внутреннее усиление безопасности админки без внешней продуктовой аудитории: поверхностью пользуются Tech Lead и небольшая доверенная группа операторов `platform_admin`, деливерабл — режим безопасности, предписанный ADR-0001 §4, а не пользовательская работа, которую нужно исследовать, и единственная настоящая продуктовая развилка (как админ получает свой первый фактор) была решена напрямую с владельцем продукта 2026-08-07 — дословно зафиксировано в **Ранее принятых решениях → PD-1**. Поэтому пункты EARS не несут ссылок `realizes: US-N` (ADR-0014 §2 применяется к спекам, выведенным из PRD).

## Результаты

- **У админ-поверхности появляется собственное удостоверение.** `platform_admin`, аутентифицировавшийся на origin админки, получает **выделенную куку `__Host-ds_admin_session`** — host-only, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/` — и админский API принимает **только** её. Украденная или подставленная через CSRF сессия портала врача больше не может дотянуться до админской команды; так закрывается позиция волны 1, которую ADR-0004 design §3.2 принял как временную.
- **Каждая админская сессия подтверждена вторым фактором.** Ни один `platform_admin` не попадает ни на одну админскую поверхность, не доказав владение TOTP-фактором **в этом же входе**. Claim `mfa` на админской сессии равен `true` по построению, а не по надежде.
- **Админ регистрирует фактор сам, в админке, без сопровождения оператора.** `platform_admin`, у которого нет TOTP-фактора, принудительно попадает на экран регистрации (QR + секрет для ручного ввода + поле подтверждения кода) до того, как отрисуется хоть одна админская поверхность, — и тот же экран является bootstrap-путём для админов, существующих сегодня (PD-1). В штатном сценарии нет ни внешней рассылки при переходе, ни обращения в поддержку, ни ручного шага в консоли IdP.
- **Шов политики из 003 получает первого жильца.** `role → mfa_required` — поставленный в 003 как задокументированная заглушка без единой привилегированной роли — заселяется ролью `platform_admin`, и проверка выполняется сразу после первичной аутентификации. 011 — это та самая «первая вертикаль с обязательной MFA-ролью, которая строит механизм», названная в 003.
- **Возможность MFA задаётся конфигурацией как код, а не кликами в консоли.** TOTP как разрешённый второй фактор и времена жизни проверок в политике входа, заставляющие фактор перепроверяться на каждом входе, объявлены в провижининге dev-стенда и несут зафиксированное обязательство паритета с продом — чтобы dev, стенд и прод не могли молча разъехаться по контролю безопасности.
- **Жизненный цикл админской сессии и MFA поддаётся аудиту.** Регистрация фактора, успех/неуспех челленджа, блокировка и установление/отказ админской сессии добавляют по одной терминальной строке в `audit_ledger` по таксономии ADR-0001 design §7.3 — вход админа реконструируем постфактум.
- **В портале врача не меняется ничего.** `__Host-ds_session`, потоки входа из 003 и поведение `doctor_guest` не затронуты; 011 добавляет рядом второй, более строгий уровень.

## Решения, принятые автором спеки

Два вопроса, которые инициатива не закрыла и которых не касалась развилка владельца. Каждый решён здесь как **решение автора (2026-08-07)**, продублирован в требовании, которое он формирует, и может быть отменён на ревью спеки.

- **LD-1 — успешное подтверждение при регистрации фактора завершает этот же вход; повторный вход не требуется.** ADR-0001 design §8.5, шаг 4, завершает сессию регистрации и требует свежего входа с MFA. Этот шаг существует потому, что средством доставки в §8.5 является **magic-link**: ссылка в почтовом ящике — более слабое первичное удостоверение, чем пароль, поэтому повышенную сессию регистрации нельзя переиспользовать. Средство доставки в 011 — **завершённая парольная аутентификация** (PD-1), а подтверждение при регистрации **и есть** успешная TOTP-проверка только что зарегистрированного фактора: оба фактора уже предъявлены в этом входе. Принудительный немедленный второй полный вход добавил бы трение, ничего не доказывая. Система повышает pending-запись на месте и выдаёт полноценную админскую сессию с `mfa = true` (EARS-5). Важный инвариант §8.5 — _интерфейс не позволяет продолжить без регистрации фактора_ — сохраняется полностью (EARS-4).
- **LD-2 — восстановление фактора в этом срезе — действие оператора, а не самостоятельный поток.** Потерянный аутентификатор запирает `platform_admin` снаружи **живой медицинской платформы**, поэтому путь восстановления обязан существовать и быть записанным — но самостоятельные коды восстановления это отдельная вертикаль (генерация, однократный показ, рекомендации по хранению, погашение, перевыпуск, аудит), которая удвоила бы этот срез. В 011 путь восстановления — **явное действие оператора**, и это действие идёт **через наш API, а не через консоль IdP**: Tech Lead, единственный владелец CODEOWNERS в Фазе 0 (ADR-0008 §2.7), вызывает доступный только роли `platform_admin` эндпоинт удаления фактора из **EARS-13**, после чего следующий вход целевого админа попадает на экран принудительной регистрации (EARS-4) и фактор регистрируется заново. **Почему эндпоинт, а не консоль:** удаление на стороне консоли никогда не наблюдается `apps/api`, поэтому строка `auth.mfa.reset`, которую предписывает EARS-9, не была бы записана никогда — непостроимый критерий. Хуже того, снятие второго фактора у другого админа — самое чувствительное админское действие в этой спеке, а ADR-0001 §7/§10 уже относят «изменение MFA» и «админские записи по управлению пользователями» к действиям повышенного риска, требующим **свежей MFA**; вынесение его за пределы API сделало бы предписанный ADR контроль недостижимым, а не отложенным. **И то, чем эта свежесть доказывается, принципиально, потому что общего механизма не существует:** `StepUpGuard`, claim `acr=mfa-fresh` и 30-минутная повышенная сессия — это _решение_ ADR-0001 §10, которое здесь никогда не было построено (`stepUp` — только метаданные матрицы, не читаемые ни одним guard). Поэтому EARS-13 доказывает свежесть **локально для маршрута**: вызывающий передаёт с запросом собственный текущий TOTP-код, что удовлетворяет замысел политики §10 для этого маршрута, не заявляя об отсутствующей машинерии. Runbook описывает **этот эндпоинт**. **Самостоятельные коды восстановления названы в разделе «Вне области»** как отслеживаемое продолжение, а не молчаливый пробел — здесь решается только _средство_ промежуточного пути; решение, что восстановление является действием оператора, остаётся в силе.

  **Предусловие по числу операторов и исключение BREAK-GLASS под ним.** Эндпоинт EARS-13 предполагает **≥2 зарегистрировавших фактор операторов `platform_admin`**: вызывающий обязан доказать свежее владение _собственным_ фактором и не может удалить свой последний — значит, при единственном операторе выполнить его некому. Такова сегодняшняя реальность Фазы 0 (AGENTS.md §7 фиксирует Tech Lead как единственного владельца CODEOWNERS), и делать вид, что это не так, значило бы превратить неаудируемый путь восстановления в несуществующий. Поэтому: **пока зарегистрировавших фактор операторов `platform_admin` меньше двух, потеря фактора запускает именованный путь BREAK-GLASS** — Tech Lead удаляет фактор через **админский API IdP** по runbook модуля, и _тот же шаг runbook_ добавляет компенсирующую строку **`auth.mfa.reset`** через выделенный ops-скрипт, чтобы журнал оставался полным, а не молча терял самое чувствительное событие в системе, плюс **обязательная пост-фактум заметка в отслеживающем Issue**. Break-glass — это **задокументированное исключение с компенсирующим путём аудита и заявленным предусловием**, а не молчаливый обход и не разрешение обходить эндпоинт после появления второго оператора. Предусловие проверяемо до поставки среза: посчитать зарегистрировавших фактор операторов.

## Область

**Входит:**

- **Выделенная кука админской сессии (выдача).** По завершении админской аутентификации на origin админки API выдаёт `__Host-ds_admin_session` — host-only (без `Domain`), `Path=/`, `HttpOnly`, `Secure`, `SameSite=Strict` — несущую только непрозрачную серверную ссылку на сессию, никогда не токен (EARS-1).
- **Выделенная кука админской сессии (валидация + разделение).** Хук админской сессии принимает на админских маршрутах **только** `__Host-ds_admin_session`; предъявленная админскому маршруту `__Host-ds_session` отвергается как неаутентифицированная, и наоборот. Выход из админки удаляет запись админской сессии и очищает её куку, не трогая сессию портала (EARS-2).
- **Заселение политики `role → mfa_required`.** Шов из 003 заселяется ролью `platform_admin` и вычисляется сразу после первичной аутентификации; роль, присутствующая в политике, не может получить полноценную админскую сессию без удовлетворённого второго фактора (EARS-3).
- **Шлюз принудительной регистрации фактора.** `platform_admin`, прошедший первичную аутентификацию и **не** имеющий зарегистрированного TOTP-фактора, переводится в состояние `mfa_pending_enrollment` и может достичь **только** экрана регистрации и двух его эндпоинтов — любая другая админская поверхность и любой другой админский маршрут API для этого состояния отвергаются (EARS-4).
- **Самостоятельный экран регистрации TOTP (админка).** QR-код + тот же секрет в **пригодном для ручного ввода** виде + поле подтверждения кода; корректный код регистрирует фактор, порождает `auth.mfa.enrolled` и завершает вход на месте (LD-1). Это же — bootstrap для существующих админов (PD-1) (EARS-5).
- **TOTP-челлендж при каждом последующем входе в админку.** После первичной аутентификации зарегистрированному `platform_admin` показывается экран челленджа; только корректный код даёт админскую сессию (EARS-6).
- **Обработка неверных кодов: рейт-лимит, блокировка, единообразные ошибки.** Попытки подтверждения ограничены по частоте и по счётчику блокировки согласно ADR-0001 §7; неудачи возвращают одно единообразное сообщение, не различающее ни «неверный код» и «фактор не зарегистрирован», ни заблокированный аккаунт от незаблокированного, с дисциплиной разброса по времени из §7 (EARS-7).
- **Включение TOTP в Zitadel как провижининг-конфигурации.** TOTP зарегистрирован как разрешённый второй фактор политики входа, ручки `secondFactorCheckLifetime` / `multiFactorCheckLifetime` / `mfaInitSkipLifetime` выставлены так, что проверка фактора **не** переживает вход, а регистрацию нельзя пропустить; объявлено в `infra/dev-stand/idp/provision.sh` с зафиксированным обязательством паритета с продом (EARS-8).
- **Удаление фактора оператором как аудируемый эндпоинт с локальным для маршрута доказательством свежего владения.** Доступный только роли `platform_admin` эндпоинт, удаляющий TOTP-фактор другого админа, на high-stakes слое с introspection, требующий **собственный текущий TOTP-код вызывающего в запросе** — проверяемый в момент вызова против зарегистрированного фактора вызывающего. Это реализует замысел политики ADR-0001 §10 («изменение MFA — действие повышенного риска, требующее свежей MFA») для этого одного маршрута **без** общего механизма step-up, который не построен. Эндпоинт порождает каноническую строку `auth.mfa.reset` и возвращает цель к принудительной регистрации. Средство промежуточного пути восстановления LD-2 при соблюдении его предусловия по числу операторов (EARS-13).
- **Аудит-след с явным каноническим сопоставлением.** Каждое событие жизненного цикла админской сессии и MFA сопоставлено с **каноническим идентификатором `<class>.<event>` из ADR-0001 design §7.3** через таблицу сопоставления в разделе «Модель событий → События» — никаких выдуманных идентификаторов — с дискриминатором уровня **`admin`**, чтобы админские строки не сливались с портальными строками `auth.session.*`; каждая — терминальная строка `audit_ledger` с маскированием ПДн (EARS-9).
- **Соответствие профилю сессии для нового уровня.** Привязка к отпечатку клиента, TTL, серверное хранение в Redis, ротация, принудительный выход и CSRF double-submit применяются к `__Host-ds_admin_session` ровно так, как задают ADR-0001 §6 / design §7.1 — новая кука не является новой моделью сессии (EARS-10).
- **Классификация endpoint-authz.** Каждый админский маршрут требует `platform_admin` **и** админской сессии с подтверждённой MFA; строки матрицы несут поднятую нижнюю границу, а сессия только с ролью отвергается (EARS-11).
- **Дисциплина UI для двух новых экранов.** Русские тексты из типизированного каталога сообщений (без хардкода строк), шлюз `build-ui-from-design-system` adopt-before-bespoke с **утверждённым владельцем продукта предложением Stage A до реализации** и **живым переподтверждением Stage B до мержа**, токен-дисциплина ADR-0013 и доступность полей ввода кода с клавиатуры и для скринридеров (EARS-12).

**Явно не входит** (каждый пункт — названный отказ, а не молчаливое умолчание):

- **Самостоятельные коды восстановления MFA.** Восстановление в 011 — действие оператора из LD-2, поставленное как эндпоинт EARS-13 (задокументированный runbook + аудит-строка `auth.mfa.reset`). Генерация/однократный показ/погашение/перевыпуск кодов восстановления — **отслеживаемый последующий Issue**, открываемый `open-ears-issues`, шаг 3a, против этой строки Области, а не комментарий в коде.
- **SMS как второй фактор для `moderator` / `support`.** ADR-0001 §4 принимает SMS для этих ролей в v1 и повышает их до TOTP в v2; ни одна из ролей ещё не является заселённым жильцом `mfa_required`. 011 заселяет политику **только** ролью `platform_admin`. Структура политики остаётся картой `role → требование`, поэтому добавление роли позже — изменение данных, а не переделка формы.
- **MFA для `expert` / `clinic_admin` / `investor`.** Тоже предписаны ADR-0001 §4, тоже пока недостижимые роли. Та же точка расширения карты политики.
- **Общий механизм step-up (`StepUpGuard`, claim `acr=mfa-fresh`, 30-минутная повышенная сессия, контракт `401 step_up_required`).** ADR-0001 §10 его принял; **он никогда не был построен** — `stepUp` существует только как метаданные матрицы, ни один guard их не потребляет, ни один маршрут их не объявляет. 011 его не строит, не проектирует и не переводит на него админские маршруты 007; подъём нижней границы базовой админской сессии до «MFA подтверждён» остаётся всей работой 011 по сессиям. EARS-13 удовлетворяет _замысел политики_ §10 для своего единственного маршрута **локальным для маршрута** средством (собственный текущий TOTP-код вызывающего в запросе) и сознательно **не** выставляет метаданные `stepUp`: эта колонка рекламирует общий механизм, и строка в ней без guard за спиной — заявление, открытое наружу (fail-open): матрица endpoint-authz обещала бы защиту, которую никто не обеспечивает.
- **Перевод EARS-13 на общий механизм step-up — отслеживаемый отложенный пункт.** Когда вертикаль step-up будет поставлена (guard, claim `acr=mfa-fresh`, TTL повышенной сессии, контракт `401 step_up_required`), маршрут удаления фактора переезжает на неё: локальная проверка кода заменяется метаданными `stepUp: true` плюс обеспечением guard. Это **именованный последующий Issue** для `open-ears-issues`, шаг 3a, против этой строки Области — не комментарий в коде и не расчёт на то, что кто-нибудь заметит.
- **Куки других приложений.** `__Host-ds_cms_session`, `__Host-ds_promo_session`, `__Host-ds_docs_session` (ADR-0004 design §3.2) не затрагиваются. Как и `__Host-ds_session` портала.
- **Поток Directual-перехода для `legacy_admin` (ADR-0001 design §8.5).** Bootstrap через magic-link и повышенную сессию решает задачу для популяции, которой у 011 нет (PD-1). Он остаётся доступным и нереализованным для того среза, которому понадобится.
- **Cross-app SSO / OIDC silent re-auth для админки.** Непрерывность через `prompt=none` из ADR-0004 design §3.2.1 намеренно **не** распространяется на origin админки — уровень с `SameSite=Strict` и обязательной MFA, молча восстанавливающийся из сессии другого приложения, отменил бы разделение, ради которого написана эта спека.
- **Passkeys / WebAuthn как альтернативный фактор.** ADR-0001 §4 фиксирует TOTP для `platform_admin` в v1.
- **Интерфейс управления своими сессиями** (список/отзыв). Принудительный выход существует на сервере (EARS-10); поверхности для него в этом срезе нет.
- **Миграция авторизации на Cerbos.** Авторизация админки остаётся быстрой проверкой роли, какой она является сегодня; перенос админской авторизации в Cerbos не связан с усилением сессии.

## Ограничения

- **Админская кука — единственное админское удостоверение, и разделение обеспечивается, а не подразумевается.** `__Host-ds_admin_session` выдаётся только на origin админки и принимается только на админских маршрутах; `__Host-ds_session` там не принимается никогда. Поскольку админка ходит в API same-origin через свой прокси `/v1/*`, ситуация «браузер просто приложил куку портала» обязана быть явным **отказом**, а не случайным успехом (EARS-2). Это ровно та слабость волны 1, которую зафиксировал ADR-0004 design §3.2.
- **`SameSite=Strict` — и его цена принимается сознательно.** Strict подавляет куку при любом кросс-сайтовом переходе на origin админки: ссылка из письма или мессенджера приводит оператора на экран входа, а не в приложение. Для админской консоли, которой пользуется горстка операторов, ходящих по закладке, это верный размен (ADR-0004 design §3.2.1 называет `strict` для admin/cms); поэтому экран входа обязан корректно восстанавливать и возвращать оператора на нужный маршрут.
- **Обязательность MFA задаётся политикой ролей в нашем бэкенде, а не общим переключателем IdP.** Политики входа Zitadel действуют на **организацию**, а не на роль: общий `forceMfa` навязал бы TOTP каждому врачу. Поэтому Zitadel даёт **возможность** (TOTP как разрешённый второй фактор + времена жизни проверок, EARS-8), а наша политика `role → mfa_required` даёт **обязательность** (EARS-3). Потеря этого разделения из виду либо запрёт врачей, либо оставит админскую MFA невынужденной.
- **Промежуточное состояние аутентификации — не сессия.** Между первичной аутентификацией и удовлетворённым вторым фактором принципал держит короткоживущую host-only `SameSite=Strict` **pending-auth**-ссылку, которая не даёт доступа ни к чему, кроме эндпоинтов регистрации/челленджа. Она хранится на сервере, одноцелевая, истекает за минуты и никогда не принимается хуком админской сессии. Pending-ссылка, способная дотянуться до админского маршрута, обнулила бы всю спеку.
- **Никаких новых примитивов аутентификации.** 011 собирается из поставленной в 003 машинерии BFF-над-Zitadel (установление/валидация сессии, вывод claim `mfa` из `amr`, хранилище сессий в Redis, привязка к отпечатку) и профиля ADR-0001 §6. Новых типов токенов, новых хранилищ удостоверений и второго источника идентичности не вводится.
- **Фейковый IdP никогда не мягче настоящего.** Шов регистрации/подтверждения TOTP добавляется в `IdpPort` и реализуется **обоими** — адаптером Zitadel и внутрирепозиторным фейком; фейк отвергает всё, что отвергает настоящий адаптер (неверный код, незарегистрированный фактор, повторно предъявленный код, истёкшее окно). Фейк, принимающий любые 6 цифр, сделал бы весь набор EARS-5/6/7 бессодержательным.
- **Админские мутации остаются high-stakes слоем.** Валидация админских мутаций через introspection (ADR-0001 §2.5/§8) не меняется; MFA поднимает нижнюю границу сессии и не заменяет её.
- **Секреты не покидают обмен при регистрации.** TOTP-секрет / provisioning URI возвращается ровно один раз аутентифицированному pending-принципалу в ответе на старт регистрации — никогда не логируется, не попадает в аудит-строку и не может быть прочитан повторно после регистрации фактора. Маскирование ПДн по ADR-0001 §7 применяется к каждому полю аудита.
- **Никаких зашитых origin, эндпоинтов и issuer.** Origin админки, issuer IdP и эндпоинт Redis приходят из конфигурации (`.env.local` на стенде, конфиг деплоя в проде), а не из литерала в коде или спеке (AGENTS.md §9).
- **Стек** (ADR-0002 / ADR-0004): эндпоинты аутентификации — NestJS + `nestjs-zod`, DTO в `packages/schemas/`, версионирование URI `/v1/...`, тесты Vitest + supertest; два экрана строятся в Refine-админке (`apps/admin`), на клиенте. Тесты, зависящие от сервисов, делают `skipIf` при отсутствии их окружения (`DATABASE_URL`, `IDP_ISSUER`, `REDIS_URL`).

## Prior decisions (предшествующие решения)

- **PD-1 — продуктовая развилка, решённая владельцем (2026-08-07): самостоятельная регистрация фактора в админке.** _Вход `platform_admin` без зарегистрированной MFA принудительно ведёт на экран регистрации TOTP (QR + подтверждение кода) до попадания на любую админскую поверхность; далее каждый вход в админку требует пароль + TOTP-код. Bootstrap для существующих админов — тот же экран принудительной регистрации при их следующем входе._ **Обоснование отказа от потока magic-link с повышенной сессией из ADR-0001 design §8.5:** §8.5 решает случай **перехода с Directual** — legacy-админов, у которых _нет пароля в новой системе_ и которым поэтому нужно внешнее удостоверение просто чтобы добраться до экрана регистрации. У наших админов такой проблемы нет: они уже входят по паролю в аутентификацию 003 на Zitadel, поэтому завершённая парольная аутентификация доступна как шлюз к регистрации. Введение magic-link по почте **ослабило** бы bootstrap (почтовый ящик становится путём к админскому фактору), ничего при этом не решая. §8.5 остаётся верным потоком для `legacy_admin` при переходе и не затрагивается. Что 011 **наследует** от §8.5: канонические идентификаторы аудит-событий (`auth.mfa.enrolled`, `auth.lockout.triggered`) и инвариант «интерфейс не даёт продолжить без регистрации фактора».
- **ADR-0001 §4** — MFA **TOTP обязателен для `platform_admin`**. Метод зафиксирован ADR; 011 не открывает заново вопрос «какой фактор» и не оценивает passkeys/SMS для этой роли.
- **ADR-0001 §6** — host-only куки на каждое приложение; общая кука между поддоменами отвергнута, потому что same-origin XSS или захват поддомена скомпрометировали бы админскую сессию и обошли бы защиты по отпечатку и CSRF. 011 приводит админку в соответствие с этим решением — именно она всё ещё одалживала куку портала.
- **ADR-0001 §7** — рейт-лимиты, блокировка аккаунта (10 неудач / 30 мин → мягкая блокировка + письмо), единообразные ответы без утечки существования аккаунта с разбросом ≤50 мс, CSRF double-submit и строжайший CSP-профиль для `admin.doctor.school`. EARS-7 применяет этот базовый уровень к эндпоинтам подтверждения TOTP, а не изобретает пороги.
- **ADR-0001 §2.5/§8** — админские мутации относятся к high-stakes слою и идут через introspection IdP; IdP — Zitadel, и он обязан оставаться на релизе с закрытыми CVE (≥ 4.9.1 / ≥ 3.4.6).
- **ADR-0001 §10** — step-up `acr=mfa-fresh`, TTL 30 мин, `StepUpGuard`, контракт `401 step_up_required`. **Принят в ADR, но не построен в коде**: проверено по дереву на момент написания — `stepUp` встречается только как метаданные матрицы endpoint-authz (`apps/api/src/authz/authz.types.ts`, отрисовываемые как колонка через `authz.matrix.ts`), их не читает ни один guard, проверки `acr` или `mfa_fresh_at` в `apps/api` нет, и ни один маршрут их не объявляет. 011 поднимает границу _на входе_, а для единственного маршрута, где замысел §10 неизбежен (EARS-13), удовлетворяет этот замысел **локально для маршрута**, вместо того чтобы делать вид, будто механизм на месте. Общий механизм остаётся непостроенным и вне области, а переезд на него отслеживается.
- **ADR-0001 design §7.1** — таблица параметров сессии (access JWT 15 мин, refresh непрозрачный ротируемый одноразовый 30 д для веба, серверное хранилище Redis, привязка к отпечатку, TTL `acr=mfa-fresh` 30 мин). `__Host-ds_admin_session` соответствует этой таблице; это вторая кука, а не вторая модель сессии (EARS-10).
- **ADR-0001 design §7.3** — таксономия аудита аутентификации `<class>.<event>`. События 011 регистрируются под ней с каноническими идентификаторами (EARS-9).
- **ADR-0001 design §8.5** — переиспользуются имена событий и инвариант «нельзя продолжить без регистрации»; **не** переиспользуется как средство bootstrap (PD-1).
- **ADR-0004 design §3.2** — поэтапная модель админской сессии. Волна 1 (007, до вебинара 2026-07-17) работает на `__Host-ds_session`; **эта спека и есть названный триггер пред-пилотного усиления**, на который ADR ссылается через #718. После мержа строка админки в списке топологии §3.2 перестаёт описывать поэтапный компромисс и описывает поставленную целевую модель.
- **ADR-0004 design §3.2.1** — паттерн куки-на-приложение с `sameSite: 'strict'` для admin/cms и CSRF double-submit на изменяющих состояние эндпоинтах. 011 реализует админскую строку этого паттерна и сознательно **не** перенимает silent re-auth через `prompt=none` для админки (Область → Не входит).
- **ADR-0002 §3** — nestjs-zod, версионирование URI, Vitest + supertest, SSOT DTO в `packages/schemas/`.
- **ADR-0003 §6** — `audit_ledger` как append-only приёмник.
- **ADR-0006 §4** — структура триплета + плоская нумерация EARS.
- **ADR-0013 + скилл `build-ui-from-design-system`** — adopt-before-bespoke и токен-дисциплина для экранов регистрации/челленджа; шлюз утверждения дизайна Stage A / Stage B применяется, потому что это `user-facing` поверхность (EARS-12).
- **Спека 003 (`003-requirements-en.md` → Область → Не входит; `003-design.md` §Швы)** — _«003 поставляет claim `mfa` в сессии и задокументированный шов политики `role → mfa_required`, но не строит регистрацию/подтверждение TOTP и не заселяет политику ни одной привилегированной ролью. Первая вертикаль с обязательной MFA-ролью (админ/ops → `platform_admin`) строит механизм.»_ 011 **и есть** эта вертикаль. Шов стоит сразу после шага первичной аутентификации и сегодня является заглушкой; EARS-3 его включает.
- **Спека 007 (`007-requirements-en.md` EARS-8, `007-design.md` §7)** — админские команды классифицированы как `authenticated` / `platform_admin` / `fast-path` и явно фиксируют поэтапную позицию сессии с опережающей ссылкой на #718. 011 поднимает границу, на которой стоят эти строки (EARS-11); форма ни одной команды 007 не меняется.

### Дельта шага 0 — что делала legacy-система

Legacy-админка Doctor.School — это страница **Bubble `page_admin`**, приводимая в движение сценариями **Directual**: внешний SaaS, кода в репозитории нет, только email+пароль, **никакой MFA** и **никакого разделения сессий** между админской страницей и остальным продуктом. Механизма, который можно было бы изучить, скопировать или мигрировать, не существует — 011 является нововведённым контролем, а дельта относительно legacy — это «от отсутствия к обязательности». Зафиксировано, чтобы будущий читатель не искал предшествующих решений, которых нет.

## Модель событий

011 — **вертикаль уровня безопасности** на записывающем пути аутентификации. Ей принадлежат выдача/валидация админской сессии и жизненный цикл TOTP-фактора. Она **потребляет** поставленную в 003 машинерию первичной аутентификации (установление сессии Zitadel, вывод claim'ов, хранилище сессий в Redis, привязка к отпечатку) и модель `ROLES`; она **производит** админского принципала с подтверждённой MFA, на котором стоит каждая админская фича (сегодня 007, позже прочие админские вертикали). Продуктовых данных ей не принадлежит.

### Команды (обрабатываются `apps/api`, origin админки)

- `StartAdminLogin(credentials)` — первичная парольная аутентификация для origin админки. При успехе **не** выдаёт админскую сессию: создаёт короткоживущую серверную запись **pending-auth** и возвращает требуемый следующий шаг — `mfa_enrollment_required` (фактор не зарегистрирован) или `mfa_challenge_required` (зарегистрирован). Порождает `AdminPrimaryAuthSucceeded` / `AdminPrimaryAuthFailed`.
- `StartMfaEnrollment()` — для pending-принципала в `mfa_pending_enrollment`: регистрирует предварительный TOTP-фактор в IdP и возвращает **один раз** provisioning URI + данные QR + секрет для ручного ввода. Ничего долговременного не порождает (фактор ещё не подтверждён).
- `VerifyMfaEnrollment(code)` — проверяет первый код против предварительного фактора; при успехе фактор становится зарегистрированным, запись pending-auth повышается **на месте** до полноценной админской сессии с `mfa = true` (LD-1), выставляется `__Host-ds_admin_session`. Порождает `MfaEnrolled` + `AdminSessionEstablished`.
- `VerifyMfaChallenge(code)` — проверяет TOTP-код для зарегистрированного pending-принципала; при успехе выдаёт админскую сессию. Порождает `MfaChallengeSucceeded` + `AdminSessionEstablished` либо `MfaChallengeFailed` (и `LockoutTriggered` на пороге §7).
- `EndAdminSession()` — очищает `__Host-ds_admin_session`, удаляет её серверную запись и сессию IdP; сессию портала не трогает. Порождает `AdminSessionEnded`.
- `RemoveMfaFactor(userId, callerTotpCode)` — действие восстановления оператором из LD-2, обрабатываемое `apps/api` на origin админки: доступная только роли `platform_admin`, high-stakes (с валидацией через introspection) команда, удаляющая зарегистрированный TOTP-фактор целевого админа и допускаемая только при наличии **собственного текущего TOTP-кода вызывающего** в запросе (локальное для маршрута доказательство свежего владения; без метаданных `stepUp` и без зависимости от guard). Следующий вход цели снова попадает в принудительную регистрацию (EARS-4). Порождает `MfaFactorRemoved` (EARS-13).

### События — сопоставление с каноническими идентификаторами (все — терминальные строки `audit_ledger`, ADR-0003 §6)

**Эта таблица нормативна.** Каждое доменное событие 011 сопоставлено с **каноническим идентификатором `<class>.<event>` из ADR-0001 design §7.3** — 011 не изобретает идентификаторов и не заводит параллельной таксономии. Внутреннее PascalCase-имя доменного события приводится к идентификатору в единственном поставленном маппере `apps/api/src/auth/session/auth-audit.ledger.ts` (`toLedgerRow`), который уже порождает ровно эту форму; 011 расширяет его `switch`, а не добавляет второй источник.

**Дискриминатор уровня.** Админский уровень и портал врача делят канонические классы `auth.session.*` и `auth.login.*`, поэтому каждая строка, которую пишет 011, несёт **`tier: "admin"`** в поле `metadata` строки журнала — идиома §7.3 с различающим полем (как `method` различает `auth.mfa.*`, а `reason` — `auth.session.terminated`), а не новый класс. Без него админский форензик-запрос молча вернёт портальные строки. Дискриминатором является **наличие `tier: "admin"`** — этого достаточно для проверки отделимости. 011 **не** утверждает, что портальные строки уже несут уровень: поставленный `toLedgerRow` не пишет его вовсе, а обратное проставление `tier: "portal"` на записывающем пути 003 не принадлежит ни одному пункту этой спеки и сознательно не подразумевается.

Поставка строки без вышестоящей регистрации — неотслеживаемый шов (AGENTS.md §6), а не допустимое сокращение.

### Модели чтения

- **`AdminAuthState`** — то, из чего админка рисует поток аутентификации: **только перечисление состояния и ничего больше** — `unauthenticated | mfa_pending_enrollment | mfa_pending_challenge | active`. Модель **не** несёт ни остатка бюджета попыток, ни признака блокировки, ни идентификатора фактора, ни секрета, ни сырых claim'ов сессии. **Почему индикаторы бюджета и блокировки убраны:** читающий эту модель — принципал, уже прошедший первичную аутентификацию, то есть ровно тот атакующий с украденным паролем, ради остановки которого и существует второй фактор. Раскрытие блокировки или числа попыток вручило бы ему через соседний эндпоинт тот самый оракул, который EARS-7 целым пунктом закрывает: единообразный ответ подтверждения ничего не стоит, если соседнее чтение сообщает, что аккаунт заблокирован (а значит, существует, держит `platform_admin` и находится под атакой). Обе поверхности подчинены **одному** правилу раскрытия, и строка 7 матрицы верификации проверяет эндпоинт состояния наравне с эндпоинтами подтверждения.
- **`AdminEnrollmentOffer`** — однократная полезная нагрузка регистрации: provisioning URI, данные QR, секрет для ручного ввода, метки issuer/аккаунта. Возвращается ровно один раз и только pending-принципалу.
- **`AdminSessionPrincipal`** (внутренняя) — провалидированный админский принципал для нижележащих guard'ов: `sub`, `roles[]`, `mfa`, `sid`, ссылка на отпечаток. Именно её разрешает каждый админский маршрут; запрос, не способный её дать, отвергается.

### Политики

- **При успешной первичной аутентификации на origin админки** → вычислить `role → mfa_required`; роль из политики **никогда** не получает админскую сессию напрямую — она получает pending-ссылку и требуемый следующий шаг (EARS-3).
- **В состоянии `mfa_pending_enrollment`** → допускать **только** экран регистрации и два его эндпоинта; отвергать любую другую админскую поверхность и маршрут (EARS-4).
- **При успешном подтверждении регистрации** → зарегистрировать фактор, породить `auth.mfa.enrolled`, повысить на месте до полноценной админской сессии (LD-1, EARS-5).
- **При успешном подтверждении челленджа** → выдать админскую сессию с `mfa = true` (EARS-6).
- **При неудачном подтверждении** → списать попытку с бюджетов §7 на пользователя/IP, вернуть единообразный отказ, а на пороге — мягко заблокировать и уведомить (EARS-7).
- **На каждом админском маршруте** → разрешать `AdminSessionPrincipal` только из `__Host-ds_admin_session`, перепроверять отпечаток, `platform_admin` и `mfa = true`, иначе отказывать с аудит-строкой (EARS-2, EARS-10, EARS-11).
- **При выходе / принудительном выходе** → удалить серверную запись и сессию IdP, очистить куку, не трогать сессию портала (EARS-2, EARS-10).

## Требования EARS

> **Соглашение о нумерации:** плоская (`EARS-1` … `EARS-13`) по ADR-0006 §4. EARS-1…9 и EARS-13 — функциональные обработчики (каждый становится дочерним Issue); EARS-10…12 — сквозные повсеместные требования и требования о нежелательном поведении. **Ссылок `realizes:` нет** — у этой спеки нет PRD `NNN-product.md` (см. врезку в заголовке и PD-1).

**Выделенная админская сессия**

- **EARS-1** — Когда `platform_admin` завершает админскую аутентификацию на origin админки (первичная аутентификация **плюс** удовлетворённый второй фактор), система должна выдать **выделенную куку `__Host-ds_admin_session`** — без атрибута `Domain`, с `Path=/`, `HttpOnly`, `Secure`, `SameSite=Strict` — значение которой является **непрозрачной серверной ссылкой на сессию**, а не токеном или полезной нагрузкой claim'ов; ответ не должен нести токен в теле, а кука портала врача `__Host-ds_session` не должна быть ни выставлена, ни изменена этим потоком.
- **EARS-2** — Админский API должен аутентифицировать админские маршруты **исключительно** через `__Host-ds_admin_session`: запрос, предъявляющий только `__Host-ds_session` — включая same-origin случай, когда браузер прикладывает её через прокси `/v1/*` админки, — должен быть отвергнут как неаутентифицированный с аудит-строкой `auth.session.rejected`, а запрос, предъявляющий только `__Host-ds_admin_session` маршруту портала, должен быть отвергнут так же; выход из админки должен удалить запись админской сессии и очистить только админскую куку, оставив параллельную сессию портала действительной.

**Обязательная MFA для `platform_admin`**

- **EARS-3** — Система должна заселить политику 003 `role → mfa_required` ролью **`platform_admin`** и вычислять её **сразу после** первичной аутентификации: когда аутентифицированный принципал держит роль, присутствующую в политике, система не должна выдавать админскую сессию по одной лишь первичной аутентификации, а должна создать короткоживущую серверную запись **pending-auth** и вернуть требуемый следующий шаг (`mfa_enrollment_required`, когда TOTP-фактор не зарегистрирован, и `mfa_challenge_required`, когда зарегистрирован); pending-ссылка не должна давать доступ **ни к одному** админскому маршруту, кроме эндпоинтов регистрации/челленджа, и никогда не должна приниматься хуком админской сессии. Политика должна оставаться картой `role → требование`, чтобы добавление следующей роли было изменением данных, а не переделкой формы.
- **EARS-4** — Пока принципал `platform_admin` находится в состоянии `mfa_pending_enrollment`, админка должна отрисовывать **только** экран регистрации TOTP — ни дашборда, ни навигации к какому-либо админскому ресурсу, ни частичных админских данных, — а API должен отвергать любой админский маршрут, кроме эндпоинтов старта и подтверждения регистрации; состояние не должно быть закрываемым, пропускаемым или обходимым прямым вводом URL, и оператор не должен иметь возможности продолжить в продукт, не завершив регистрацию фактора (инвариант ADR-0001 design §8.5, PD-1).
- **EARS-5** — Когда `platform_admin` в состоянии `mfa_pending_enrollment` открывает экран регистрации, система должна зарегистрировать предварительный TOTP-фактор и показать **один раз** сканируемый QR-код, тот же секрет в **пригодном для ручного переноса** виде (для приложений-аутентификаторов, не умеющих сканировать) и поле подтверждения кода; а когда оператор отправляет **корректный** код, система должна подтвердить фактор как зарегистрированный, добавить аудит-строку **`auth.mfa.enrolled`** (никогда не содержащую секрет) и — поскольку и первичная аутентификация, и TOTP-проверка удовлетворены в этом же входе (**LD-1**) — **повысить запись pending-auth на месте** до полноценной админской сессии с `mfa = true`, выдав `__Host-ds_admin_session` согласно EARS-1 **без** требования второго полного входа. Этот же экран должен быть bootstrap-путём для уже существующих админов (PD-1). Некорректный код должен оставить оператора на экране регистрации с неподтверждённым фактором, с применением EARS-7.
- **EARS-6** — Когда **зарегистрированный** `platform_admin` завершает первичную аутентификацию на origin админки, система должна показать **TOTP-челлендж** и выдать админскую сессию **только** по корректному, неистёкшему и ранее не использованному коду; код, принятый один раз, не должен приниматься повторно внутри своего окна действия, а между первичной аутентификацией и удовлетворённым челленджем не должна быть достижима ни одна админская поверхность и ни один админский маршрут API.
- **EARS-7** — Когда подтверждение TOTP (при регистрации или челлендже) не проходит, система должна списать попытку с бюджетов ADR-0001 §7 на пользователя (10 / 15 мин) и на IP (20 / 15 мин), добавить аудит-строку `auth.mfa.failure` и вернуть **единственный единообразный отказ**, не различающий ни неверный код от незарегистрированного фактора, ни заблокированный аккаунт от незаблокированного, соблюдая дисциплину разброса по времени ≤50 мс из §7; при переходе порога блокировки §7 (10 неудачных попыток / 30 мин) система должна **мягко заблокировать** аккаунт, добавить строку `auth.lockout.triggered` и отправить уведомление §7 — и заблокированному аккаунту должно быть отказано в админской сессии даже при последующем предъявлении корректного кода.
- **EARS-8** — Система должна включить TOTP как разрешённый второй фактор в IdP **как провижининг-конфигурацию, а не как ручное действие в консоли**: политика входа должна регистрировать второй фактор OTP и выставлять `secondFactorCheckLifetime` / `multiFactorCheckLifetime` достаточно короткими, чтобы проверка фактора **не** переживала вход, а `mfaInitSkipLifetime` — так, чтобы регистрацию нельзя было пропустить; настройки должны быть объявлены в провижининге dev-стенда (`infra/dev-stand/idp/provision.sh`), чтобы свежеразвёрнутый стенд был MFA-способен без ручных шагов, а соответствующее **обязательство паритета с продом** должно быть зафиксировано в документации деплоя. Поскольку политики входа IdP действуют на организацию, а не на роль, общий переключатель `forceMfa` использоваться **не должен** — обязательность по ролям обеспечивает EARS-3, а включение общего переключателя навязало бы TOTP каждому `doctor_guest`.
- **EARS-9** — Система должна добавлять ровно одну терминальную строку `audit_ledger` (ADR-0003 §6) на каждое событие жизненного цикла админской сессии и MFA, используя **ровно тот канонический идентификатор ADR-0001 design §7.3, в который её доменное событие отображено таблицей сопоставления в разделе «Модель событий → События»** (`auth.login.success` / `auth.login.failure` / `auth.mfa.enrolled` / `auth.mfa.used` / `auth.mfa.failure` / `auth.mfa.reset` / `auth.lockout.triggered` / `auth.session.created` / `auth.session.terminated` / `auth.session.rejected`) — без выдуманных идентификаторов и без параллельной таксономии, — порождаемую через единственный поставленный маппер `auth-audit.ledger.ts`, чтобы второй источник не мог разъехаться; каждая такая строка должна нести **`tier: "admin"`**, чтобы админские строки отличались от портальных в общих классах `auth.session.*` / `auth.login.*`, а также действующее лицо, время, IP и user-agent. **`auth.session.rejected` должен быть дополнительно зарегистрирован вышестоящим документом** — строкой опережающей ссылки в ADR-0001 design §7.3 с указанием на эту спеку, приземлённой в том же срезе, по принятой в репозитории форме регистрации. **Ни одна** строка не должна когда-либо содержать TOTP-секрет, provisioning URI или отправленный код, а поля ПДн должны быть замаскированы согласно ADR-0001 §7.

**Восстановление фактора оператором**

- **EARS-13** — Когда оператор с ролью `platform_admin` вызывает команду удаления фактора против **другого** админского аккаунта **и передаёт в запросе собственный текущий TOTP-код**, система должна проверить этот код против зарегистрированного фактора **вызывающего** в момент вызова, удалить зарегистрированный TOTP-фактор целевого аккаунта и добавить строку **`auth.mfa.reset`**, несущую действующего оператора в каноническом поле `by_admin`, после чего следующий вход цели должен снова попасть в состояние принудительной регистрации из EARS-4. Отсутствующий, неверный, истёкший или повторно предъявленный код вызывающего должен отклонять удаление под **той же дисциплиной единообразного отказа и рейт-лимитов, что и EARS-7** — без отдельной ошибки и без отдельного бюджета попыток. Эндпоинт должен быть классифицирован как `access: authenticated`, `required_roles: platform_admin` и должен идти по **high-stakes** слою валидации через introspection (ADR-0001 §2.5/§8).

  Требование кода вызывающего **реализует замысел политики ADR-0001 §10** — изменение MFA является действием повышенного риска и требует свежей MFA — **для этого одного маршрута, локальными для маршрута средствами**. Общий механизм step-up (`StepUpGuard`, claim `acr=mfa-fresh`, 30-минутная повышенная сессия, контракт `401 step_up_required`) **в этом репозитории не построен и здесь не строится**; соответственно маршрут **не** должен объявлять метаданные `stepUp`, потому что эта колонка рекламирует общий механизм, и строка за которой нет guard заставила бы сгенерированную матрицу endpoint-authz обещать защиту, которую никто не обеспечивает. Перевод маршрута на общий механизм, когда его вертикаль будет поставлена, — отслеживаемый отложенный пункт (Область → Не входит).

  Удаление **собственного** последнего фактора вызывающего через этот эндпоинт должно быть отклонено, чтобы оператор не мог снять с себя контроль и снова войти через регистрацию без челленджа. **Операционное предусловие:** этот путь предполагает **≥2 зарегистрировавших фактор операторов `platform_admin`** — при меньшем числе его не может выполнить никто, и вместо него применяется именованное исключение BREAK-GLASS из LD-2.

**Сквозные (повсеместные / нежелательное поведение)**

- **EARS-10** — Уровень `__Host-ds_admin_session` должен полностью соответствовать профилю сессии ADR-0001 §6 / design §7.1: запись сессии хранится **на сервере в Redis**, привязана к устойчивому **отпечатку** клиента (хеш UA + IP /24 + accept-language), который перепроверяется на каждом запросе и при несовпадении инвалидирует сессию, соблюдаются заданные TTL и ротация refresh, сессия отзывается принудительным выходом и защищена **CSRF double-submit** на каждом изменяющем состояние админском эндпоинте (ADR-0004 design §3.2.1). Админский уровень не должен вводить **никакой** новой модели сессии, типа токена или хранилища удостоверений — это вторая кука поверх поставленной в 003 машинерии.
- **EARS-11** — Каждый админский маршрут API должен быть классифицирован в матрице endpoint-authz как **`access: authenticated`, `required_roles: platform_admin`** с дополнительным требованием, что разрешённый админский принципал несёт **`mfa = true`**; сессия, несущая роль `platform_admin`, но **не** подтверждённый второй фактор, должна быть **отвергнута** на каждом админском маршруте (никогда не понижена молча, никогда не обслужена частично), а существующие команды и чтения 007 должны сохранить свою форму и свою high-stakes позицию с introspection (ADR-0001 §2.5/§8), стоя на этой поднятой границе.
- **EARS-12** — Экраны регистрации и челленджа должны быть поставлены **в этом же срезе вместе со своим бэкендом** (F-22): построены через шлюз `build-ui-from-design-system` adopt-before-bespoke с **предложением Stage A, утверждённым владельцем продукта до реализации**, и **живым переподтверждением Stage B на работающем стенде до мержа**; все тексты должны разрешаться из типизированного русского каталога сообщений админки (`apps/admin/messages/ru.json`, заведённого в 007 EARS-10 и обеспечиваемого ESLint-правилом `local/no-hardcoded-display-string` в области `apps/admin/app/**` + `apps/admin/components/**`), **без хардкода пользовательских строк** — включая единообразное сообщение об отказе из EARS-7 и подсказку по восстановлению, указывающую на операторский путь LD-2; токен-дисциплина ADR-0013 (никаких произвольных значений Tailwind) должна соблюдаться для любой кастомной стилизации; а поля ввода кода должны быть управляемы с клавиатуры и размечены для скринридеров, секрет должен выделяться как текст (не только картинкой), а QR — нести текстовую альтернативу.

## Инварианты

- Админский маршрут API достижим **только** с `__Host-ds_admin_session`; `__Host-ds_session` никогда не аутентифицирует админский маршрут, а админская кука — маршрут портала (EARS-1, EARS-2).
- Каждая установленная админская сессия несёт `mfa = true`. **Нет** пути кода, выдающего админскую сессию по одной лишь первичной аутентификации (EARS-3, EARS-5, EARS-6, EARS-11).
- Pending-ссылка — не сессия: она достигает эндпоинтов регистрации/челленджа и ничего более, хранится на сервере, короткоживущая и никогда не принимается хуком админской сессии (EARS-3, EARS-4).
- `platform_admin` без зарегистрированного фактора видит ровно один экран — регистрации — и никаких админских данных до подтверждения фактора (EARS-4).
- TOTP-секрет показывается ровно один раз аутентифицированному pending-принципалу и никогда не появляется в логе, аудит-строке или последующем ответе (EARS-5, EARS-9).
- TOTP-код одноразов внутри своего окна действия (EARS-6).
- Неудачное подтверждение неотличимо от любого другого неудачного подтверждения — и по телу ответа, и по времени (EARS-7).
- **Ни одна поверхность, достижимая лишь первично аутентифицированным принципалом, не раскрывает признак блокировки, остаток попыток или факт существования аккаунта** — правило единообразного отказа связывает `AdminAuthState` ровно так же, как ответы подтверждения; правило раскрытия одно, а не два (EARS-7, «Модели чтения»).
- Мягко заблокированный аккаунт не может получить админскую сессию, верен код или нет, пока блокировка не истечёт или не будет снята (EARS-7).
- Общий переключатель `forceMfa` в IdP никогда не включается; обязательность живёт в политике ролей (EARS-3, EARS-8).
- Каждое событие жизненного цикла админской сессии и MFA добавляет ровно одну терминальную строку `audit_ledger` под своим **каноническим идентификатором §7.3** из таблицы сопоставления, несущую `tier: "admin"`, с маскированием ПДн и без секретов (EARS-9).
- Удаление фактора происходит **только** через аудируемый эндпоинт EARS-13 **либо** через единственное именованное исключение BREAK-GLASS из LD-2, пока зарегистрировавших фактор операторов `platform_admin` меньше двух. Третьего пути нет, и _ненаблюдаемого_ — тоже никогда: break-glass несёт компенсирующую строку `auth.mfa.reset`, записываемую ops-скриптом из runbook, плюс пост-фактум заметку в отслеживающем Issue, поэтому любое удаление фактора — через API или через break-glass — оставляет строку журнала с зафиксированным действующим лицом (EARS-13, LD-2).
- Оператор не может удалить собственный последний фактор **через API** (EARS-13); единственный способ, которым фактор единственного оператора оказывается удалён, — путь break-glass из LD-2 при его предусловии и с его компенсирующей строкой аудита.
- Поведение сессии портала врача этой фичей не меняется ни на байт (EARS-1, EARS-2).

## Зависимости и последовательность

- **Фича 003 (аутентификация пользователя) — поставлена и является прямым апстримом.** 011 собирается из установления/валидации сессии BFF-над-Zitadel из 003, claim `mfa`, выведенного из `amr`, хранилища сессий в Redis и хука отпечатка. Шов `role → mfa_required`, поставленный в 003 как задокументированная заглушка, — ровно то, что заселяет EARS-3. 011 **не** добавляет новых примитивов аутентификации.
- **Фича 007 (минимальная админка событий) — поставлена и является усиливаемой поверхностью.** Команды и чтения 007 сохраняют форму; поднимается только граница, на которой они стоят (EARS-11). Текст спеки 007 уже несёт опережающую ссылку на #718 как на пред-пилотное усиление, поэтому поставка 011 разрешает эту ссылку, а не противоречит ей.
- **Возможность TOTP в Zitadel (dev-стенд + прод).** Провижининг из EARS-8 — **предпосылка** для наборов e2e EARS-5/6/7: ручки политики входа существуют в `infra/dev-stand/idp/provision.sh` сегодня, но не выставлены, и никакой TOTP/multifactor-конфигурации нигде не включено. EARS-8 ставится в очередь перед обработчиками регистрации/челленджа; ребро `blocked_by` проводится соответственно (`open-ears-issues`, шаг 4). **Паритет с продом — обязательство времени деплоя, а не изменение кода**: админ, который может зарегистрировать фактор на стенде и не может в проде, — это поставленный инцидент.
- **Шов TOTP в `IdpPort` + фейк.** Порт (`apps/api/src/auth/idp/idp.types.ts`) получает регистрацию/подтверждение TOTP; **оба** — адаптер Zitadel и внутрирепозиторный фейк — реализуют его, фейк не мягче настоящего (Ограничения). Это одно изменение, приезжающее с EARS-5 и потребляемое EARS-6/7.
- **DTO в `packages/schemas/`.** DTO запросов/ответов админской аутентификации (`AdminAuthState`, `AdminEnrollmentOffer`, полезные нагрузки подтверждения) — Zod-схемы в SSOT-пакете, разделяемые API и Refine-админкой через сгенерированный SDK (ADR-0002 §3). Форма claim `mfa` в `auth.schema.ts` переиспользуется, а не переопределяется.
- **Утверждение дизайна (Stage A) блокирует реализацию экранов.** По AGENTS.md §6 и скиллу `build-ui-from-design-system` экранам регистрации и челленджа нужно утверждённое владельцем предложение Stage A **до** постройки и живое переподтверждение Stage B **до** мержа PR. Админского канваса нет (пробел Stage A, зафиксированный в 007), поэтому предложение стартует от стокового Refine и одобренного реестра.
- **Postgres + Zitadel + Redis dev-стенда.** Наборы e2e идут против стенда (`DATABASE_URL`, `IDP_ISSUER`, `REDIS_URL`), `skipIf` при отсутствии; эндпоинты читаются из `.env.local` и не хардкодятся (`.claude/rules/dev-stand.md`).
- **Срок пилота (2026 Q3).** #718 — **пред-пилотное** требование: админские команды относятся к high-stakes слою, а пилот — момент, когда админская поверхность перестаёт эксплуатироваться исключительно её авторами. Срез сознательно не втискивается в окно живого мероприятия (#718, «Примечания»).
- **Step-up (`StepUpGuard` / `acr=mfa-fresh`) — НЕ построен, и потому не является зависимостью.** Проверено по дереву: `stepUp` — только метаданные матрицы endpoint-authz (`apps/api/src/authz/authz.types.ts`, где собственный комментарий отсылает механизм к ADR; отрисовываются как колонка через `authz.matrix.ts`); ни один guard их не потребляет, проверки `acr` / `mfa_fresh_at` в `apps/api` нет нигде, ни один маршрут их не объявляет. **Поэтому у 011 нет зависимости от step-up и нет ребра `blocked_by` на неё:** EARS-13 несёт собственное локальное для маршрута доказательство свежего владения (текущий TOTP-код вызывающего), переиспользующее путь проверки, который этот срез и так строит в EARS-5/6. Постройка общего механизма — отдельная вертикаль; переезд этого маршрута на неё — отслеживаемый отложенный пункт, названный в разделе «Область → Не входит».
- **Обратная запись в вышестоящую таксономию.** `auth.session.rejected` требует строки опережающей ссылки в ADR-0001 design §7.3 в том же срезе, что и EARS-9, — правка документа за пределами каталога этой спеки, несомая дочерним Issue по аудиту.
- **Продолжение, открываемое из этой спеки.** Самостоятельные коды восстановления MFA (Область → Не входит) — отслеживаемый Issue с настоящим критерием готовности, открываемый `open-ears-issues`, шаг 3a. Операторский путь восстановления LD-2 — промежуточное решение, поставляемое как эндпоинт EARS-13 и описанное в runbook модуля, а не оставленное комментарием в коде.
