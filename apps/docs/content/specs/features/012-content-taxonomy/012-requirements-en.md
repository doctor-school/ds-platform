# 012 — Content taxonomy (Requirements)

## Outcomes

- A content operator describes a project, expert, topic or partner once and reuses the same retained record everywhere.
- Events relate to several projects, experts and topics through real many-to-many rows; projects relate to experts and partners in both directions.
- An expert is one editorial record that may exist without a User or optionally link one existing User; a unique optional User reference prevents duplicate Experts for one User.
- `event_experts` is the only authored and public speaker list, carrying event-specific role and order. `event_speakers` is retained migration input only; migration never name-merges and reports ambiguous, duplicate and unmatched rows with provenance.
- Operators create, search, edit, publish, retire and restore taxonomy data in the existing Refine admin. No Delete action exists.
- Later Academy surfaces read publish-safe taxonomy records and every relationship direction through `/v1` REST; no copy, export or synchronization step exists.

## Scope

**In:**

- Top-level retained entities:
  - `projects`: stable id + slug, kind `school | media | program`, title, description, optional cover-media reference;
  - `experts`: stable id + system-owned slug, structured family/given/patronymic names, professional role, credentials, affiliation, bio, optional photo-media reference and optional unique `user_id`;
  - `topics`: stable id + slug and title, maintained as a curated list;
  - `partners`: stable id + slug, title, optional logo-media reference and optional website URL.
- Every taxonomy value is an ordinary editorial text column. An expert's name and regalia are the public professional details experts already publish about themselves; they are stored, searched and audited like any other editorial content, with no encryption, key management or separate compliance workflow.
- Common entity fields: `status: draft | published | retired`, nullable `deleted_at`, nullable set-once `first_published_at`, monotonic `version`, and timestamps. Create starts in `draft`; ordinary restore returns an entity to `draft` without clearing `first_published_at`. Expert restore additionally requires `content_removed_at IS NULL`; an editorially removed record is the explicit 409 `CONTENT_REMOVED` exception.
- Retained joins: `event_projects`, `event_experts`, `project_experts`, `project_partners`, `event_topics`; each has a stable id, `status: active | retired`, nullable `deleted_at`, `version`, timestamps and a uniqueness constraint for its logical endpoint pair. `project_partners` additionally carries `is_primary`; at most one active link per project is primary, while any number of non-primary links preserves the approved many-to-many model.
- `event_experts`: required event-specific `role` and non-negative `position`; after migration it is the only speaker authoring/read model. Migration provenance refers to stable legacy ids in dedicated audit/report data rather than keeping a dual live projection.
- Refine resources for entity list/detail/create/edit and lifecycle actions; relationship editors on the relevant event/project forms; search and explicit retained-row filters; the migration review queue; plus the Expert editorial-removal action, which collects the per-project curator resolution before clearing descriptive values.
- Publish-safe public entity reads, bidirectional relationship reads and the canonical ordered `event_experts` speaker projection.

**Out:**

- Doctor-facing rendering: `/`, `/webinars` facets/archive, `/projects`, `/experts` and their detail pages belong to 013–016.
- `event_recordings`, `leads`, Payload CMS, partner commercial terms/contracts, public taxonomy search, recommendation/ranking, expert self-service or account provisioning.
- New roles for taxonomy authoring; it reuses `platform_admin`. No second role, step-up elevation or per-mutation live identity-provider revalidation is introduced.
- A general audit-history browser. Feature 010 already captures mutations in `audit_ledger`; 012 only keeps retained rows explicitly addressable for inspect/restore.

## Authoring and publication contract

| Kind    | Required on create                                                            | Additional fields required to publish                                                                        | Optional fields                                                |
| ------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| Project | `title` (trimmed 1–160); system generates `slug`                              | `kind: school \| media \| program`, `description` (trimmed plain text 1–2000), exactly one eligible curator  | `cover_ref`                                                    |
| Expert  | `family_name`, `given_name` (trimmed 1–80 each); slug generated by the system | `professional_role` (1–160), `credentials` (1–500), `affiliation` (1–240), `bio` (trimmed plain text 1–4000) | `patronymic` (0–80), `user_id`, `photo_ref`; initials fallback |
| Topic   | `title` (trimmed 1–120); system generates `slug`                              | no additional field or relationship                                                                          | none                                                           |
| Partner | `title` (trimmed 1–160); system generates `slug`                              | no additional field or relationship                                                                          | `logo_ref`, HTTPS `website_url`                                |

- Every slug is system-owned lowercase ASCII, 1–80 characters, matches `[a-z0-9]+(?:-[a-z0-9]+)*` and is not a canonical UUID. Create/update schemas reject a client slug; the server derives a collision-safe stable slug and the admin exposes only **Copy public link**. Slug uniqueness covers every retained row. Detail resolution treats canonical UUID text as id-only and every other token as slug-only.
- Drafts may leave only the table's additional publish fields unset. Omitted PATCH members stay unchanged; explicit `null` clears an optional field or a nullable draft-only incomplete field. A mutation of an already-published entity must leave its publication contract valid. A refused publish/update returns 409 `PUBLISH_REQUIREMENTS_NOT_MET` with field-addressed errors and makes no mutation.
- A project can publish with zero events and zero partners when its fields and curator are complete. Experts, topics and partners can publish with zero relationships. Optional media and partner website never block publication.
- Website input, when present, is an absolute HTTPS URL no longer than 2048 characters. Media input, when present, is one still JPEG, PNG or WebP, at most 10 MiB, at most 6000 px on either post-orientation decoded axis and at most 25 million aggregate decoded pixels; no minimum dimensions apply. Multi-frame/animated PNG or WebP and any decoder page/frame count other than one are 400 `MEDIA_INVALID` before full-frame allocation or upload. Refine performs the same preflight, while server validation is authoritative.
- A no-file create/PATCH is strict `application/json`; a media upload is `multipart/form-data` with one JSON `payload` part and at most the kind-specific `cover|photo|logo` file. Clients never submit storage refs/keys. PATCH omission keeps media, JSON `mediaAction: clear` clears it, and a file plus clear/multiple/wrong file parts is 400 `MEDIA_INPUT_CONFLICT`; multipart without a file is 415 `UNSUPPORTED_MEDIA_TYPE`. The first media vertical (#1283) owns one shared decoder/normalizer consumed by project covers, expert photos and partner logos: it applies orientation, converts to sRGB, and re-encodes the one still frame as canonical WebP under one pinned codec/profile version; that version and exact options enter the fingerprint. It strips EXIF/XMP/GPS/ICC/original filename and every ancillary block, derives MIME from normalized bytes, and persists no original upload. Object-storage failure is 503 `MEDIA_STORAGE_UNAVAILABLE` with no domain/audit mutation.
- The same #1283 vertical owns a retained `media_cleanup_jobs` queue distinct from idempotency-record cleanup. Every committed replace/`mediaAction: clear` writes a cleanup row for the superseded reference in the same transaction as the ref swap; its worker rechecks that the object is unreferenced, deletes every version/derivative, purges or invalidates the CDN key, retries until complete and retains a non-content record after clearing raw keys. An editorial removal releases the expert photo through exactly the same queue.
- Input-mask declaration: `none` for every operator-entered 012 field, because these values are editorial text, a URL/integer, or a file rather than a fixed-format identifier; a mask would fabricate or rewrite content instead of assisting entry. The admin therefore uses ordinary text/textarea controls with trim and character counters. Every slug is system-generated and appears only as a read-only public-link preview with Copy public link; website uses a URL control; `event_experts.position` uses an integer control with step 1 and range 0–32767; event role is trimmed 1–80 characters. File controls declare the accepted formats and reject size/dimension limits before submit.

## Constraints

- **Retained rows only.** No application path issues `DELETE`, `TRUNCATE`, data-bearing drop, `ON DELETE CASCADE`, or identifier reuse for these entities, joins or migrated `event_speakers`. Every foreign key is `RESTRICT`/`NO ACTION`.
- **Lifecycle consistency.** Entities use `draft | published | retired`; joins use `active | retired`; content-removed Experts cannot restore. Legacy source rows are immutable provenance managed only by migration review/cutover.
- **Public default deny.** Public reads include only `published` entities with `deleted_at IS NULL`, `active` joins with `deleted_at IS NULL`, and events allowed by the existing public-event policy. A draft, retired or unknown public id produces the same 404 shape.
- **Explicit retained reads.** Admin lists default to non-retired entities / active joins. Retained rows appear only through an explicit status or `includeRetired=true` query; an admin detail by stable id remains addressable for restore.
- **One current speaker projection.** After the migration gate, only active `event_experts` whose Experts are published/non-retired render, ordered by `position` and stable relationship id. No free-text authoring, legacy fallback or name deduplication participates.
- **Publish completeness.** Drafts may be incomplete only as defined by the authoring matrix. Publication applies that matrix; no relationship is required except a project's exactly one active `curator` linked to a published, non-retired expert.
- **Published-project curator invariant.** A published project has exactly one eligible curator at every committed state. Publication, curator-link mutations, curator replacement, editorial removal and expert lifecycle mutations share LD-4's expert-first lock order and revalidate after locking. Retiring that expert or retiring/demoting the sole curator link is refused until an atomic replacement succeeds or the project itself is retired.
- **Fresh lifecycle consent.** Retire or restore confirmation is valid only for the exact server-signed dependency snapshot shown in `LifecycleImpact`; a target edit, incident-relation change, opposite-endpoint eligibility change or overlapping serialization conflict requires a new preview.
- **Taking an Expert off the site is editorial removal, not Delete.** `RemoveExpertContent` clears structured names, professional fields and photo, retires incident joins, resolves sole-curator projects and retains row/id/slug/User link with `content_removed_at`; restore is 409 `CONTENT_REMOVED`.
- **No stub seam.** Schema, migrations, API, generated SDK, Refine UI and browser wiring ship as real vertical slices. Seeds, fake repositories, placeholder selectors or manual DB steps do not satisfy an EARS clause.
- **Existing Expert names are reviewed data, not parsed input.** The EARS-20 migration uses a complete explicit stable-Expert-id mapping for every retained non-content-removed row present at migration time; it never splits or otherwise infers structured names from legacy `name`. The migration preserves ids, slugs, lifecycle state and relations, leaves `user_id` null unless separately linked, and fails closed before any schema mutation when an unexpected row is not in that reviewed mapping. The production inventory reviewed on 2026-08-29 contained zero Expert rows, so the approved mapping is empty; the fail-closed coverage assertion guards against rows created before deployment.
- **Retained, bounded idempotency records.** A canonical UUID key is globally reserved across actors/routes from first use; cross-actor or cross-route reuse is always 409 `IDEMPOTENCY_KEY_REUSED`. A record is `active` for the 24 h replay window and stores the actor, route, request fingerprint, stored response and a fenced `lease_epoch`. Expiry UPDATEs the row to `expired` + `deleted_at`, closes replay and clears actor/request/response/fingerprint content while permanently retaining the globally unique key and terminal non-content state. A bounded upload authorization expires with its lease; cleanup retains the deterministic locator and waits past the maximum authorization plus clock-skew grace before its final HEAD/delete/absence decision, so no stale owner can PUT after completion. The row is never physically deleted, reactivated or reused.

## Prior decisions

- **ADR-0003 §3.6:** every application-owned entity and relationship is retained; normal reads filter `deleted_at IS NULL`, historical/restore reads opt in, and all FKs are restrictive.
- **ADR-0002 §§3–4, 9:** Zod is the request/response SSOT, REST is versioned under `/v1`, public growing lists use opaque cursors, admin tables may use offset pagination, mutation errors are RFC 7807 and mutations are idempotent.
- **ADR-0009 §§3, 7:** when a person asks to be taken off the site, the retained row stays and its descriptive values are cleared. 012's editorial removal is exactly that mechanism applied to public professional content; it introduces no separate compliance queue.
- **ADR-0004 §3:** taxonomy editing extends the existing Refine admin through custom data/auth/access providers; it does not create a second backend or use Payload CMS.
- **ADR-0013 + AGENTS.md §6:** implementation runs the design-system-first gate; interaction states and token discipline come from `@ds/design-system`.
- **Feature 007 historical input:** before cutover the event aggregate owns `specialties[]` and ordered `event_speakers`; 012 migrates that source into canonical `event_experts` and then disables legacy reads/writes.
- **Feature 010:** taxonomy entity/join and migration-review mutations append attributed audit rows, including immutable provenance, original classification, reviewer and resolution.
- **Feature 011 EARS-10/11 + ADR-0001 §§7/10:** taxonomy routes accept the dedicated MFA-verified admin session and state-changing routes require CSRF double-submit; the route guard requires `platform_admin`.

## Lead technical decisions

- **LD-1 — optimistic versioning and lifecycle-snapshot binding.** ADR-0002 requires idempotency but does not prevent two different valid requests from overwriting one another. Every mutable taxonomy/speaker row therefore carries a monotonic `version`, returned as an ETag. Create endpoints require no `If-Match`; PATCH, publish, retire, restore and content removal require the target ETag; curator replacement requires the project ETag. A lifecycle preview additionally returns a signed opaque `impactToken` over transition, target identity/version, issued-at/15-minute expiry and the canonical versions and lifecycle/public-eligibility inputs of every incident relation and opposite endpoint. Retire/restore confirmation runs at `SERIALIZABLE` and recomputes that dependency fingerprint. For those two lifecycle methods, any target-ETag/token/dependency mismatch, tampered/expired token, wrong transition/target or serialization abort has precedence as 412 `LIFECYCLE_IMPACT_STALE`; 412 `PRECONDITION_FAILED` is reserved for a stale `If-Match` on non-lifecycle methods. Either deterministic refusal makes no domain/media/audit mutation but fenced-completes and replays its idempotency result; it is never auto-retried.
- **LD-2 — canonical speaker ordering and migration gate.** `position` is editorial order and stable relationship id is the tie-break. The migration runs before disabling `event_speakers`: duplicate-preserving reviewed rows provide classification without identity inference; retained cutover state holds phase plus exact phase-aware/minimum-compatible production release SHA and ordinal; table-level BEFORE-write and AFTER-insert triggers fence direct DML; and deploy rollback rejects a target below the durable floor before provider mutation. Static free-text contracts are removed only by a later contract deployment after closed-set verification. After final cutover every write/read uses only `event_experts`.
- **LD-3 — system-owned slug identity.** Every entity-kind mutation rejects `slug`; the service generates a stable collision-safe non-UUID slug reserved by the retained row. UUID-shaped detail tokens resolve by id only.
- **LD-4 — atomic curator replacement with shared lock order.** Curator-affecting commands lock every affected expert row in stable-id order first, then project rows in stable-id order, then `project_experts` rows; they re-read eligibility and relations only after those locks. `ReplaceProjectCurator(projectId, expertId)` locks the current and candidate experts plus the project, verifies the candidate is still published/non-retired, demotes the previous curator relation to `member`, then promotes or restores the target relation in the same transaction. This order satisfies the immediate partial unique index; if promotion fails, transaction rollback restores the former curator. Expert lifecycle commands and `RemoveExpertContent` lock the expert, re-query its current curator projects, lock them in stable-id order and revalidate before changing status. No committed state has zero or two eligible curators, including under replacement-versus-retirement races.
- **LD-5 — one admin authority, mirrored from feature 007.** Every 012 admin mutation passes the local dedicated-session/fingerprint/MFA check of feature 011 plus CSRF double-submit, and its route guard requires the `platform_admin` role on that session. There is no second role, no step-up elevation, no per-mutation live IdP call and therefore no provider-outage failure mode of 012's own. Missing/invalid session is 401 `ADMIN_SESSION_REQUIRED`; a session without the role is 403 `PLATFORM_ADMIN_REQUIRED`. Public reads are zero-auth.
- **LD-6 — structured-name search.** NFKC-normalized expert search uses `pg_trgm` indexes over `family_name`, `given_name`, nullable `patronymic` and system slug; public/admin `name` is derived display, not a stored search column.
- **LD-7 — Expert editorial removal.** `RemoveExpertContent` is one `platform_admin` transaction that resolves curator projects, clears structured/descriptive fields and photo, retires incident joins, enqueues cleanup and writes feature-010 audit.
- **LD-8 — retained committed-media cleanup.** #1283 owns one `media_cleanup_jobs` technical table distinct from idempotency-record cleanup. It uses retained `status: active | expired`, `execution_state: pending | processing | completed`, nullable `deleted_at`, monotonic fenced `lease_epoch` and bounded leases. A committed replace/clear/removal transaction records the old server-generated object/CDN keys plus entity/slot pointer; a worker rechecks references and retries until every version/derivative and CDN key is acknowledged absent. Completion atomically sets `expired` + `deleted_at`, clears raw keys, endpoint pointer, lease/error content and retains only job id, cleanup kind, outcome and timestamps; no row is deleted/reactivated. The domain reference change remains feature-010 audited, while `media_cleanup_jobs` is an explicit tested technical-table audit exclusion.
- **LD-9 — base taxonomy versus surface read models.** 012 owns exact base entity/relationship DTOs and one primary-partner designation, but it does not make a page issue N relationship calls. Feature 015 owns one batched project-catalog/page projection with kind-specific content count, nullable primary partner and enriched team; feature 016 owns one batched expert-catalog projection with name search, single project filter and filtered/total counts. Their PRDs/specs must declare exact DTOs and query plans with bounded SQL before implementation, while 012 relationship reads remain independently cursor-paginated.
- **LD-10 — exact existing-Expert name migration.** Before changing the `experts` columns, the migration asserts that every retained non-content-removed Expert id is covered by the reviewed `id → family_name, given_name, patronymic` mapping. The approved production inventory at 2026-08-29 is empty, so this migration carries an empty mapping and an assertion that the source row set is still empty. Any newly-created row aborts the migration for explicit per-row review; no whitespace split, heuristic fallback, User match or second review subsystem exists.

## Event Model

### Commands

- `CreateTaxonomyEntity(kind, fields)` / `UpdateTaxonomyEntity(kind, id, fields)` — create a `draft` entity or edit the same retained row.
- `PublishTaxonomyEntity(kind, id)` — `draft → published`, after validating its public projection.
- `PreviewLifecycleImpact(target, transition)` — return the currently visible related projections that retire would remove or restore would add plus the signed `impactToken` for that complete dependency snapshot.
- `Retire(target, impactToken)` / `Restore(target, impactToken)` — explicit entity/join lifecycle transitions with no cascade; a content-removed Expert refuses restore with 409.
- `CreateRelationship(kind, endpoints, attributes)` / `UpdateRelationship(id, attributes)` — create or change one retained join; `event_experts` accepts only `expertId`, `role` and `position`.
- `ReplaceProjectCurator(projectId, expertId)` — replace a published project's curator atomically; no retire/demote gap is exposed.
- `RemoveExpertContent(expertId, curatorResolutions)` — one `platform_admin` transaction unpublishes and retires the expert, clears every descriptive value and the photo reference, retires incident joins, resolves each published sole-curator project by replacement or retirement, and sets `content_removed_at`.

Every mutating taxonomy HTTP endpoint requires `Idempotency-Key` as one canonical globally reserved UUID. Missing/blank is 428 `IDEMPOTENCY_KEY_REQUIRED`; malformed/non-canonical is 400 `IDEMPOTENCY_KEY_INVALID`. POST create requires no `If-Match`; PATCH/publish/retire/restore/remove-content require the target ETag; replace-curator requires the project ETag. Retire/restore additionally require `Lifecycle-Impact-Token` from their transition-specific preview.

### Events

| Event                                                      | Meaning                                                                                                                                          |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `TaxonomyEntityCreated/Updated/Published/Retired/Restored` | One entity changed state or content; feature 010 records the row diff in the same transaction.                                                   |
| `TaxonomyRelationshipCreated/Updated/Retired/Restored`     | One explicit relationship changed; no endpoint or sibling relation changes with it.                                                              |
| `SpeakerMigrationReviewResolved`                           | One queued source was explicitly resolved to an existing/new Expert or content-removed; provenance and original classification remain immutable. |
| `ProjectCuratorReplaced`                                   | One transaction demotes the former curator, then promotes the eligible replacement; rollback preserves the former curator on failure.            |
| `ExpertContentRemoved`                                     | Editorial removal cleared structured/descriptive Expert values and media while retaining identity.                                               |

### Read models

- `TaxonomyAdminList/Detail` — all authoring fields, status, version and relationship summaries; offset/page pagination, search and explicit retained filters.
- Full public entities are exact: `PublicProject { id, slug, kind, title, description, coverUrl, primaryPartner }`; `PublicExpert { id, slug, name, professionalRole, credentials, affiliation, bio, photoUrl, initials }`; `PublicTopic { id, slug, title }`; `PublicPartner { id, slug, title, logoUrl, websiteUrl }`; `primaryPartner` is `PublicPartnerSummary | null`, and optional URLs are present and nullable.
- Exact summaries are `PublicEventSummary { id, slug, title, school, startsAt, state }`, `PublicProjectSummary { id, slug, kind, title, description, coverUrl, primaryPartner }`, `PublicExpertSummary { id, slug, name, professionalRole, credentials, affiliation, photoUrl }`, `PublicTopicSummary { id, slug, title }`, and `PublicPartnerSummary { id, slug, title, logoUrl, websiteUrl }`. Bidirectional items use those summaries; only event↔expert adds `{ role, position }` and project↔expert adds `{ role: curator | member }`.
- `PublicEventPageSpeaker` is exactly `{ expertId, expertSlug, name, credentials, photoUrl, role }`, with derived `name` and present/nullable `photoUrl`. One canonical ordered `event_experts` resolver feeds both this page/endpoint item and `UpcomingBroadcastCard.speakers[] { name }`; retained source rows never enter either projection after cutover.
- `LifecycleImpact` — transition, target id/version, the affected currently-public rows and opaque signed `impactToken`. Each affected row is exactly `{ kind, id, title, slug, status }`: `kind` is an entity kind (`event | project | expert | topic | partner`) or a join kind (`event↔project | event↔expert | event↔topic | project↔expert | project↔partner`); `title` is always present and never null — the entity title, the expert's name, or, for a join, the operator-readable pairing of its two endpoints' display forms defined in `012-design.md` §3.1; `slug` is the public slug and is `null` exactly for join rows and entity kinds that have none; `status` is the row's own lifecycle state (`published | retired` for entities, `active | retired` for joins, never `draft` under currently-public scoping). This is enough for the confirmation dialog to name every affected record without a follow-up read per id. Every entity display field is one the corresponding public summary already exposes and `status` comes from the affected row itself on this `platform_admin`-only route, so it contains no hidden record content.
- Base taxonomy lists and relationship reads keep the ADR-0002 cursor envelope and deliberately omit surface-specific aggregate totals/search. Feature 015 owns a single batched project-card/page read model with kind-specific content counts, nullable `primaryPartner` and enriched team; feature 016 owns a single batched expert-catalog read model with `q`, one project filter, filtered count and total. Neither feature may implement those surfaces as N+1 calls to 012 relationship routes.

### Policies

- Slugs and logical endpoint pairs remain unique across retained rows; a duplicate create returns a conflict and points the operator to the retained row for restore. Every slug is generated once by the service, remains stable for the retained row's lifetime and is never accepted by create or update input.
- A project has at most one active curator and one primary Partner. Each Event→Expert pair and active position is unique; legacy source identity exists only in migration-review provenance.
- Topic assignment always selects an existing non-retired topic. `specialties[]` is never read from or written to `topics`.
- Media binaries use the existing object-storage abstraction; public DTOs expose CDN URLs, never storage keys. Retiring/restoring a row never deletes its media; only a replace, clear or editorial removal enqueues cleanup.

## EARS requirements

> Flat numbering per ADR-0006 §4. Every clause realizes one or more PRD stories and is covered by `012-scenarios.feature`.

- **EARS-1** _(realizes: US-1, US-9)_ — When a `platform_admin` creates or edits a project through its Refine resource, the system shall validate the authoring matrix and persist one first-class retained `projects` row with stable id/slug/version, kind `school | media | program`, title, description and optional cover reference, and render that same row on list/detail; a project shall never be an event string or second copy.
- **EARS-2** _(realizes: US-2, US-9)_ — When a `platform_admin` creates or edits an Expert, the system shall persist one retained `experts` row with stable id/system slug/version, structured family/given/patronymic names, professional role, credentials, affiliation, bio, optional User link and optional normalized photo, with initials fallback. Ordinary retire/restore keeps payload/media; editorial removal clears descriptive fields and media through the retained cleanup flow while preserving row identity.
- **EARS-3** _(realizes: US-5, US-9)_ — When a `platform_admin` creates or edits a topic through its Refine resource, the system shall persist one curated `topics` row with stable id/slug/version and title; topics shall never be free-form event tags.
- **EARS-4** _(realizes: US-6, US-9)_ — When a `platform_admin` creates or edits a partner through its Refine resource, the system shall persist one descriptive `partners` row with stable id/slug/version and title plus optional logo reference and optional HTTPS website URL; commercial terms and contacts are not fields of the public contract.
- **EARS-5** _(realizes: US-1, US-2, US-5, US-6, US-10, US-12)_ — When an operator publishes a valid `draft` entity, the system shall validate the exact field matrix, set `first_published_at` once without changing the already stable system-owned slug, and transition it to `published`; only a project additionally requires exactly one active `curator` linked to a published, non-retired expert, and it may have zero events/partners while every other kind may have zero relationships. Public list/detail shall then expose only the kind allow-list and CDN media URLs, while incomplete drafts, retired rows and internal fields/storage keys remain absent and indistinguishable from unknown. Any later PATCH that would make a published projection incomplete shall return 409 `PUBLISH_REQUIREMENTS_NOT_MET` without changing its value, version or audit history.
- **EARS-6** _(realizes: US-4, US-11)_ — When an operator links an event and a project, the system shall create or restore one `event_projects` row, allow one event to have several projects, expose event→projects and project→events reads, and never modify the event or project lifecycle as a side effect.

## Invariants

- No taxonomy entity, join, migration-review, cutover-state or retained legacy provenance row is physically deleted; stable ids/slugs/pairs are never reused.
- A slug is system-owned for the row's lifetime; mutations never accept it, retained rows keep reserving it, and UUID/slug token namespaces remain disjoint.
- `retired ⇔ deleted_at IS NOT NULL`; entity restore yields `draft`, join restore yields `active`, and a content-removed Expert returns 409.
- Every published project has exactly one active curator whose expert is published and non-retired; curator replacement is atomic and direct invalidation is refused.
- Every committed event speaker projection has at most one visible canonical `event_experts` row per position. In `source_closed`, only 012 relationship writes and linked-Expert publish/retire use the shared expert→project→event lock order; every rollback-eligible reader uses canonical `event_experts`, while retained source rows are immutable provenance without a write or projection boundary.
- Retire and restore confirmation are accepted only against the unchanged transition-specific signed dependency snapshot that the operator saw.
- A public relationship is visible only when the join is active and every taxonomy endpoint is published and non-retired.
- Retained legacy source rows and review provenance are immutable migration history and never participate in post-cutover authoring or projection.
- `specialties[]` and topics are different axes and never synchronize.
- One authored Postgres row feeds admin and public projections; no export/sync/fake seam exists.
- Expert retirement is reversible; editorial removal is not: it clears every descriptive value in one transaction, resolves every sole-curator project by atomic replacement or retirement, releases the media reference through the cleanup queue, and leaves neither an invalid published project nor a restorable record.
- Idempotency UUIDs are globally reserved. Records use fenced request/cleanup leases, expire by retained lifecycle UPDATE, clear every live payload/fingerprint/upload/actor reference, and are never physically deleted or reused; per feature 010's explicit allowlist they do not produce domain-audit rows.
