# 012 — Контентная таксономия (Требования)

## Результаты

- Контент-оператор один раз описывает проект, эксперта, тему или партнёра и везде переиспользует ту же сохраняемую запись.
- Мероприятия связаны с несколькими проектами, экспертами и темами настоящими m2m-строками; проекты связаны с экспертами и партнёрами в обоих направлениях.
- Эксперт — одна retained-запись с structured names и optional unique User link. `project_experts.role` равен `curator | member`; `event_experts` несёт только Expert, role и position.
- `event_experts` — единственный редактируемый и публичный список спикеров с role и order. `event_speakers` — только legacy free-text вход, удаляемый cutover-релизом, а его строки один раз заводятся вручную заново после него; миграция не сопоставляет по имени.
- Операторы создают, ищут, редактируют, публикуют, выводят из оборота и восстанавливают таксономию в существующей Refine-админке. Действия Delete нет.
- Последующие поверхности Академии читают безопасные публичные записи и каждое направление связей через REST `/v1`; копии, экспорта или шага синхронизации нет.

## Рамки

**Входит:**

- Верхнеуровневые сохраняемые сущности:
  - `projects`: стабильные id + slug, тип `school | media | program`, название, описание, опциональная ссылка на медиа обложки;
  - `experts`: стабильные id + системный slug, раздельные фамилия/имя/опциональное отчество, профессиональная роль, регалии, аффилиация, био, опциональная ссылка на фото и опциональный уникальный `user_id`;
  - `topics`: стабильные id + slug и название, поддерживаемый курируемый список;
  - `partners`: стабильные id + slug, название, опциональные ссылка на логотип и URL сайта.
- Каждое значение таксономии — обычная редакционная текстовая колонка. Имя и регалии эксперта — те же публичные профессиональные данные, которые эксперты и так публикуют о себе; они хранятся, ищутся и аудируются как любой другой редакционный контент, без шифрования, управления ключами и отдельного compliance-процесса.
- Общие поля сущности: `status: draft | published | retired`, nullable `deleted_at`, nullable set-once `first_published_at`, монотонная `version` и timestamps. Создание начинает с `draft`; обычное восстановление возвращает сущность в `draft`, не очищая `first_published_at`. Восстановление эксперта дополнительно требует `content_removed_at IS NULL`; редакционно снятая запись — явное исключение с 409 `CONTENT_REMOVED`.
- Сохраняемые джойны: `event_projects`, `event_experts`, `project_experts`, `project_partners`, `event_topics`; у каждого стабильный id, `status: active | retired`, nullable `deleted_at`, `version`, timestamps и уникальность логической пары концов. `project_partners` дополнительно несёт `is_primary`; у проекта не более одной active primary-связи, а любое число non-primary связей сохраняет подтверждённую many-to-many модель.
- `event_experts`: обязательные `expert_id`, event-specific `role`, неотрицательная `position`; это единственная current speaker relation после cutover. Отдельной таблицы миграции нет: перенос выполняется вручную теми же admin-командами, и их аудит — обычный taxonomy audit.
- Refine-ресурсы сущностей, lifecycle, двунаправленных relationship editors, shared lists/selectors и Expert editorial removal.
- Безопасные публичные чтения сущностей, двунаправленные чтения связей и каноническая упорядоченная проекция `event_experts`.

**Не входит:**

- Врачебный рендеринг: `/`, фасеты/архив `/webinars`, `/projects`, `/experts` и их страницы относятся к 013–016.
- `event_recordings`, `leads`, Payload CMS, коммерческие условия/договоры партнёров, публичный поиск по таксономии, рекомендации/ранжирование, самообслуживание эксперта или создание аккаунта пользователя из Expert; явная опциональная связь существующего User↔Expert входит в EARS-19.
- Новые роли для редактирования таксономии; оно переиспользует `platform_admin`. Второй роли, step-up-подтверждения и per-mutation обращения к провайдеру идентичности не вводится.
- Универсальный интерфейс просмотра аудита. Фича 010 уже пишет мутации в `audit_ledger`; 012 лишь сохраняет строки адресуемыми для просмотра/восстановления.

## Контракт редактирования и публикации

| Вид     | Обязательно при создании                                     | Дополнительно обязательно для публикации                                                                     | Опционально                                                  |
| ------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| Проект  | `title` (trimmed 1–160); `slug` генерирует система           | `kind: school \| media \| program`, `description` (trimmed plain text 1–2000), ровно один допустимый куратор | `cover_ref`                                                  |
| Эксперт | `family_name`, `given_name` (trimmed 1–80); `slug` системный | `professional_role` (1–160), `credentials` (1–500), `affiliation` (1–240), `bio` (trimmed plain text 1–4000) | `patronymic` (0–80), `user_id`, `photo_ref`; фолбэк-инициалы |
| Тема    | `title` (trimmed 1–120); `slug` генерирует система           | дополнительных полей и связей нет                                                                            | нет                                                          |
| Партнёр | `title` (trimmed 1–160); `slug` генерирует система           | дополнительных полей и связей нет                                                                            | `logo_ref`, HTTPS `website_url`                              |

- Slug каждого проекта/эксперта/темы/партнёра генерируется системой, collision-safe и не UUID. Create/update schemas отклоняют client slug; admin показывает Copy public link. Retained-строка навсегда резервирует slug.
- В draft можно не заполнить только дополнительные publish-поля из таблицы. Пропущенные члены PATCH не меняются; явный `null` очищает опциональное поле или nullable-поле неполного draft. Мутация уже опубликованной сущности обязана сохранить валидность её publish-контракта. Отклонённая публикация/правка возвращает 409 `PUBLISH_REQUIREMENTS_NOT_MET` с ошибками по полям и ничего не меняет.
- Проект может публиковаться с нулём мероприятий и партнёров, когда заполнены поля и куратор. Эксперт, тема и партнёр могут публиковаться с нулём связей. Опциональные медиа и сайт партнёра никогда не блокируют публикацию.
- URL сайта, если задан, — абсолютный HTTPS длиной не более 2048 символов. Медиа, если задано, — один still JPEG, PNG или WebP не более 10 MiB, не более 6000 px по каждой post-orientation decoded axis и не более 25 миллионов aggregate decoded pixels; минимального размера нет. Multi-frame/animated PNG или WebP и любой decoder page/frame count не равный одному дают 400 `MEDIA_INVALID` до full-frame allocation или upload. Refine выполняет такой же preflight, серверная валидация остаётся авторитетной.
- Create/PATCH без файла — строгий `application/json`; media upload — `multipart/form-data` с одной JSON-частью `payload` и не более чем kind-specific файлом `cover|photo|logo`. Клиент никогда не передаёт storage refs/keys. Omission в PATCH сохраняет медиа, JSON `mediaAction: clear` очищает его, а file плюс clear/multiple/wrong file parts дают 400 `MEDIA_INPUT_CONFLICT`; multipart без файла — 415 `UNSUPPORTED_MEDIA_TYPE`. Первая media vertical (#1283) владеет одним shared decoder/normalizer для project covers, expert photos и partner logos: он применяет orientation, переводит в sRGB и заново кодирует один still frame в canonical WebP под одной pinned codec/profile version; эта version и exact options входят в fingerprint. Он удаляет EXIF/XMP/GPS/ICC/original filename и каждый ancillary block, выводит MIME из normalized bytes и не сохраняет original upload. Ошибка object storage — 503 `MEDIA_STORAGE_UNAVAILABLE` без domain/audit mutation.
- Та же #1283 vertical владеет retained-очередью `media_cleanup_jobs`, отдельной от cleanup записей идемпотентности. Каждый committed replace/`mediaAction: clear` в той же транзакции, что ref swap, пишет cleanup row для superseded reference; worker повторно проверяет отсутствие ссылок, удаляет все versions/derivatives, purge/invalidate CDN key, retry до завершения и сохраняет non-content запись после очистки raw keys. Редакционное снятие эксперта освобождает фото через ту же очередь.
- Декларация input mask: `none` для каждого вводимого оператором поля 012, потому что значения — редакционный текст, URL/integer либо файл, а не идентификатор фиксированного формата; маска выдумывала бы или переписывала содержимое вместо помощи при вводе. Поэтому админка использует обычные text/textarea-контролы с trim и счётчиками символов. Каждый slug генерируется системой и показывается только как read-only preview публичной ссылки с Copy public link; сайт — URL-контрол; `event_experts.position` — целочисленный контрол с step 1 и диапазоном 0–32767; роль на мероприятии — trimmed 1–80 символов. File-контролы объявляют форматы и отклоняют лимиты размера/разрешения до отправки.

## Ограничения

- **Только retained rows.** Ни один прикладной путь не выполняет `DELETE`, `TRUNCATE`, data-bearing drop, `ON DELETE CASCADE` и не переиспользует идентификаторы этих сущностей и джойнов. Все FK — `RESTRICT`/`NO ACTION`. Единственное осознанное исключение — удаление legacy-пути спикеров в cutover release: таблица `event_speakers` и на retained-джойне `event_experts` колонка `legacy_speaker_id` с её составным foreign key и unique index — data-bearing drop колонки допустим потому, что она существует только как ключ удаляемой миграции и не хранит данных таксономии.
- **Lifecycle.** Entity использует `draft | published | retired`, join — `active | retired`; content-removed Expert не восстанавливается. У legacy-строк `event_speakers` нет lifecycle: Tech Lead один раз выписывает их в таблицу соответствия, а cutover release их удаляет.
- **Публичный default deny.** Публичные чтения включают только сущности `published` с `deleted_at IS NULL`, джойны `active` с `deleted_at IS NULL` и мероприятия, разрешённые существующей публичной политикой событий. Публичные draft/retired/unknown дают одинаковую форму 404.
- **Явное чтение сохранённого.** Admin-списки по умолчанию показывают не-retired сущности / active джойны. Сохранённые строки появляются только при явном status или `includeRetired=true`; admin-detail по стабильному id остаётся доступен для восстановления.
- **Одна текущая проекция спикеров.** После cutover release рендерятся только active `event_experts` с published/non-retired Экспертами, по `position` и stable relation id. Free-text authoring, legacy fallback и name dedupe не участвуют.
- **Полнота публикации.** Draft может быть неполным только по правилам матрицы редактирования. Публикация применяет эту матрицу; никакая связь не обязательна, кроме ровно одной active-связи `curator` проекта с published/non-retired экспертом.
- **Инвариант куратора опубликованного проекта.** В каждом committed-состоянии у published-проекта ровно один допустимый куратор. Публикация, мутации curator-связей, замена куратора, редакционное снятие и lifecycle-мутации эксперта используют общий expert-first порядок блокировок LD-4 и повторно проверяют состояние после блокировки. Retire этого эксперта и retire/понижение единственной curator-связи запрещены, пока не выполнена атомарная замена либо не retired сам проект.
- **Актуальное согласие на lifecycle-переход.** Подтверждение retire или restore действует только для точного подписанного сервером dependency snapshot, показанного в `LifecycleImpact`; изменение цели, incident relation, eligibility противоположного конца или пересекающийся serialization conflict требуют нового preview.
- **Editorial removal Эксперта — не Delete.** `RemoveExpertContent` очищает structured names, professional fields и photo, retires incident joins, разрешает sole-curator projects и сохраняет row/id/slug/User link с `content_removed_at`; restore даёт 409.
- **Без заглушек.** Схема, миграции, API, generated SDK, Refine UI и браузерная проводка поставляются настоящими вертикальными слайсами. Seeds, fake repositories, placeholder-селекторы и ручные шаги в БД не закрывают EARS.
- **Имена существующих Экспертов проверяются, а не разбираются алгоритмом.** Миграция EARS-20 использует полный явный mapping по стабильному `expert.id` для каждой retained non-content-removed строки, существующей на момент миграции; она никогда не делит legacy `name` и не выводит из него structured names. Миграция сохраняет id, slug, lifecycle state и relations, оставляет `user_id` null без отдельной явной привязки и fail closed до изменения схемы, если встретит строку вне проверенного mapping. Проверенный 2026-08-29 production inventory содержал ноль строк Expert, поэтому утверждённый mapping пуст; fail-closed assertion защищает от строк, созданных до deploy.
- **Сохраняемые ограниченные записи идемпотентности.** Canonical UUID key глобально резервируется между actors/routes с первого использования; cross-actor или cross-route reuse всегда даёт 409 `IDEMPOTENCY_KEY_REUSED`. Запись остаётся `active` 24 часа replay-окна и хранит actor, route, request fingerprint, сохранённый ответ и fenced `lease_epoch`. Expiry UPDATE row в `expired` + `deleted_at`, закрывает replay и очищает actor/request/response/fingerprint content, навсегда сохраняя глобально уникальный key и terminal non-content state. Bounded upload authorization истекает вместе с lease; cleanup сохраняет deterministic locator и ждёт позже maximum authorization плюс clock-skew grace перед final HEAD/delete/absence decision, поэтому stale owner не может PUT после completion. Row никогда физически не удаляется, не reactivated и не reused.

## Prior decisions

- **ADR-0003 §3.6:** каждая прикладная сущность и связь сохраняется; обычные чтения фильтруют `deleted_at IS NULL`, historical/restore чтения подключают строки явно, все FK restrictive.
- **ADR-0002 §§3–4, 9:** Zod — SSOT запросов/ответов, REST версионирован под `/v1`, растущие публичные списки используют opaque cursor, admin-таблицы могут использовать offset, ошибки мутаций — RFC 7807, мутации идемпотентны.
- **ADR-0009 §§3, 7:** когда человек просит убрать себя с сайта, сохраняемая строка остаётся, а её описательные значения очищаются. Редакционное снятие в 012 — ровно этот механизм, применённый к публичному профессиональному контенту; отдельной compliance-очереди он не вводит.
- **ADR-0004 §3:** редактирование таксономии расширяет существующую Refine-админку через custom data/auth/access providers; второй backend и Payload CMS не создаются.
- **ADR-0013 + AGENTS.md §6:** реализация проходит design-system-first гейт; interaction states и token discipline приходят из `@ds/design-system`.
- **Фича 007 historical input:** до cutover агрегат хранит `event_speakers`; cutover release фичи 012 убирает legacy reads/writes вместе с самой таблицей, после чего Tech Lead заново создаёт эти несколько строк на production как canonical `event_experts`.
- **Фича 010:** entity/join mutations получают audit; вручную созданные Эксперты и связи `event_experts` — обычные аудируемые taxonomy-мутации.
- **Фича 011 EARS-10/11 + ADR-0001 §§7/10:** taxonomy routes принимают выделенную MFA-verified admin session, state-changing routes требуют CSRF double-submit, а route guard требует `platform_admin`.

## Технические решения лида

- **LD-1 — оптимистические версии и привязка lifecycle snapshot.** ADR-0002 требует идемпотентность, но не мешает двум разным валидным запросам перезаписать друг друга. Поэтому каждая mutable taxonomy/speaker-строка несёт монотонную `version`, возвращаемую как ETag. Create endpoints не требуют `If-Match`; PATCH, publish, retire, restore и редакционное снятие требуют ETag цели; curator replacement — ETag проекта. Lifecycle preview дополнительно возвращает подписанный opaque `impactToken` по transition, identity/version цели, issued-at/15-minute expiry и каноническим версиям и lifecycle/public-eligibility inputs каждой incident relation и противоположного конца. Confirmation retire/restore работает на `SERIALIZABLE` и пересчитывает dependency fingerprint. Для этих двух lifecycle methods любой target-ETag/token/dependency mismatch, tampered/expired token, wrong transition/target или serialization abort имеет precedence как 412 `LIFECYCLE_IMPACT_STALE`; 412 `PRECONDITION_FAILED` остаётся только для stale `If-Match` non-lifecycle методов. Каждый deterministic refusal не меняет domain/media/audit, но fenced-completes и replay idempotency result; auto-retry нет.
- **LD-2 — канонический порядок и ручная миграция.** `position` задаёт порядок, stable relation id — tie-break. В production лежит шестнадцать legacy-строк по восьми мероприятиям, поэтому миграция — разовый ручной проход в порядке: один cutover release везёт канонический резолвер, убранный free-text контракт, удаление отменённого дизайна и единственную forward-миграцию, которая удаляет `event_experts.legacy_speaker_id` и `event_speakers` → Tech Lead вручную заново создаёт legacy-строки на production как обычных Экспертов и связи event↔expert по таблице соответствия, составленной из legacy-строк и показанной Product Lead → Product Lead смотрит на живые карточки мероприятий. Кроме этой таблицы соответствия нет ничего: ни queue, ни classification artifact, ни cutover phase, ни table trigger, ни rollback floor, ни импорта, ни admin-экрана миграции, и identity не выводится из имён. Одинаковые legacy-строки одного человека становятся одним Экспертом, а разница регалий по мероприятиям живёт в `role` связи. После релиза все reads/writes используют только `event_experts`.
- **LD-3 — system-owned slug identity.** Каждая entity mutation отклоняет `slug`; сервис генерирует stable collision-safe non-UUID slug, который retained-строка резервирует навсегда.
- **LD-4 — атомарная замена куратора с общим порядком блокировок.** Команды, влияющие на куратора, сначала блокируют все затронутые expert rows в порядке stable id, затем project rows в порядке stable id, затем `project_experts`; eligibility и связи перечитываются только после этих блокировок. `ReplaceProjectCurator(projectId, expertId)` блокирует текущего и кандидата плюс проект, проверяет, что кандидат всё ещё published/non-retired, понижает прежнюю curator-связь до `member`, затем повышает или восстанавливает целевую связь в той же транзакции. Этот порядок удовлетворяет immediate partial unique index; при ошибке promotion rollback возвращает прежнего куратора. Lifecycle-команда эксперта и `RemoveExpertContent` блокируют эксперта, заново запрашивают его текущие curator-проекты, блокируют их по stable id и повторно валидируют перед сменой status. Committed-состояния с нулём или двумя допустимыми кураторами нет и при гонке replacement с retire.
- **LD-5 — одна admin-авторизация, повторяющая фичу 007.** Каждая admin-мутация 012 проходит local dedicated-session/fingerprint/MFA фичи 011 плюс CSRF double-submit, а её route guard требует роль `platform_admin` на этой сессии. Второй роли, step-up-подтверждения и per-mutation вызова IdP нет, поэтому у 012 нет и собственного режима отказа провайдера. Missing/invalid session — 401 `ADMIN_SESSION_REQUIRED`; сессия без роли — 403 `PLATFORM_ADMIN_REQUIRED`. Public reads — zero-auth.
- **LD-6 — structured-name search.** NFKC-query использует `pg_trgm` по `family_name`, `given_name`, nullable `patronymic` и system slug; `name` — derived display, не storage column.
- **LD-7 — editorial removal Эксперта.** Одна `platform_admin` transaction очищает structured/descriptive fields и photo, retires joins, разрешает curator projects, ставит cleanup и audit.
- **LD-8 — retained cleanup committed-media.** #1283 владеет одной technical-таблицей `media_cleanup_jobs`, отдельной от cleanup записей идемпотентности. В ней есть retained `status: active | expired`, `execution_state: pending | processing | completed`, nullable `deleted_at`, монотонный fenced `lease_epoch` и bounded leases. Транзакция committed replace/clear/снятия записывает старые server-generated object/CDN keys плюс entity/slot pointer; worker перечитывает ссылки и повторяет работу, пока отсутствие каждой версии/производной и CDN key не подтверждено. Completion атомарно ставит `expired` + `deleted_at`, очищает raw keys, endpoint pointer, lease/error content и сохраняет только job id, cleanup kind, outcome и timestamps; строка не удаляется и не реактивируется. Изменение domain reference остаётся под feature-010 audit, а `media_cleanup_jobs` — явное проверяемое technical-table audit exclusion.
- **LD-9 — base taxonomy и surface read models разделены.** 012 владеет точными base entity/relationship DTO и одним primary-partner designation, но не заставляет page issue делать N relationship calls. Feature 015 владеет одной batched project-catalog/page projection с kind-specific content count, nullable primary partner и enriched team; feature 016 — одной batched expert-catalog projection с name search, single project filter и filtered/total counts. Их PRD/spec обязаны зафиксировать exact DTO и query plans с bounded SQL до реализации, а 012 relationship reads остаются независимо cursor-paginated.
- **LD-10 — точная миграция имён существующих Экспертов.** До изменения колонок `experts` миграция проверяет, что каждый retained non-content-removed Expert id покрыт подтверждённым mapping `id → family_name, given_name, patronymic`. Утверждённый production inventory на 2026-08-29 пуст, поэтому миграция несёт пустой mapping и assertion, что исходный набор строк всё ещё пуст. Любая новая строка прерывает миграцию для явной поштучной проверки; whitespace split, heuristic fallback, User match или вторая review subsystem не создаются.

## Модель событий

### Команды

- `CreateTaxonomyEntity(kind, fields)` / `UpdateTaxonomyEntity(kind, id, fields)` — создать сущность в `draft` или изменить ту же сохраняемую строку.
- `PublishTaxonomyEntity(kind, id)` — `draft → published` после валидации публичной проекции.
- `PreviewLifecycleImpact(target, transition)` — вернуть текущие видимые связанные проекции, которые retire уберёт или restore добавит, и подписанный `impactToken` полного dependency snapshot.
- `Retire` / `Restore` — lifecycle entity/join без каскада; content-removed Expert даёт 409.
- `CreateRelationship(kind, endpoints, attributes)` / `UpdateRelationship(id, attributes)` — создать или изменить один retained join; `event_experts` принимает только `expertId`, `role` и `position`.
- `ReplaceProjectCurator(projectId, expertId)` — атомарно заменить куратора опубликованного проекта, не открывая gap для retire/понижения.
- `RemoveExpertContent(expertId, curatorResolutions)` — одна транзакция `platform_admin` снимает эксперта с публикации и выводит из оборота, очищает каждое описательное значение и ссылку на фото, выводит из оборота инцидентные джойны, разрешает каждый published sole-curator project заменой или retire и ставит `content_removed_at`.

Каждый mutating taxonomy HTTP endpoint требует `Idempotency-Key` как один canonical globally reserved UUID. Missing/blank даёт 428 `IDEMPOTENCY_KEY_REQUIRED`; malformed/non-canonical — 400 `IDEMPOTENCY_KEY_INVALID`. POST create не требует `If-Match`; PATCH/publish/retire/restore/remove-content требуют ETag цели; replace-curator — ETag проекта. Retire/restore дополнительно требуют `Lifecycle-Impact-Token` из transition-specific preview.

### События

| Событие                                                    | Смысл                                                                                                                          |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `TaxonomyEntityCreated/Updated/Published/Retired/Restored` | Изменились данные или состояние одной сущности; фича 010 пишет diff строки в той же транзакции.                                |
| `TaxonomyRelationshipCreated/Updated/Retired/Restored`     | Изменилась одна явная связь; концы и соседние связи не меняются.                                                               |
| `ProjectCuratorReplaced`                                   | Одна транзакция понижает прежнего куратора, затем повышает допустимую замену; при ошибке rollback сохраняет прежнего куратора. |
| `ExpertContentRemoved`                                     | Editorial removal очистил structured/descriptive Expert fields и media, сохранив identity.                                     |

### Модели чтения

- `TaxonomyAdminList/Detail` — все поля редактирования, status, version и сводки связей; page/offset, поиск и явные retained-фильтры.
- Полные публичные сущности точны: `PublicProject { id, slug, kind, title, description, coverUrl, primaryPartner }`; `PublicExpert { id, slug, name, professionalRole, credentials, affiliation, bio, photoUrl, initials }`; `PublicTopic { id, slug, title }`; `PublicPartner { id, slug, title, logoUrl, websiteUrl }`; `primaryPartner` — `PublicPartnerSummary | null`, optional URL присутствуют как nullable.
- Точные summaries: `PublicEventSummary { id, slug, title, school, startsAt, state }`, `PublicProjectSummary { id, slug, kind, title, description, coverUrl, primaryPartner }`, `PublicExpertSummary { id, slug, name, professionalRole, credentials, affiliation, photoUrl }`, `PublicTopicSummary { id, slug, title }`, `PublicPartnerSummary { id, slug, title, logoUrl, websiteUrl }`. Bidirectional items используют эти summaries; только event↔expert добавляет `{ role, position }`, project↔expert — `{ role: curator | member }`.
- `PublicEventPageSpeaker` — ровно `{ expertId, expertSlug, name, credentials, photoUrl, role }`, где `name` вычисляется из структурированных полей, а `photoUrl` присутствует и nullable. Один canonical ordered resolver `event_experts` питает этот page/endpoint item и `UpcomingBroadcastCard.speakers[] { name }`; ни одна legacy-строка не входит ни в одну проекцию.
- `LifecycleImpact` — переход, id/version цели, затрагиваемые сейчас публичные строки и opaque подписанный `impactToken`. Каждая затронутая строка — ровно `{ kind, id, title, slug, status }`: `kind` — вид сущности (`event | project | expert | topic | partner`) либо вид джойна (`event↔project | event↔expert | event↔topic | project↔expert | project↔partner`); `title` всегда присутствует и никогда не null — заголовок сущности, имя эксперта либо, для джойна, операторски читаемая пара отображаемых форм обоих концов, определённая в `012-design.md` §3.1; `slug` — публичный slug, и он `null` ровно для строк-джойнов и для видов сущностей, у которых slug'а нет; `status` — собственное состояние lifecycle строки (`published | retired` для сущностей, `active | retired` для джойнов, никогда `draft` при scoping по текущим публичным проекциям). Этого достаточно, чтобы диалог подтверждения назвал каждую затронутую запись без дополнительного чтения по каждому id. Каждое отображаемое поле сущности уже присутствует в соответствующей публичной summary, а `status` берётся из самой затронутой строки на этом маршруте только для `platform_admin`, поэтому скрытого содержимого в ответе нет.
- Base taxonomy lists и relationship reads сохраняют ADR-0002 cursor envelope и намеренно не несут surface-specific aggregate totals/search. Feature 015 владеет одной batched project-card/page read model с kind-specific content counts, nullable `primaryPartner` и enriched team; feature 016 — одной batched expert-catalog read model с `q`, одним project filter, filtered count и total. Ни одна feature не реализует эти поверхности через N+1 вызовы relationship routes 012.

### Политики

- Slug и логические пары концов остаются уникальными среди сохранённых строк; конфликт создания направляет оператора к сохранённой строке для restore. Каждый slug один раз генерируется сервисом, остаётся стабильным весь срок жизни retained-строки и никогда не принимается во входе create/update.
- У проекта не более одного active curator и primary Partner. Каждая Event→Expert pair и active position уникальна.
- Тема выбирается только из существующих не-retired тем. `specialties[]` никогда не читается из `topics` и не записывается туда.
- Медиа используют существующую абстракцию object storage; публичные DTO отдают CDN URL, не storage keys. Retire/restore никогда не удаляет медиа; очередь cleanup создаёт только replace, clear или редакционное снятие.

## EARS-требования

> Плоская нумерация по ADR-0006 §4. Каждая формулировка реализует одну или несколько историй PRD и покрыта `012-scenarios.feature`.

- **EARS-1** _(realizes: US-1, US-9)_ — Когда `platform_admin` создаёт или редактирует проект через его Refine-ресурс, система должна проверить матрицу редактирования и сохранить одну полноценную retained-строку `projects` со стабильными id/slug/version, типом `school | media | program`, названием, описанием и опциональной ссылкой на обложку, а затем показать ту же строку в list/detail; проект никогда не должен быть строкой мероприятия или второй копией.
- **EARS-2** _(realizes: US-2, US-9)_ — Когда `platform_admin` создаёт или редактирует Эксперта, система сохраняет одну retained-строку `experts` со стабильными id/system slug/version, отдельными фамилией/именем/отчеством, профессиональной ролью, регалиями, аффилиацией, био, опциональной User-связью и нормализованным фото, с фолбэком из инициалов. Обычные retire/restore сохраняют payload/media; editorial removal очищает описательные поля и медиа через retained cleanup, сохраняя identity строки.
- **EARS-3** _(realizes: US-5, US-9)_ — Когда `platform_admin` создаёт или редактирует тему через её Refine-ресурс, система должна сохранить одну курируемую строку `topics` со стабильными id/slug/version и названием; темы никогда не должны быть свободными тегами мероприятия.
- **EARS-4** _(realizes: US-6, US-9)_ — Когда `platform_admin` создаёт или редактирует партнёра через его Refine-ресурс, система должна сохранить одну описательную строку `partners` со стабильными id/slug/version и названием плюс опциональные ссылку на логотип и HTTPS URL сайта; коммерческие условия и контакты не являются полями публичного контракта.
- **EARS-5** _(realizes: US-1, US-2, US-5, US-6, US-10, US-12)_ — Когда оператор публикует валидную сущность из `draft`, система должна проверить точную матрицу полей, один раз установить `first_published_at`, не меняя уже стабильный системный slug, и перевести сущность в `published`; только проект дополнительно требует ровно одного active `curator`, связанного с published/non-retired экспертом, и может иметь ноль мероприятий/партнёров, а каждый другой вид — ноль связей. Public list/detail после этого отдают только allow-list вида и CDN URL, а incomplete draft, retired и internal/storage поля остаются скрыты и неотличимы от unknown. Любой последующий PATCH, который сделал бы published-проекцию неполной, должен вернуть 409 `PUBLISH_REQUIREMENTS_NOT_MET` без изменения значения, version или audit history.
- **EARS-6** _(realizes: US-4, US-11)_ — Когда оператор связывает мероприятие с проектом, система должна создать или восстановить одну строку `event_projects`, позволить мероприятию иметь несколько проектов, отдать event→projects и project→events и не менять lifecycle концов побочным эффектом.
- **EARS-7** _(realizes: US-3)_ — Когда оператор связывает Эксперта с Мероприятием, система должна сохранить одну retained-строку `event_experts` с обязательной event-specific ролью и неотрицательной позицией, отклонить duplicate pair или занятую active-позицию и никогда не принимать free-text спикера.
- **EARS-8** _(realizes: US-2, US-3, US-10)_ — Когда после миграции читается публичная проекция спикеров, один canonical resolver должен вернуть допустимые `event_experts` по позиции и stable relation id; он не читает `event_speakers`, не выводит identity из имени и не строит бессрочную merged-проекцию.
- **EARS-9** _(realizes: US-1, US-2, US-11)_ — Когда оператор связывает эксперта с проектом или заменяет куратора опубликованного проекта, система должна сохранить retained-строки `project_experts` с `curator | member`, обеспечить не более одного active curator, выполнить замену одной version-checked транзакцией с общим expert/project lock order LD-4 и post-lock проверкой eligibility, сохранить ровно одного допустимого куратора у каждого published-проекта при конкурентном expert lifecycle и отдать project→experts и expert→projects с ролью.
- **EARS-10** _(realizes: US-6, US-11, US-12)_ — Когда оператор связывает партнёра с проектом, система должна сохранить одну retained-строку `project_partners` с явным `isPrimary`, допустить не более одной active primary-связи на проект и любое число non-primary связей, а затем отдать project→partners и partner→projects только с title/logo URL/website URL и primary-флагом отношения. Exact project entity/summary DTO встраивают eligible primary partner или `null`; commercial/internal данные не входят ни в одну проекцию.
- **EARS-11** _(realizes: US-5, US-11)_ — Когда оператор размечает мероприятие, event form должна предложить только существующие non-retired темы без inline creation, сохранить одну строку `event_topics` на пару, отдать оба направления и оставить `specialties[]` побайтно неизменным.
- **EARS-12** _(realizes: US-10, US-11, US-12)_ — Когда public caller читает base taxonomy collections 012 или любое направление relationship под `/v1/public`, система должна запросить те же авторские строки, вернуть только точные full/enriched-summary/relationship item DTO выше, применить published/active/non-deleted allow-list на каждом hop, использовать opaque cursor с `{ data, pagination: { nextCursor, hasMore } }`, не вернуть duplicate pair и не раскрыть draft, retired endpoint, inactive join или admin-only field. Unknown/ineligible source даёт 404 `RESOURCE_NOT_FOUND`; eligible source без eligible relations — 200 с empty data и terminal pagination. Page не должен собирать эти независимо paginated base routes через N+1: фича 015 владеет одной bounded-SQL batched project catalog/page projection с content count, nullable primary partner и enriched team, а фича 016 — одной bounded-SQL expert catalog projection с name search, одним project filter и filtered/total counts.
- **EARS-13** _(realizes: US-7)_ — Когда оператор запрашивает retire сущности или связи, admin сначала должен показать transition-specific `LifecycleImpact` и сохранить его подписанный `impactToken`; confirmation должна требовать тот же target `If-Match` плюс `Lifecycle-Impact-Token`, а сервер — транзакционно отвергать изменившийся dependency snapshot цели/relation/endpoint с 412 `LIFECYCLE_IMPACT_STALE`. Сервер должен запретить retire/понижение единственного допустимого curator-эксперта/связи опубликованного проекта, иначе один раз выставить `retired` + `deleted_at`, сохранить строки/FK, не менять lifecycle связанного и убрать цель из defaults/current public только фильтрацией.
- **EARS-14** _(realizes: US-7)_ — Restore entity/join требует signed impact/current preconditions, даёт entity→draft или join→active, refuses content-removed Expert и не имеет Delete route/control.
- **EARS-15** _(realizes: US-9)_ — Admin list поддерживает pagination, total, immediate title/derived-name/system-slug search и retained filters; Expert search использует structured-column indexes LD-6.
- **EARS-16** _(realizes: US-1, US-2, US-3, US-4, US-5, US-6, US-7, US-8, US-9, US-12)_ — Taxonomy admin routes требуют dedicated MFA session, CSRF и `platform_admin`; public reads zero-auth. RFC 7807 codes включают validation/media/cursor/idempotency, `RELATIONSHIP_CONFLICT | SLUG_CONFLICT | USER_EXPERT_CONFLICT | PUBLISH_REQUIREMENTS_NOT_MET | PUBLISHED_PROJECT_REQUIRES_CURATOR | INVALID_TRANSITION | SPEAKER_POSITION_OCCUPIED | CONTENT_REMOVED`, preconditions и storage unavailable.
- **EARS-17** _(realizes: US-7, US-10, US-11)_ — Каждая taxonomy mutation требует canonical UUID idempotency, method preconditions и feature-010 audit; deterministic outcomes replay, coordination rows retained, failure имеет zero domain side effects.
- **EARS-18** _(realizes: US-1, US-2, US-3, US-4, US-5, US-6, US-7, US-8, US-9)_ — До старта любого нового/изменённого taxonomy/event-admin UI slice команда должна завершить Stage A, сверив admin slice с утверждёнными владельцем вкладочными Refine-композициями из #1282/#1337 и исследованными блоками и матрицами состояний `@ds/design-system` из #1578; действительно новый класс или композиция снова входит в `build-ui-from-design-system`, а уже покрытый slice повторно использует принятые решения без нового раунда вариантов. Portal-поверхности фичи 014 отдельно продолжают следовать своим вендоренным канвасам. Реализация использует утверждённые блоки `@ds/design-system` с полными states, без entity Delete UI или manual API seam, а реальный результат проходит live Playwright и owner Stage B до merge.
- **EARS-19** _(realizes: US-13)_ — Когда `platform_admin` создаёт или редактирует Эксперта, система должна разрешить отсутствие Пользователя, выбор одного существующего несвязанного Пользователя либо явную позднюю link/unlink; `GET /v1/admin/experts/eligible-users?q&page&pageSize&currentExpertId` должен возвращать bounded-страницу активных User options, упорядоченную по nullable `displayName`, обязательному `identifier` и стабильному User `id`, где `identifier` равен email при его наличии, иначе phone; поиск должен покрывать display name, email и phone, а option DTO — раскрывать только `{ id, displayName, identifier }`; read должен исключать Пользователей, которыми владеет другой retained Expert, и при редактировании включать уже связанного Пользователя текущего Эксперта; одному Пользователю соответствует не более одного Эксперта, оба entry path сходятся в одну запись, сопоставление по имени никогда не устанавливает identity, duplicate ownership даёт 409 `USER_EXPERT_CONFLICT` без мутации.
- **EARS-20** _(realizes: US-14)_ — Когда редактируется Эксперт, система должна хранить отдельно обязательные фамилию и имя плюс опциональное отчество; миграция retained legacy Expert использует полный явно проверенный mapping стабильных id из LD-10 и fail closed вместо вывода любой части имени; slug каждой taxonomy-сущности генерируется системой и отклоняется во входе мутации, а detail админки даёт «Копировать публичную ссылку».
- **EARS-21** _(realizes: US-15)_ — Когда оператор редактирует медиа сущности, каждый применимый слот поддерживает upload, replace и remove; replace/remove атомарно меняет ссылку и ставит retained cleanup job, а storage key или URL input не показывается.
- **EARS-22** _(realizes: US-16)_ — Когда оператор создаёт event↔project, event↔expert, event↔topic, project↔expert или project↔partner с любой endpoint-страницы, обе поверхности вызывают одну relationship-команду и сохраняют ровно одну retained join-строку с одним владельцем хранения.
- **EARS-23** _(realizes: US-17)_ — Когда оператор использует taxonomy list или selector, система даёт пагинацию; применяет text search и каждый filter сразу без Enter или Apply; показывает каждое active value чипом; даёт одно «Сбросить всё»; использует общий search/select combobox; скрывает или disables control без возможного эффекта.
- **EARS-24** _(realizes: US-8, US-18)_ — Когда платформа переключается на канонических спикеров, она делает это одним релизом: canonical resolver из EARS-8 читает только `event_experts` — без legacy merge branch и без legacy fallback; поле free-text speakers отсутствует в Zod/OpenAPI-контракте создания и обновления события, во всех admin write seam, включая форму мероприятия и тело создания legacy-эфира, и во всех public и admin read DTO; удаляются все объекты отменённого дизайна, перечисленные в §2.3 дизайна, — обе миграционные таблицы, оба trigger на `event_speakers` вместе с их функциями, модуль схемы миграции, reconcile-seam, deploy-guard rollback floor вместе с его hook, тестом и разделами README, а также fence-сьют, который удаляется, а не перенацеливается; и та же forward-миграция удаляет колонку `event_experts.legacy_speaker_id` вместе с составным foreign key `event_experts_event_legacy_speaker_fk` на `event_speakers(event_id, id)` и её unique index, а затем и саму `event_speakers`, при этом `legacy_speaker_id` также уходит из admin-контракта связи event↔expert. Удаление этой колонки на retained-джойне `event_experts` допустимо потому, что колонка существует только как ключ удаляемой миграции и не хранит данных таксономии. После выкатки этого релиза Tech Lead вручную заново создаёт шестнадцать legacy-строк на production как обычных Экспертов со structured names (EARS-19–20), связанных с их мероприятиями общей командой связи event↔expert (EARS-7, EARS-22) с event-specific `role` и `position`, работая по таблице соответствия, составленной из legacy-строк и показанной Product Lead. Не существует ни review queue, ни import artifact, ни списка classification, ни cutover state SSOT, ни table trigger, ни deploy rollback floor, ни скрипта импорта, ни admin-экрана миграции, и никакие name matching, Expert/User inference, normalization/equality algorithm или generated suggestion не устанавливают и не предлагают identity. Один релиз означает, что app-only откат ниже него после выполнения миграции невозможен, и это принято: `deploy:prod` снимает снапшот базы перед миграцией, поэтому восстановление — это накат вперёд или restore, а окно, в котором мероприятия отображаются без спикеров, принято как продуктовое поведение.

## Инварианты

- Ни одна сущность таксономии и ни один джойн физически или каскадно не удаляются; стабильные ids/slugs/pairs не переиспользуются. Единственное исключение — сам legacy-путь спикеров: таблица `event_speakers` и колонка `event_experts.legacy_speaker_id` с её foreign key и unique index, удаляемые один раз cutover release.
- Slug системный весь срок жизни строки; мутации его не принимают, retained-строка продолжает резервировать его, пространства UUID и slug-токенов остаются непересекающимися.
- `retired ⇔ deleted_at IS NOT NULL`; entity restore→draft, join restore→active, content-removed Expert даёт 409.
- У каждого published-проекта ровно один active curator с published/non-retired экспертом; замена атомарна, прямая инвалидация запрещена.
- В каждой committed-проекции спикеров события не более одной видимой canonical-строки `event_experts` на position. После cutover только relationship writes 012 и publish/retire связанного Эксперта используют общий порядок блокировок expert→project→event, и каждый reader использует canonical `event_experts`.
- Подтверждение retire и restore принимается только для неизменившегося transition-specific подписанного dependency snapshot, который видел оператор.
- Публичная связь видима только при active-джойне и published/non-retired концах таксономии.
- После cutover release ни один путь кода не читает legacy-строку спикера и не существует ни таблицы `event_speakers`, ни колонки `event_experts.legacy_speaker_id`; связи `event_experts`, которые Tech Lead заново создаёт на production, — единственная запись о спикерах.
- `specialties[]` и topics — разные оси и никогда не синхронизируются.
- Одна авторская Postgres-строка питает admin и public проекции; export/sync/fake seam нет.
- Retire эксперта обратим; редакционное снятие — нет: оно очищает каждое описательное значение в одной транзакции, разрешает каждый sole-curator project атомарной заменой или retire, освобождает ссылку на медиа через очередь cleanup и не оставляет ни invalid published project, ни восстановимой записи.
- Idempotency UUID глобально reserved. Записи используют fenced request/cleanup leases, expire через retained lifecycle UPDATE, очищают каждый live payload/fingerprint/upload/actor reference и никогда не удаляются физически и не переиспользуются; по explicit allowlist фичи 010 они не создают domain-audit rows.

## Зависимости и последовательность

- Фича 007 даёт те шестнадцать historical source rows; 012 владеет кодовым cutover на canonical `event_experts` и следующим за ним ручным проходом.
- EARS-24 упорядочен так: единственный cutover release — код плюс одна forward-миграция, удаляющая `event_experts.legacy_speaker_id` и `event_speakers`, — → Tech Lead вручную заново создаёт legacy-строки на production по таблице соответствия → Product Lead обычным образом смотрит на живые карточки мероприятий; EARS-7/8 никогда не читают `event_speakers` после этого релиза.
- Фича 011 уже поставила выделенную MFA-verified admin session и CSRF double-submit, которые 012 переиспользует; дополнительной работы по авторизации до первой мутации таксономии нет.
- GitHub [#1306](https://github.com/doctor-school/ds-platform/issues/1306) владеет потоком редакционного снятия. Он заблокирован только вертикалью эксперта #1284, а начинать его лучше не раньше появления реальных `project_experts`, `event_experts` и publication handlers, чтобы разрешение sole-curator projects проверялось на реальном published-состоянии.
- Фича 010 audit coverage включает entity и join mutations.
- 013–016 потребляют base public API 012 только после попадания этой спеки в `main`; весь врачебный рендеринг принадлежит им, а 015/016 также владеют явно указанными в LD-9 batched surface projections.
- Revised Stage A [#1605](https://github.com/doctor-school/ds-platform/issues/1605) обязателен до любого reworked runtime UI и подтверждает, что вкладочные Refine-решения #1282/#1337 вместе с блоками дизайн-системы из #1578 покрывают admin rework, а portal-поверхности фичи 014 продолжают следовать своим вендоренным канвасам. Только действительно новый класс повторно открывает design research.
- Rework ограничен тремя PR-волнами: **model/migration** [#1606](https://github.com/doctor-school/ds-platform/issues/1606) (EARS-19–20) → [#1607](https://github.com/doctor-school/ds-platform/issues/1607) единственный cutover release плюс ручной проход после него (EARS-24) → фича-014 [#1608](https://github.com/doctor-school/ds-platform/issues/1608) после cutover; **reversible media/relations** [#1609](https://github.com/doctor-school/ds-platform/issues/1609) (EARS-21), [#1610](https://github.com/doctor-school/ds-platform/issues/1610) (EARS-22) и фича-014 #1611; затем **shared UX** [#1297](https://github.com/doctor-school/ds-platform/issues/1297) (также EARS-23) до фича-014 #1612.
