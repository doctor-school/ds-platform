# 012 — Контентная таксономия (Требования)

## Результаты

- Контент-оператор один раз описывает проект, эксперта, тему или партнёра и везде переиспользует ту же сохраняемую запись.
- Мероприятия связаны с несколькими проектами, экспертами и темами настоящими m2m-строками; проекты связаны с экспертами и партнёрами в обоих направлениях.
- Эксперт — одна самостоятельная редакционная запись. `project_experts.role` равен `curator | member`; `event_experts` несёт роль на мероприятии, позицию и опциональное явное сопоставление с одной legacy-строкой спикера.
- Существующие свободнотекстовые спикеры продолжают отображаться во время постепенной миграции. Связанный опубликованный эксперт заменяет в текущей проекции только явно сопоставленную legacy-строку; нет сопоставления по имени, дедупликации, перезаписи или неявного вывода строки из оборота.
- Операторы создают, ищут, редактируют, публикуют, выводят из оборота и восстанавливают таксономию в существующей Refine-админке. Действия Delete нет.
- Последующие поверхности Академии читают безопасные публичные записи и каждое направление связей через REST `/v1`; копии, экспорта или шага синхронизации нет.

## Рамки

**Входит:**

- Верхнеуровневые сохраняемые сущности:
  - `projects`: стабильные id + slug, тип `school | media | program`, название, описание, опциональная ссылка на медиа обложки;
  - `experts`: стабильные id + slug, имя, профессиональная роль, регалии, аффилиация, био, опциональная ссылка на фото; FK на пользователя платформы в 012 нет;
  - `topics`: стабильные id + slug и название, поддерживаемый курируемый список;
  - `partners`: стабильные id + slug, название, опциональные ссылка на логотип и URL сайта.
- Каждое значение таксономии — обычная редакционная текстовая колонка. Имя и регалии эксперта — те же публичные профессиональные данные, которые эксперты и так публикуют о себе; они хранятся, ищутся и аудируются как любой другой редакционный контент, без шифрования, управления ключами и отдельного compliance-процесса.
- Общие поля сущности: `status: draft | published | retired`, nullable `deleted_at`, nullable set-once `first_published_at`, монотонная `version` и timestamps. Создание начинает с `draft`; обычное восстановление возвращает сущность в `draft`, не очищая `first_published_at`. Восстановление эксперта дополнительно требует `content_removed_at IS NULL`; редакционно снятая запись — явное исключение с 409 `CONTENT_REMOVED`.
- Сохраняемые джойны: `event_projects`, `event_experts`, `project_experts`, `project_partners`, `event_topics`; у каждого стабильный id, `status: active | retired`, nullable `deleted_at`, `version`, timestamps и уникальность логической пары концов. `project_partners` дополнительно несёт `is_primary`; у проекта не более одной active primary-связи, а любое число non-primary связей сохраняет подтверждённую many-to-many модель.
- `event_experts`: обязательный event-specific `role`, неотрицательная `position` и nullable unique `legacy_speaker_id`. Runtime-prerequisite #1278 заменяет старый primary key таблицы `event_speakers` — `(event_id, position)` — стабильной UUID `id` row identity, добавляет partial active-slot `UNIQUE(event_id, position) WHERE status='active'` плюс явный `UNIQUE(event_id,id)` и retained lifecycle fields, включая nullable `content_removed_at`. Поэтому старая retained и новая active строки одной позиции сосуществуют, same-event composite FK `(event_id,legacy_speaker_id) → event_speakers(event_id,id)` исполним, а редакционно снятую legacy-строку нельзя восстановить или заново наполнить.
- Refine-ресурсы списка/детали/создания/редактирования сущностей и lifecycle-действий; редакторы связей на соответствующих формах мероприятия/проекта; поиск и явные фильтры сохранённых строк; плюс действие редакционного снятия на детали эксперта и legacy-спикера, которое собирает per-project curator resolution до очистки описательных значений.
- Безопасные публичные чтения сущностей, двунаправленные чтения связей и объединённая текущая проекция спикеров.

**Не входит:**

- Врачебный рендеринг: `/`, фасеты/архив `/webinars`, `/projects`, `/experts` и их страницы относятся к 013–016.
- `event_recordings`, `leads`, Payload CMS, коммерческие условия/договоры партнёров, публичный поиск по таксономии, рекомендации/ранжирование, массовая миграция спикеров, самообслуживание эксперта или связь user↔expert.
- Новые роли для редактирования таксономии; оно переиспользует `platform_admin`. Второй роли, step-up-подтверждения и per-mutation обращения к провайдеру идентичности не вводится.
- Универсальный интерфейс просмотра аудита. Фича 010 уже пишет мутации в `audit_ledger`; 012 лишь сохраняет строки адресуемыми для просмотра/восстановления.

## Контракт редактирования и публикации

| Вид     | Обязательно при создании                                 | Дополнительно обязательно для публикации                                                                     | Опционально                     |
| ------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------- |
| Проект  | `title` (trimmed 1–160); пропущенный `slug` генерируется | `kind: school \| media \| program`, `description` (trimmed plain text 1–2000), ровно один допустимый куратор | `cover_ref`                     |
| Эксперт | `name` (trimmed 1–160); пропущенный `slug` генерируется  | `professional_role` (1–160), `credentials` (1–500), `affiliation` (1–240), `bio` (trimmed plain text 1–4000) | `photo_ref`; фолбэк-инициалы    |
| Тема    | `title` (trimmed 1–120); пропущенный `slug` генерируется | дополнительных полей и связей нет                                                                            | нет                             |
| Партнёр | `title` (trimmed 1–160); пропущенный `slug` генерируется | дополнительных полей и связей нет                                                                            | `logo_ref`, HTTPS `website_url` |

- Каждый authored slug — lowercase ASCII длиной 1–80, соответствует `[a-z0-9]+(?:-[a-z0-9]+)*` и не является canonical UUID. Если slug не задан при создании, сервер применяет каноническую transliteration/slugification к display label и отвергает конфликтующий candidate, а не молча меняет identity; UI показывает тот же candidate. Уникальность slug — обычный per-table unique index по всем сохранённым строкам этого вида, поэтому четыре вида занимают непересекающиеся пространства имён без таблицы резерваций. Конфликт даёт 409 `SLUG_CONFLICT`. Detail resolution трактует canonical UUID text только как id, любой другой token — только как slug, поэтому `/:idOrSlug` однозначен. Первая успешная публикация один раз ставит `first_published_at`; любое последующее изменение slug, включая после retire/restore, даёт 409 `SLUG_IMMUTABLE`.
- В draft можно не заполнить только дополнительные publish-поля из таблицы. Пропущенные члены PATCH не меняются; явный `null` очищает опциональное поле или nullable-поле неполного draft. Мутация уже опубликованной сущности обязана сохранить валидность её publish-контракта. Отклонённая публикация/правка возвращает 409 `PUBLISH_REQUIREMENTS_NOT_MET` с ошибками по полям и ничего не меняет.
- Проект может публиковаться с нулём мероприятий и партнёров, когда заполнены поля и куратор. Эксперт, тема и партнёр могут публиковаться с нулём связей. Опциональные медиа и сайт партнёра никогда не блокируют публикацию.
- URL сайта, если задан, — абсолютный HTTPS длиной не более 2048 символов. Медиа, если задано, — один still JPEG, PNG или WebP не более 10 MiB, не более 6000 px по каждой post-orientation decoded axis и не более 25 миллионов aggregate decoded pixels; минимального размера нет. Multi-frame/animated PNG или WebP и любой decoder page/frame count не равный одному дают 400 `MEDIA_INVALID` до full-frame allocation или upload. Refine выполняет такой же preflight, серверная валидация остаётся авторитетной.
- Create/PATCH без файла — строгий `application/json`; media upload — `multipart/form-data` с одной JSON-частью `payload` и не более чем kind-specific файлом `cover|photo|logo`. Клиент никогда не передаёт storage refs/keys. Omission в PATCH сохраняет медиа, JSON `mediaAction: clear` очищает его, а file плюс clear/multiple/wrong file parts дают 400 `MEDIA_INPUT_CONFLICT`; multipart без файла — 415 `UNSUPPORTED_MEDIA_TYPE`. Первая media vertical (#1283) владеет одним shared decoder/normalizer для project covers, expert photos и partner logos: он применяет orientation, переводит в sRGB и заново кодирует один still frame в canonical WebP под одной pinned codec/profile version; эта version и exact options входят в fingerprint. Он удаляет EXIF/XMP/GPS/ICC/original filename и каждый ancillary block, выводит MIME из normalized bytes и не сохраняет original upload. Ошибка object storage — 503 `MEDIA_STORAGE_UNAVAILABLE` без domain/audit mutation.
- Та же #1283 vertical владеет retained-очередью `media_cleanup_jobs`, отдельной от cleanup записей идемпотентности. Каждый committed replace/`mediaAction: clear` в той же транзакции, что ref swap, пишет cleanup row для superseded reference; worker повторно проверяет отсутствие ссылок, удаляет все versions/derivatives, purge/invalidate CDN key, retry до завершения и сохраняет non-content запись после очистки raw keys. Редакционное снятие эксперта освобождает фото через ту же очередь.
- Декларация input mask: `none` для каждого поля 012, потому что значения — редакционный текст, отдельно валидируемый slug/URL/integer либо файл, а не идентификатор фиксированного формата; маска выдумывала бы или переписывала содержимое вместо помощи при вводе. Поэтому админка использует обычные text/textarea-контролы с trim и счётчиками символов. Slug получает generated preview и проверку шаблона/длины; сайт — URL-контрол; `event_experts.position` — целочисленный контрол с step 1 и диапазоном 0–32767; роль на мероприятии — trimmed 1–80 символов. File-контролы объявляют форматы и отклоняют лимиты размера/разрешения до отправки.

## Ограничения

- **Только retained rows.** Ни один прикладной путь не выполняет `DELETE`, `TRUNCATE`, data-bearing drop, `ON DELETE CASCADE` и не переиспользует идентификаторы этих сущностей, джойнов или мигрированных `event_speakers`. Все FK — `RESTRICT`/`NO ACTION`.
- **Согласованный lifecycle.** `retired` тогда и только тогда, когда `deleted_at` не null; у `draft`, `published` и `active` он null. Обычные переходы сущности: `draft → published`, `draft|published → retired`, `retired → draft`; джойна и migrated speaker: `active → retired → active`. Expert или migrated legacy speaker с `content_removed_at IS NOT NULL` — явное невосстановимое исключение. Вывод сущности из оборота никогда не меняет её джойны.
- **Публичный default deny.** Публичные чтения включают только сущности `published` с `deleted_at IS NULL`, джойны `active` с `deleted_at IS NULL` и мероприятия, разрешённые существующей публичной политикой событий. Публичные draft/retired/unknown дают одинаковую форму 404.
- **Явное чтение сохранённого.** Admin-списки по умолчанию показывают не-retired сущности / active джойны. Сохранённые строки появляются только при явном status или `includeRetired=true`; admin-detail по стабильному id остаётся доступен для восстановления.
- **Одна текущая проекция спикеров.** Active-сопоставление подавляет matched legacy-строку только при опубликованном не-retired эксперте. Иначе legacy-фолбэк остаётся. Строки сортируются по `position ASC`, затем source rank (`expert` перед `legacy`), затем стабильному row id; одинаковые имена никогда не дедуплицируются. Каждая запись в `event_experts` сначала блокирует затронутую строку эксперта или строки экспертов, затем parent event; каждая запись в `event_speakers` и publish/retire связанного эксперта входят в тот же канонический порядок expert→event. Каждая команда после блокировок перечитывает lifecycle эксперта и обе таблицы спикеров и перед commit повторно проверяет объединённые видимые слоты.
- **Полнота публикации.** Draft может быть неполным только по правилам матрицы редактирования. Публикация применяет эту матрицу; никакая связь не обязательна, кроме ровно одной active-связи `curator` проекта с published/non-retired экспертом.
- **Инвариант куратора опубликованного проекта.** В каждом committed-состоянии у published-проекта ровно один допустимый куратор. Публикация, мутации curator-связей, замена куратора, редакционное снятие и lifecycle-мутации эксперта используют общий expert-first порядок блокировок LD-4 и повторно проверяют состояние после блокировки. Retire этого эксперта и retire/понижение единственной curator-связи запрещены, пока не выполнена атомарная замена либо не retired сам проект.
- **Актуальное согласие на lifecycle-переход.** Подтверждение retire или restore действует только для точного подписанного сервером dependency snapshot, показанного в `LifecycleImpact`; изменение цели, incident relation, eligibility противоположного конца или пересекающийся serialization conflict требуют нового preview.
- **Снять человека с сайта — редакционное действие, а не Delete.** Обычные retire/restore остаются обратимыми и сохраняют payload/media эксперта. Отдельно `RemoveExpertContent` снимает запись с публикации, выводит её из оборота, очищает `name`, `professional_role`, `credentials`, `affiliation`, `bio` и ссылку на фото, выводит из оборота все инцидентные джойны, освобождает фото через `media_cleanup_jobs` и разрешает каждый published sole-curator project допустимой заменой либо retire проекта — всё в одной транзакции `platform_admin`. `RemoveLegacySpeakerContent` делает то же для немигрированного свободнотекстового спикера, очищая `event_speakers.name`/`regalia`. Обе команды ставят `content_removed_at`, сохраняют строку, id и slug и делают restore 409 `CONTENT_REMOVED`. Ни ключевого материала, ни legal-hold проверки, ни gate по бэкапам, ни заморозки публикации в этом нет.
- **Без заглушек.** Схема, миграции, API, generated SDK, Refine UI и браузерная проводка поставляются настоящими вертикальными слайсами. Seeds, fake repositories, placeholder-селекторы и ручные шаги в БД не закрывают EARS.
- **Сохраняемые ограниченные записи идемпотентности.** Canonical UUID key глобально резервируется между actors/routes с первого использования; cross-actor или cross-route reuse всегда даёт 409 `IDEMPOTENCY_KEY_REUSED`. Запись остаётся `active` 24 часа replay-окна и хранит actor, route, request fingerprint, сохранённый ответ и fenced `lease_epoch`. Expiry UPDATE row в `expired` + `deleted_at`, закрывает replay и очищает actor/request/response/fingerprint content, навсегда сохраняя глобально уникальный key и terminal non-content state. Bounded upload authorization истекает вместе с lease; cleanup сохраняет deterministic locator и ждёт позже maximum authorization плюс clock-skew grace перед final HEAD/delete/absence decision, поэтому stale owner не может PUT после completion. Row никогда физически не удаляется, не reactivated и не reused.

## Prior decisions

- **ADR-0003 §4:** каждая прикладная сущность и связь сохраняется; обычные чтения фильтруют `deleted_at IS NULL`, historical/restore чтения подключают строки явно, все FK restrictive.
- **ADR-0002 §§3–4, 9:** Zod — SSOT запросов/ответов, REST версионирован под `/v1`, растущие публичные списки используют opaque cursor, admin-таблицы могут использовать offset, ошибки мутаций — RFC 7807, мутации идемпотентны.
- **ADR-0009 §§3, 7:** когда человек просит убрать себя с сайта, сохраняемая строка остаётся, а её описательные значения очищаются. Редакционное снятие в 012 — ровно этот механизм, применённый к публичному профессиональному контенту; отдельной compliance-очереди он не вводит.
- **ADR-0004 §3:** редактирование таксономии расширяет существующую Refine-админку через custom data/auth/access providers; второй backend и Payload CMS не создаются.
- **ADR-0013 + AGENTS.md §6:** реализация проходит design-system-first гейт; interaction states и token discipline приходят из `@ds/design-system`.
- **Фича 007:** текущий агрегат мероприятия владеет `specialties[]` и упорядоченными `event_speakers`; 012 добавляет таксономию рядом и переводит reconciliation спикеров с физической замены на стабильные сохраняемые строки. 007 же задаёт прецедент авторизации и идемпотентности, который 012 повторяет.
- **Фича 010:** каждая таблица сущностей/связей таксономии и migrated speaker-domain получает generic audit trigger, поэтому её мутации пишут атрибутированные `data.<table>.<op>` без отдельной реализации аудита таксономии. Значения эксперта и спикера — обычные аудируемые колонки; retained technical coordination tables остаются без audit только через явный allowlist фичи 010 и собственное доказательство ограниченного lifecycle.
- **Фича 011 EARS-10/11 + ADR-0001 §§7/10:** taxonomy routes принимают выделенную MFA-verified admin session, state-changing routes требуют CSRF double-submit, а route guard требует `platform_admin`.

## Технические решения лида

- **LD-1 — оптимистические версии и привязка lifecycle snapshot.** ADR-0002 требует идемпотентность, но не мешает двум разным валидным запросам перезаписать друг друга. Поэтому каждая mutable taxonomy/speaker-строка несёт монотонную `version`, возвращаемую как ETag. Create endpoints не требуют `If-Match`; PATCH, publish, retire, restore и редакционное снятие требуют ETag цели; curator replacement — ETag проекта. Lifecycle preview дополнительно возвращает подписанный opaque `impactToken` по transition, identity/version цели, issued-at/15-minute expiry и каноническим версиям и lifecycle/public-eligibility inputs каждой incident relation и противоположного конца. Confirmation retire/restore работает на `SERIALIZABLE` и пересчитывает dependency fingerprint. Для этих двух lifecycle methods любой target-ETag/token/dependency mismatch, tampered/expired token, wrong transition/target или serialization abort имеет precedence как 412 `LIFECYCLE_IMPACT_STALE`; 412 `PRECONDITION_FAILED` остаётся только для stale `If-Match` non-lifecycle методов. Каждый deterministic refusal не меняет domain/media/audit, но fenced-completes и replay idempotency result; auto-retry нет.
- **LD-2 — стабильный порядок и сериализация объединённых спикеров.** `position` задаёт редакционный порядок. Полный tie-break: `position ASC`, source rank (`expert` перед `legacy`), stable row id ASC; write path также отвергает конфликт видимого слота, кроме случая, когда mapped expert намеренно занимает позицию подавленной legacy-строки. Каждый create/update/retire/restore `event_experts` 012 сначала блокирует все затронутые old/new строки экспертов в порядке stable id, затем parent-row `events`, после чего перечитывает lifecycle экспертов и обе child-таблицы и пересчитывает проекцию; каждый reconciliation legacy-спикеров 007 блокирует ту же event boundary. Publish/retire эксперта уже держит expert lock, затем блокирует все связанные parent events в порядке stable id и выполняет ту же проверку, потому что может раскрыть unpaired expert или matched legacy fallback. Глобальный порядок остаётся expert→project→event. Поэтому каждое committed-чтение детерминировано и не имеет name-based поведения или cross-table uniqueness race.
- **LD-3 — постоянная и разделённая slug identity.** `first_published_at` один раз ставится в транзакции первой публикации и никогда не очищается. Authored slugs не могут быть canonical UUID, поэтому UUID-shaped detail tokens разрешаются только по id, остальные — только по slug. Обычный `UNIQUE (slug)` каждой таблицы покрывает и сохранённые строки, поэтому slug никогда не освобождается для повторного использования — в том числе после редакционного снятия, когда сохранённая строка удерживает свой slug и просто перестаёт публиковаться.
- **LD-4 — атомарная замена куратора с общим порядком блокировок.** Команды, влияющие на куратора, сначала блокируют все затронутые expert rows в порядке stable id, затем project rows в порядке stable id, затем `project_experts`; eligibility и связи перечитываются только после этих блокировок. `ReplaceProjectCurator(projectId, expertId)` блокирует текущего и кандидата плюс проект, проверяет, что кандидат всё ещё published/non-retired, понижает прежнюю curator-связь до `member`, затем повышает или восстанавливает целевую связь в той же транзакции. Этот порядок удовлетворяет immediate partial unique index; при ошибке promotion rollback возвращает прежнего куратора. Lifecycle-команда эксперта и `RemoveExpertContent` блокируют эксперта, заново запрашивают его текущие curator-проекты, блокируют их по stable id и повторно валидируют перед сменой status. Committed-состояния с нулём или двумя допустимыми кураторами нет и при гонке replacement с retire.
- **LD-5 — одна admin-авторизация, повторяющая фичу 007.** Каждая admin-мутация 012 проходит local dedicated-session/fingerprint/MFA фичи 011 плюс CSRF double-submit, а её route guard требует роль `platform_admin` на этой сессии. Второй роли, step-up-подтверждения и per-mutation вызова IdP нет, поэтому у 012 нет и собственного режима отказа провайдера. Missing/invalid session — 401 `ADMIN_SESSION_REQUIRED`; сессия без роли — 403 `PLATFORM_ADMIN_REQUIRED`. Public reads — zero-auth.
- **LD-6 — обычные редакционные колонки и обычный поиск.** Identity, регалии и био эксперта, `name`/`regalia` legacy-спикера и `event_experts.role` — обычные `text`-колонки: это публичные профессиональные данные, которые эксперты и так публикуют о себе, поэтому 012 не вводит шифрование, производные lookup-дайджесты, внешние ссылки на ключи и теневые таблицы токенов. Admin-поиск — case-insensitive подстрочное совпадение по хранимым колонкам на `pg_trgm`: миграция включает расширение и добавляет `experts_name_trgm_idx USING gin (name gin_trgm_ops)`, а handler делает trim и NFKC-нормализацию запроса перед предикатом `ILIKE '%q%'`, переиспользуемым для slug и названий других видов. Фича 010 аудирует эти колонки как любое редакционное поле; там, где она ведёт список маскируемых колонок, 012 добавляет только эти обычные физические имена, чтобы UPDATE при снятии записывался как diff и не публиковал очищенные значения заново.
- **LD-7 — редакционное снятие — одна обычная admin-транзакция.** `RemoveExpertContent(expertId, curatorResolutions)` и `RemoveLegacySpeakerContent(eventId, speakerId)` — команды `platform_admin` на поверхности таксономии, а не очередь, worker или процесс согласования. Каждая выполняется в одной транзакции в порядке блокировок LD-4: разрешить каждый published sole-curator project заменой или retire, поставить `status='retired'` + `deleted_at` + `content_removed_at`, обнулить каждую описательную колонку, вывести из оборота инцидентные джойны и очистить `event_experts.role`, поставить освобождённую ссылку на медиа в `media_cleanup_jobs` и записать обычные audit-строки фичи 010. Дальше admin показывает фиксированную метку `[удалён]`, публичные чтения дают 404, а restore/repopulation — 409 `CONTENT_REMOVED`; заново вывести человека на сайт — это новое редактирование, а не отмена. Legacy-спикер, уже сопоставленный active-связью, снимается через своего эксперта.
- **LD-8 — retained cleanup committed-media.** #1283 владеет одной technical-таблицей `media_cleanup_jobs`, отдельной от cleanup записей идемпотентности. В ней есть retained `status: active | expired`, `execution_state: pending | processing | completed`, nullable `deleted_at`, монотонный fenced `lease_epoch` и bounded leases. Транзакция committed replace/clear/снятия записывает старые server-generated object/CDN keys плюс entity/slot pointer; worker перечитывает ссылки и повторяет работу, пока отсутствие каждой версии/производной и CDN key не подтверждено. Completion атомарно ставит `expired` + `deleted_at`, очищает raw keys, endpoint pointer, lease/error content и сохраняет только job id, cleanup kind, outcome и timestamps; строка не удаляется и не реактивируется. Изменение domain reference остаётся под feature-010 audit, а `media_cleanup_jobs` — явное проверяемое technical-table audit exclusion.
- **LD-9 — base taxonomy и surface read models разделены.** 012 владеет точными base entity/relationship DTO и одним primary-partner designation, но не заставляет page issue делать N relationship calls. Feature 015 владеет одной batched project-catalog/page projection с kind-specific content count, nullable primary partner и enriched team; feature 016 — одной batched expert-catalog projection с name search, single project filter и filtered/total counts. Их PRD/spec обязаны зафиксировать exact DTO и query plans с bounded SQL до реализации, а 012 relationship reads остаются независимо cursor-paginated.

## Модель событий

### Команды

- `CreateTaxonomyEntity(kind, fields)` / `UpdateTaxonomyEntity(kind, id, fields)` — создать сущность в `draft` или изменить ту же сохраняемую строку.
- `PublishTaxonomyEntity(kind, id)` — `draft → published` после валидации публичной проекции.
- `PreviewLifecycleImpact(target, transition)` — вернуть текущие видимые связанные проекции, которые retire уберёт или restore добавит, и подписанный `impactToken` полного dependency snapshot.
- `Retire(target, impactToken)` / `Restore(target, impactToken)` — явные lifecycle-переходы без каскада; оба требуют совпадающий `Lifecycle-Impact-Token`, обычная сущность восстанавливается в `draft`, джойн — в `active`, а expert или legacy speaker с `content_removed_at IS NOT NULL` отказывает с 409 `CONTENT_REMOVED`.
- `CreateRelationship(kind, endpoints, attributes)` / `UpdateRelationship(id, attributes)` — создать или изменить один сохраняемый джойн; `event_experts` принимает `role`, `position` и опциональный `legacySpeakerId`.
- `ReplaceProjectCurator(projectId, expertId)` — атомарно заменить куратора опубликованного проекта, не открывая gap для retire/понижения.
- `RemoveExpertContent(expertId, curatorResolutions)` — одна транзакция `platform_admin` снимает эксперта с публикации и выводит из оборота, очищает каждое описательное значение и ссылку на фото, выводит из оборота инцидентные джойны, разрешает каждый published sole-curator project заменой или retire и ставит `content_removed_at`.
- `RemoveLegacySpeakerContent(eventId, speakerId)` — то же редакционное снятие для немигрированного свободнотекстового спикера: очистить `name`/`regalia`, поставить `content_removed_at`, вывести строку из оборота, не трогая мероприятие. Спикер, сопоставленный active-связью, снимается через своего эксперта.

Каждый mutating taxonomy HTTP endpoint требует `Idempotency-Key` как один canonical globally reserved UUID. Missing/blank даёт 428 `IDEMPOTENCY_KEY_REQUIRED`; malformed/non-canonical — 400 `IDEMPOTENCY_KEY_INVALID`. POST create не требует `If-Match`; PATCH/publish/retire/restore/remove-content требуют ETag цели; replace-curator — ETag проекта. Retire/restore дополнительно требуют `Lifecycle-Impact-Token` из transition-specific preview.

### События

| Событие                                                    | Смысл                                                                                                                                                                                                     |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TaxonomyEntityCreated/Updated/Published/Retired/Restored` | Изменились данные или состояние одной сущности; фича 010 пишет diff строки в той же транзакции.                                                                                                           |
| `TaxonomyRelationshipCreated/Updated/Retired/Restored`     | Изменилась одна явная связь; концы и соседние связи не меняются.                                                                                                                                          |
| `EventSpeakerMatched`                                      | Строка `event_experts` теперь явно ссылается на одного сохранённого legacy-спикера; обычное сопоставление не меняет legacy-строку, но последующее редакционное снятие может очистить её `name`/`regalia`. |
| `ProjectCuratorReplaced`                                   | Одна транзакция понижает прежнего куратора, затем повышает допустимую замену; при ошибке rollback сохраняет прежнего куратора.                                                                            |
| `ExpertContentRemoved`                                     | Редакционное снятие очистило описательные значения и медиа эксперта или legacy-спикера, сохранив строку.                                                                                                  |

### Модели чтения

- `TaxonomyAdminList/Detail` — все поля редактирования, status, version и сводки связей; page/offset, поиск и явные retained-фильтры.
- Полные публичные сущности точны: `PublicProject { id, slug, kind, title, description, coverUrl, primaryPartner }`; `PublicExpert { id, slug, name, professionalRole, credentials, affiliation, bio, photoUrl, initials }`; `PublicTopic { id, slug, title }`; `PublicPartner { id, slug, title, logoUrl, websiteUrl }`; `primaryPartner` — `PublicPartnerSummary | null`, optional URL присутствуют как nullable.
- Точные summaries: `PublicEventSummary { id, slug, title, school, startsAt, state }`, `PublicProjectSummary { id, slug, kind, title, description, coverUrl, primaryPartner }`, `PublicExpertSummary { id, slug, name, professionalRole, credentials, affiliation, photoUrl }`, `PublicTopicSummary { id, slug, title }`, `PublicPartnerSummary { id, slug, title, logoUrl, websiteUrl }`. Bidirectional items используют эти summaries; только event↔expert добавляет `{ role, position }`, project↔expert — `{ role: curator | member }`.
- `PublicEventPageSpeaker` — ровно legacy `{ source: legacy, name, credentials }` либо expert `{ source: expert, expertId, expertSlug, name, credentials, photoUrl, role }`; `photoUrl` присутствует и nullable. Один resolver питает эту ordered page/endpoint union и `UpcomingBroadcastCard.speakers[] { name }`.
- `LifecycleImpact` — переход, id/version цели, идентификаторы затрагиваемых сейчас публичных событий/проектов/экспертов/тем/партнёров и opaque подписанный `impactToken`; скрытого содержимого в ответе нет.
- Base taxonomy lists и relationship reads сохраняют ADR-0002 cursor envelope и намеренно не несут surface-specific aggregate totals/search. Feature 015 владеет одной batched project-card/page read model с kind-specific content counts, nullable `primaryPartner` и enriched team; feature 016 — одной batched expert-catalog read model с `q`, одним project filter, filtered count и total. Ни одна feature не реализует эти поверхности через N+1 вызовы relationship routes 012.

### Политики

- Slug и логические пары концов остаются уникальными среди сохранённых строк; конфликт создания направляет оператора к сохранённой строке для restore. Возможность менять slug определяется только `first_published_at`.
- У проекта не более одного active `curator`; у опубликованного проекта ровно один допустимый куратор, меняемый только атомарной командой замены. Остальные эксперты проекта — `member`. У проекта может быть много partner links, но не более одной active `is_primary=true`; public project DTO показывает только этого optional primary partner, а bidirectional partner reads возвращают все eligible links. Legacy-спикер сопоставлен не более чем одной сохранённой строке `event_experts` и обязан принадлежать тому же событию.
- Тема выбирается только из существующих не-retired тем. `specialties[]` никогда не читается из `topics` и не записывается туда.
- Медиа используют существующую абстракцию object storage; публичные DTO отдают CDN URL, не storage keys. Retire/restore никогда не удаляет медиа; очередь cleanup создаёт только replace, clear или редакционное снятие.

## EARS-требования

> Плоская нумерация по ADR-0006 §4. Каждая формулировка реализует одну или несколько историй PRD и покрыта `012-scenarios.feature`.

- **EARS-1** _(realizes: US-1, US-9)_ — Когда `platform_admin` создаёт или редактирует проект через его Refine-ресурс, система должна проверить матрицу редактирования и сохранить одну полноценную retained-строку `projects` со стабильными id/slug/version, типом `school | media | program`, названием, описанием и опциональной ссылкой на обложку, а затем показать ту же строку в list/detail; проект никогда не должен быть строкой мероприятия или второй копией.
- **EARS-2** _(realizes: US-2, US-9)_ — Когда `platform_admin` создаёт или редактирует эксперта через его Refine-ресурс, система должна проверить матрицу редактирования и сохранить одну самостоятельную редакционную строку `experts` со стабильными id/slug/version и обычными текстовыми именем, профессиональной ролью, регалиями, аффилиацией, био и опциональной ссылкой на фото из shared normalizer, с фолбэком из инициалов и без обязательной связи с пользователем платформы или параллельного типа эксперта. Обычные retire/restore сохраняют payload/media. Отдельно `RemoveExpertContent` должна в одной транзакции `platform_admin` разрешить каждый published sole-curator project допустимой заменой или retire проекта, снять запись с публикации и вывести из оборота, обнулить каждую описательную колонку, вывести из оборота инцидентные джойны, освободить фото через `media_cleanup_jobs`, поставить `content_removed_at`, сохранив строку, id и slug, и сделать любой последующий restore или repopulation 409 `CONTENT_REMOVED`. `RemoveLegacySpeakerContent` должна сделать то же для одного явно указанного немигрированного legacy-спикера, очищая `event_speakers.name`/`regalia` без сопоставления по имени; спикер, уже сопоставленный active-связью, отклоняется и снимается через своего эксперта.
- **EARS-3** _(realizes: US-5, US-9)_ — Когда `platform_admin` создаёт или редактирует тему через её Refine-ресурс, система должна сохранить одну курируемую строку `topics` со стабильными id/slug/version и названием; темы никогда не должны быть свободными тегами мероприятия.
- **EARS-4** _(realizes: US-6, US-9)_ — Когда `platform_admin` создаёт или редактирует партнёра через его Refine-ресурс, система должна сохранить одну описательную строку `partners` со стабильными id/slug/version и названием плюс опциональные ссылку на логотип и HTTPS URL сайта; коммерческие условия и контакты не являются полями публичного контракта.
- **EARS-5** _(realizes: US-1, US-2, US-5, US-6, US-10, US-12)_ — Когда оператор публикует валидную сущность из `draft`, система должна проверить точную матрицу полей, навсегда заблокировать slug однократной установкой `first_published_at` и перевести сущность в `published`; только проект дополнительно требует ровно одного active `curator`, связанного с published/non-retired экспертом, и может иметь ноль мероприятий/партнёров, а каждый другой вид — ноль связей. Public list/detail после этого отдают только allow-list вида и CDN URL, а incomplete draft, retired и internal/storage поля остаются скрыты и неотличимы от unknown. Любой последующий PATCH, который сделал бы published-проекцию неполной, должен вернуть 409 `PUBLISH_REQUIREMENTS_NOT_MET` без изменения значения, version или audit history.
- **EARS-6** _(realizes: US-4, US-11)_ — Когда оператор связывает мероприятие с проектом, система должна создать или восстановить одну строку `event_projects`, позволить мероприятию иметь несколько проектов, отдать event→projects и project→events и не менять lifecycle концов побочным эффектом.
- **EARS-7** _(realizes: US-3, US-8)_ — Когда оператор связывает эксперта с мероприятием, система должна сохранить одну строку `event_experts` с обязательной ролью, неотрицательной позицией и опциональным явным `legacySpeakerId`; legacy id обязан указывать на retained-спикера того же события и быть уникальным среди retained expert links, имя никогда не используется для сопоставления, а каждая запись expert link должна заблокировать затронутых экспертов до parent event, перечитать lifecycle и обе speaker tables и отвергнуть конфликт объединённого видимого слота с 409 `SPEAKER_POSITION_OCCUPIED`.
- **EARS-8** _(realizes: US-2, US-3, US-8, US-10)_ — Когда читается публичная проекция спикеров события, система должна объединить active-linked экспертов с active legacy-строками по полному порядку LD-2: допустимый published-эксперт заменяет только явно matched строку, а unmatched и fallback для draft/retired/unlinked эксперта остаются; обычный match не перезаписывает, не retire и не name-dedupe legacy-строку, и только явное редакционное снятие может очистить `name`/`regalia` явно mapped строки. Один canonical resolver должен питать `/events/:key/speakers`, точную union `PublicEventPageSpeaker` и тонкую `UpcomingBroadcastCard.speakers[] { name }`, чтобы поставленные public surfaces не расходились.

После gates первое использование глобально резервирует key между actors, routes и expiry и атомарно связывает один request fingerprint по concrete target/query, canonical JSON, SHA-256/длине загруженного файла, `media_profile_version`, `If-Match` и `Lifecycle-Impact-Token`. Upload authorization истекает с request lease; cleanup хранит locator до authorization плюс clock-skew/in-flight grace. На границе 24 часов одна database transaction ставит `expired` + `deleted_at`, закрывает replay/upload и очищает actor/request/response/fingerprint content, а глобально уникальный key и terminal non-content state остаются навсегда. Row не удаляется, не reactivated и не reused. ## Инварианты

- Ни одна сущность таксономии, джойн или мигрированная legacy-строка спикера физически или каскадно не удаляется; стабильные ids/slugs/pairs не переиспользуются.
- Slug редактируется только пока `first_published_at IS NULL`; retire, restore и редакционное снятие никогда не сбрасывают этот постоянный identity-lock, а сохранённая строка продолжает удерживать свой slug через per-table unique index. Пространства authored UUID и slug-токенов остаются непересекающимися.
- `retired ⇔ deleted_at IS NOT NULL`; обычное восстановление сущности даёт `draft`, обычное восстановление джойна/migrated speaker — `active`, а редакционно снятый expert или legacy speaker возвращает 409 `CONTENT_REMOVED`.
- У каждого published-проекта ровно один active curator с published/non-retired экспертом; замена атомарна, прямая инвалидация запрещена.
- В каждой committed-проекции спикеров события не более одной видимой строки на position; expert-speaker writes 012 блокируют затронутых экспертов до event, а legacy-speaker writes 007 и publish/retire связанного эксперта используют те же затронутые per-event boundaries в глобальном порядке expert→project→event.
- Подтверждение retire и restore принимается только для неизменившегося transition-specific подписанного dependency snapshot, который видел оператор.
- Публичная связь видима только при active-джойне и published/non-retired концах таксономии.
- Сопоставленная legacy-строка спикера остаётся сохранённой и неизменной при обычном matching/lifecycle; единственное исключение очистки значений — явное редакционное снятие над `event_speakers.name`/`event_speakers.regalia`, чей маркер `content_removed_at` нельзя restore/repopulate, а единственное правило подавления в проекции — явное допустимое сопоставление.
- `specialties[]` и topics — разные оси и никогда не синхронизируются.
- Одна авторская Postgres-строка питает admin и public проекции; export/sync/fake seam нет.
- Retire эксперта обратим; редакционное снятие — нет: оно очищает каждое описательное значение в одной транзакции, разрешает каждый sole-curator project атомарной заменой или retire, освобождает ссылку на медиа через очередь cleanup и не оставляет ни invalid published project, ни восстановимой записи.
- Idempotency UUID глобально reserved. Записи используют fenced request/cleanup leases, expire через retained lifecycle UPDATE, очищают каждый live payload/fingerprint/upload/actor reference и никогда не удаляются физически и не переиспользуются; по explicit allowlist фичи 010 они не создают domain-audit rows.

## Зависимости и последовательность

- Фича 007 даёт существующую форму мероприятия и legacy-проекцию спикеров; [#1278](https://github.com/doctor-school/ds-platform/issues/1278) делает speaker rows стабильно retained, а 012 добавляет явный expert match/current-projection без поломки немигрированных событий.
- GitHub [#1278](https://github.com/doctor-school/ds-platform/issues/1278) — critical-path runtime prerequisite после merge спеки и до любой новой entity 012: он владеет retained-row conformance текущих таблиц, UUID-PK `event_speakers` с partial active-position uniqueness и `UNIQUE(event_id,id)`, общей parent-event блокировкой, retained-контрактом записей идемпотентности и удалением существующих cascade/delete paths. 012 потребляет этот runtime и не дублирует его.
- Фича 011 уже поставила выделенную MFA-verified admin session и CSRF double-submit, которые 012 переиспользует; дополнительной работы по авторизации до первой мутации таксономии нет.
- GitHub [#1306](https://github.com/doctor-school/ds-platform/issues/1306) владеет потоком редакционного снятия и приходит после появления реальных `project_experts`, `event_experts` и publication handlers, потому что должен разрешать sole-curator projects на реальном published-состоянии.
- Фича 010 даёт generic audit capture; каждая новая entity/join/speaker-domain таблица должна попасть под его coverage guard, а каждый technical-table exclusion — под явный allowlist parity guard.
- 013–016 потребляют base public API 012 только после попадания этой спеки в `main`; весь врачебный рендеринг принадлежит им, а 015/016 также владеют явно указанными в LD-9 batched surface projections.
- EARS-18 Stage A ([#1282](https://github.com/doctor-school/ds-platform/issues/1282)) — первый UI-гейт и блокирует UI-части EARS-1…15; каждый entity kind и каждый join/projection остаётся отдельным bounded vertical slice, а не одним CRUD issue на четыре сущности.
- EARS-Issues идут четырьмя волнами после #1278 и Stage A: **W1** вертикали сущностей (#1283 общий media normalizer, #1284 эксперт, #1285 проект/тема, #1286 партнёр); **W2** связи (#1288, #1291, #1292, #1293, затем #1289 → #1290); **W3** публикация, lifecycle, admin-списки и публичные чтения (#1287, #1294, #1295, #1296, #1297) плюс редакционное снятие #1306; **W4** cross-route sweeps (#1298 → #1299 → #1300). Ни один prerequisite не тестирует будущую table/handler, partial deployment до закрытия parent запрещён.
