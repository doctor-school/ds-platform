# 014 — Event recordings and the archived-event page (Requirements)

## Delivery waves

Every EARS clause below is tagged **`wave: core`** or **`wave: facets`**. The split exists so 014 runs in parallel with the 012 implementation:

- **`core`** — no dependency on feature 012. Recording records and lifecycle, the `legacy` broadcast lifecycle with its admin create surface, the operator attach/publish surface, the post-live event-page state over feature 004's existing `PublicEventPage` projection, the login gate and the return-to-origin rule, «Мои события», the reusable event card/list/pagination unit, and the `/webinars` «Предстоящие | Прошедшие» tabs.
- **`facets`** — reads 012's public taxonomy API (`projects`, `experts`, `topics` and their event joins). Its child Issues are wired `blocked_by` the 012 relations wave; nothing in `core` waits on them. This includes the project and topic **fields on the post-live page itself** (EARS-19), not only the listing facets — the 004 page projection carries `speakers[]`, `specialties[]` and `partners[]`, and projects and topics are 012 entities. The `core` post-live page therefore ships complete against the 004 projection and gains its taxonomy fields when 012 lands.

`open-ears-issues` reads these tags to build the two waves. Two clauses are **process gates, not code Issues** — EARS-10's ownership rule and EARS-16's Stage-A/Stage-B gate; they are tracked obligations verified by artifact, and `open-ears-issues` must not turn them into implementation Issues (EARS-10's actual build lands with the first consuming surface).

## What «finished» means

014 uses one word for one state. **A finished event is an event whose `EventLifecycleState` is `ended` — nothing else.**

| State                | 014 treatment                                                                                                                                                                                                                                                                     |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `draft`, `published` | Not finished. Pre-live event page per feature 004; no recording may be published; absent from the «Прошедшие» tab and from «Записи».                                                                                                                                              |
| `live`               | Not finished. The 006 room owns the surface.                                                                                                                                                                                                                                      |
| `ended`              | **Finished.** The post-live state, the recording, the plaque, the «Прошедшие» tab and the «Записи» tab all apply here and only here.                                                                                                                                              |
| `hidden`             | Not finished. The event is off the platform entirely: no public surface lists it and a direct link renders feature 004's notice with no CTA — absent from the «Прошедшие» tab and from «Мои события» → «Записи». Renamed from `archived` on 2026-09-02; the meaning is unchanged. |

This preserves feature 004's merged visibility contract: `hidden` keeps the notice-only render (004 EARS-5, owner variant «а»), and a cancelled or never-aired event reaching `hidden` via 004's `published → hidden` route never qualifies as finished and never acquires a player. 014 supersedes no 004 clause — it renames the state and its labels and changes nothing about its meaning.

A **`legacy`** event is finished in its own machine: `in_archive` is its equivalent of `ended`. The word «Архив» in 014 therefore always names the **shown** archive of past broadcasts, never the off-platform state. Owner ruling, 2026-09-02: «Архивировать означает ровно одно — поместить в архив. […] Архив мы ПОКАЗЫВАЕМ и это легитимное название статуса. Явно надо переименовать этот статус в "Скрыто с платформы" или что-то вроде того, но точно не "Архивирован".»

| Legacy state | 014 treatment                                                                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `hidden`     | Not finished. The state a legacy event is born in while the operator prepares it. No public surface lists it; a direct link renders feature 004's notice.                      |
| `in_archive` | **Finished.** «Архивирован» — listed and rendered in the public Archive exactly like an `ended` platform broadcast with a published recording. Same card, same tab, same page. |

A broadcast that never ran through the platform's own room is not a platform event pushed into `ended` by a backfill command — it is a `legacy` event with its own two-state lifecycle (EARS-23…EARS-27).

## Outcomes

- A finished broadcast keeps its value: the event page gains a post-live state with a player instead of becoming a stale announcement.
- A recording is a first-class retained record with an explicit kind — `edited` or `raw` — and its own publication status, never a video URL column on the event.
- The edited-over-raw display rule is computed from the data at read time; publishing the edited cut later changes the page with no operator page edit.
- A visitor without an account reads a past event's page in full; only playback requires an account, and the sign-in path returns the visitor to the page they came from.
- A finished event with no published recording states an honest, operator-dated «запись готовится» plaque instead of an empty player, and the plaque clears itself the moment a recording is published.
- A registered doctor finds their whole registration history in «Мои события» — including past events whose recording is not ready — each entry one click from its recording.
- `/webinars` becomes a browsable archive: «Предстоящие | Прошедшие» tabs plus project, expert and topic facets, both delivered inside the reusable event card/list/pagination unit that 015, 016 and «Мои события» consume afterwards.

## Scope

**In:**

- Retained `event_recordings`: stable id, `event_id`, `kind: edited | raw`, playable source reference and provider, optional poster reference, optional duration, `status: draft | published | retired`, nullable `deleted_at`, nullable set-once `first_published_at`, monotonic `version`, timestamps. At most one non-retired recording per `(event_id, kind)`.
- A recording's **own status scheme**, independent of attaching it: `AttachRecording` creates a `draft`; `PublishRecording` / `UnpublishRecording` / `RetireRecording` / `RestoreRecording` move it. Attaching never publishes.
- One new nullable `events.recording_expected_by` column: the per-event readiness date the operator sets, and the only source of the «запись готовится» timeframe.
- Refine authoring on the existing feature-007 event detail, which becomes a **tabbed** detail with an own **«Записи» tab** — the Product Lead's Stage-A pick (option B, 2026-08-17, recorded in `014-product.md` → Approved mockup; same composition as the 012 admin pick #1282), still stock Refine plus `@ds/design-system` primitives and still not a new Refine resource tree. In that tab: a recordings panel (attach, edit source, publish, unpublish, retire, restore) plus the readiness-date field, with every status-changing action confirming in a modal. No Delete action exists.
- **The `legacy` broadcast lifecycle and its admin surface.** `events.origin: platform | legacy` selects the machine. A `legacy` event — an эфир held before the platform existed, or outside it — has its own closed set of exactly two states, `in_archive` («Архивирован») ⇄ `hidden` («Скрыто»), its own two commands `ArchiveLegacyBroadcast` («Архивировать») and `HideLegacyBroadcast` («Скрыть»), and never a room, a stream config, a presence window or a `live` state. Without it the archive the PRD premises cannot exist, because the platform's own `ended` is reachable only through `OpenRoom` + `CloseRoom`. Recorded in 007 as an amendment because 007 is live in production.
- **The «Это архивный эфир» checkbox on the create-event form** (Release 1) — one creation surface, not two: checking the box switches the ordinary create form to its legacy variant (title, held-at, duration, speakers, a mandatory recording; no partner, no program PDF) and produces one `legacy` event born `hidden`. Its look is Stage-A/Stage-B gated separately (`build-ui-from-design-system`); this spec names the surface and its fields, not its composition.
- **The recording backfill for platform-born эфиры** (EARS-29, [#1742](https://github.com/doctor-school/ds-platform/issues/1742)) — a manifest-driven run that attaches and publishes recordings for events with `origin: platform` and `state: ended` through the very same 014 attach and publish commands, idempotent and with a dry-run. It writes no lifecycle field, adds no table and defines no second write path; its delivery form — an operator CLI in `apps/api` — is the owner’s Stage-A choice recorded below.
- **The `archived` → `hidden` rename** of the broadcast lifecycle's terminal state, with labels status «Скрыто» / command «Скрыть». The meaning is unchanged; a data migration rewrites existing rows and every surface reads the new value.
- Public post-live reads of `/v1/public/events/:idOrSlug`: the announcement projection stays public and complete on feature 004's existing `PublicEventPage` allow-list (`speakers[]`, `specialties[]`, `partners[]`, `programPdfUrl?`); a `recording` projection reports presence, kind, poster and the readiness date — **never a playable source**. The project and topic fields are the `facets`-wave addition (EARS-19), not a `core` prerequisite.
- An authenticated playback read that returns the playable source for the recording the display rule selects, plus the secondary raw source when both kinds are published.
- Portal `/webinars/[slug]` post-live state built from `design-source/webinar-archive.dc.html`: `viewer: authed | guest`, `recording: montage | raw-only | preparing`, `secondaryUi: spoiler`.
- The platform-wide post-login return-to-origin rule, realized for 014's login-gated surfaces.
- Portal `/account/events` («Мои события») with the canvas tabs «Предстоящие | Записи», full registration history — «Предстоящие» nearest-first, «Записи» newest-first — rendered by the shared list unit.
- The reusable **event card + list + pagination unit** in `@ds/design-system` / the portal (epic decision #7) — **owned and built by 014**, because 014 starts before the 013 build.

- **(`facets`)** The controlled facet unit from `design-source/events-filter.dc.html` — Проект / Эксперт / Тема, searchable single-select dropdowns with per-option counts — plus the server-side filtering that backs it, reading 012's public taxonomy API.

## Constraints

- **Retained rows only.** No application path issues `DELETE`, `TRUNCATE` or `ON DELETE CASCADE` for `event_recordings`, and no id is reused. `event_recordings.event_id` is `RESTRICT`. Retiring a recording never changes the event's lifecycle state.
- **Lifecycle consistency.** `retired ⇔ deleted_at IS NOT NULL`; `draft` and `published` iff it is null. Transitions are `draft → published`, `published → draft` (unpublish), `draft|published → retired`, `retired → draft`. `first_published_at` is set once on the first publish and never cleared.
- **Finished ≡ `ended` on a `platform` event, `in_archive` on a `legacy` one.** Every 014 rule keyed on «finished» reads exactly those two values, per the mapping tables above. The recording publish gate applies to `platform` events only: `draft`, `published`, `live` and `hidden` each return 409 `EVENT_NOT_FINISHED`. On a `legacy` event the ordering is inverted rather than relaxed — the recording is published while the event is still `hidden`, because a published recording is the precondition of `ArchiveLegacyBroadcast`. `timeframe=past` on the listing and the «Записи» tab select `ended` platform events and `in_archive` legacy events and nothing else. No 014 rule treats `hidden` as post-live, and feature 004's visibility policy stays authoritative for that state.
- **The gate is server-side.** A playable source reference is absent from every unauthenticated response body. Hiding the player in CSS, returning a source the client declines to render, or gating in a Next.js client component alone does not satisfy EARS-5.
- **One event page.** `/webinars/[slug]` stays the single event route for every context. The post-live state is a state of that page — no second route, no `/archive/...` mirror, and no separate route for a `legacy` эфир.
- **Two machines, never one graph with a fork.** `origin` is immutable and each event obeys exactly one machine. Every broadcast command on a `legacy` event and every legacy command on a `platform` event is 409 `INVALID_TRANSITION` with no mutation, and the admin lifecycle bar renders only the commands of the event's own machine. The owner's ruling this closes: «у них же должен быть отдельный жизненный цикл, а не развилка из двух вариантов в одном ЖЦ.»
- **The display rule is derived, never stored.** No `is_primary`, `is_featured` or ordering column on `event_recordings` selects the main player; selection is `edited` first, else `raw`, over published non-retired rows only.
- **Honest emptiness.** A finished event with no published recording renders the plaque. A published recording whose embedded player fails to load or times out in the browser renders an explicit unavailability message with a retry affordance — a **client-side** branch, because the API hands out an embed reference and never fetches the media, so it cannot know the provider is unreachable. Neither state may be an empty box, a spinner that never resolves, or a silently missing section.
- **No stub seam.** Schema, migration, Zod contract, generated SDK, API handler, Refine panel and portal surface ship as real vertical slices. Seeds, fake sources, placeholder cards and manual DB steps do not satisfy an EARS clause.
- **One list unit.** The tabs, pagination and facets exist once, in the shared event card/list/pagination unit. A `/webinars`-only copy is a defect; 015, 016 and «Мои события» consume the same unit.
- **Facets read 012, they do not re-model it.** No 014 table stores a project, expert or topic; facet options and counts come from 012's public taxonomy reads.
- **Bounded queries.** A listing page issues a bounded number of statements — the page query plus one facet-option query. Per-card or per-facet N+1 fan-out is refused at review.

## Lead technical decisions

- **LD-1 — recording identity and the at-most-one-per-kind rule.** `event_recordings` carries a stable UUID id; the operator-error branch in the PRD («more than one recording of the same kind») is enforced as a partial unique index `UNIQUE (event_id, kind) WHERE deleted_at IS NULL`, so a retired row frees the slot for a replacement while history is retained. A second attach of the same kind is 409 `RECORDING_KIND_OCCUPIED`, naming the retained row to edit or retire.
- **LD-2 — publication is separate from attachment, and it is gated on `ended` alone.** The owner's «у записи своя статусная схема» is realized as the 012-shaped `draft | published | retired` scheme on the recording row itself, orthogonal to the event's own `eventLifecycleState`. On a `platform` event the gate reads exactly one state: publishing requires `state = ended`, and `draft`, `published`, `live` **and `hidden`** are all refused with 409 `EVENT_NOT_FINISHED`. Including `hidden` in the refusal is deliberate — feature 004 routes a cancelled or never-aired event `published → hidden`, so treating `hidden` as post-live would hand a player to a broadcast that never happened, and would contradict 004's notice-only render. On a `legacy` event the gate does not apply: the operator publishes the recording while the эфир is still `hidden`, and that published recording is what makes `ArchiveLegacyBroadcast` legal (LD-10). An `ended` event with only draft recordings renders the plaque.
- **LD-3 — the derived selection projection.** One resolver computes `RecordingProjection { state: montage | raw-only | preparing, primaryKind, secondaryKind }` from published non-retired rows: both kinds → `montage` (`primary=edited`, `secondary=raw`); raw only → `raw-only`; edited only → `montage` with no secondary; none → `preparing`. That single resolver feeds the public page projection, the authenticated playback route, the «Мои события» entries and the archive-listing badge, so no two surfaces can disagree.
- **LD-4 — two-layer read split at the gate.** `GET /v1/public/events/:idOrSlug` returns `recording: { state, primaryKind, secondaryKind, posterUrl, expectedBy }` and no source. `GET /v1/events/:idOrSlug/recordings` (`access: authenticated`) returns the playable `{ kind, provider, embedRef }` for the primary and, when present, the secondary. This keeps the announcement cacheable as a public document while the source stays behind the session, and it makes the gate testable as an HTTP fact rather than a rendering detail.
- **LD-5 — the readiness date lives on the event, not the recording.** The plaque exists precisely when no recording does, so its timeframe cannot hang off a recording row. `events.recording_expected_by` is a nullable date set by the operator on the event form; the plaque renders it, and renders a bare honest line without a date when it is unset. Publishing a recording makes the plaque unreachable without clearing the column, so a re-retired recording restores a still-correct plaque.
- **LD-6 — return-to-origin is one platform mechanism.** The rule is realized once, in the portal auth entry, as a signed same-origin `returnTo` carried through registration/login/verification and consumed on the first authenticated navigation. 014 states the rule and implements the mechanism for its own gated surface; other specs consume the same mechanism rather than re-deriving a per-page redirect. Only same-origin relative paths are accepted; anything else falls back to the surface's default landing, so the mechanism is not an open redirect.
- **LD-7 — the shared list unit is a controlled component with an injected data source.** 014 builds `EventList` (card grid + tabs + pagination) and `EventFilters` (the three facets) as controlled units — props for the selected tab, facet values, option lists with counts and page cursor, plus `onChange` callbacks — exactly the shape `events-filter.dc.html` encodes. The unit issues no fetches of its own; each consuming surface (`/webinars`, project page, expert page, «Мои события») supplies the data. That is what lets the `facets` wave land as a capability of the unit without touching the `core` surfaces that already consume it.
- **LD-8 — one bounded archive query with a companion facet-count query, and `timeframe=past` means `ended`.** The `/webinars` listing filters by `timeframe` plus AND-composed facet ids in one paginated statement; facet option lists and counts come from one companion query per request. `timeframe=past` selects `ended` platform events and `in_archive` legacy events; `timeframe=upcoming` keeps feature 004's existing upcoming membership rule; `draft` and `hidden` are in neither, so the tab counts and both tab bodies stay consistent with 004's visibility policy. The same membership rule governs the «Записи» tab of «Мои события», which additionally filters to the doctor's own registrations and therefore holds no legacy эфир nobody could have registered for. Zero-yield options are returned with a null count and remain selectable, per the owner's answer 7. Counts reflect the other facets' current selections; a facet's own selection does not filter its own option list.
- **LD-9 — «Мои события» tabs are a projection over the same registration history.** `GET /v1/me/events` gains `tab=upcoming|recordings` and returns the full history for the tab in its canvas order — upcoming nearest-first, recordings newest-first — over the existing `registrations` join. The «Записи» tab lists **every** past registered event — a recording-less entry carries the `preparing` badge (owner answer 4) — so the tab is the doctor's history, not a recording index.
- **LD-10 — a `legacy` эфир gets its OWN lifecycle, not a backfill edge into 007's.** The 2026-08-17 design added one edge `published → ended` behind `MarkEventEnded` so an off-platform broadcast could reach `ended`. The owner rejected that model on 2026-09-02, before it reached production: «Трансляция не может пройти вне платформы. […] у них же должен быть отдельный жизненный цикл, а не развилка из двух вариантов в одном ЖЦ.» and «сам дизайн жизненного цикла неправильный. Если это эфир, который прошёл ДО запуска платформы, то зачем там кнопка "Выйти в эфир"? Для него должен быть другой жизненный цикл!». The rewrite: `events.origin: platform | legacy` picks the machine at creation and never changes. A `platform` event keeps 007's `draft → published → live → ended → hidden` untouched — no new edge, and `MarkEventEnded` is withdrawn. A `legacy` event has exactly two states — the owner's shape verbatim, «По ЖЦ архивного эфира: два состояния — "Архивирован" (отображается в Архиве) и "Скрыто"» — and never acquires a room, a stream config, a presence window or a `live` state, so its lifecycle bar can never offer «Выйти в эфир». Because feature 007 runs in production, the second machine and the rename are recorded there as an amendment block naming 014 as source, not as an inline rewrite. Cancelled and never-aired platform events keep 004's `published → hidden` route and remain outside 014's scope.
- **LD-12 — the broadcast terminal state is renamed `archived` → `hidden`, meaning unchanged.** Owner ruling, 2026-09-02: «Архивировать означает ровно одно — поместить в архив. […] Архив мы ПОКАЗЫВАЕМ и это легитимное название статуса. Явно надо переименовать этот статус в "Скрыто с платформы" или что-то вроде того, но точно не "Архивирован".» Stage-A pick «1»: status «Скрыто», command «Скрыть». This is a data migration plus a contract rename, not a behaviour change — the state still means «no platform surface shows this event», it is still admin-only, and a direct link still renders feature 004's notice. No dual-read shim and no compatibility alias: every row is rewritten and every surface reads the new value in one cutover, because a half-renamed enum is exactly the boolean-scatter ambiguity 007 removed. With the word «Архив» freed, the legacy command that places an эфир into the shown archive is «Архивировать» and it means precisely that.
- **LD-13 — the legacy archive precondition is a published recording, not a date.** `ArchiveLegacyBroadcast` is refused unless the эфир already carries a published non-retired recording under 014's own recording rules. Rationale: the public Archive card promises playable content (EARS-26 makes a legacy entry indistinguishable from an `ended` broadcast with a recording), so archiving a legacy эфир with nothing to play would ship the plaque as launch content. The operator therefore prepares the эфир in `hidden` — title, held-at, duration, speakers, recording — and archives it as one explicit act.
- **LD-11 — tab and facet state live in the URL — lead decision.** The PRD leaves «whether tab + facet selection survive in the URL» to Stage A and no canvas carries it; the owner resolved tab-versus-toggle only. This is a lead call under the AGENTS.md §6 decision-debt rule, recorded here rather than left in a design subsection: **the selected tab, every facet value and the page cursor are query parameters of `/webinars`.** Rationale: a filtered archive view is the thing a doctor sends to a colleague, so it must be linkable; reload and browser back/forward must not silently reset a narrowed archive; and because LD-7's unit is deliberately fetch-free, the URL is the only place the server component can read the selection from, which keeps the listing a server-rendered read instead of a client fetch. The existing «Неделя | Месяц» switcher on the same surface moves to the same mechanism, so `/webinars` has **one** persistence rule rather than two — mixed persistence on one surface is the fidelity trap this decision closes.

## Event Model

### Commands

- `AttachRecording(eventId, kind, source, posterFile?)` — create one `draft` row, normalize an optional uploaded poster, and derive duration from validated source metadata. Never publishes.
- `UpdateRecording(recordingId, fields, posterFile?, posterAction?)` — edit the source or upload/replace/remove the poster; duration is re-derived and never client-authored.
- `PublishRecording(recordingId)` / `UnpublishRecording(recordingId)` — `draft → published` (sets `first_published_at` once) / `published → draft`.
- `RetireRecording(recordingId)` / `RestoreRecording(recordingId)` — `→ retired` + `deleted_at` / `retired → draft`. No Delete command or route exists.
- `SetRecordingReadinessDate(eventId, expectedBy | null)` — set or clear `events.recording_expected_by`.
- `CreateLegacyBroadcast(title, heldAt, durationMin, speakers[], recording)` — create one `origin: legacy` event born `hidden`. No room, no stream config, no presence window.
- `ArchiveLegacyBroadcast(eventId)` — «Архивировать»: `hidden → in_archive` for a `legacy` event carrying a published non-retired recording. Refusals: 409 `EVENT_NOT_FINISHED`, 409 `INVALID_TRANSITION`.
- `HideLegacyBroadcast(eventId)` — «Скрыть»: `in_archive → hidden` for a `legacy` event. Refusal: 409 `INVALID_TRANSITION`.

Every mutating recording endpoint and every legacy-lifecycle command require a canonical UUID `Idempotency-Key` and the target ETag (`If-Match`) on non-create methods, per feature 007's precedent.

### Events

| Event                                         | Meaning                                                                                                                                 |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `RecordingAttached`                           | One draft recording of an explicit kind now exists for the event; nothing about the page changed yet.                                   |
| `RecordingPublished` / `RecordingUnpublished` | The derived projection changed; the page and the archive badge follow with no operator page edit.                                       |
| `RecordingRetired` / `RecordingRestored`      | A retained row left or re-entered the authoring set; the kind slot freed or re-occupied.                                                |
| `RecordingReadinessDateSet`                   | The plaque's timeframe changed for that event.                                                                                          |
| `LegacyBroadcastCreated`                      | A pre-platform эфир now exists as a `legacy` event in `hidden`; nothing public changed yet.                                             |
| `LegacyBroadcastArchived`                     | A `legacy` event with a published recording entered the shown Archive; it now appears in «Прошедшие» exactly like an `ended` broadcast. |
| `LegacyBroadcastHidden`                       | A `legacy` event left the shown Archive; no public surface lists it any more.                                                           |

### Read models

- `RecordingProjection { state: montage | raw-only | preparing, primaryKind, secondaryKind, posterUrl, expectedBy }` — public, source-free.
- `PlayableRecording { kind: edited | raw, provider, embedRef, durationSec }` — authenticated only; the playback route returns `{ primary, secondary }` where `secondary` is `PlayableRecording | null`.
- `PublicEventSummary` (from feature 012 / 004) gains a nullable `recordingState` so an archive card can carry the «Запись доступна / готовится» badge without a second call.
- `ArchiveListing { data: PublicEventSummary[], pagination: { nextCursor, hasMore }, counts: { upcoming, past } }` — the tab counts the canvas renders as «Предстоящие · N | Прошедшие · N».
- `FacetOptions { projects: FacetOption[], experts: FacetOption[], topics: FacetOption[] }` where `FacetOption { id, slug, label, count: number | null }`; `count` is null for a zero-yield option, which stays selectable.
- `MyEventsListing { tab: upcoming | recordings, data: (PublicEventSummary & { registeredAt, recordingState })[], pagination }`.
- `RecordingAdminDetail` — every authoring field plus `status`, `version`, `firstPublishedAt` and `deletedAt`, for the Refine panel.

### Policies

- Public reads expose a recording only when it is `published`, non-retired, and its event is publicly readable. A `draft` or `retired` recording is indistinguishable from none: the page shows the plaque.
- Playback reads require an authenticated session and nothing else — no event registration, no role, no attendance record.
- The primary/secondary selection is recomputed on every read; no cached ordering is persisted.
- A recording of a `platform` event can be published only while that event is `ended`; `draft`, `published`, `live` and `hidden` are all refused. A recording of a `legacy` event is published while the event is `hidden` — that published recording is the precondition of `ArchiveLegacyBroadcast`.
- The post-live page state and the «Прошедшие» tab key on `ended` for a `platform` event and on `in_archive` for a `legacy` one. The «Записи» tab keys on the same pair, intersected with the doctor's own registrations. A `hidden` event of either origin keeps feature 004's notice-only render and appears in no listing.
- 014 adds **no** transition to feature 007's broadcast machine. It renames that machine's terminal state and adds a second, disjoint machine for `legacy` events; the two never share a command.
- Facet options and counts include only published, non-retired taxonomy records with active joins, per 012's public default-deny.

## Invariants

- No `event_recordings` row is physically deleted or cascade-deleted, and no recording id is reused; `event_recordings.event_id` is restrictive.
- At most one non-retired `event_recordings` row exists per `(event_id, kind)`; a retired row frees the slot while remaining addressable.
- `retired ⇔ deleted_at IS NOT NULL`; `first_published_at` is monotone — set once, never cleared, unaffected by unpublish, retire or restore.
- A published recording exists on an `ended` platform event or on a `legacy` event of either state; no `draft`, `published`, `live` or `hidden` platform event ever carries one.
- A `hidden` event of either origin renders feature 004's notice, holds no player and belongs to no 014 listing, tab or count.
- `events.origin` is immutable, exactly one lifecycle applies to any event at any time, and the two machines share no command. A `legacy` event never holds a room record, a stream config, a presence window or a `live` state.
- An `in_archive` legacy event always carries at least one published non-retired recording.
- No row, contract field or label anywhere retains the value `archived` for the broadcast lifecycle after the rename migration.
- No response reachable without an authenticated session contains a playable source reference for any recording.
- Exactly one of `montage`, `raw-only` or `preparing` describes a finished event at every committed state, and it is derived — never stored.
- The player position of a finished event is never empty: it holds a player, the guest gate, the plaque, or the explicit unavailability message.
- `/webinars/[slug]` is the only route rendering an event page, pre-live or post-live.
- The tabs, pagination and facet controls exist in exactly one shared unit; every consuming surface renders that unit.
- No 014 table stores a project, expert or topic; facet data comes from 012's public reads only.
- «Мои события» renders exactly two tabs, and «Записи» contains every past registered event regardless of recording presence.
- A listing request costs a bounded number of statements independent of page size.
