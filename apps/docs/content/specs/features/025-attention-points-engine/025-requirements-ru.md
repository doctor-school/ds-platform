# 025 — Движок очков внимания (требования)

## Результаты

- У каждого врача **ровно один счёт очков внимания**, который витрина врача, Академия и мобильное приложение читают и пополняют через один API; баланс одинаков везде по построению, а не за счёт синхронизации.
- Счёт несёт три **номинала**: **Pul** (единственный тратимый, никогда не обменивается на деньги), **Bre** (репутация) и **Con** (осведомлённость, только растёт). Фиксированный вес 1 Con = 2 Bre используется только лидербордом и отчётностью о внимании.
- Каждое движение — **неизменяемая проводка двойной записи**; баланс — свёртка проводок; исправление — компенсирующая проводка; каждая проводка называет **правило и версию правила**, которые её породили, поэтому эксперименты сравнимы, а отчёты для спонсора сходятся после перенастройки.
- Каждая сумма начисления, цена, лимит, порог и формула — **настраиваемый версионируемый параметр с умолчанием**, меняется через admin API без релиза.
- Одна и та же (врач, единица контента, действие) **начисляется не более одного раза**, с какой бы витрины или устройства она ни пришла, включая офлайн-синхронизацию мобильного приложения; ошибки никогда не отнимают очки.
- Pul **резервируется при записи** на платную единицу, **списывается только при подтверждённом присутствии** и **возвращается** при отмене, неявке или отмене единицы платформой — поэтому нет отрицательного баланса и процедуры возврата.
- **Аванс** — флаг единицы, одинаковый для всех врачей; ссылка прихода только записывает источник. Аванс — обязательство, погашаемое будущими начислениями Pul, с потолком 150 Pul на персону; он никогда не становится отрицательным балансом и никогда не закрывает открытый контент.
- Модель чтения **лидерборда** — месячная, по специальности, по согласию — ранжирует 2·Con + Bre, заработанные за календарный месяц; баланс Pul никогда не ранжирует.
- Фича **036** получает **агрегаты внимания** по проекту и выходу, собранные из проводок с версиями правил, без строк по отдельным врачам.

## Границы

**Входит:**

- **Реестр**: счета персон и системные счета, которые нужны двойной записи (дизайн ADR-0016 §2.11), проводки (§2.12) с номиналом, уникальным `event_id`, ключом дедупликации и версией правила; триггер неизменяемости и месячные партиции по ADR-0003 §3 — по образцу работающего `audit_ledger`.
- **Движок начислений**: приём доменных фактов-источников начисления из модели событий, вычисление активной версии правила, запись проводок и выпуск `PointsCredited`.
- **Книга правил**: версионируемые правила начисления, цены событий и режимы гейтинга, потолок аванса, реферальный лимит, доля присутствия, окно неявки, лимит одновременных резервов и формула лидерборда — каждое с умолчанием из PRD.
- **Сторона трат**: решение гейтинга, резерв / списание / снятие резерва по **прайс-листу единиц любого вида** (события, курсы, обучения, стажировки, офлайн-мероприятия, …), аванс и его обязательство, погашение будущими начислениями.
- **Сторона чтения** через API: собственные балансы и история врача, решение гейтинга для одного врача и одной единицы, модель чтения месячного лидерборда, агрегаты внимания для 036.
- **Admin API** правил, настроек, прайс-листа и компенсирующих исправлений, чтения каталога и журнала и выдачи стартового бонуса, каждое изменение — с записью аудита.
- **Шов удаления данных**: закрытие и заморозка счёта персоны.

**Не входит (у каждого пункта есть владелец):**

- **Все экраны.** Строка цены, прогресс аванса, подсказка порога и денежное утверждение «бесплатно для врача», отвязанное от `pulCost`, на странице события — фича **020**, согласование в [#3801](https://github.com/doctor-school/ds-platform/issues/3801); обещание при регистрации и начисление в состоянии успеха — фича **021**, согласование в [#3801](https://github.com/doctor-school/ds-platform/issues/3801); три баланса, открытый аванс и история проводок в кабинете — фича **022**, Issue [#1791](https://github.com/doctor-school/ds-platform/issues/1791); блок лидерборда специальности по согласию и переключатель согласия — фича **018**, Issue [#1495](https://github.com/doctor-school/ds-platform/issues/1495); экраны обучения — фича **024**; мобильное приложение — свой трек (функциональная карта, решение владельца 2026-08-22), потребляющий этот API.
- **Экраны администратора** для правил, настроек, прайс-листа, исправлений и выдачи стартового бонуса — просмотр каталога типов фактов, структурный редактор правил, симуляция черновика правила по журналу. 025 поставляет только admin **API**; admin UI отложен в отдельный Issue [#3815](https://github.com/doctor-school/ds-platform/issues/3815); тот Issue владеет поверхностью в `apps/admin` и её браузерной проверкой.
- **Лист ожидания** на единицах с ограниченным числом мест — регистрация на событие (**020** / **005**); 025 только отказывает в резерве сверх лимита одновременных резервов (EARS-21).
- **Само подтверждение присутствия** — presence beats и факт присутствия принадлежат комнате и регистрации на событие; 025 потребляет факт подтверждённого присутствия и владеет только настройкой доли присутствия, по которой он считается (EARS-9).
- **Подтверждение телефона и проверка профиля** — аккаунта (фича **022**, поверх **003**); 025 потребляет факты.
- **Вызовы производителей** — каждая фича-производитель (021, 022, 024, 020 / комната и будущие владельцы курсов, обучений и стажировок) регистрирует свои типы фактов и вызывает `record` в своём срезе; 025 владеет механизмом каталога, а не их доменными событиями.
- **Деньги** — биллинг спонсоров, счета, денежная сторона агрегатов внимания и именные отчёты для спонсора по отдельному согласию ст. 9 — фича **036**.
- **Стоки следующей волны**, Pul за партнёрский или промо-контент, рекламный коэффициент, аналитика аномалий для администратора — не на запуске (PRD, «Вне рамок»).

## Ограничения

- **Одно семейство реестра.** Нигде нет колонки баланса, нет второго реестра, нет счёта на витрину; денежная единица того же семейства принадлежит 036 и здесь не пишется.
- **Проводки неизменяемы.** Ни UPDATE, ни DELETE не доходят до строки проводки — это обеспечивает база данных, а не только код; исправление — новая проводка, которая называет ту, что сторнирует.
- **Каждое число — параметр.** Ни одна сумма начисления, цена, лимит, доля или вес не записаны литералом в коде; каждое читается из активной версии правила, настройки или прайс-листа и проставляется в проводку, которую порождает.
- **Правила зависят только от внимания.** Ни один вход правила не читает спонсора, источник прихода от медпреда или партнёра, назначение, продажу или спонсорскую ценность для отдельного врача (323-ФЗ ст. 74, кодекс AIPM — «Комплаенс-ограничения» PRD); такой источник прихода записывается в проводку только как атрибуция. Единственный приход, который читает правило, — реферальная ссылка врача врачу из EARS-11 (`referral.attributed`).
- **Pul — не деньги.** Ни одно поле API, problem detail или текст администратора не выражает сумму Pul в деньгах, не называет цену в Pul «бесплатно» и не называет очки «баллами» в смысле НМО; ни одно поле не выводит утверждение «бесплатно» из нулевой цены в Pul.
- **Уроки никогда не стоят Pul**, а события никогда не начисляют Pul; событие с аккредитацией НМО всегда открыто.
- **Никакого наследия очков.** В реестр ничего не переносится со старой платформы; стартовый бонус (EARS-43) — новая выдача, а не конвертация.
- **Только серверные свидетельства.** Начисление за урок и модуль — только по вычисленным фактам завершения 024, за событие — только по серверному факту присутствия; завершение, заявленное клиентом, никогда не источник начисления.
- **Производитель сообщает, что произошло.** Производитель никогда не называет правило, сумму, номинал или ключ дедупликации; сколько стоит факт — решает книга правил.

## Prior decisions (предшествующие решения)

- **ADR-0016 §6 + дизайн §2.11–§2.12:** одно append-only семейство реестра; счета реестра по субъекту (`person` · `project_fund` · `organisation` · `system`) с единицей `attention_points` | `money`; неизменяемые проводки двойной записи с проектом, выходом, `rule_id` / `rule_version`, субъектом атрибуции (организация, участник) и `reverses_posting_id`; баланс — свёртка; при удалении данных счёт закрывается и замораживается, проводки никогда не переписываются.
- **ADR-0003 §2.7 / §3:** append-only с уникальным `event_id`, триггером, отказывающим в UPDATE/DELETE, и месячными партициями — образец — работающий `audit_ledger` (`packages/db/src/schema/audit-ledger.ts`).
- **ADR-0016 §6 и дизайн §2.11–§2.12 в редакции этого PR** (реестр не в продакшене, поэтому ADR переписан inline): проводка с единицей `attention_points` несёт **`denomination`** (`pul` · `bre` · `con`), поэтому у персоны остаётся **один** счёт очков внимания; каждая проводка несёт **`event_id` единственного доменного факта**, который её породил, и уникальна по (`event_id`, `leg`), где `leg` называет проводку внутри её факта (номинал + вид записи); глобальная дедупликация живёт в непартиционированной **`points_posting_keys`** — одна строка на факт по его `event_id` и ключу дедупликации (врач + единица контента + действие), вставляемая в той же транзакции до проводок факта. Так реестр очков выполняет дедупликацию по `event_id` и неизменяемость ADR-0003 §3 поверх месячных партиций; сам ADR-0003 не меняется.
- **ADR-0009:** согласие на распространение в лидерборде (152-ФЗ ст. 10.1) — ещё одна версионируемая запись по цели в `consent_records`; 025 не заводит своего хранилища согласий.
- **ADR-0001:** врач читает только свой счёт; admin API требует роли администратора; потребители передают факты сервис-сервис, никогда — токеном одного врача на счёт другого.
- **Владелец, 2026-11-06 (Issue #1794):** аванс — флаг события для всех врачей; каждое начисление — настраиваемый параметр, и каждая проводка записывает версию правила; никакого наследия очков.
- **Владелец, 2026-11-09 (Issue #3835):** единый универсальный движок правил — дословные решения в production-поправке ниже.

## Production-поправка — единый универсальный движок правил (2026-11-09, #3835)

Ядро реестра (#3807, миграция 0058) и книга правил с приёмом начислений (#3808, миграция 0059 — 21 засеянная строка правил версии 1, счёт `issuance`, триггер неизменяемости версий правил и `POST /v1/admin/points/rules/:ruleId/versions`) работают в продакшене с release-2026.11.07-1; ни один производитель пока не вызывает приём. Эта поправка переопределяет: **EARS-3** (закрытое действие, вычисляемое по своему единственному правилу `accrual.<action>`), **EARS-4** (ключ дедупликации «(персона, единица контента, действие)»), **EARS-25** (одна схема параметров на жёстко заданный id правила, закрытое перечисление действий, `points-rule-unknown`); команду модели событий `AccrueFromFact` (её заменяет `RecordFact`) и форму параметров `PublishRuleVersion`; пункты «Движок начислений» и «Книга правил» раздела «Границы»; строку «Результатов» про «(врач, единица контента, действие)» (тот же результат теперь держится лимитом `oncePer` правила); формулировку предшествующих решений «ключ дедупликации (врач + единица контента + действие)» (ключ теперь — область лимита применённого правила); строки инвариантов про ключ дедупликации и про одну строку `points_posting_keys` на факт; и строки 3, 4 и 25 таблицы проверки. Она добавляет **EARS-32…46**. Работающая в продакшене базовая редакция сохранена ниже. Требования, ещё не работающие в продакшене, — EARS-5…11, 13…19, 21, 23 и 26 — переписаны inline в теле как засеянные правила и настройки этого движка, с сохранением каждой суммы PRD. **Ни один номер EARS не сдвигается**: каждый номер сохраняет свой предмет, поэтому Issues #3809–#3816 сохраняют свои ссылки (production-поправка дизайна, «Clause map»). Миграция аддитивна поверх 0058 и 0059 (EARS-44). Механика: production-поправка дизайна от той же даты.

**Указание владельца (2026-11-09, дословно, #3835):** «нам нужен какой-то, видимо, универсальный механизм, который позволит вообще на любое действие вешать там либо списание награды, да, либо ее начисление … чтобы мы могли без каких-либо там доработок … корректировать это, да, и настраивать … лучше сразу заложить основу … с учетом будущего самого приложения».

**Предшествующие решения (этой поправки).**

- **Решение владельца 1 — траты не только на эфиры** (2026-11-09, дословно): «Конечно не только на эфиры. Даже в требованиях это было: там будут и курсы, и обучения, и стажировки, и оффлайн мероприятия и много всего другого» → общее списание `debit` и жизненный цикл резерва работают по прайс-листу единиц любого вида (EARS-26, EARS-35), в первом срезе движка.
- **Решение владельца 2 — кампании** (дословно): «Да, лучше предусмотреть эти вещи заранее» → сроки действия и управление совмещением (приоритет, эксклюзивная группа) входят в форму правила уже сейчас (EARS-37, EARS-38).
- **Решение владельца 3 — ретроактивность** (дословно): «Пока нет, но для ранее зареганных юзеров в DS надо предусмотреть возможность начисления стартового бонуса» → никакого автоматического перевычисления при публикации (EARS-42); явная, аудируемая выдача стартового бонуса врачам, зарегистрированным до движка (EARS-43).
- **Решения ведущего агента** (исследование #3835 по Talon.One, Voucherify, Open Loyalty и Antavo; холды — по Modern Treasury Ledgers): каталог типов фактов — код, правила — данные; условия — ограниченное JSON-AST, а не CEL и не язык свободного текста; применяется каждое подходящее правило, если управление совмещением не говорит иного (никакого «первое совпадение побеждает»); движок остаётся внутри `apps/api/src/points/` на той же базе, без отдельного сервиса; честная граница «без доработок» — по-настоящему новый вид факта, предиката, эффекта или лимита требует разработчика, всё остальное — данные администратора.
- **Комплаенс по построению переезжает** с «список действий закрыт» на «читаемый словарь закрыт»: правило читает только атрибуты, объявленные в каталоге, зарегистрированные предикаты и настройки (EARS-32, EARS-34); ограничение «Правила зависят только от внимания» не меняется.

**Переопределённые требования.**

- **EARS-3 в редакции поправки — записанный факт вычисляется по каждому подходящему правилу.** _(realizes: US-2, US-3, US-11, US-12, US-15)_ Когда `record` принимает факт (EARS-33), система должна выбрать каждое правило, чья версия, активная на `occurredAt` факта, перечисляет тип факта в своём триггере, имеет `active` и действует на `occurredAt` (EARS-37); вычислить условие (EARS-34) и лимиты (EARS-36) каждого; разрешить совмещение (EARS-38); применить эффекты стороны списания раньше начислений (EARS-35); и записать каждое применённое правило как **один факт реестра** с `event_id = <event id факта>#<id правила>`, собственной строкой `points_posting_keys` (EARS-4 в редакции поправки) и по одной неизменяемой проводке двойной записи на каждый ненулевой номинал и вид записи, каждая проводка — с `event_id` этого факта реестра, `leg`, номиналом, `rule_id` и `rule_version` применённого правила, типом факта как `action`, проектом и выходом, когда факт их называет, субъектом атрибуции, когда он записан, `occurred_at` и `recorded_at`. Строка журнала факта (EARS-40) и проводки каждого применённого правила пишутся в одной транзакции; после COMMIT система должна выпустить по одному `PointsCredited` на каждую персону, получившую начисление, с её проводками начисления — это по-прежнему единственное событие, по которому потребитель может утверждать начисленную сумму.
- **EARS-4 в редакции поправки — дедупликация по факту и по области лимита правила.** _(realizes: US-4, US-1)_ Когда приходит факт, чей `event_id` уже есть в журнале фактов, — повтор или его воспроизведение офлайн-синхронизацией мобильного приложения, — система ничего не должна вычислять и записывать и должна ответить исходным результатом (`duplicate` со ссылкой на исходные применения). Когда ключ дедупликации применения правила `<ключ лимита>:<значения области oncePer>` (EARS-36; ключ лимита по умолчанию — id правила) уже имеет строку `points_posting_keys`, это правило пропускается с пометкой следа `limit-reached`, а остальные правила факта всё равно применяются; факт, у которого все иначе применимые правила останавливаются на существующем ключе `oncePer`, отвечает `duplicate`. Поэтому один урок, о котором сообщили витрина врача, Академия и офлайн-синхронизация под тремя event id, начисляется один раз по правилу урока `oncePer(subject, ref)`. Обе уникальности должны обеспечиваться ограничениями базы данных, а не только чтением перед записью.
- **EARS-25 в редакции поправки — одна схема правила, любой id правила.** _(realizes: US-11, US-12)_ Когда администратор публикует версию через `POST /v1/admin/points/rules/:ruleId/versions`, система должна принять новый id правила, выбранный администратором (строчный slug через точку вне пространства имён `setting.` и вне системного id `manual-correction`), так же как существующий; проверить тело по **одной** схеме правила — `rule` (триггер, условие, эффект, лимиты, срок действия, active, совмещение, метка) или, для id `setting.`, по схеме этой настройки (EARS-39), с различением по `kind` — и по каталогу: каждый триггер называет зарегистрированный тип факта (EARS-32); условие проходит проверку типов (EARS-34); вид эффекта и номиналы допустимы (EARS-35, EARS-12), без начисления Pul по типу факта, который каталог помечает как не зарабатывающий Pul; каждое поле области лимита существует в каждом типе факта триггера, и начисление называет лимит или явный `unlimited` (EARS-36); ни одна сумма не превышает `setting.effect.maxAmount`; `kind` версии совпадает с `kind` прежних версий этого id. Она должна отклонять нарушение RFC 7807 problem `points-rule-parameters-invalid` (422) с путём поля, отклонять прошедший `effectiveFrom` (`points-rule-effective-from-past`, 422), отклонять id 0059, выведенный движком из оборота (дизайн, «Clause map»), с `points-rule-retired` (422), сохранять версию новой неизменяемой строкой, действующей с момента публикации или с более позднего `effectiveFrom`, записывать аудит, отвечать предупреждением о совмещении, если оно есть (EARS-38), и применять версию к фактам, записанным после, без релиза; прошлые проводки сохраняют свою версию, прошлые факты не перевычисляются (EARS-42).

**Добавленные требования.**

- **EARS-32** _(realizes: US-15, US-11)_ — Система должна держать **каталог типов фактов**, который регистрирует разработчик, в `packages/schemas/src/points/`: каждая запись — стабильный тип через точку в прошедшем времени (например, `lesson.completed`), его субъект (персона, чьего счёта он касается), вид ссылки (о чём факт — `lesson`, `module`, `item`, `person` или ничего), строгая Zod-схема типизированных атрибутов и признак, может ли правило по нему начислять Pul; зарегистрированные предикаты (EARS-34) входят в тот же читаемый словарь. Unit-тест по всему каталогу (`packages/schemas/src/points/fact-types.spec.ts`, запускается в CI) должен отклонять любой атрибут или предикат, который называет или несёт спонсора, организацию, источник прихода от медпреда или партнёра, назначение, продажу или спонсорскую ценность для отдельного врача; единственный приход, который открывает словарь, — реферальная ссылка врача врачу (`person.referrer`, EARS-11). Регистрация типа факта — изменение кода; привязка к нему награды, лимита или цены — данные администратора.
- **EARS-33** _(realizes: US-15, US-4)_ — Когда производитель сообщает, что произошло, через `points.record(tx, fact)` с `fact = { type, eventId, personId, ref?, occurredAt, attributes, projectId?, output?, attribution? }`, система должна проверить факт по его записи каталога, вычислить его внутри транзакции производителя как savepoint (EARS-3 в редакции поправки) и вернуть `{ outcome: 'applied' | 'duplicate' | 'no-effect', applied: { ruleId, ruleVersion, effect, postings }[], publishAfterCommit }`; производитель вызывает `publishAfterCommit()` после своего COMMIT и никогда после отката, а `record(fact)` без транзакции открывает свою и публикует после своего COMMIT. В схеме факта **нет** поля для суммы, id правила, номинала или ключа дедупликации; `attribution` пишется только в проводки и не читается ни одним правилом. Факт, который отклоняет его запись каталога (неизвестный тип, отсутствующая или запрещённая `ref`, неизвестный или неверно типизированный атрибут), выбрасывает ошибку и ничего не пишет; отказывающий эффект стороны списания (EARS-35) выбрасывает свой RFC 7807 problem и ничего не пишет, так что производитель закрывается отказом; факт, к которому не применилось ни одно правило, всё равно попадает в журнал с результатом `no-effect`, поэтому производитель может сообщать факты раньше, чем кто-то решит их награждать. Офлайн-синхронизация мобильного приложения воспроизводит факты через тот же `record`.
- **EARS-34** _(realizes: US-11)_ — Система должна выражать условие правила как JSON-**AST условия**, проверяемое Zod, — комбинаторы `all`, `any`, `not`; сравнения `eq`, `ne`, `in`, `gt`, `gte`, `lt`, `lte`; операнды `{ attr }` (объявленный атрибут типа факта триггера), `{ pred }` (зарегистрированный предикат — чтение без побочных эффектов по журналу, счёту или API чтения владельца, например `person.phoneVerified`, `person.completedLessons`, `person.referrer`, `item.price`, `item.limitedSeats`), `{ setting }` (EARS-39) и литералы — без циклов, без функций пользователя, без вычисления строк, с глубиной и числом узлов, ограниченными языком. При публикации версии система должна проверить типы условия по схеме атрибутов **каждого** типа факта триггера и по типам результатов предикатов и отклонить неизвестный или неверно типизированный операнд с `points-rule-parameters-invalid`, называя путь поля; отсутствующее условие равно `true`; при вычислении условие не читает ничего, кроме своих операндов. Предикат, вычисляемый для факта, должен видеть состояние **с учётом этого факта**: предикат по журналу считает вычисляемый факт уже записанным в журнал (поэтому первый `lesson.completed` приглашённого засчитывает сам себя в `person.completedLessons`, EARS-11), а чтения счёта и проекций видят состояние до собственных эффектов этого факта.
- **EARS-35** _(realizes: US-2, US-5, US-6, US-7, US-11)_ — Система должна поддерживать ровно такие **виды эффектов**: `credit` (выпуск → получатель, неотрицательное целое по номиналу; получатель — субъект факта или персона, которую возвращает зарегистрированный предикат, например пригласивший из EARS-11), `debit` (только Pul, персона → сток, константа или сумма из прайс-листа по ссылке факта, EARS-26), `reserve` (только Pul, сумма из прайс-листа по ссылке факта, удерживаемая по ключу холда в режиме гейтинга единицы; аванс — опция `reserve`, EARS-14…17), `settle` (открытый холд → сток, EARS-19) и `release` (открытый холд сторнируется вместе с авансом и его обязательством, если они есть, EARS-18). Для одного факта система должна применять `debit`, `reserve`, `settle` и `release` раньше `credit`; если любой `debit` или `reserve` отказывает — `points-insufficient-pul`, `points-threshold-short`, `points-reserve-limit` или `points-phone-unverified` для персоны с неподтверждённым телефоном (EARS-5), — весь факт отклоняется и ничего не пишется, включая строку журнала; `settle` или `release` без открытого холда — пустая операция со следом `no-open-hold`; `credit` никогда не отказывает. Погашение обязательств EARS-20 выполняется шагом ядра после каждого начисления Pul и не является правилом. Каждый `reserve`, `settle` и `release` должен в той же транзакции, что и его проводки, записывать проекцию холда `points_reserves` (счёт персоны, регистрация, единица, цена, части из баланса и из аванса, состояние `held` · `settled` · `released`), а для части из аванса — `points_obligations`; резерв, целиком покрытый авансом, не пишет проводки на счёт персоны, поэтому `PointsAccount.pul.reserved` и `advance` (EARS-2) читаются из этих проекций, которые пересобираются из проводок и журнала (`event_id` факта реестра `<fact>#<rule>` называет строку журнала с персоной и регистрацией). Обязательства ведутся и гасятся **по каждому обязательству отдельно**: EARS-20 пишет по одному leg `obligation-settle:<obligationId>` на каждое гасимое обязательство, начиная со старейшего, а `points_obligations` держит для каждого обязательства открытую, погашенную и оставшуюся суммы; когда холд обязательства снимается (EARS-18), система должна сторнировать оставшуюся авансовую часть этого обязательства и вернуть персоне уже погашенный Pul, сторнировав ровно его собственные legs `obligation-settle`, так что обязательство сообщает остаток долга 0, каждое другое обязательство сохраняет свой истинный остаток, а персона оказывается в положении, как если бы этой регистрации не было.
- **EARS-36** _(realizes: US-4, US-5, US-11)_ — Система должна поддерживать, как список **лимитов** правила, каждый из которых должен пройти, `oncePer(scope)` — область — подмножество `subject`, `beneficiary`, `ref` и объявленных атрибутов каждого типа факта триггера — обеспечиваемый ключом дедупликации `<ключ лимита>:<значения области>` в `points_posting_keys` (EARS-4 в редакции поправки), где ключ лимита — id правила, если правило не называет **общий ключ лимита**, чтобы несколько правил выдавали не больше одного из себя (EARS-43); `countPer(scope, period, n)` — не больше `n` применений правила для области за календарный `day`, `week` или `month` по Europe/Moscow, подсчитанных по проводкам с id правила, `n` — литерал или `{ setting }`, причём подсчёт и сравнение сериализуются по области лимита — advisory-блокировкой уровня транзакции по ключу (id правила, значения области, начало периода), которая берётся после блокировок персон и в одном возрастающем порядке ключей, — потому что область не обязана быть заблокированным счётом (EARS-11: факты многих приглашённых считаются в лимит одного пригласившего), так что параллельные факты никогда не превышают `n`; `concurrentOpen(n, filter)` — не больше `n` открытых холдов персоны на единицах, подходящих под фильтр прайс-листа (EARS-21); и `unlimited`, принимаемый только при явном указании. Применение, которое остановил лимит, записывается в след с этим лимитом.
- **EARS-37** _(realizes: US-11)_ — Когда версия правила несёт `validFrom` / `validUntil` и `active`, система должна применять правило только к фактам, чей `occurredAt` лежит в [`validFrom`, `validUntil`), и только пока версия, активная на `occurredAt`, имеет `active: true`; отключение правила — публикация новой версии с `active: false`, действующей сразу и без релиза; факт вне окна записывается в след как `not-valid`. `effectiveFrom` (какая версия) и срок действия (когда правило вообще применяется) независимы.
- **EARS-38** _(realizes: US-11)_ — Когда несколько правил, которые применились бы к одному факту, разделяют `exclusiveGroup`, система должна применить только правило с наибольшим `priority` (при равенстве — с лексически наименьшим id) и записать остальные в след как `superseded`; правила без группы совмещаются, каждое применяется само; группа разрешается после условий, срока действия и лимитов, поэтому правило, остановленное своим лимитом, никогда не подавляет участника с меньшим приоритетом. Когда администратор публикует активное правило `credit`, разделяющее тип факта триггера с другим активным правилом `credit` без общей эксклюзивной группы, система должна принять его и вернуть **предупреждение** о совмещении с названием другого правила.
- **EARS-39** _(realizes: US-11)_ — Система должна держать параметры политики как версионируемые **настройки** в пространстве имён `setting.` той же неизменяемой таблицы версий, каждую со своей строгой схемой в коде, — `setting.presence.share`, `setting.advance.cap`, `setting.noShow.window`, `setting.reserve.limitedSeats.max`, `setting.leaderboard.conWeight`, `setting.leaderboard.breWeight`, `setting.leaderboard.top`, `setting.leaderboard.neighbours`, `setting.effect.maxAmount`, — публикуемые через тот же endpoint (EARS-25 в редакции поправки), читаемые условиями и лимитами как операнды `{ setting }`, никогда не запускаемые фактом и никогда не порождающие проводку.
- **EARS-40** _(realizes: US-12, US-13)_ — Система должна дописывать каждый принятый факт в **журнал фактов** `points_facts` — `event_id` (уникальный), тип, персона, ссылка, `occurred_at`, атрибуты, `received_at`, результат и **след вычисления** (для каждого рассмотренного правила: id и версия правила, совпадение триггера, результат условия, срок действия, вердикт каждого лимита, вердикт совмещения и `event_id` применённого факта реестра) — в той транзакции, которая пишет его проводки; журнал должен быть неизменяемым (UPDATE и DELETE отклоняет триггер, кроме перенаправления `person_id` процедурой удаления ADR-0009, как для проводок) и нести только ссылки и атрибуты, объявленные в каталоге, никогда — атрибуцию.
- **EARS-41** _(realizes: US-7, US-15)_ — Когда потребитель запрашивает `points.quote(personId, draftFact)`, система должна выполнить то же вычисление, что `record`, — те же правила, условия, лимиты, совмещение и отказы, — ничего не записывая, не блокируя и не публикуя, и вернуть возможный результат, правила, которые применились бы, с их эффектами и проводками, и problem, который вызвал бы отказ; `record` и `quote` используют один путь кода, поэтому объявленное решение и исполненное не могут разойтись (EARS-13 — это `quote` записи на единицу).
- **EARS-42** _(realizes: US-11, US-12)_ — Когда версия правила публикуется, включается или получает срок действия, система должна вычислять её только по фактам, записанным после её публикации, и никогда не перевычислять факт из журнала; выдача за поведение, случившееся раньше, — только явная аудируемая операция EARS-43 или ручная корректировка (EARS-28).
- **EARS-43** _(realizes: US-2)_ — Когда администратор запускает **выдачу стартового бонуса** через `POST /v1/admin/points/starter-bonus` с обязательной причиной и моментом `registeredBefore` не позже текущего, система должна отклонить запуск с `points-starter-bonus-no-rule` (422), если нет активного правила с триггером `person.starter-bonus-eligible`, а иначе записать через `record` факт `person.starter-bonus-eligible` с производным event id `starter-bonus:<personId>` для каждого врача, чей аккаунт создан до этого момента и чей счёт очков не закрыт, так что повторный или возобновлённый запуск отвечает `duplicate` и никогда не выдаёт дважды; засеянное правило `accrual.starter-bonus` [+20 Pul] начисляет его `oncePer(subject)` под общим ключом лимита `welcome` с `accrual.registration`, поэтому врач получает не больше одного из стартового бонуса и гранта за регистрацию; запуск должен до первой выдачи записать одну запись `audit_ledger` со своим run id, администратором, причиной и моментом, нести этот run id атрибутом `runId` каждого записанного им факта и по завершении записать одну запись `audit_ledger` со счётчиками (применено, duplicate, пропущено), так что и прерванный до завершения запуск оставляет каждую выдачу привязанной к администратору и причине. Выдача никогда не конвертирует наследственный баланс очков — его нет, — и публикация правила никогда её не запускает.
- **EARS-44** _(realizes: US-11, US-12)_ — Система должна поставлять правила PRD из EARS-5…11, 14…19 и 21 и настройки EARS-39 строками **одной новой миграции** (0060), которая добавляет колонки движка и журнал фактов — таблицы холдов, обязательств и прайс-листа поставляются со слайсом трат (#3810), — и вставляет на эпоху для каждого засеянного id правила и настройки версию `max(version) + 1` этого id (1, если версий нет): в базе только со строками 0059 это версия 2 каждого id правила начисления 0059, чей смысл переносится, и версия 1 каждого нового id правила и настройки; ничего для выведенных из оборота id 0059 (дизайн, «Clause map»). Засев вытесняет каждую более раннюю версию своего id, потому что активна наибольшая действующая версия. Она должна оставить нетронутой каждую строку 0058 и 0059, включая 21 засеянную строку версии 1, и каждую существующую проводку и не должна содержать отказывающей проверки: существующая проводка неизменяема, ссылается на свою версию по FK и никогда не перевычисляется (EARS-42), а базы dev и stage содержат проводки и версии выше 1, записанные прошлыми прогонами e2e, — проверка уронила бы stage-деплой, через который проходит каждый релиз. Компромисс явный: засев вытеснил бы настоящую публикацию администратора так же, как вытесняет публикацию e2e, — проверка по `published_by` их не различит (строки e2e тоже несут публикатора-администратора), а пропуск такого id оставил бы активным его тело в схеме v1, которое движок не может разобрать. Поэтому защита production — проверка только чтением #3850, которая блокирует релиз с 0060, пока там есть опубликованная администратором версия выше 1 (`Release-requires: #3850`). Миграция завершается NOTICE с каждым id, чей засев вытесняет версию, записанную не миграцией, чтобы это было видно в логе деплоя; вытесненные строки остаются на месте без изменений как история. После её применения ни одно требование PRD о начислении или трате не требует кода движка под конкретное действие.
- **EARS-45** _(realizes: US-11, US-13)_ — Когда администратор запрашивает `GET /v1/admin/points/fact-types` (каталог со схемами атрибутов и предикатами), `GET /v1/admin/points/rules` (каждый id правила и настройки с активной версией и историей версий) или `GET /v1/admin/points/facts?personId=…` (строки журнала этой персоны со следами вычисления, с курсорной пагинацией), система должна вернуть их под ролью администратора и отклонять любого другого вызывающего (403).
- **EARS-46** _(realizes: US-1, US-12, US-15)_ — Когда врач со входом запрашивает `GET /v1/me/points/postings?cursor=…&limit=…`, система должна вернуть `PostingHistory` только **его собственного** счёта (у маршрута нет параметра персоны): каждую проводку по счёту персоны, от новых к старым по (`occurred_at`, `id`), каждую с id проводки, `occurredAt`, номиналом, знаковой `amount` со стороны персоны (начисление — плюс, списание — минус), типом факта как `action`, ссылкой, `ruleId`, `ruleVersion` и `reversesPostingId`, когда он задан, с курсорной пагинацией с ограниченным размером страницы и стабильным `nextCursor`; она не должна отдавать поле атрибуции и идентификатор другой персоны, а её суммы Pul подчиняются EARS-30.

## Модель событий

### Команды

- `AccrueFromFact({ eventId, personId, action, contentRef?, projectId?, occurredAt, attribution? })` — внутренняя; её выдаёт политика, принимающая факт-источник начисления. Идемпотентна по `eventId` и по ключу дедупликации. _(Переопределена production-поправкой: `RecordFact`.)_
- `RecordFact({ type, eventId, personId, ref?, occurredAt, attributes, projectId?, output?, attribution? })` — внутрипроцессный `points.record(tx?, fact)`; его вызывает каждый производитель. Идемпотентна по `eventId` и по ключу `oncePer` каждого применённого правила; может получить отказ от эффекта стороны списания (`points-insufficient-pul`, `points-threshold-short`, `points-reserve-limit`, `points-phone-unverified`).
- `QuoteFact({ personId, draftFact })` — внутрипроцессный `points.quote`; никогда не пишет.
- `PublishRuleVersion({ ruleId, parameters, effectiveFrom? })` — admin API `POST /v1/admin/points/rules/:ruleId/versions`; `parameters` — одна схема правила или схема настройки (EARS-25 в редакции поправки).
- `SetItemPrice({ itemRef, itemKind, mode: 'open' | 'advance' | 'threshold', pulCost, limitedSeats })` — admin API `PUT /v1/admin/points/prices/:itemRef`.
- `PostCorrection({ reversesPostingId, reason })` / `PostManualAdjustment({ personId, denomination, amount, reason })` — admin API `POST /v1/admin/points/corrections`.
- `GrantStarterBonus({ registeredBefore, reason })` — admin API `POST /v1/admin/points/starter-bonus`.
- `CloseAccount({ personId, cause: 'erasure' | 'consent-refusal' })` — внутренняя; её выдаёт жизненный цикл персональных данных (037 / процедура удаления ADR-0009).

Резерв, списание и снятие холда больше не отдельные команды: это эффекты засеянных правил на фактах регистрации ниже (EARS-35).

- `FactJournalEntry { eventId, type, ref?, occurredAt, receivedAt, outcome, trace }` — `GET /v1/admin/points/facts` (EARS-45).

### Политики

- Факт-источник начисления превращается в проводки только через версию правила, активную на `occurredAt` факта; перенастроенное правило никогда не переписывает прошлые проводки.
- Проводка, которая опустила бы доступный Pul персоны ниже нуля, отклоняется; цену покрывают резервы и авансы, а не долги.
- Источник прихода от спонсора, медпреда или партнёра записывается в поля атрибуции проводки и не читается ни одним правилом.
- Закрытый счёт не принимает новых проводок.

## Требования EARS

> Плоская нумерация по ADR-0006 §4. Каждое требование несёт `realizes: US-N` по [`025-product-ru.md`](./025-product-ru.md) и помечено тегом в [`025-scenarios.feature`](./025-scenarios.feature). Умолчания в квадратных скобках — параметры правила, настройки или прайс-листа (EARS-25, EARS-39), никогда не литералы. EARS-3, EARS-4 и EARS-25 ниже — работающая в продакшене базовая редакция, переопределённая production-поправкой выше; EARS-32…46 объявлены там. Где требование ниже называет **засеянное правило**, это правило — данные администратора, поставляемые EARS-44, а его триггер, условие, эффект и лимиты — названные; его изменение — новая версия правила, никогда не код движка.

- **EARS-1** _(realizes: US-1, US-15)_ — Когда движку впервые нужен счёт очков внимания персоны (первый факт начисления по этой персоне), система должна открыть **ровно один** счёт реестра с `subject_kind = person`, `unit = attention_points` для этой персоны, уникальный по (`subject_id`, `unit`), и каждая витрина, Академия, мобильное приложение и каждая фича-потребитель должны получать этот же счёт через один API; счетов на витрину или на устройство быть не должно. Чтение никогда не открывает счёт: чтение по персоне, у которой счёта ещё нет, отвечает нулевой свёрткой открытого счёта.
- **EARS-2** _(realizes: US-1, US-15)_ — Когда врач со входом запрашивает `GET /v1/me/points`, система должна вернуть модель чтения `PointsAccount`, в которой доступный Pul, Bre и Con — **свёртка проводок счёта персоны**, а зарезервированный Pul и открытый аванс с остатком обязательства читаются из проекций холдов `points_reserves` и `points_obligations` (EARS-35), — нигде не читая и не записывая изменяемую колонку баланса, и тот же запрос с любого клиента должен возвращать те же значения; запрос счёта другой персоны должен отклоняться (403).
- **EARS-3** _(realizes: US-2, US-3, US-12, US-15)_ — Когда принят факт-источник начисления из модели событий, система должна вычислить версию правила, **активную на `occurredAt` факта**, для этого действия и записать по одной неизменяемой проводке двойной записи на каждый ненулевой номинал (с системного счёта выпуска на счёт персоны) после вставки единственной строки `points_posting_keys` факта (его `event_id` и ключ дедупликации), каждая проводка — с `event_id` факта, `leg`, называющим проводку внутри факта (номинал + вид записи), номиналом, `rule_id` и `rule_version`, проектом и выходом, когда факт их называет, субъектом атрибуции, когда он записан, `occurred_at` и `recorded_at`, всё в одной транзакции, после чего выпустить `PointsCredited` — единственное событие, по которому потребитель может утверждать начисленную сумму.
- **EARS-4** _(realizes: US-4, US-1)_ — Когда приходит факт-источник начисления, чей `event_id` или чей ключ дедупликации **(персона, единица контента, действие)** уже имеет строку `points_posting_keys`, — пришёл ли он с другой витрины, из Академии, повтором или из офлайн-синхронизации мобильного приложения, — система **не** должна записывать проводку и должна ответить исходным результатом (`duplicate` со ссылкой на существующие проводки), чтобы повторённый или одновременный факт никогда не начислялся дважды; уникальность должна обеспечиваться ограничениями базы данных, а не только чтением перед записью.
- **EARS-5** _(realizes: US-2)_ — Когда по врачу записан `account.registered` или `phone.verified` и выполнены оба (в любом порядке — условие читает `person.registered` и `person.phoneVerified`), засеянное правило `accrual.registration` должно начислить **грант за регистрацию** [+20 Pul] `oncePer(subject)` под общим ключом лимита `welcome` (EARS-43); Pul персоны с неподтверждённым телефоном не должен быть тратимым — каждый `debit` и `reserve` отказывает с `points-phone-unverified` (EARS-35).
- **EARS-6** _(realizes: US-2, US-3)_ — Когда фича 022 записывает `profile.verified` по врачу, засеянное правило `accrual.profile` должно начислить **грант за профиль** [+30 Pul, +2 Bre] `oncePer(subject)`.
- **EARS-7** _(realizes: US-2, US-3, US-4)_ — Когда фича 024 записывает `lesson.completed` — свой вычисленный статус завершения, который уже требует времени просмотра или пройденного теста, — засеянные правила должны начислить **награду за урок** [+10 Pul, +1 Bre] двумя частями: `accrual.lesson` начисляет [+10 Pul], когда `mode` факта — онлайн, `oncePer(subject, ref)` под ключом лимита `lesson.pul`, а `accrual.lesson.any-mode` начисляет [+1 Bre] при любом `mode` (онлайн, офлайн или открытое обучение), `oncePer(subject, ref)` под ключом лимита `lesson`; поэтому Bre за урок начисляется один раз при любом режиме, офлайн- или открытое прохождение не приносит Pul, а онлайн-прохождение после офлайн всё равно приносит Pul, но не второй Bre (дизайн, «Clause map», порядок режимов); ошибка в тесте, неудачная попытка или повторное прохождение никогда не должны порождать списывающую проводку; подкаст, завершённый вне своего урока, — не тип факта и не начисляет ничего.
- **EARS-8** _(realizes: US-2, US-3)_ — Когда фича 024 записывает `module.completed` (все уроки пройдены и тест модуля сдан), засеянные правила должны начислить **награду за модуль** [+20 Pul, +3 Bre, +1 Con] двумя частями: `accrual.module` [+20 Pul] для онлайн-`mode` под ключом лимита `module.pul` и `accrual.module.any-mode` [+3 Bre, +1 Con] при любом `mode` под ключом лимита `module`, оба `oncePer(subject, ref)`, с тем же порядком режимов, что в EARS-7.
- **EARS-9** _(realizes: US-3, US-5)_ — Когда записан `attendance.confirmed` с серверной `presenceSharePercent` не меньше `setting.presence.share` [30 % длительности единицы], засеянное правило `accrual.participation` должно начислить **награду за участие** [+2 Bre, +1 Con] `oncePer(subject, ref)`, одинаково при любой цене и для открытых единиц; каталог помечает `attendance.confirmed` и факты вовлечённости EARS-10 как не зарабатывающие Pul, поэтому ни одно правило на них не может начислить Pul (EARS-25 в редакции поправки); доля присутствия ниже настройки не считается присутствием.
- **EARS-10** _(realizes: US-3, US-4)_ — Когда записаны вопрос врача спикеру, оценка единицы или интерактивный ответ во время эфира (`event.question-asked`, `event.rated`, `event.interactive-answered`), засеянные правила `accrual.question`, `accrual.rating` и `accrual.interactive` должны каждое начислить свою **награду за вовлечённость** [+1 Bre] не более `oncePer(subject, ref)`; повторное сообщение того же действия по той же единице отвечает `duplicate` (EARS-4 в редакции поправки).
- **EARS-11** _(realizes: US-2, US-3, US-8)_ — Когда `phone.verified` или `lesson.completed` записан по приглашённому, у которого задан `person.referrer` (ссылка, которую 021 записала через `referral.attributed`) и есть и подтверждённый телефон, и хотя бы один завершённый урок, засеянное правило `accrual.referral-inviter` должно начислить пригласившему — получателю `person.referrer` — [+30 Pul, +2 Bre] с лимитами `oncePer(beneficiary, subject)` и `countPer(beneficiary, month, 5)` (**месячный реферальный лимит**, Europe/Moscow), а засеянное правило `accrual.referral-invitee` — начислить приглашённому [+30 Pul] `oncePer(subject)`; когда лимит пригласившего достигнут, пропускается только применение пригласившему (`limit-reached`), применение приглашённому всё равно проходит.
- **EARS-12** _(realizes: US-4, US-3)_ — Система **не** должна записывать проводку, списывающую Bre или Con со счёта персоны, кроме компенсирующей проводки, сторнирующей конкретное прежнее начисление (EARS-28); ни одно правило не выражает штраф, и ни одна проводка не конвертирует номиналы (1 Con = 2 Bre — только вес на стороне чтения); ручная корректировка (EARS-28) может быть положительной в любом номинале и отрицательной только в Pul.
- **EARS-13** _(realizes: US-7, US-15)_ — Когда врач со входом запрашивает `GET /v1/me/points/gating/:itemRef`, система должна вернуть `GatingDecision` для этого врача, вычисленное как `quote` (EARS-41) черновика факта `registration.created` по этой единице: `open` для единицы без строки прайс-листа, со строкой `open` или нулевой ценой и для любого урока или модуля; для платной единицы — `reserve`, когда доступный Pul покрывает цену, `reserve-with-advance` в режиме аванса, когда недостача укладывается в потолок аванса (EARS-16), иначе `short` с точной **недостачей** (цена − доступный Pul) и `earnHint`, чей `pulToEarn` — недостача **плюс остаток открытых обязательств** (потому что EARS-20 сначала направляет каждое новое начисление Pul на обязательства), а `lessonsNeeded` — `ceil(pulToEarn / начисление Pul активной версии accrual.lesson)`; никогда не отрицательное число и никогда не решение «не хватает» в режиме аванса в пределах потолка.
- **EARS-14** _(realizes: US-5)_ — Когда записан `registration.created` по единице, чья строка прайс-листа имеет цену в Pul > 0, и доступный Pul врача её покрывает, засеянное правило `spend.reserve` (`oncePer(subject, registrationId)`) должно **зарезервировать** цену проводкой со счёта персоны на системный счёт резерва со ссылкой на регистрацию и единицу; открытая единица или нулевая цена не порождают проводки (результат `no-effect`).
- **EARS-15** _(realizes: US-6, US-8)_ — Когда записан `registration.created` по единице **в режиме аванса**, а доступный Pul меньше цены, эффект `reserve` должен зарезервировать доступный Pul из баланса и покрыть **ровно недостачу** авансовой проводкой с системного счёта аванса, открыв персоне обязательство на эту сумму; решение должно быть одинаковым для каждого врача на этой единице и не должно читать источник прихода.
- **EARS-16** _(realizes: US-6)_ — Если открытие аванса подняло бы открытые обязательства персоны выше `setting.advance.cap` [150 Pul, считается на персону], то эффект `reserve` должен считать единицу **пороговой** для этого врача (EARS-17); открытое обязательство никогда не закрывает действие без резерва — открытые единицы и уроки остаются открытыми — и никогда не представляется API как отрицательный баланс.
- **EARS-17** _(realizes: US-7)_ — Когда записан `registration.created` по единице **в режиме порога** (или по единице в режиме аванса сверх потолка), а доступный Pul меньше цены, эффект `reserve` должен отклонить факт с RFC 7807 problem `points-threshold-short`, несущим недостачу и `earnHint` из EARS-13, ничего не записать и оставить запись закрытой отказом у её производителя.
- **EARS-18** _(realizes: US-5, US-6)_ — Когда регистрация с холдом отменена врачом в любое время (`registration.cancelled`), аннулирована из-за отмены или переноса единицы платформой (`registration.voided`) или единица закончилась без `attendance.confirmed` по этой регистрации в пределах `setting.noShow.window` [24 часа после окончания единицы] — тогда sweep неявок записывает `registration.no-show`, идемпотентно через производный event id `no-show:<registrationId>`, — засеянное правило `spend.release` должно **снять** холд компенсирующей проводкой (`reverses_posting_id` → резерв) и аннулировать аванс, использованный на эту единицу, вместе с его обязательством компенсирующей проводкой; при неявке награда за участие не начисляется; других последствий нет. `attendance.confirmed`, записанный после снятия по неявке, ничего не списывает (`no-open-hold`, снятый резерв остаётся снятым) и всё же начисляет награду за участие из EARS-9 со следом «поздно».
- **EARS-19** _(realizes: US-5)_ — Когда записан `attendance.confirmed` по регистрации с холдом с долей присутствия не меньше `setting.presence.share` (EARS-9), засеянное правило `spend.settle` (`oncePer(subject, registrationId)`) должно **списать** холд проводкой с системного счёта резерва на системный счёт стока со ссылкой на резерв, ровно один раз на регистрацию.
- **EARS-20** _(realizes: US-6)_ — Когда персоне с открытым обязательством начисляется Pul, система должна сначала **погасить обязательство** проводкой со счёта персоны на системный счёт аванса на `min(начисленный Pul, остаток обязательства)` в той же транзакции, начиная со старейшего обязательства, и выпустить `AdvanceSettled` с остатком.
- **EARS-21** _(realizes: US-5)_ — Если резерв дал бы персоне больше открытых холдов на единицах с ограниченным числом мест, чем `setting.reserve.limitedSeats.max` [3], — лимит `concurrentOpen` правила `spend.reserve`, отфильтрованный по строкам прайс-листа с `limitedSeats`, — то система должна отклонить факт с problem `points-reserve-limit` и ничего не записать; лист ожидания остаётся за 020.
- **EARS-22** _(realizes: US-5, US-4)_ — Система должна отклонять любую проводку, которая опустила бы **доступный Pul** персоны **ниже нуля**, сериализуя проводки по счёту персоны, чтобы одновременные резервы не могли его перерасходовать, и не должна записывать проводок истечения по времени — Pul не сгорает.
- **EARS-23** _(realizes: US-9)_ — Когда запрашивается `GET /v1/points/leaderboard/:specialtyCode?month=YYYY-MM`, система должна вычислить среди врачей этой специальности с **активным согласием `leaderboard-dissemination`** счёт **`setting.leaderboard.conWeight` [2]·Con + `setting.leaderboard.breWeight` [1]·Bre, заработанные в этом календарном месяце** (начисления месяца за вычетом их сторно; баланс Pul никогда не ранжирует), ранжировать только этих врачей и вернуть первые `setting.leaderboard.top` [10] плюс — для врача со входом — его собственное место и счёт с `setting.leaderboard.neighbours` [5] соседями выше и ниже; врач без согласия получает своё возможное место приватно и никогда не появляется в ответе другого врача и не сдвигает номера мест в нём.
- **EARS-24** _(realizes: US-9)_ — Строка врача в лидерборде должна существовать только пока активно отдельное версионируемое согласие `leaderboard-dissemination` (152-ФЗ ст. 10.1), выключенное по умолчанию, с выбором имени врача (фамилия с инициалами или псевдоним) и отдельными флагами города и фото; когда согласие отозвано, строки нет уже в следующем ответе лидерборда.
- **EARS-25** _(realizes: US-11, US-12)_ — Когда администратор публикует версию правила через `POST /v1/admin/points/rules/:ruleId/versions`, система должна проверить её параметры по схеме правила (суммы начисления по действию и номиналу, лимиты, доля присутствия, окно неявки, потолок аванса, реферальный лимит, лимит одновременных резервов, веса и размеры лидерборда — набор действий закрытое перечисление без входов назначения, продажи, спонсора или источника прихода), сохранить её как новую неизменяемую версию, действующую с момента публикации или с более позднего `effectiveFrom`, записать аудит и применять её к проводкам, созданным после, без релиза; прошлые проводки сохраняют свою версию.
- **EARS-26** _(realizes: US-11)_ — Когда администратор задаёт строку прайс-листа единицы через `PUT /v1/admin/points/prices/:itemRef` с видом единицы (вид, зарегистрированный в каталоге, — `event`, `course`, `training`, `internship`, `offline-event`, `lesson`, `module`, …), режимом `open`, `advance` или `threshold`, ценой в Pul [стандарт 50, премиум или с ограниченным числом мест 100] и флагом `limitedSeats`, система должна принять любой режим для вида, который каталог помечает как платный, отклонить любой режим, кроме `open`, для урока или модуля и для события с аккредитацией НМО (problem `points-gating-invalid`), записать аудит и применять изменение к резервам и списаниям, созданным после; существующие холды сохраняют цену, по которой были сделаны.
- **EARS-27** _(realizes: US-12)_ — Каждая проводка должна нести непустые `rule_id` и `rule_version` (сторно несёт версию сторнируемой проводки), что обеспечивает ограничение базы данных, должна быть уникальна по (`event_id`, `leg`), а строка проводки должна получать отказ в UPDATE и DELETE от триггера базы данных; проводки партиционируются по месяцу `occurred_at`, как `audit_ledger`.
- **EARS-28** _(realizes: US-13)_ — Когда администратор проводит исправление через `POST /v1/admin/points/corrections` — сторно названной проводки или ручную корректировку с обязательной причиной, положительную в любом номинале или отрицательную только в Pul (EARS-12), — система должна записать его новой компенсирующей проводкой (`reverses_posting_id` для сторно, правило `manual-correction` для корректировки), отклонить повторное сторно той же проводки, записать в `audit_ledger` администратора, причину и id проводок и никогда не изменять и не удалять существующую проводку; ручная корректировка не должна опускать доступный Pul ниже нуля (EARS-22).
- **EARS-29** _(realizes: US-14)_ — Когда 036 запрашивает `GET /v1/admin/points/aggregates` по проекту (опционально по выходу и месяцу), система должна вернуть суммы по номиналу, id правила и версии правила вместе с числом различных персон, собранные из проводок, и **не** должна возвращать идентификаторов персон; именные данные — у 036 по её отдельному согласию, а разрез по спонсору из контракта потребителя PRD — это соединение проектов с их организациями на стороне 036.
- **EARS-30** _(realizes: US-10, US-15)_ — Каждый ответ API движка, несущий сумму Pul, должен отдавать её целым `pulCost` / `amount` с единицей `Pul`, **не** должен отдавать поле, выводящее «бесплатно» или денежное утверждение из нулевой цены в Pul, и ни один problem detail, текст администратора или имя поля не называет цену в Pul «бесплатно», а очки — «баллами»; денежное утверждение принадлежит потребителю и независимо от `pulCost` (020, #3801).
- **EARS-31** _(realizes: US-1, US-13)_ — Когда жизненный цикл персональных данных закрывает счёт персоны по удалению данных или отказу от согласия, система должна проставить `closed_at` счёту, отклонять каждую последующую проводку на него (problem `points-account-closed`), сама не снимать резервы и не гасить обязательства и оставить каждую существующую проводку без изменений; субъект проводки перенаправляется только процедурой удаления ADR-0009.

## Инварианты

- У одной персоны не больше одного открытого счёта очков внимания.
- Баланс каждого номинала равен свёртке его проводок; хранимого баланса нет.
- Ни одна строка проводки никогда не изменяется и не удаляется; каждая проводка уникальна по (`event_id`, `leg`) с непустыми id и версией правила, и у каждого факта ровно одна строка `points_posting_keys`. _(Переопределено production-поправкой, EARS-3/EARS-4 в редакции поправки: у каждого применённого правила — факта реестра `<event id факта>#<id правила>` — ровно одна строка `points_posting_keys`, поэтому у факта журнала 0…n строк ключей.)_
- У ключа дедупликации (персона, единица контента, действие) не больше одного набора проводок начисления. _(Переопределено production-поправкой: у ключа `oncePer` применённого правила `<ключ лимита>:<значения области>` не больше одного набора проводок, а у `event_id` факта — не больше одной строки журнала.)_
- Доступный Pul никогда не ниже нуля; Bre и Con уменьшаются только сторно конкретного начисления.
- Ни одно событие не начисляет Pul; ни один урок или модуль не стоит Pul; событие с аккредитацией НМО всегда открыто.
- Источник прихода от спонсора, медпреда или партнёра никогда не меняет решение гейтинга, цену или начисление.
- Открытые обязательства персоны никогда не превышают активный потолок аванса.
- Ответ лидерборда содержит только врачей с активным согласием на распространение, ранжированных между собой.
- Агрегат внимания не содержит идентификаторов персон.
- Ни одно правило не читает ничего, кроме атрибутов из каталога, зарегистрированных предикатов и настроек; ни один тип факта или предикат не открывает спонсора, источник прихода, кроме реферальной ссылки, назначение или продажу.
- Факт из журнала никогда не перевычисляется; версия правила применяется только к фактам, записанным после её публикации.
- `record` и `quote` используют один путь вычисления.

## Зависимости и порядок

- **Сначала реестр** (EARS-1, 3, 4, 22, 27) — все остальные требования проводят через него. Поставлен (#3807).
- **Затем движок** (EARS-3, 4, 25 в редакции поправки; EARS-32…42, 44, 45) — один срез внутри `apps/api/src/points/`: каталог, схема правила и вычислитель условий, виды лимитов, эффекты `credit` и `debit`, `record` / `quote`, журнал и аддитивная миграция засева. Он предшествует каждому требованию ниже.
- **Источники начисления ждут своих производителей**: EARS-5/6 — `phone.verified` / `profile.verified` из 022 (Issue #1791), EARS-7/8 — фактов завершения 024, EARS-9/10/18/19 — фактов регистрации и присутствия 020, EARS-11 — `referral.attributed` из 021. Срез каждого производителя — одна регистрация типа факта и один вызов `record`; непоставленный производитель оставляет требование неисполнимым, а не заглушенным, и e2e требования ведёт реальный факт, когда производитель существует.
- **Траты** (EARS-13–21, 26) — эффекты `reserve` / `settle` / `release`, прайс-лист, лимит `concurrentOpen` и sweep неявок — предшествуют платным событиям 020; `eventEconomyFacts()` сохраняет `pulCost: 0` (`DEBT.md`), пока EARS-26 не даст единицам реальных цен.
- **Стартовый бонус** (EARS-43) — после движка; запускает администратор, когда решит Product Lead.
- **Лидерборд** (EARS-23/24) предшествует 018 #1495; **агрегаты** (EARS-29) — 036.
- **Admin UI** для EARS-25/26/28/43/45 — просмотр каталога, структурный редактор правил и симуляция по журналу — отдельный Issue #3815.

## Открытые вопросы, перенесённые дальше

Для Product Lead; спроектировано в обход, а не решено здесь:

- **Обмен Con↔Bre, видимый врачу** — по умолчанию только вес (EARS-12, EARS-23); видимый врачу обмен был бы новым видом проводки, а не изменением схемы.
- **Веса биллинга спонсора** для Con, Bre и Pul (036) — каждая проводка несёт версию правила (EARS-27), поэтому любое взвешивание можно пересчитать из EARS-29.
- **Урок пройден сначала офлайн, потом онлайн** (EARS-7, EARS-8) — по умолчанию: Bre (и Con модуля) начисляется один раз при любом режиме, а более позднее онлайн-прохождение всё равно приносит Pul, так что врач получает полную награду [+10 Pul, +1 Bre] и никогда второй Bre; альтернатива — офлайн-прохождение навсегда лишает урок его Pul — достигается публикацией новых версий двух правил без общего ключа дедупликации: правило Pul получает условие через зарегистрированный предикат — применяться, только если ранее этот урок не был пройден (ни офлайн, ни онлайн), а правило Bre сохраняет свой ключ; возврат `accrual.lesson` под общий ключ `lesson` привёл бы к столкновению двух правил на каждом онлайн-прохождении и потере Pul или Bre.
- **Сумма стартового бонуса** — по умолчанию [+20 Pul], как грант за регистрацию (EARS-43); сумма — версия правила, которую Product Lead задаёт до запуска.
- **Цены в Pul на курсы и обучения** — прайс-лист принимает любой платный вид (EARS-26); правило PRD «уроки никогда не стоят Pul» оставляет уроки и модули открытыми, поэтому курс с платным доступом не должен оценивать свои уроки — вид регистрируется как платный, только когда это говорит спецификация его владельца.
