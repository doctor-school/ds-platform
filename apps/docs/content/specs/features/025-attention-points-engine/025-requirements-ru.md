# 025 — Движок очков внимания (требования)

## Результаты

- У каждого врача **ровно один счёт очков внимания**, который витрина врача, Академия и мобильное приложение читают и пополняют через один API; баланс одинаков везде по построению, а не за счёт синхронизации.
- Счёт несёт три **номинала**: **Pul** (единственный тратимый, никогда не обменивается на деньги), **Bre** (репутация) и **Con** (осведомлённость, только растёт). Фиксированный вес 1 Con = 2 Bre используется только лидербордом и отчётностью о внимании.
- Каждое движение — **неизменяемая проводка двойной записи**; баланс — свёртка проводок; исправление — компенсирующая проводка; каждая проводка называет **правило и версию правила**, которые её породили, поэтому эксперименты сравнимы, а отчёты для спонсора сходятся после перенастройки.
- Каждая сумма начисления, цена, лимит, порог и формула — **настраиваемый версионируемый параметр с умолчанием**, меняется через admin API без релиза.
- Одна и та же (врач, единица контента, действие) **начисляется не более одного раза**, с какой бы витрины или устройства она ни пришла, включая офлайн-синхронизацию мобильного приложения; ошибки никогда не отнимают очки.
- Pul **резервируется при записи** на платное событие, **списывается только при подтверждённом присутствии** и **возвращается** при отмене, неявке или отмене события платформой — поэтому нет отрицательного баланса и процедуры возврата.
- **Аванс** — флаг события, одинаковый для всех врачей; ссылка прихода только записывает источник. Аванс — обязательство, погашаемое будущими начислениями Pul, с потолком 150 Pul на персону; он никогда не становится отрицательным балансом и никогда не закрывает открытый контент.
- Модель чтения **лидерборда** — месячная, по специальности, по согласию — ранжирует 2·Con + Bre, заработанные за календарный месяц; баланс Pul никогда не ранжирует.
- Фича **036** получает **агрегаты внимания** по проекту и выходу, собранные из проводок с версиями правил, без строк по отдельным врачам.

## Границы

**Входит:**

- **Реестр**: счета персон и системные счета, которые нужны двойной записи (дизайн ADR-0016 §2.11), проводки (§2.12) с номиналом, уникальным `event_id`, ключом дедупликации и версией правила; триггер неизменяемости и месячные партиции по ADR-0003 §3 — по образцу работающего `audit_ledger`.
- **Движок начислений**: приём доменных фактов-источников начисления из модели событий, вычисление активной версии правила, запись проводок и выпуск `PointsCredited`.
- **Книга правил**: версионируемые правила начисления, цены событий и режимы гейтинга, потолок аванса, реферальный лимит, доля присутствия, лимит одновременных резервов и формула лидерборда — каждое с умолчанием из PRD.
- **Сторона трат**: решение гейтинга, резерв / списание / снятие резерва, аванс и его обязательство, погашение будущими начислениями.
- **Сторона чтения** через API: собственные балансы и история врача, решение гейтинга для одного врача и одного события, модель чтения месячного лидерборда, агрегаты внимания для 036.
- **Admin API** правил, цен и режимов гейтинга и компенсирующих исправлений, каждое изменение — с записью аудита.
- **Шов удаления данных**: закрытие и заморозка счёта персоны.

**Не входит (у каждого пункта есть владелец):**

- **Все экраны.** Строка цены, прогресс аванса, подсказка порога и денежное утверждение «бесплатно для врача», отвязанное от `pulCost`, на странице события — фича **020**, согласование в [#3801](https://github.com/doctor-school/ds-platform/issues/3801); обещание при регистрации и начисление в состоянии успеха — фича **021**, согласование в [#3801](https://github.com/doctor-school/ds-platform/issues/3801); три баланса, открытый аванс и история проводок в кабинете — фича **022**, Issue [#1791](https://github.com/doctor-school/ds-platform/issues/1791); блок лидерборда специальности по согласию и переключатель согласия — фича **018**, Issue [#1495](https://github.com/doctor-school/ds-platform/issues/1495); экраны обучения — фича **024**; мобильное приложение — свой трек (функциональная карта, решение владельца 2026-08-22), потребляющий этот API.
- **Экраны администратора** для правил, цен, режимов гейтинга и исправлений. 025 поставляет только admin **API**; admin UI отложен в отдельный Issue, который ведущий открывает вместе с набором EARS (`open-ears-issues`); тот Issue владеет поверхностью в `apps/admin` и её браузерной проверкой.
- **Лист ожидания** на событиях с ограниченным числом мест — регистрация на событие (**020** / **005**); 025 только отказывает в резерве сверх лимита одновременных резервов (EARS-21).
- **Само подтверждение присутствия** — presence beats и факт присутствия принадлежат комнате и регистрации на событие; 025 потребляет факт подтверждённого присутствия и владеет только параметром доли присутствия, по которому он считается (EARS-9).
- **Подтверждение телефона и проверка профиля** — аккаунта (фича **022**, поверх **003**); 025 потребляет факты.
- **Деньги** — биллинг спонсоров, счета, денежная сторона агрегатов внимания и именные отчёты для спонсора по отдельному согласию ст. 9 — фича **036**.
- **Стоки следующей волны**, Pul за партнёрский или промо-контент, рекламный коэффициент, аналитика аномалий для администратора — не на запуске (PRD, «Вне рамок»).

## Ограничения

- **Одно семейство реестра.** Нигде нет колонки баланса, нет второго реестра, нет счёта на витрину; денежная единица того же семейства принадлежит 036 и здесь не пишется.
- **Проводки неизменяемы.** Ни UPDATE, ни DELETE не доходят до строки проводки — это обеспечивает база данных, а не только код; исправление — новая проводка, которая называет ту, что сторнирует.
- **Каждое число — параметр.** Ни одна сумма начисления, цена, лимит, доля или вес не записаны литералом в коде; каждое читается из активной версии правила и проставляется в проводку, которую порождает.
- **Правила зависят только от внимания.** Ни один вход правила не читает источник прихода, спонсора, назначение, продажу или спонсорскую ценность для отдельного врача (323-ФЗ ст. 74, кодекс AIPM — «Комплаенс-ограничения» PRD); источник прихода записывается в проводку только как атрибуция.
- **Pul — не деньги.** Ни одно поле API, problem detail или текст администратора не выражает сумму Pul в деньгах, не называет цену в Pul «бесплатно» и не называет очки «баллами» в смысле НМО; ни одно поле не выводит утверждение «бесплатно» из нулевой цены в Pul.
- **Уроки никогда не стоят Pul**, а события никогда не начисляют Pul; событие с аккредитацией НМО всегда открыто.
- **Никакого наследия очков.** В реестр ничего не переносится со старой платформы.
- **Только серверные свидетельства.** Начисление за урок и модуль — только по вычисленным фактам завершения 024, за событие — только по серверному факту присутствия; завершение, заявленное клиентом, никогда не источник начисления.

## Предшествующие решения

- **ADR-0016 §6 + дизайн §2.11–§2.12:** одно append-only семейство реестра; счета реестра по субъекту (`person` · `project_fund` · `organisation` · `system`) с единицей `attention_points` | `money`; неизменяемые проводки двойной записи с проектом, выходом, `rule_id` / `rule_version`, субъектом атрибуции (организация, участник) и `reverses_posting_id`; баланс — свёртка; при удалении данных счёт закрывается и замораживается, проводки никогда не переписываются.
- **ADR-0003 §2.7 / §3:** append-only с уникальным `event_id`, триггером, отказывающим в UPDATE/DELETE, и месячными партициями — образец — работающий `audit_ledger` (`packages/db/src/schema/audit-ledger.ts`).
- **Согласование, записанное здесь (без правки ADR в этом PR).** ADR-0003 описывает одну таблицу реестра с уникальным `event_id`; ADR-0016 §2.12 — счета и проводки без `event_id`. 025 сохраняет двухтабличную форму ADR-0016 и даёт **каждой проводке уникальный `event_id`** (ключ идемпотентности факта, который её породил) — выполняются оба ограничения. Перечисление единиц ADR-0016 остаётся `attention_points` | `money`; три единицы PRD — это **`denomination`** (`pul` · `bre` · `con`) у проводки с единицей `attention_points`, поэтому у персоны остаётся **один** счёт очков внимания (§2.11), а не три. Оба пункта — объявленные приращения к таблице дизайна ADR-0016; их вносит `do-adr-revision`, когда реестр поставлен.
- **ADR-0009:** согласие на распространение в лидерборде (152-ФЗ ст. 10.1) — ещё одна версионируемая запись по цели в `consent_records`; 025 не заводит своего хранилища согласий.
- **ADR-0001:** врач читает только свой счёт; admin API требует роли администратора; потребители передают факты сервис-сервис, никогда — токеном одного врача на счёт другого.
- **Владелец, 2026-11-06 (Issue #1794):** аванс — флаг события для всех врачей; каждое начисление — настраиваемый параметр, и каждая проводка записывает версию правила; никакого наследия очков.

## Модель событий

### Команды

- `AccrueFromFact({ eventId, personId, action, contentRef?, projectId?, occurredAt, attribution? })` — внутренняя; её выдаёт политика, принимающая факт-источник начисления. Идемпотентна по `eventId` и по ключу дедупликации.
- `ReserveForSignUp({ personId, eventRef, registrationId })` — внутренняя; по `RegistrationCreated` из 020 для события с ценой в Pul. Может получить отказ (`points-threshold-short`, `points-reserve-limit`).
- `SettleReserve({ registrationId })` — внутренняя; при подтверждённом присутствии.
- `ReleaseReserve({ registrationId, reason: 'doctor-cancel' | 'event-cancel' | 'event-reschedule' | 'no-show' })` — внутренняя.
- `PublishRuleVersion({ ruleId, parameters, effectiveFrom? })` — admin API `POST /v1/admin/points/rules/:ruleId/versions`.
- `SetContentGating({ contentRef, mode: 'open' | 'advance' | 'threshold', pulCost, limitedSeats })` — admin API `PUT /v1/admin/points/gating/:contentRef`.
- `PostCorrection({ reversesPostingId, reason })` / `PostManualAdjustment({ personId, denomination, amount, reason })` — admin API `POST /v1/admin/points/corrections`.
- `CloseAccount({ personId, cause: 'erasure' | 'consent-refusal' })` — внутренняя; её выдаёт жизненный цикл персональных данных (037 / процедура удаления ADR-0009).

### Политики

- Факт-источник начисления превращается в проводки только через версию правила, активную на `occurredAt` факта; перенастроенное правило никогда не переписывает прошлые проводки.
- Проводка, которая опустила бы доступный Pul персоны ниже нуля, отклоняется; цену покрывают резервы и авансы, а не долги.
- Источник прихода записывается в поля атрибуции проводки и не читается ни одним правилом.
- Закрытый счёт не принимает новых проводок.

## Требования EARS

> Плоская нумерация по ADR-0006 §4. Каждое требование несёт `realizes: US-N` по [`025-product-ru.md`](./025-product-ru.md) и помечено тегом в [`025-scenarios.feature`](./025-scenarios.feature). Умолчания в квадратных скобках — параметры версии правила (EARS-25), никогда не литералы.

- **EARS-1** _(realizes: US-1, US-15)_ — Когда движку впервые нужен счёт очков внимания персоны (первый факт начисления или первое чтение по этой персоне), система должна открыть **ровно один** счёт реестра с `subject_kind = person`, `unit = attention_points` для этой персоны, уникальный по (`subject_id`, `unit`), и каждая витрина, Академия, мобильное приложение и каждая фича-потребитель должны получать этот же счёт через один API; счетов на витрину или на устройство быть не должно.
- **EARS-2** _(realizes: US-1, US-15)_ — Когда врач со входом запрашивает `GET /v1/me/points`, система должна вернуть модель чтения `PointsAccount`, вычисленную как **свёртка проводок** — доступный и зарезервированный Pul, Bre, Con и открытый аванс с остатком обязательства, — нигде не читая и не записывая изменяемую колонку баланса, и тот же запрос с любого клиента должен возвращать те же значения; запрос счёта другой персоны должен отклоняться (403).
- **EARS-3** _(realizes: US-2, US-3, US-12, US-15)_ — Когда принят факт-источник начисления из модели событий, система должна вычислить версию правила, **активную на `occurredAt` факта**, для этого действия и записать по одной неизменяемой проводке двойной записи на каждый ненулевой номинал (с системного счёта выпуска на счёт персоны) с уникальным `event_id` факта, ключом дедупликации, номиналом, `rule_id` и `rule_version`, проектом и выходом, когда факт их называет, субъектом атрибуции, когда он записан, `occurred_at` и `recorded_at`, всё в одной транзакции, после чего выпустить `PointsCredited` — единственное событие, по которому потребитель может утверждать начисленную сумму.
- **EARS-4** _(realizes: US-4, US-1)_ — Когда приходит факт-источник начисления, чей `event_id` или чей ключ дедупликации **(персона, единица контента, действие)** уже имеет проводку, — пришёл ли он с другой витрины, из Академии, повтором или из офлайн-синхронизации мобильного приложения, — система **не** должна записывать проводку и должна ответить исходным результатом (`duplicate` со ссылкой на существующие проводки), чтобы повторённый или одновременный факт никогда не начислялся дважды; уникальность должна обеспечиваться ограничениями базы данных, а не только чтением перед записью.
- **EARS-5** _(realizes: US-2)_ — Когда телефон зарегистрированного врача становится подтверждённым (выполнены и `DoctorRegistered`, и `PhoneVerified`, в любом порядке), система должна начислить **грант за регистрацию** [+20 Pul] один раз на персону; Pul персоны с неподтверждённым телефоном не должен быть тратимым.
- **EARS-6** _(realizes: US-2, US-3)_ — Когда фича 022 сообщает `ProfileVerified` по врачу, система должна начислить **грант за профиль** [+30 Pul, +2 Bre] один раз на персону.
- **EARS-7** _(realizes: US-2, US-3, US-4)_ — Когда фича 024 сообщает `LessonCompleted` — свой вычисленный статус завершения, который уже требует времени просмотра или пройденного теста, — система должна начислить **награду за урок** [+10 Pul, +1 Bre] один раз на (персона, урок); когда `mode` завершения — офлайн или открытое обучение, Pul-компонента не начисляется (только Bre и Con); ошибка в тесте, неудачная попытка или повторное прохождение никогда не должны порождать списывающую проводку; подкаст, завершённый вне своего урока, не начисляет ничего.
- **EARS-8** _(realizes: US-2, US-3)_ — Когда фича 024 сообщает `ModuleCompleted` (все уроки пройдены и тест модуля сдан), система должна начислить **награду за модуль** [+20 Pul, +3 Bre, +1 Con] один раз на (персона, модуль) с тем же правилом офлайн/открытого обучения для Pul-компоненты, что в EARS-7.
- **EARS-9** _(realizes: US-3, US-5)_ — Когда приходит `AttendanceConfirmed` по регистрации, чья серверная доля присутствия не меньше настроенной **доли присутствия** [30 % длительности события], система должна начислить **награду за участие** [+2 Bre, +1 Con] один раз на (персона, событие), одинаково при любой цене и для открытых событий, и **не** должна начислять Pul ни за какое событие; доля присутствия ниже параметра не считается присутствием.
- **EARS-10** _(realizes: US-3, US-4)_ — Когда сообщается вопрос врача спикеру, оценка события или интерактивный ответ во время эфира, система должна начислить **награду за вовлечённость** [+1 Bre за каждое] не более **одного раза на (персона, событие, действие)**; повторное сообщение того же действия по тому же событию — `duplicate` по EARS-4.
- **EARS-11** _(realizes: US-2, US-3, US-8)_ — Когда у приглашённого, пришедшего по реферальной ссылке врача, есть и подтверждённый телефон, и первый завершённый урок, система должна начислить **реферальную награду** пригласившему [+30 Pul, +2 Bre] и приглашённому [+30 Pul], каждую один раз на приглашённого; когда пригласивший уже получил **месячный реферальный лимит** [5 за календарный месяц, Europe/Moscow], награда пригласившему за этого приглашённого не проводится, а награда приглашённому проводится.
- **EARS-12** _(realizes: US-4, US-3)_ — Система **не** должна записывать проводку, списывающую Bre или Con со счёта персоны, кроме компенсирующей проводки, сторнирующей конкретное прежнее начисление (EARS-28); ни одно правило не выражает штраф, и ни одна проводка не конвертирует номиналы (1 Con = 2 Bre — только вес на стороне чтения).
- **EARS-13** _(realizes: US-7, US-15)_ — Когда врач со входом запрашивает `GET /v1/me/points/gating/:contentRef`, система должна вернуть `GatingDecision` для этого врача: `open` для открытой единицы и любого урока; для платного события — `reserve`, когда доступный Pul покрывает цену, `reserve-with-advance` в режиме аванса, когда недостача укладывается в потолок аванса (EARS-16), иначе `short` с точной **недостачей** и `earnHint` — числом уроков, нужных при активной награде за урок, — никогда не отрицательное число и никогда не решение «не хватает» в режиме аванса в пределах потолка.
- **EARS-14** _(realizes: US-5)_ — Когда 020 сообщает `RegistrationCreated` по событию с ценой в Pul > 0 и доступный Pul врача её покрывает, система должна **зарезервировать** цену проводкой со счёта персоны на системный счёт резерва со ссылкой на регистрацию и событие; открытое событие или нулевая цена не порождают проводки.
- **EARS-15** _(realizes: US-6, US-8)_ — Когда 020 сообщает `RegistrationCreated` по событию **в режиме аванса**, а доступный Pul меньше цены, система должна зарезервировать доступный Pul из баланса и покрыть **ровно недостачу** авансовой проводкой с системного счёта аванса, открыв персоне обязательство на эту сумму; решение должно быть одинаковым для каждого врача на этом событии и не должно читать источник прихода.
- **EARS-16** _(realizes: US-6)_ — Если открытие аванса подняло бы открытые обязательства персоны выше **потолка аванса** [150 Pul, считается на персону], то система должна считать событие **пороговым** для этого врача (EARS-17); открытое обязательство никогда не закрывает действие без резерва — открытые события и уроки остаются открытыми — и никогда не представляется API как отрицательный баланс.
- **EARS-17** _(realizes: US-7)_ — Когда 020 просит резерв по событию **в режиме порога** (или по событию в режиме аванса сверх потолка), а доступный Pul меньше цены, система должна отклонить резерв с RFC 7807 problem `points-threshold-short`, несущим недостачу и `earnHint` из EARS-13, не записать проводку и оставить запись на событие закрытой отказом в 020.
- **EARS-18** _(realizes: US-5, US-6)_ — Когда зарезервированная регистрация отменена врачом в любое время, событие отменено или перенесено платформой, или событие закончилось без `AttendanceConfirmed` по этой регистрации в пределах окна расчёта (неявка), система должна **снять** резерв компенсирующей проводкой (`reverses_posting_id` → резерв) и аннулировать аванс, использованный на это событие, вместе с его обязательством компенсирующей проводкой; при неявке награда за участие не начисляется; других последствий нет.
- **EARS-19** _(realizes: US-5)_ — Когда приходит `AttendanceConfirmed` по зарезервированной регистрации (правило присутствия EARS-9), система должна **списать** резерв проводкой с системного счёта резерва на системный счёт стока со ссылкой на резерв, ровно один раз на регистрацию.
- **EARS-20** _(realizes: US-6)_ — Когда персоне с открытым обязательством начисляется Pul, система должна сначала **погасить обязательство** проводкой со счёта персоны на системный счёт аванса на `min(начисленный Pul, остаток обязательства)` в той же транзакции, начиная со старейшего обязательства, и выпустить `AdvanceSettled` с остатком.
- **EARS-21** _(realizes: US-5)_ — Если резерв дал бы персоне больше **лимита одновременных резервов на события с ограниченным числом мест** [3 открытых резерва], то система должна отклонить его с problem `points-reserve-limit` и не записать проводку; лист ожидания остаётся за 020.
- **EARS-22** _(realizes: US-5, US-4)_ — Система должна отклонять любую проводку, которая опустила бы **доступный Pul** персоны **ниже нуля**, сериализуя проводки по счёту персоны, чтобы одновременные резервы не могли его перерасходовать, и не должна записывать проводок истечения по времени — Pul не сгорает.
- **EARS-23** _(realizes: US-9)_ — Когда запрашивается `GET /v1/points/leaderboard/:specialtyCode?month=YYYY-MM`, система должна вычислить среди врачей этой специальности с **активным согласием `leaderboard-dissemination`** счёт **[2]·Con + [1]·Bre, заработанные в этом календарном месяце** (начисления месяца за вычетом их сторно; баланс Pul никогда не ранжирует), ранжировать только этих врачей и вернуть первые [10] плюс — для врача со входом — его собственное место и счёт с [5] соседями выше и ниже; врач без согласия получает своё возможное место приватно и никогда не появляется в ответе другого врача и не сдвигает номера мест в нём.
- **EARS-24** _(realizes: US-9)_ — Строка врача в лидерборде должна существовать только пока активно отдельное версионируемое согласие `leaderboard-dissemination` (152-ФЗ ст. 10.1), выключенное по умолчанию, с выбором имени врача (фамилия с инициалами или псевдоним) и отдельными флагами города и фото; когда согласие отозвано, строки нет уже в следующем ответе лидерборда.
- **EARS-25** _(realizes: US-11, US-12)_ — Когда администратор публикует версию правила через `POST /v1/admin/points/rules/:ruleId/versions`, система должна проверить её параметры по схеме правила (суммы начисления по действию и номиналу, лимиты, доля присутствия, потолок аванса, реферальный лимит, лимит одновременных резервов, веса и размеры лидерборда — набор действий закрытое перечисление без входов назначения, продажи, спонсора или источника прихода), сохранить её как новую неизменяемую версию, действующую с момента публикации или с более позднего `effectiveFrom`, записать аудит и применять её к проводкам, созданным после, без релиза; прошлые проводки сохраняют свою версию.
- **EARS-26** _(realizes: US-11)_ — Когда администратор задаёт гейтинг единицы через `PUT /v1/admin/points/gating/:contentRef`, система должна принять для события `open`, `advance` или `threshold` с ценой в Pul [стандарт 50, премиум или с ограниченным числом мест 100], отклонить любой режим, кроме `open`, для урока или модуля, отклонить любой режим, кроме `open`, для события с аккредитацией НМО (problem `points-gating-invalid`), записать аудит и применять изменение к резервам, созданным после; существующие резервы сохраняют цену, по которой были сделаны.
- **EARS-27** _(realizes: US-12)_ — Каждая проводка должна нести непустые `rule_id` и `rule_version` (сторно несёт версию сторнируемой проводки), что обеспечивает ограничение базы данных, а строка проводки должна получать отказ в UPDATE и DELETE от триггера базы данных; проводки партиционируются по месяцу `occurred_at`, как `audit_ledger`.
- **EARS-28** _(realizes: US-13)_ — Когда администратор проводит исправление через `POST /v1/admin/points/corrections` — сторно названной проводки или ручную корректировку с обязательной причиной, — система должна записать его новой компенсирующей проводкой (`reverses_posting_id` для сторно, правило `manual-correction` для корректировки), отклонить повторное сторно той же проводки, записать в `audit_ledger` администратора, причину и id проводок и никогда не изменять и не удалять существующую проводку; ручная корректировка не должна опускать доступный Pul ниже нуля (EARS-22).
- **EARS-29** _(realizes: US-14)_ — Когда 036 запрашивает `GET /v1/admin/points/aggregates` по проекту (опционально по выходу и месяцу), система должна вернуть суммы по номиналу, id правила и версии правила вместе с числом различных персон, собранные из проводок, и **не** должна возвращать идентификаторов персон; именные данные — у 036 по её отдельному согласию.
- **EARS-30** _(realizes: US-10, US-15)_ — Каждый ответ API движка, несущий сумму Pul, должен отдавать её целым `pulCost` / `amount` с единицей `Pul`, **не** должен отдавать поле, выводящее «бесплатно» или денежное утверждение из нулевой цены в Pul, и ни один problem detail, текст администратора или имя поля не называет цену в Pul «бесплатно», а очки — «баллами»; денежное утверждение принадлежит потребителю и независимо от `pulCost` (020, #3801).
- **EARS-31** _(realizes: US-1, US-13)_ — Когда жизненный цикл персональных данных закрывает счёт персоны по удалению данных или отказу от согласия, система должна проставить `closed_at` счёту, отклонять каждую последующую проводку на него (problem `points-account-closed`), сама не снимать резервы и не гасить обязательства и оставить каждую существующую проводку без изменений; субъект проводки перенаправляется только процедурой удаления ADR-0009.

## Инварианты

- У одной персоны не больше одного открытого счёта очков внимания.
- Баланс каждого номинала равен свёртке его проводок; хранимого баланса нет.
- Ни одна строка проводки никогда не изменяется и не удаляется; у каждой проводки уникальный `event_id`, непустые id и версия правила.
- У ключа дедупликации (персона, единица контента, действие) не больше одного набора проводок начисления.
- Доступный Pul никогда не ниже нуля; Bre и Con уменьшаются только сторно конкретного начисления.
- Ни одно событие не начисляет Pul; ни один урок или модуль не стоит Pul; событие с аккредитацией НМО всегда открыто.
- Источник прихода никогда не меняет решение гейтинга, цену или начисление.
- Открытые обязательства персоны никогда не превышают активный потолок аванса.
- Ответ лидерборда содержит только врачей с активным согласием на распространение, ранжированных между собой.
- Агрегат внимания не содержит идентификаторов персон.

## Зависимости и порядок

- **Сначала реестр** (EARS-1, 3, 4, 22, 27) — все остальные требования проводят через него.
- **Источники начисления ждут своих производителей**: EARS-5/6 — `PhoneVerified` / `ProfileVerified` из 022 (Issue #1791), EARS-7/8 — фактов завершения 024, EARS-9/10/18/19 — фактов регистрации и присутствия 020. Непоставленный производитель оставляет требование неисполнимым, а не заглушенным; требование движка поставляется со своим e2e на реальном факте, когда производитель существует.
- **Траты** (EARS-13–21) предшествуют платным событиям 020; `eventEconomyFacts()` сохраняет `pulCost: 0` (`DEBT.md`), пока EARS-26 не даст событиям реальных цен.
- **Лидерборд** (EARS-23/24) предшествует 018 #1495; **агрегаты** (EARS-29) — 036.
- **Admin UI** для EARS-25/26/28 — отдельный Issue, открываемый вместе с этим набором.

## Открытые вопросы, перенесённые дальше

Для Product Lead; спроектировано в обход, а не решено здесь:

- **Обмен Con↔Bre, видимый врачу** — по умолчанию только вес (EARS-12, EARS-23); видимый врачу обмен был бы новым видом проводки, а не изменением схемы.
- **Веса биллинга спонсора** для Con, Bre и Pul (036) — каждая проводка несёт версию правила (EARS-27), поэтому любое взвешивание можно пересчитать из EARS-29.
- **Окно расчёта неявки** — время после `EventEnded`, после которого неподтверждённый резерв снимается; параметр книги правил с предлагаемым умолчанием 24 часа (дизайн §5).
