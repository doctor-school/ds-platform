# 028 — Правовые страницы (Требования)

## Результаты

- Один общий набор правовых документов (Markdown, версионируется в репозитории), читается через один общий каркас страницы на каждом хосте — `apps/doctor` (оболочка 017) и `apps/portal` (оболочка 008) — никогда две форкнутые копии одного текста.
- Каждое согласие, которое врач отмечает при регистрации (021), открывается как настоящая читаемая страница, дословно тот же текст, по URL, стабильному при будущих правках.
- Посетитель без чекбокса в руках всё равно может найти те же документы, реквизиты юрлица и рабочий канал связи с любой страницы на обоих хостах.

## Область

- Страница «Документы и контакты» на `apps/doctor` и на `apps/portal`, каждая в оболочке своего хоста.
- Страница чтения документа (один общий компонент, проекция на хост), список документов R1 (одна строка: Политика персональных данных и согласия), страницы документов для каждого согласия 021, страница согласия на фото/видео.
- Блок контактов (mailto + чипы Telegram/ВКонтакте/YouTube) и строка реквизитов (юрлицо · ИНН · ОГРН · адрес — без лицензии).
- Никакой подписи или ссылки на Академию в списке документов врача и никакого ответного выхода в списке Академии: ссылка в футере витрины остаётся единственным выходом в Академию (REQ-24, EARS-6).
- Удаление всех ссылок на старый сайт, включая перенаправление `ACADEMY_PRIVACY_POLICY_URL`.

### Вне области

- Блок лицензии (строка в списке документов + номер лицензии в строке реквизитов, **US-11**) — слайс 2, решение владельца 2026-09-06 («Данных лицензии нет, не выводим её сейчас!»).
- **US-5** — понятное для человека объяснение обращения с персональными данными — слайс 1 публикует только дословный юридический текст политики/согласий, а не его понятный пересказ; такой пересказ — вход владельца/юриста, не инженерная задача.
- «Пользовательское соглашение» — слайс 2, решение владельца 2026-09-06.
- «Правила начисления очков» — слайс 2; текст пишет и владеет им фича 025, 028 только публикует.
- Документы R3 (договоры, устав, документы бирюзовой модели) и условия оплаты/возврата — слайс 2, `blocked_by` **037** (жизненный цикл персональных данных для формулировок хранения/версионирования).
- Админ-интерфейс для авторинга документов — контент поставляется как проверенный Markdown в этом репозитории; без CMS.
- Сама юридическая формулировка текстов (политика/согласия) — вход от владельца/юриста, не инженерная задача.

## Ограничения

- Без CMS, без таблицы в БД, без админ-экрана — документы это файлы в `packages/legal-content/`, проверяются как код.
- Документ без утверждённого контента отсутствует, никогда не заглушка и не «скоро» (правило владельца, 2026-08-27: скрывать блок до появления контента).
- Ни одна поверхность не может ссылаться на `doctor.school/index/*` (старый сайт).

## Prior decisions

- ADR-0013 §A1 — переиспользование межфронтенд-возможностей: канвасы `design-source/doctor-docs.dc.html` / `academy-docs.dc.html` — источник истины этапа A для обеих страниц; решение об одном общем наборе ниже реализует правило канонического ядра ADR-0013 §A1.
- Развилка канваса 1 (`docsVariant: Б`) — каждый хост показывает свою проекцию одного общего правового набора; каноническая логика и контент существуют один раз, только тонкая проекция на хост (AGENTS.md §6, переиспользование между фронтами).
- Развилка канваса, промпт 21 (`tocVariant: А`) — прилипающее оглавление слева при 1440, свёрнутый список над текстом при 390.
- Развилка канваса 2, промпт 21 (`doc: короткий`) — каждое согласие 021 и согласие на фото/видео — своя страница документа в коротком варианте, никогда не дополнительная строка в списке.
- REQ-24 сохраняет два размещения (ссылка в футере и «Стать экспертом»); список документов 028 не добавляет третьего — решение владельца на этапе B 2026-09-07, EARS-6.

## Модель контента (уровень дизайна; детали в `028-design.md`)

Документы — файлы Markdown в новом общем пакете `packages/legal-content/`, фронтматтер `slug` / `title` / `edition` (дата ISO) / `kind: policy | consent`. Один общий компонент чтения в `packages/design-system` рендерит любой документ; `apps/doctor` и `apps/portal` добавляют только тонкий роут + проекцию списка. Импорты между приложениями запрещены.

## Требования EARS

- **EARS-1** (`realizes: US-3, US-6`) — КОГДА посетитель запрашивает страницу «Документы и контакты» витрины врача, СИСТЕМА ДОЛЖНА отрендерить её в оболочке 017 со списком документов, блоком контактов и строкой реквизитов.
- **EARS-2** (`realizes: US-3, US-6`) — КОГДА посетитель запрашивает страницу «Документы и контакты» Академии, СИСТЕМА ДОЛЖНА отрендерить её в оболочке 008 с теми же тремя блоками из того же общего набора документов.
- **EARS-3** (`realizes: US-2`) — ПОКА действует слайс 1, СИСТЕМА ДОЛЖНА показывать ровно одну запись в списке документов на обоих хостах — «Политика персональных данных и согласия» — и НЕ ДОЛЖНА показывать строки лицензии, «Пользовательского соглашения» или «Правил начисления очков», нарисованные на канвасах.
- **EARS-4** (`realizes: US-12`) — СИСТЕМА ДОЛЖНА рендерить блок контактов с `support@doctor.school` (врач) или `academy@doctor.school` (Академия) как ссылку `mailto:` плюс чипы Telegram/ВКонтакте/YouTube, с подписями точно как нарисовано на канвасе этого хоста.
- **EARS-5** (`realizes: US-9, US-10`) — СИСТЕМА ДОЛЖНА рендерить одну строку реквизитов на обоих хостах вида «ООО «Ивекскон» · ИНН <…> · ОГРН <…> · <юридический адрес>», без номера лицензии в R1.
- **EARS-6** (`realizes: US-3`) — СИСТЕМА НЕ ДОЛЖНА размещать в списке документов врача никакой подписи или ссылки на Академию: единственный переход витрины в Академию — ссылка в футере (REQ-24), и второй выход с этой страницы ему противоречит. Список Академии так же НЕ ДОЛЖЕН содержать встречной подписи на витрину врача.
- **EARS-7** (`realizes: US-4, US-13, US-14`) — КОГДА посетитель открывает собственный URL документа, СИСТЕМА ДОЛЖНА отрендерить его заголовок, «редакция от <дата>», оглавление (прилипающая левая колонка при ≥1440px, свёрнутое над текстом при ≤390px — `tocVariant: А`), тело, ссылку назад к списку документов и список «Другие документы» с остальными опубликованными документами.
- **EARS-8** (`realizes: US-1, US-2, US-7`) — КОГДА врач открывает ссылку согласия рядом с чекбоксом регистрации 021, СИСТЕМА ДОЛЖНА открыть страницу именно этого согласия (короткий вариант `doc`) на том же хосте, дословно текст чекбокса, не теряя уже заполненную форму регистрации.
- **EARS-9** (`realizes: US-2`) — СИСТЕМА ДОЛЖНА публиковать каждый из трёх текстов согласий 021 (декларация медработника, согласие на передачу данных партнёрам, согласие на рассылку) и согласие на распространение фото/видео как собственную страницу документа, никогда как строку в списке.
- **EARS-10** (`realizes: US-16, US-17`) — КОГДА текст документа исправлен и переопубликован, СИСТЕМА ДОЛЖНА сохранить его URL неизменным, чтобы ссылки из текста согласий, формы регистрации и сохранённых записей согласий продолжали указывать на тот же документ.
- **EARS-11** (`realizes: US-4, US-16`) — КОГДА документ переопубликован с новой датой редакции, СИСТЕМА ДОЛЖНА показать чип «обновлено» в его строке списка документов; СИСТЕМА НЕ ДОЛЖНА показывать числовой номер версии нигде на этой поверхности.
- **EARS-12** (`realizes: US-18`) — ПОКА у документа нет утверждённого владельцем контента, СИСТЕМА ДОЛЖНА полностью скрывать его строку и его страницу — без заглушки, без состояния «скоро».
- **EARS-13** (`realizes: US-8, US-15`) — СИСТЕМА ДОЛЖНА направлять `ACADEMY_PRIVACY_POLICY_URL` и каждую ссылку согласия/футера на собственные документы этой поверхности и НЕ ДОЛЖНА нигде ссылаться на `doctor.school/index/*`.
- **EARS-14** (`realizes: US-13`) — СИСТЕМА ДОЛЖНА рендерить каждый документ и страницу списка читаемо при 390px и 1440px, в светлой и тёмной теме, используя только примитивы и типографику `packages/design-system`.
- **EARS-15** (`realizes: US-14`) — СИСТЕМА ДОЛЖНА проходить гейт `playwright-axe` на странице списка документов и странице документа, с настоящей структурой заголовков и ссылками, называющими свою цель.

## Инварианты

- Один общий набор документов, читаемый обоими хостами — никогда форкнутая по хостам копия одного текста (US-6, AGENTS.md §6).
- URL документа стабилен при правках текста (EARS-10); меняются только дата редакции и чип «обновлено».
- Документ без утверждённого контента никогда не рендерится (EARS-12) — заглушка для пользователя на этой поверхности является дефектом, а не допустимой заменой.
