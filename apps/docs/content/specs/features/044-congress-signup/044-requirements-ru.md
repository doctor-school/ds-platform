# 044 — Регистрация на конгресс (Требования)

## Результаты

- Регистрация на конгресс, отправленная на сайте конгресса, становится, одной транзакцией, аккаунтом Doctor.School и регистрацией в существующей таблице `registrations` — участник никогда не регистрируется повторно.
- Приём заявки неотличим снаружи вне зависимости от того, была ли у почты уже аккаунт, и идемпотентен при повторе: один аккаунт, одна регистрация, никакого сигнала перечисления.
- Типизированные ответы и принятое согласие живут на строке регистрации; собственный профиль уже существующего аккаунта никогда не переписывается неаутентифицированной формой.
- Организующая команда видит ровно одну вещь в `apps/admin` — реестр только для чтения по регистрациям этого мероприятия и печатный список участников, построенный из реестра в его текущем отфильтрованном виде — через новую грубую роль, которой отказано везде в остальном.

## Область

- Публичный, неаутентифицированный эндпоинт приёма заявки в `apps/api`, защищённый от ботов и ограниченный по частоте, достижимый same-origin через собственный nginx-прокси `/api` сайта конгресса.
- Окно регистрации на конгресс — моменты открытия и закрытия, удерживаемые как константы в собственном коде или конфигурации API и вычисляемые на этом эндпоинте до любого побочного эффекта.
- Нормализация отправленного контактного телефона и выводимая на чтении по ней отметка «возможный дубль», показываемая в реестре и в печатном списке.
- Безпарольный вариант создания аккаунта общего движка 003 (`AuthService.register`, `apps/api/src/auth/auth.service.ts:434`), включая создание пользователя-человека без учётных данных в порте IdP (`apps/api/src/auth/idp/idp.types.ts:279`, `:84`).
- Новая колонка ответов на `registrations` (`packages/db/src/schema/registrations.ts:42-93`) плюс её Zod-форма в `packages/schemas`, и новая запись исхода письма на той же строке.
- Одна строка `consent_records` на каждое принятие (`packages/db/src/schema/consent-records.ts:26-36`) под новой целью персональных данных конгресса.
- Публичный эндпоинт только для чтения списка специальностей над `specialties_minzdrav` (`packages/db/src/schema/specialties.ts:61-108`).
- Письмо-подтверждение: новый член семейства шаблонов, отправляемый вне пути ответа, с зафиксированным исходом.
- Роль `event-registrar` в `apps/api/src/authz/authz.types.ts:18-27`, HTTP-маршрут над `RegistrationService.eventRoster()` (`apps/api/src/registration/registration.service.ts:178-181` — маршрута сегодня нет), навигация админки с учётом роли, экран реестра и печатный список в `apps/admin`.
- Существующий платформенный путь регистрации для уже вошедшего врача (`RegistrationService.register`, `:84`) на опубликованном мероприятии с `participationFormat: offline`, приземляющийся в тот же реестр.

### Вне области

- **Разметка, внешний вид и клиентское поведение формы-заявки на сайте конгресса** — владеет `doctor-school/orthobio-site#78` в этом репозитории. Каждый EARS ниже, чей триггер называет форму, владеет только платформенной стороной этой заявки; сама поверхность формы отложена в этот отслеживаемый Issue и не является поставкой здесь.
- **Зависимости на стороне сайта** — nginx-прокси `/api` и ослабление `form-action 'none'` CSP сайта заявлены как зависимости в `doctor-school/orthobio-site#78`, а не как требования этой спеки.
- **CSV / экспорт** — владелец, дословно: «пока, наверное, этого не делаем». Печатный список из отфильтрованного реестра — единственный выходной формат v1.
- **Редактирование и удаление в админке** — владелец, дословно: «Пока только просмотр. Удаление по запросу будем делать вручную.»
- **Вторая форма ответов на платформе** для пути уже вошедшего врача в v1 (EARS-16 называет, что вместо неё показывает реестр).
- **Очередь повторов или outbox для письма-подтверждения** — EARS-11 называет путь восстановления вместо этого.
- **Редактируемое из админки окно регистрации** — моменты открытия и закрытия для этого конгресса — константы; их изменение — это деплой, а не настройка.
- **Предел вместимости, счётчик мест или лист ожидания** — окно является единственной границей приёма заявок (EARS-28).
- **Автоматическое слияние или отклонение регистраций с одинаковым телефоном** — платформа только помечает их; разрешение настоящего дубля — это ручное удаление по запросу силами команды (EARS-30).
- Микросайт конгресса (фича **026**), конструктор мероприятий (фича **041**) и миграция исторической базы (фича **043**).
- Шаг подтверждения по почте до того, как регистрация засчитывается — владелец, дословно: «Если ты хочешь прийти на мероприятие, ты укажешь свою почту. Укажешь чужую - не попадёшь.»

## Ограничения

- У API нет CORS и не будет: единственный браузерный путь с сайта конгресса — same-origin через собственный nginx-прокси `/api` этого сайта. Исходящий адрес прокси должен быть в `TRUSTED_PROXIES` (`apps/api/src/config/trust-proxy.ts:97-120`), иначе каждая заявка ограничивается по частоте против прокси вместо клиента (`rate-limit.types.ts`, ключ = идентификатор + `request.ip`, `:57-62`, `:32-36`).
- Защита от ботов включается по маршруту через декоратор `@BotProtected` (`apps/api/src/bot-protection/bot-protection.guard.ts`) над Yandex SmartCaptcha (`smart-captcha.provider.ts`); она не активна платформенно и должна быть объявлена на маршруте приёма заявки.
- `users.phone` уникален и является идентификатором входа (`packages/db/src/schema/users.ts:29-101`); непроверенный введённый телефон никогда не должен туда писаться.
- `registrations` уникальна по `(user_id, event_id)` — тотально, не частично (`registrations.ts:42-93`); это и есть механизм идемпотентности, новой таблицы заявок не заводится.
- `consent_records` только-для-добавления и неизменяема (`consent-records.ts:26-36`); `purpose` — свободный текст в БД, закрытый список живёт в `@ds/schemas`.
- Успешный вход по email-OTP **не** переключает `email_verified`, и email-непроверенный аккаунт никогда не получает код `otp_email` (`apps/api/src/auth/auth.service.ts:216-239`); единственные писатели проверенного состояния — выделенный путь верификации (`:684`) и завершение сброса пароля (`:413`).
- У `AdminDataList` (`apps/admin/components/admin-data-list.tsx:62-371`) есть пагинация, мгновенный поиск и фильтры по статусу, но **нет** поля сортировки в состоянии запроса — серверная сортировка новая.
- Нигде в `apps/admin` или `packages/design-system` сегодня нет ни стиля `@media print`, ни экспорта — печатному списку не на что опереться.

## Prior decisions

- ADR-0006 §4 — плоская нумерация `EARS-N`; состав триплета этого каталога.
- ADR-0014 §2 — каждый EARS ниже несёт `realizes: US-N` обратно к `044-product.md`.
- ADR-0009 §2.1 — идентификатор версии согласия, записываемый на каждое принятие, — это дата публикации статической страницы согласия плюс sha256 её опубликованного текста.
- ADR-0013 — реестр и печатный список собраны из примитивов `@ds/design-system` со стилизацией только токенами; реестр переиспользует одобренный владельцем Stage-A базовый набор админки, зафиксированный в `012-requirements-en.md:203` (EARS-18) — табличные Refine-композиции и исследованные блоки дизайн-системы, без нового круга опций.
- ADR-0001 §1, §8 — `event-registrar` — это инкрементальная грубая роль в модели групп IdP; источник истины авторизации — клейм ролей проекта Zitadel `urn:zitadel:iam:org:project:roles` (`zitadel.idp.ts:119`), а не зеркало `users.role`.
- ADR-0016 §1, §7 — путь по существующей почте прикрепляется к одному существующему человеку; согласия — версионируемые записи, никогда не флаги.
- Декларация медработника — предусловие только двери витрины врача (`doctor-register.service.ts:308-341`); ни один гейт нигде не читает `consent_records` при последующем запросе (recon §6). Аккаунт без этой строки — уже нормальное состояние для аккаунта, происходящего из Академии, поэтому аккаунту, происходящему из конгресса, не нужна никакая новая терпимость где бы то ни было — это граничная линия, а не требование.

## Модель событий

**Команды** — `SubmitCongressSignUp` (публичная, неаутентифицированная), `RegisterForEvent` (существующая, для аутентифицированного врача), `ListEventRoster` (регистратор), `PrintAttendanceSheet` (регистратор, на клиенте).

**События** — `CongressAccountCreated` (безпарольный), `CongressRegistrationRecorded`, `CongressConsentCaptured`, `ConfirmationEmailDispatched` / `ConfirmationEmailFailed`.

**Модели чтения** — реестр мероприятия (ответы регистрации, присоединённые к факту регистрации, несущие выводимую на чтении отметку «возможный дубль»), публичный список специальностей, печатный список (проекция текущего отфильтрованного реестра).

**Политики** — «сбой письма никогда не откатывает регистрацию»; «существующая почта никогда не переписывает профиль»; «повторная заявка — это no-op, который выглядит как первый успех».

## Требования EARS

### Пакет работ #2288 — публичный приём заявки

- **EARS-1** (`realizes: US-1, US-12`) — СИСТЕМА ДОЛЖНА выставлять приём заявки на конгресс как публичный, неаутентифицированный эндпоинт, несущий декоратор `@BotProtected` (Yandex SmartCaptcha) и собственный ограничитель частоты с фиксированным окном под своей отдельной областью с потолком 60 заявок на 15 минут на адрес клиента — выше платформенного значения по умолчанию в 20 на 15 минут (`apps/api/src/auth/rate-limit/rate-limit.types.ts:34`), потому что участники конгресса регистрируются всплесками с общих NAT-адресов клиник и площадок, тогда как каждая заявка по-прежнему проходит капчу, — и НЕ ДОЛЖНА добавлять заголовки CORS к API: единственный браузерный путь — same-origin через nginx-прокси `/api` сайта конгресса.
- **EARS-2** (`realizes: US-12`) — ГДЕ исходящий адрес nginx сайта конгресса настроен в `TRUSTED_PROXIES`, СИСТЕМА ДОЛЖНА резолвить ключ ограничения частоты из переданного адреса клиента, а не адреса прокси, так чтобы повторы одного участника никогда не ограничивали всех остальных.
- **EARS-3** (`realizes: US-10, US-11`) — СИСТЕМА ДОЛЖНА валидировать заявку по Zod-схеме в `packages/schemas`, требующей фамилию, имя, контактный телефон, email, специальность, место работы, город, область и согласие на обработку персональных данных, с отчеством НЕОБЯЗАТЕЛЬНЫМ, и ДОЛЖНА принимать специальность только как идентификатор `specialties_minzdrav` или явную опцию «Другое / не медицинский работник» — никогда как свободный текст.
- **EARS-4** (`realizes: US-1`) — КОГДА у отправленной почты нет аккаунта, СИСТЕМА ДОЛЖНА создать пользователя-человека в IdP БЕЗ учётных данных через новый безпарольный вариант рядом с `AuthService.register`, и ДОЛЖНА произвести upsert локальной строки `users` с ролью гостя по умолчанию, предзаполненной из отправленных ответов (отображаемое имя из фамилии/имени).
- **EARS-5** (`realizes: US-1, US-10`) — СИСТЕМА ДОЛЖНА сохранять отправленные ответы на строке `registrations` в новой типизированной колонке ответов, чья форма проверяется схемой `packages/schemas` из EARS-3, и НЕ ДОЛЖНА писать отправленный контактный телефон в `users.phone`.
- **EARS-6** (`realizes: US-2, US-10`) — КОГДА у отправленной почты уже есть аккаунт, СИСТЕМА ДОЛЖНА прикрепить регистрацию к этому аккаунту и НЕ ДОЛЖНА писать ни один отправленный ответ в поля профиля этого аккаунта.
- **EARS-7** (`realizes: US-2`) — СИСТЕМА ДОЛЖНА возвращать ответ, идентичный по форме, коду статуса и классу тайминга для пути нового аккаунта и пути существующего аккаунта, не раскрывая, существовал ли аккаунт уже. Различающееся тело письма-подтверждения (EARS-13) не является каналом раскрытия: оно достигает только адреса, отправившего форму, никогда третьей стороны, способной сравнить ответы.
- **EARS-8** (`realizes: US-3`) — КОГДА заявка приходит для пары `(аккаунт, мероприятие)`, которая уже зарегистрирована, СИСТЕМА ДОЛЖНА вернуть тот же самый идентичный успешный ответ, не создавая второй аккаунт и вторую строку регистрации, и НЕ ДОЛЖНА записывать вторую строку `consent_records`, ЕСЛИ ТОЛЬКО опубликованная версия согласия не отличается от уже записанной для этой пары — в этом случае новая версия записывается как новая строка принятия.
- **EARS-9** (`realizes: US-7`) — СИСТЕМА ДОЛЖНА писать ровно одну строку `consent_records` на каждое принятие под новой целью персональных данных конгресса, с проставленным сервером идентификатором версии, составленным из даты публикации страницы согласия и sha256 её опубликованного текста (ADR-0009 §2.1).
- **EARS-10** (`realizes: US-7`) — СИСТЕМА НЕ ДОЛЖНА писать строку согласия `medical-worker-declaration` для регистрации на конгресс и НЕ ДОЛЖНА требовать её на этом пути.
- **EARS-11** (`realizes: US-4, US-13`) — СИСТЕМА ДОЛЖНА зафиксировать аккаунт, регистрацию и согласие до отправки письма-подтверждения, ДОЛЖНА отправлять это письмо вне пути ответа, и НЕ ДОЛЖНА откатывать, задерживать или проваливать регистрацию из-за сбоя отправки.
- **EARS-12** (`realizes: US-13`) — СИСТЕМА ДОЛЖНА записывать исход письма-подтверждения (отправлено или сбой, с временной меткой) на строке регистрации; КОГДА заявка повторяет уже зарегистрированную пару, чей записанный исход — `failed`, СИСТЕМА ДОЛЖНА отправить письмо-подтверждение повторно и обновить этот исход; ГДЕ записанный исход — `sent`, СИСТЕМА НЕ ДОЛЖНА отправлять второе письмо. Очередь повторов или запланированный обход не вводятся.
- **EARS-13** (`realizes: US-4`) — СИСТЕМА ДОЛЖНА отправлять письмо-подтверждение, отрендеренное через общий `apps/api/src/mailer/email-layout.ts` в форме `apps/api/src/mailer/notice-emails.ts`, с текстом, зависящим только от того, новый аккаунт или существующий (одобрено владельцем, #2287 issuecomment-5756369423):

  Новый аккаунт — тема «Doctor.School — вы зарегистрированы на {название мероприятия}»:

  ```
  Вы зарегистрированы на {название мероприятия}: {дата}, {место}.
  Для вас создан аккаунт Doctor.School на этот адрес электронной почты. Пароль не нужен: чтобы войти, укажите этот адрес и введите код из письма.
  [Войти]
  Если это были не вы, просто проигнорируйте это письмо.
  Команда Doctor.School
  ```

  Существующий аккаунт — та же тема и первая строка; второй абзац заменён на:

  ```
  Регистрация добавлена в ваш аккаунт Doctor.School. Создавать новый не нужно.
  ```

## Инварианты

- Один человек — одна сущность: отправленная почта, у которой уже есть аккаунт, никогда не производит второй аккаунт (ADR-0016 §1).
- Неаутентифицированная заявка никогда не пишет в профиль уже существующего аккаунта — ответы живут на строке регистрации и больше нигде (EARS-5, EARS-6).
- Ответ приёма заявки не несёт сигнала перечисления ни в теле, ни в статусе, ни в классе тайминга (EARS-7, EARS-8).
- Сбой письма-подтверждения никогда не виден как потерянная регистрация; регистрация фиксируется первой, а исход — записанный факт на ней (EARS-11, EARS-12).
- `event-registrar` — deny-by-default: маршрут реестра — это допущение, всё остальное отклоняется на сервере (EARS-19).
- Аккаунт, происходящий из конгресса, не несёт строки `medical-worker-declaration`, и ни одна поверхность не считает это отсутствие ошибкой (граничная линия, Prior decisions).
- Окно регистрации вычисляется до любого побочного эффекта: заявка вне окна не оставляет за собой ни аккаунта, ни регистрации, ни строки согласия, ни письма, а её отказ не несёт сигнала перечисления (EARS-28).
- Вместимость приёма заявок ограничена только окном — ни лимита мест, ни листа ожидания, ни отказа по вместимости (EARS-28).
- Отметка «возможный дубль» — это выведение на чтении по нормализованному контактному телефону, никогда не хранимый флаг: удаление одной из регистраций с общим телефоном снимает отметку с выжившей без единой записи (EARS-29, EARS-30).
- Общий телефон никогда не меняет того, что наблюдает участник: ответ приёма заявки — тот же самый идентичный успех на каждом пути (EARS-7, EARS-30).
