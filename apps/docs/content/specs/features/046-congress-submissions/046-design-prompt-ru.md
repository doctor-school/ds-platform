# Stage A · 046 «Заявки на Конгресс» — пакет для Claude Design

> Пакет для владельца продукта: запускается в claude.ai/design, выбор варианта на холсте = решение Stage A.
> Источники: PRD `046-product-ru.md`, требования `046-requirements-ru.md`, дизайн `046-design.md` (ветка спецификации #2385, worktree `.claude/worktrees/2385`), ТЗ организаторов Конгресса 2027, процедура `build-ui-from-design-system/design-approval.md` (Stage A).
> По контракту Stage A пакет несёт ТОЛЬКО содержание (набор экранов и состояний, сценарии, US-N) и 2 варианта направления с паспортом происхождения. Токены бренда и ограничения дизайн-системы здесь не повторяются: их держит синхронизированный проект «DS Platform» в Claude Design.

**Критерии владельца, по которым отфильтрованы варианты** (из постановки задачи техлидом):

- К1 — максимально просто и прозрачно для врача, без двусмысленности.
- К2 — любой путь заканчивается успешной отправкой и ясным пониманием, что отправлено и в каком статусе.
- К3 — никакой многошаговой акробатики.
- К4 — одна дверь: регистрация на orthobio.ru → вход по коду из письма → кабинет на платформе.

## 2. Сценарии и истории (из PRD)

Истории US-1…US-14 — дословно в `046-product-ru.md` («Пользовательские истории»). Ниже — сценарии, по которым владелец проверяет варианты на холсте.

1. **Из письма к первому докладу** (US-1, US-3, US-7, US-14): письмо 044 → «Подать материалы в кабинете» → код из письма → К-2 → «Устный доклад» → автор 1 уже заполнен → тема и часть текста → закрыл вкладку → вернулся на следующий день, текст на месте (К-11) → «Отправить» → согласие ПДн (К-12) → К-16 «Отправлена» → Л-1.
2. **Нет регистрации** (US-2): К-1 — одна строка и ссылка на orthobio.ru/registration.
3. **Постер и возраст** (US-4): К-4 → «Постерный доклад» → К-5 дата рождения → при 23.04.1987 и раньше — К-6, доклад и тезисы доступны.
4. **Тезисы по докладу** (US-5, US-6): К-16 доклада → «Подать тезисы по этой работе» → К-9 с темой и авторами → пять разделов под общим счётчиком → РИНЦ и два подтверждения → «Отправить».
5. **Четвёртые тезисы** (US-6): К-14; если одни из трёх отклонены — проходят.
6. **Приём закрыт** (US-7): 16 января черновик доклада — К-15.
7. **Комитет возвращает доклад** (US-8…US-10): А-2 фильтр «Устный доклад» → А-3 → А-4 «На доработке» + комментарий → Л-4 → К-18 → «Отправить снова» после закрытия приёма → Л-1.
8. **Партнёр читает** (US-12): А-5, поиск по фамилии, телефон автора.
9. **Дедлайн перенесли** (US-11, US-13): А-1 → К-4/К-15 сразу показывают новую дату → Л-5 приходит заново.

### Исследование (веб, до вариантов)

- **Одна страница против мастера.**
  - NN/g: мастер подходит новичкам и редким процессам. Минусы — больше кликов, нет обзора формы, плохо переносит прерывания. [F] https://www.nngroup.com/articles/wizards/
  - NN/g: одна колонка, визуально сгруппированные секции, ошибки у поля с сохранением ввода. Формы по этим правилам — 78% успешных отправок с первой попытки против 42%. [F] https://www.nngroup.com/articles/web-form-design/
  - NN/g: длина сама по себе не повод дробить форму. [S] https://www.nngroup.com/articles/forms-vs-applications/
- **Список задач (task list).** GOV.UK применяет его к длинным транзакциям, которые заполняют за несколько сессий, и только после упрощения. У каждой задачи своя страница, одна кнопка отправки в конце; статусы «Completed / Incomplete / Cannot start yet / There is a problem». [F] https://design-system.service.gov.uk/patterns/complete-multiple-tasks/ · [F] https://design-system.service.gov.uk/components/task-list/
- **Экран «вопрос на страницу».** GOV.UK: связанные вопросы можно группировать на одной странице с заголовком-утверждением. [F] https://design-system.service.gov.uk/patterns/question-pages/
- **Проверка перед отправкой и подтверждение.**
  - GOV.UK check answers: строка-декларация над кнопкой, которая называет действие. [F] https://design-system.service.gov.uk/patterns/check-answers/
  - GOV.UK confirmation: номер, «что дальше и когда». [F] https://design-system.service.gov.uk/patterns/confirmation-pages/
- **Порталы тезисов.**
  - Oxford Abstracts: панель «название · статус · Изменить»; после дедлайна — только чтение; неполная заявка видна и в панели, и в письме. [F] https://help.oxfordabstracts.com/knowledge/your-personal-dashboard · [F] https://help.oxfordabstracts.com/knowledge/making-a-submission
  - Ex Ordo: до 6 шагов в боковой колонке с отметкой полноты, любой шаг открывается напрямую, квитанция на экране и в письме. [F] https://support.exordo.com/article/473-how-to-submit-a-paper
  - ScholarOne: чтобы исправить отправленное, заявку «возвращают в черновик» — это антипаттерн, правка молча снимает отправку. У нас «Забрать на исправление» — явное действие с объяснением. [F] https://news.ddw.org/news/answers-to-your-abstract-submission-questions/
- **Общий счётчик структурированных тезисов.**
  - GOV.UK character count: живой остаток, превышение разрешено с предупреждением, чтобы вставленный текст можно было сократить. [F] https://design-system.service.gov.uk/components/character-count/
  - ScholarOne: один счётчик на всё тело («Current Character Count: 50 out of 2800»), но обновляется только по «Сохранить» — у нас он живой. [F] https://www.preventionresearch.org/wp-content/uploads/2011/08/SPR_2012_ScholarOne-step-by-step-instructions-9-7-11.pdf
- **Авторы.**
  - MOJ «add another»: повторяющаяся группа полей на одной странице, «Удалить» внутри элемента, автонумерация. [F] https://design-patterns.service.justice.gov.uk/components/add-another/
  - Ex Ordo: отметка «докладчик» у автора, порядок перетаскиванием. [F] https://support.exordo.com/article/473-how-to-submit-a-paper
  - Confex: докладчик обязан быть в списке авторов. [F] https://gsa.confex.com/gsa/help3.htm
- **Автосохранение.** GitLab Pajamas: статус в строке рядом с содержимым, а не всплывающим уведомлением — «Сохраняем…» → «Сохранено»; при сбое «Не удалось сохранить» с повтором, который не исчезает до успеха. [F] https://design.gitlab.com/patterns/saving-and-feedback/
- **Статус с комментарием рецензента.** Oxford Abstracts показывает отзывы кнопкой «Reviews (N)» [F] https://help.oxfordabstracts.com/knowledge/show-reviews-to-submitters-1; OpenReview — кнопка «Revision» [F] https://docs.openreview.net/how-to-guides/submissions-comments-reviews-and-decisions/how-to-edit-a-submission-after-the-deadline-authors. Единой карточки «комментарий + срок + действие» публично не нашлось, поэтому К-18 проектируем сами.

([F] — страница открыта и прочитана; [S] — только сниппет поиска.)

### Отброшено по критериям владельца

- **Пошаговый мастер** (шаг 1 «Тема» → шаг 2 «Авторы» → …). Нарушает К3. Кроме того, NN/g фиксирует плохую переносимость прерываний, а автор пишет текст за несколько заходов (сц. 1).
- **Список задач GOV.UK** (страница-оглавление → отдельная страница на раздел → проверка → отправка). Это многостраничная навигация, что нарушает К3. Сам GOV.UK ставит его только после упрощения и для многосессионных транзакций, а наша самая длинная форма (тезисы) — это тема, авторы и 5 текстовых полей.
- **Отдельный шаг «Проверьте ответы» перед отправкой.** Лишний экран (К3). Его задачу — «ясно, что отправлено» (К2) — выполняет К-16: после отправки автор видит ровно отправленный текст с меткой «Отправлена». Строка-декларация согласий над кнопкой («Отправляя, вы …») сохраняется в обоих вариантах.
- **Правка отправленного «возвратом в черновик» при редактировании** (ScholarOne). Нарушает К1: статус молча меняется. У нас «Забрать на исправление» — явная кнопка с объяснением последствий.
- **Отдельная страница выбора вида.** Выбор встроен в раздел (К-4) — это на один экран меньше.

Отбор прошли два варианта. Оба — одна страница; отличаются тем, как автор видит полноту формы.

### Вариант 1 — «Одна страница, всё видно сразу» (рекомендуется)

**Паспорт происхождения**

| Поле                     | Значение                                                                                                                                                                                                                                                                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Паттерн / реестр         | NN/g «web form design» (одна колонка, сгруппированные секции, ошибки у поля) + GOV.UK question pages (группировка связанных вопросов) + GOV.UK character count (общий счётчик) + MOJ «add another» (авторы) + GitLab Pajamas «saving and feedback» (строка сохранения) + Oxford Abstracts personal dashboard (список «тема · статус · действие») |
| Единица в дизайн-системе | Существующие: `Form`/`FormSection`/`FormFieldGroup`/`FormActions`/`FormErrorSummary`, `Input`, `Textarea`, `Checkbox`, `Badge`, `Alert`, `Card`, `Button`, `AlertDialog`, `EmptyState`, `Container`. Новые классы: см. §4.                                                                                                                       |
| Лицензия                 | Паттерны — открытые руководства (GOV.UK/MOJ — OGL v3 / MIT для кода; NN/g, Pajamas — методика). Кода не заимствуем.                                                                                                                                                                                                                              |
| Новые зависимости        | Нет.                                                                                                                                                                                                                                                                                                                                             |
| Настраиваем / пишем      | Настраиваем: примитивы формы и счётчик `Textarea`. Пишем: повторитель авторов, строку автосохранения, общий счётчик пяти полей, карточки выбора вида со строкой состояния, ввод даты, набор меток статуса (§4).                                                                                                                                  |

**Как выглядит:**

- **Раздел.** Сверху — список заявок, у каждой метка статуса, тема и одно действие; у «Отклонена» и «На доработке» комментарий комитета виден прямо в списке. Ниже — «Новая заявка»: три карточки вида, у каждой строка состояния приёма и лимита.
- **Форма.** Одна страница: «Тема» → «Авторы» → текстовые поля вида → (тезисы: общий счётчик закреплён у полей) → согласия и строка-декларация → «Отправить». Строка «Сохранено» у заголовка формы. Если отправка не прошла, сводка ошибок наверху со ссылками к полям.
- **После отправки.** Та же страница в режиме чтения: метка «Отправлена», дата, «что дальше», при возможности — «Забрать на исправление» и «Подать тезисы по этой работе».

**Против критериев владельца:**

- ✅ К1 — всё видно одним экраном; у каждой недоступности есть объяснение.
- ✅ К2 — после отправки автор видит ровно отправленный текст и статус; письмо Л-1 это дублирует.
- ✅ К3 — ноль промежуточных экранов между «Отправить» и результатом, кроме первого согласия и вопроса о дате рождения для постера.
- ✅ К4 — вход не меняется.
- ⚠️ На телефоне форма тезисов длинная — пять полей и счётчик. Закреплённый счётчик это смягчает.

### Вариант 2 — «Одна страница с оглавлением полноты»

**Паспорт происхождения**

| Поле                     | Значение                                                                                                                                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Паттерн / реестр         | Всё из варианта 1 + боковая колонка шагов Ex Ordo с отметкой полноты, свёрнутая до якорей на той же странице (без переходов) + статусы задач GOV.UK task list («Заполнено / Не заполнено / Есть ошибка») как подписи разделов. |
| Единица в дизайн-системе | Как в варианте 1 + новый класс «оглавление раздела с отметками полноты» (на широком экране липкая колонка, на телефоне — компактная строка «Заполнено 3 из 5» вверху).                                                         |
| Лицензия                 | Как в варианте 1.                                                                                                                                                                                                              |
| Новые зависимости        | Нет.                                                                                                                                                                                                                           |
| Настраиваем / пишем      | Всё из варианта 1 + оглавление с живыми отметками (пишем).                                                                                                                                                                     |

**Как выглядит.** Та же одна страница, что в варианте 1, плюс колонка «Тема ✓ · Авторы ✓ · Актуальность ○ · … · Согласия ○». Она заранее показывает, чего не хватит для отправки, — ещё до нажатия.

**Против критериев владельца:**

- ✅ К2 и К3 — как в варианте 1; отметки заранее говорят, что осталось.
- ⚠️ К1 — второй источник правды о полноте рядом с формой. Для формы из 4–8 полей это визуальный шум; в устном докладе он почти пуст.
- ⚠️ Ещё один новый класс для исследования и сопровождения.
- ⚠️ Отметка «заполнено» не равна «пройдёт при отправке»: лимит, даты и возраст проверяются только по «Отправить». Возможна двусмысленность «всё зелёное, а не отправилось».

### Рекомендация

**Вариант 1.** Он прямее всего отвечает на К1–К3 и не добавляет второго индикатора полноты, который может разойтись с проверкой при отправке. Всё «что мешает отправить» (закрыт приём, лимит, возраст) и так показано на карточке вида и на черновике — до ввода текста. Вариант 2 — это вариант 1 плюс один элемент; если владелец на холсте захочет видеть полноту заранее, его можно добавить позже, не перестраивая форму.

**Вопросы владельцу на холсте (явные развилки видимых элементов):**

1. Комментарий комитета в списке: полностью или первой строкой с «Показать целиком»? В форме К-18 он всегда полностью.
2. Раздел — отдельная страница со ссылкой со страницы аккаунта (как в спецификации) или вкладка кабинета «d-lk» (`doctor-cabinet.dc.html`)?
3. Кадр «заявка на выступление» в `doctor-congress.dc.html` помечаем устаревшим и заменяем кнопкой «Подать материалы в кабинете»? Изменение страницы Конгресса в объём 046 не входит — это нужно зафиксировать отдельно.

## 4. Дизайн-система: что берём как есть, что новое

### Как есть (`packages/design-system/src`)

- **Каркас формы:** `Form` / `FormItem` / `FormLabel` / `FormDescription` / `FormMessage` / `FormErrorSummary`; `FormSection` / `FormFieldGroup` / `FormActions` (`blocks/field-group.tsx`).
- **Поля:** `Input`; `Textarea` со встроенным счётчиком на одно поле (превышение подсвечивается, текст не обрезается — совпадает с GOV.UK). Годится для полей доклада и постера.
- **Выбор:** `Checkbox` — согласия и подтверждения; `Switch` — «Учитывать первого автора» в А-1; `NativeSelect` / `Combobox` — статус в А-4 и фильтры.
- **Сообщения:** `Alert` — отказы К-13…К-15 и К-19, комментарий в К-18 (нужно проверить, есть ли у `Alert` вариант warning/destructive; подтверждены только info и success); `EmptyState` — К-1 и К-2; `AlertDialog` — «Удалить черновик», «Забрать на исправление».
- **Оболочка:** `Card`, `Button`, `Link`, `Container`; `Skeleton` — загрузка.
- **Админка:** `Sheet` (#2396) — карточка А-3 с листанием ↑/↓, прецедент — стол регистрации 044 `apps/admin/components/desk-registration-form.tsx`; `apps/admin/components/admin-data-list.tsx` + `filter-bar` / `filter-chip` / `pagination` — реестр А-2 по образцу `apps/admin/lib/congress-roster.ts`.
- **Письма:** общий макет `email-layout.ts` / `notice-emails.ts` (как 044).

### Новые классы элементов (каждый проходит `research-ui-element` до кода)

1. **Повторитель авторов** («добавить ещё», порядок, ровно один «Докладчик», удаление, автор 1 из регистрации). В DS повторителя нет. Источники: MOJ add-another, Ex Ordo, Confex.
2. **Строка автосохранения** («Сохранено / Сохраняем… / Не удалось сохранить — повторим»). В DS нет ни toast, ни saved-индикатора. Источник: GitLab Pajamas.
3. **Общий счётчик нескольких полей** (пять разделов тезисов → один счётчик, закреплённый при прокрутке). Счётчик `Textarea` работает только на одно поле. Источник: GOV.UK character count, ScholarOne.
4. **Ввод даты** — дата рождения (К-5) и календарные дни в настройках (А-1). В DS есть только `MonthPicker` и календарные сетки. Развилка для исследования: GOV.UK date input (день / месяц / год) против нативного `type=date`.
5. **Карточка выбора вида со строкой состояния** (радиокарточка или карточка-кнопка с «Приём до … / откроется … / закрыт … / 2 из 3 / недоступно: причина»). В DS только одиночный `Radio`, без `RadioGroup` и без карточного варианта.
6. **Набор меток статуса заявки** (6 статусов). У `Badge` нет семантического набора статусов (подтверждены live / success / updated / label / speaker). В админке свои `status-chip.tsx` и `state-badge.tsx`, но это не общий DS-класс. Решение для исследования: расширить `Badge` статусными вариантами одним классом для кабинета и админки — не заводить третий.
7. **История статусов в карточке** (кто · когда · из какого в какой · комментарий). Готового списка-хронологии в DS нет. Возможно, это композиция `DisclosureSummary` и списка — проверить при исследовании.
8. _(только вариант 2)_ **Оглавление полноты раздела.**
