# 046 — Приём тезисов и заявок на доклад конгресса (Требования)

## Результаты

- Участник конгресса подаёт тезисы и заявки на доклад вместе со своей регистрацией 044, в одном запросе с сайта конгресса, и может подать несколько.
- До дедлайна автор правит заявки и добавляет новые по подписанной ссылке из письма, без пароля и без входа на платформу.
- Дедлайн подачи — настройка API, которую сайт конгресса читает у платформы; его смена не требует релиза платформы или правки сайта.
- Партнёр конгресса видит реестр заявок своего конгресса с контактами, ищет и фильтрует его по спикерам и по тезисам и больше ничего на платформе не видит и не меняет.

## Область

- Два вида заявки — тезисы и заявка на доклад — и их Zod-схема в `packages/schemas`.
- Расширение публичного эндпоинта приёма заявки 044 необязательным массивом заявок; хранение заявок, привязанных к строке `registrations`.
- Окно подачи: два ключа конфигурации API и публичный эндпоинт формы подачи (окно, список тем, лимиты полей).
- Письмо со списком заявок и ссылкой на правку; эндпоинты правки по ссылке.
- Роль `congress-partner`, её граница авторизации и навигация админки; реестр заявок и карточка заявки в `apps/admin`.
- Форма подачи и страница правки на сайте конгресса (`doctor-school/orthobio-site`, orthobio-site#99) — поведение, которое сайт обязан реализовать поверх этого контракта.

### Вне области

- Рецензирование, отбор, статусы решения и публикация тезисов на страницах конгресса.
- Отзыв заявки автором; удаление — вручную командой по запросу, как в 044.
- Загрузка файлов; экспорт реестра в файл.
- Экран выдачи ролей, привязанных к мероприятию, — #2378; сам механизм привязки определяет поправка 044 (#2380), 046 его не переопределяет.
- Приём заявок через платформенный путь регистрации вошедшего врача (044 EARS-16).
- Постерный доклад как вид заявки — открытый вопрос владельцу (`046-product-ru.md`, «Открытые вопросы», пункт 2), не требование.

## Ограничения

- Путь приёма 044 (`apps/api/src/congress/congress-signup.service.ts`, `congress-signup.controller.ts`) — единственная дверь: аккаунт без пароля через движок 003, строка согласия, регистрация, письмо через `apps/api/src/mailer/notice-emails.ts`. 046 не заводит второй публичный эндпоинт создания аккаунта.
- `registrations` уникальна по `(user_id, event_id)` (`packages/db/src/schema/registrations.ts`); заявки ссылаются на эту строку, а ответы участника остаются в её колонке `answers` (`registrations.ts:147`).
- У API нет CORS; сайт конгресса ходит same-origin через свой nginx-прокси `/api` (044 EARS-1, EARS-2).
- Окно 044 читается из `CONGRESS_SIGNUP_WINDOW_OPENS_AT` / `CONGRESS_SIGNUP_WINDOW_CLOSES_AT` в `apps/api/src/congress/congress-signup.config.ts`; окно подачи зеркалирует эту форму, а не изобретает свою.
- Кто и когда создал или изменил запись — механизм спеки 010 (`apps/api/src/audit/README.md`).
- Привязка роли к мероприятию — хранилище, которое определяет поправка 044 (#2380); набор ролей — `apps/api/src/authz/authz.types.ts:18-30`.

## Prior decisions

- Решения владельца продукта (чат, 2026-09-25), дословно:
  - «Существует три варианта участия в Конгрессе, для каждого из них предусмотрена своя форма: Участник … Каждая другая форма подразумевает заполнение формы участника. То есть быть участником обязательно в любом случае, остальные два варианта опциональны. Подать тезисы для обсуждения на Конгрессе. Выступить с докладом на Конгрессе. Подаётся тема, название доклада, список соавторов доклада.»
  - «Тезисы вводятся текстом, тут всё чётко структурируем, так как это контент для отображения на страницах Конгресса.»
  - О дедлайне подачи: «Да, но тоже вынести эту дату в настройки, чтобы можно было легко менять.»
  - «Партнёр Конгресса - видит исключительно заявки на тезисы и доклады. Не видит полный список участников … Им доступна выборка по спикерам и по тезисам. Аналогично с поиском и фильтрацией.»; «Контакты он тоже видит, так как они выходят с людьми на связь по поводу докладов. Read-only.»
  - О выдаче ролей: вручную через Zitadel пока; «задачу на заведение платформенного админа и его интерфейса завести всё равно надо» (#2378).
- ADR-0006 §4 — плоская нумерация `EARS-N`. ADR-0014 §2 — каждый EARS несёт `realizes: US-N`.
- ADR-0002 — контракт Zod-first в `packages/schemas`. ADR-0013 — экраны из примитивов `@ds/design-system`, реестр на одобренной композиции `AdminDataList`.
- ADR-0001 §1, §8 — грубая роль из клейма ролей проекта Zitadel. ADR-0016 §1 — заявка принадлежит одной существующей сущности человека.

## Модель событий

**Команды** — `SubmitCongressSignUp` (044, расширена необязательными заявками), `ReadSubmissionForm` (публичная), `ReadOwnSubmissions` / `AddSubmission` / `EditSubmission` (по ссылке), `ListCongressSubmissions` / `ReadCongressSubmission` (партнёр конгресса, платформенный администратор).

**События** — `CongressSubmissionRecorded`, `CongressSubmissionEdited`, `SubmissionsEmailDispatched` / `SubmissionsEmailFailed`.

**Модели чтения** — форма подачи (окно, темы, лимиты); собственные заявки регистрации (по ссылке); реестр заявок мероприятия с контактами подавшего.

**Политики** — «заявка без регистрации участника невозможна»; «публичный маршрут только добавляет, правит только ссылка»; «окно подачи вычисляется до любого побочного эффекта»; «сбой письма никогда не откатывает заявку»; «партнёр — deny-by-default, допущен только реестр заявок своего мероприятия».

## Требования EARS

Набор полей тезисов и доклада ниже — **базовый набор, подлежащий подтверждению владельцем** (`046-product-ru.md`, «Открытые вопросы», пункт 1). Требования ссылаются на таблицы полей и лимитов в `046-design.md`, поэтому окончательный набор владельца меняет таблицы, а не номера и формулировки требований.

### Пакет работ «приём заявок» — API

- **EARS-1** (`realizes: US-1, US-2`) — СИСТЕМА ДОЛЖНА различать ровно два вида заявки, `abstract` (тезисы) и `talk` (заявка на доклад), и ДОЛЖНА валидировать каждую заявку по Zod-схеме в `packages/schemas/src/congress/`, дискриминированной по виду; каждая заявка несёт идентификатор, сгенерированный клиентом (UUID).
- **EARS-2** (`realizes: US-1`) — СИСТЕМА ДОЛЖНА принимать тезисы только со всеми полями базового набора тезисов из `046-design.md` («Набор полей тезисов») — название, тема из закрытого списка тем, от одного автора, разделы «Актуальность», «Материалы и методы», «Результаты», «Выводы» и ключевые слова — и ДОЛЖНА отклонять тезисы, чей раздел или поле превышает свой лимит символов, посчитанный на сервере после обрезки пробелов по краям; тема принимается только как значение закрытого списка, никогда как свободный текст.
- **EARS-3** (`realizes: US-2`) — СИСТЕМА ДОЛЖНА принимать заявку на доклад только с темой из того же закрытого списка, названием доклада и списком соавторов из `046-design.md` («Набор полей доклада»), в котором хотя бы один соавтор отмечен как выступающий.
- **EARS-4** (`realizes: US-1, US-2`) — СИСТЕМА ДОЛЖНА нормализовать фамилию, имя и отчество каждого автора по правилу 044 EARS-33 и email автора — обрезкой пробелов и приведением к нижнему регистру — до сохранения; место работы автора сохраняется как введено.
- **EARS-5** (`realizes: US-1, US-2, US-3`) — СИСТЕМА ДОЛЖНА принимать необязательный массив заявок, не более 10 на запрос, в теле публичного эндпоинта приёма заявки 044; КОГДА массив непуст, СИСТЕМА ДОЛЖНА сначала пройти весь каскад 044 без изменений — капча, лимит частоты, окно регистрации, аккаунт, согласие, регистрация — и ДОЛЖНА записать каждую заявку строкой, привязанной к строке `registrations` этого участника на это мероприятие, в той же транзакции, что и регистрация; заявка без строки регистрации не записывается никогда.
- **EARS-6** (`realizes: US-3`) — КОГДА публичный запрос несёт заявку, чей клиентский идентификатор уже записан для той же регистрации, СИСТЕМА ДОЛЖНА не создавать вторую строку и НЕ ДОЛЖНА менять сохранённое содержимое этой заявки; публичный маршрут только добавляет заявки, а правка существующей заявки возможна только по ссылке (EARS-13, EARS-14). Регистрация не может держать больше 10 заявок; запрос, превышающий этот предел, отклоняется целиком до побочных эффектов.
- **EARS-7** (`realizes: US-1, US-2, US-3`) — СИСТЕМА ДОЛЖНА отвечать на запрос с заявками ровно тем же ответом `{ "status": "accepted" }`, кодом статуса и классом тайминга, что и 044 EARS-7, независимо от того, существовал ли аккаунт, была ли регистрация и были ли какие-то из заявок уже записаны.
- **EARS-8** (`realizes: US-8`) — СИСТЕМА ДОЛЖНА читать окно подачи из двух обязательных ключей конфигурации API, `CONGRESS_SUBMISSION_WINDOW_OPENS_AT` и `CONGRESS_SUBMISSION_WINDOW_CLOSES_AT`, — дат-времени ISO-8601 с явным смещением, с закрытием строго после открытия, — валидируемых рядом с ключами 044 в конфигурации модуля конгресса; значение без смещения, неразбираемое или перевёрнутое окно ДОЛЖНО закрывать подачу (fail closed). Производственные значения — 2026-10-01T00:00+03:00 и 2026-12-01T00:00+03:00 по сегодняшнему решению владельца; ни строки в базе данных, ни экрана в админке для окна не заводится.
- **EARS-9** (`realizes: US-9`) — КОГДА запрос с непустым массивом заявок приходит до открытия окна подачи, СИСТЕМА ДОЛЖНА отклонить его целиком машиночитаемым состоянием `submissions-not-yet-open`, несущим момент открытия; КОГДА после закрытия — состоянием `submissions-closed`; окно подачи ДОЛЖНО вычисляться сразу после окна регистрации 044 и до любого побочного эффекта, а отказ ДОЛЖЕН быть одинаковым для любого отправителя. Запрос без заявок окном подачи не связан и подчиняется только окну 044.
- **EARS-10** (`realizes: US-8, US-9`) — СИСТЕМА ДОЛЖНА выставлять публичный, только-для-чтения, кэшируемый эндпоинт формы подачи через тот же same-origin прокси, возвращающий состояние окна подачи (`not-yet-open` / `open` / `closed`) с обоими моментами, закрытый список тем и лимиты символов каждого поля из той же декларации схемы, которой сервер валидирует заявки, так чтобы сайт никогда не держал собственную копию дат, тем или лимитов.
- **EARS-11** (`realizes: US-5`) — СИСТЕМА ДОЛЖНА после фиксации заявок и вне пути ответа отправлять автору письмо, отрендеренное через `apps/api/src/mailer/email-layout.ts` в форме `notice-emails.ts`, перечисляющее все заявки регистрации (вид, название, тема, авторы с отметкой выступающих) и несущее ссылку на правку из EARS-13; КОГДА регистрация создана в этом же запросе, СИСТЕМА ДОЛЖНА отправить одно письмо — подтверждение 044 с блоком заявок, — а не два. Текст письма утверждается на Stage-A.
- **EARS-12** (`realizes: US-5`) — СИСТЕМА ДОЛЖНА записывать исход письма о заявках (отправлено или сбой, с временной меткой) на регистрации и НЕ ДОЛЖНА откатывать, задерживать или проваливать запись заявки из-за сбоя отправки; КОГДА повторный публичный запрос или правка по ссылке застаёт записанный исход `failed`, СИСТЕМА ДОЛЖНА отправить письмо повторно.
- **EARS-13** (`realizes: US-4`) — СИСТЕМА ДОЛЖНА выпускать ссылку на правку как подписанный HMAC-SHA256 токен над идентификатором регистрации ключом `CONGRESS_SUBMISSION_LINK_SECRET`, помещённый во фрагмент адреса страницы правки на сайте конгресса и передаваемый в API заголовком `x-congress-submission-token`; токен ДОЛЖЕН давать доступ только к заявкам этой регистрации, НЕ ДОЛЖЕН создавать сессию платформы или входить в аккаунт, и его пригодность для записи ДОЛЖНА истекать вместе с окном подачи, вычисляемым в момент использования. Неверный, подделанный или чужой токен ДОЛЖЕН получать один и тот же общий отказ.
- **EARS-14** (`realizes: US-4, US-9`) — СИСТЕМА ДОЛЖНА выставлять по токену EARS-13 чтение собственных заявок регистрации, добавление новой заявки и замену содержимого существующей заявки по её клиентскому идентификатору, с валидацией EARS-1…EARS-4 и пределом EARS-6; запись ДОЛЖНА отклоняться состояниями EARS-9 до любого побочного эффекта, когда окно подачи не открыто, а чтение ДОЛЖНО оставаться доступным, пока существует регистрация, так чтобы после дедлайна автор видел свои заявки только для чтения. Каждая успешная запись вызывает письмо EARS-11.
- **EARS-15** (`realizes: US-4, US-6`) — СИСТЕМА ДОЛЖНА фиксировать на каждой строке заявки моменты создания и последнего изменения и ДОЛЖНА записывать каждое создание и изменение заявки механизмом «кто и когда» спеки 010 с аккаунтом регистрации как действующим лицом и каналом (`public-intake` или `edit-link`).

### Пакет работ «роль партнёра и реестр заявок» — API и `apps/admin`

- **EARS-16** (`realizes: US-6, US-7`) — СИСТЕМА ДОЛЖНА добавить `congress-partner` в набор ролей API как грубую роль из клейма ролей проекта Zitadel и ДОЛЖНА ограничивать её одним мероприятием через хранилище привязки ролей к мероприятию, определённое поправкой 044 (#2380); партнёр мероприятия видит только заявки этого мероприятия.
- **EARS-17** (`realizes: US-7`) — СИСТЕМА ДОЛЖНА отказывать принципалу, держащему только `congress-partner`, на каждом эндпоинте API, кроме списка заявок и карточки заявки своего мероприятия и эндпоинтов сессии, — включая реестр участников 044, его печатный список, заявки других мероприятий и каждую мутацию. Список и карточка заявок допущены также для платформенного администратора по любому мероприятию.
- **EARS-18** (`realizes: US-7`) — СИСТЕМА ДОЛЖНА показывать принципалу, держащему только `congress-partner`, в навигации админки единственный пункт — реестр заявок; клиентский гейт — проекция серверного отказа EARS-17, никогда не его замена.
- **EARS-19** (`realizes: US-6`) — СИСТЕМА ДОЛЖНА рендерить реестр заявок в `apps/admin` на композиции `AdminDataList` со столбцами №, вид, название, тема, спикеры, авторы, подавший (ФИО), email, телефон, подана, изменена, и ДОЛЖНА сортировать его на сервере по любому столбцу, кроме №, в обоих направлениях, с состоянием сортировки в запросе списка вместе с поиском, фильтрами и страницей.
- **EARS-20** (`realizes: US-6`) — СИСТЕМА ДОЛЖНА предлагать серверные фильтры реестра заявок — select по виду и по теме; поиск по вхождению «спикер» по ФИО и месту работы соавторов, отмеченных выступающими; поиск по вхождению «тезисы» по названию, теме и ключевым словам тезисов; поиск по вхождению по ФИО любого автора и по ФИО, email и телефону подавшего; диапазон по дате подачи, — каждый компонуемый с остальными, с сортировкой и страницей.
- **EARS-21** (`realizes: US-6`) — СИСТЕМА ДОЛЖНА открывать из строки реестра карточку заявки с полным содержимым — все поля тезисов или доклада, авторы с местом работы, email и отметкой выступающего — и контактами подавшего: ФИО, email и контактный телефон из ответов регистрации 044.
- **EARS-22** (`realizes: US-7`) — СИСТЕМА ДОЛЖНА рендерить реестр и карточку только для чтения: ни для какой роли не появляется аффорданс создания, правки или удаления, и API не выставляет мутации заявки для админки.

### Пакет работ «формы сайта конгресса» — orthobio-site#99

Форма UX ниже — предложение, подтверждение которого за владельцем (`046-product-ru.md`, «Открытые вопросы», пункт 3); требования фиксируют поведение, от которого зависит контракт API, а визуальную форму задаёт Stage-A.

- **EARS-23** (`realizes: US-1, US-2, US-3`) — СИСТЕМА ДОЛЖНА рендерить на сайте конгресса одну форму: обязательный блок участника 044, затем разделы «Подать тезисы» и «Подать заявку на доклад», каждый добавляемый несколько раз и удаляемый до отправки, с повторителем авторов и счётчиком символов под каждым ограниченным полем по лимитам из EARS-10, и ДОЛЖНА отправлять участника и все заявки одним запросом EARS-5, генерируя клиентский идентификатор каждой заявки один раз при её добавлении в форму.
- **EARS-24** (`realizes: US-9`) — СИСТЕМА ДОЛЖНА на сайте конгресса читать состояние окна подачи из EARS-10 и, КОГДА оно не `open`, НЕ ДОЛЖНА показывать разделы подачи, показывая вместо них сообщение о том, что приём ещё не открыт (с датой открытия) или закрыт, при этом блок участника остаётся доступным по правилам окна 044.
- **EARS-25** (`realizes: US-4`) — СИСТЕМА ДОЛЖНА рендерить на сайте конгресса страницу правки, которая читает токен из фрагмента адреса, передаёт его заголовком EARS-13, показывает заявки регистрации в тех же разделах формы, позволяет исправить их и добавить новые, пока окно подачи открыто, и показывает их только для чтения, когда оно закрыто.

## Инварианты

- Заявки не существует без строки регистрации участника на то же мероприятие; удаление регистрации удаляет её заявки (EARS-5).
- Публичный маршрут никогда не меняет и не удаляет записанную заявку; правит только держатель ссылки (EARS-6, EARS-14).
- Ответ приёма заявки не несёт сигнала перечисления: тот же `accepted` на каждом пути, с заявками и без (EARS-7).
- Окно подачи вычисляется до любого побочного эффекта; запрос с заявками вне окна не оставляет ни аккаунта, ни регистрации, ни заявки, ни письма (EARS-9).
- Даты окна, темы и лимиты полей живут в одном месте — конфигурации и схеме API; сайт их только читает (EARS-10).
- Ссылка на правку — не вход: она никогда не создаёт сессию платформы и не даёт доступа ни к чему, кроме заявок своей регистрации (EARS-13).
- `congress-partner` — deny-by-default: допущены только список и карточка заявок своего мероприятия и эндпоинты сессии (EARS-17).
- Сбой письма никогда не выглядит как потерянная заявка (EARS-12).
