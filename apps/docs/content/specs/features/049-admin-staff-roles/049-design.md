# 049 — Admin staff roles (Design)

Requirements: [`049-requirements-en.md`](./049-requirements-en.md) · Builds on: [`047-design.md`](../047-staff-access/047-design.md) («Доступы»), [`007-design.md`](../007-event-admin-minimal/007-design.md) (event authoring and lifecycle), 011 (admin session, break-glass CLI), ADR-0001 §10 + A1/A3 (live revalidation).

## Role keys and where each is read

| Place                                                                                                                                                       | `superadmin`                                                 | `broadcast_director`                                      |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------- |
| Zitadel project role, seeded by `infra/dev-stand/idp/provision.sh` (`SEED_ROLE` default; the prod converge in `tools/deploy/prod.mjs` runs the same script) | added                                                        | added                                                     |
| `ROLES` (`apps/api/src/authz/authz.types.ts`)                                                                                                               | added                                                        | added                                                     |
| `STAFF_ROLES` precedence (`apps/api/src/auth/staff-role.ts`)                                                                                                | first                                                        | after `congress-program-committee`, before `legacy_admin` |
| `MFA_REQUIRED_BY_ROLE` (`mfa-policy.ts`)                                                                                                                    | `true`                                                       | `true`                                                    |
| `AdminAuthorityRole` (`idp.types.ts`) + revoked code                                                                                                        | `SUPERADMIN_REQUIRED`                                        | `BROADCAST_DIRECTOR_REQUIRED`                             |
| `GRANTABLE_STAFF_ROLES` (`packages/schemas/src/admin/staff-access.ts`)                                                                                      | **not** added                                                | added                                                     |
| Admin RU label (`apps/admin/messages/ru.json`, role labels)                                                                                                 | «Суперадминистратор»                                         | «Режиссёр трансляций»                                     |
| e2e fixture (`packages/e2e/admin/admin-session.ts`)                                                                                                         | a superadmin account (holds `superadmin` + `platform_admin`) | a director-only account                                   |

The key style follows the existing set: global roles take an underscore (`platform_admin`, `pd_officer`), event-bound roles a hyphen. `users.role` is free text, so the mirror needs no migration; `mirrorRoleFromClaims` records `superadmin` for a superadministrator (it is first), and `isParticipant` already excludes every non-`doctor_guest` mirror value.

A superadministrator holds `superadmin` **and** `platform_admin` as two keys of one project grant. The guard has no hierarchy: a route admits the roles its `@Authz` row names and nothing else. That is why the ~109 `[platform_admin]` rows stay untouched and a superadministrator still reaches them — through its `platform_admin` key.

**Invariant: a `superadmin` holder always holds `platform_admin` (EARS-5, EARS-6).** The operator command grants both. The 047 revocation refuses to remove `platform_admin` from an account that still holds `superadmin` (`409 STAFF_REVOKE_SUPERADMIN_HOLDER`). The command's `remove` takes `superadmin` only and never touches `platform_admin`. No path writes a grant that has `superadmin` without `platform_admin`, so a superadmin-only session cannot exist.

## Admin-session endpoints (EARS-1)

The six admin-auth rows that list roles — `POST mfa/enroll/start`, `mfa/enroll/verify`, `mfa/verify`, `mfa/reverify`, `GET session`, `POST logout` (`admin-auth.controller.ts`) — become `[platform_admin, event-registrar, congress-program-committee, broadcast_director, superadmin]`. `superadmin` is listed so that the row names every staff role the admin admits. Under the invariant above every holder also holds `platform_admin`, so no session is admitted through `superadmin` alone. `POST login` stays `public`; `startLogin` admits a principal through `requiresMfa`, so the policy entry is what opens the door.

## Live revalidation — ADR-0001 A4 (EARS-3, EARS-7)

`requiredAuthorityRole` (`admin-authority.guard.ts`) gains two branches, in this order before the existing ones:

1. a row naming `superadmin` → ask the IdP about `superadmin` (whatever else the session holds) → `403 SUPERADMIN_REQUIRED` when withdrawn;
2. after `pd_officer` and the `platform_admin` branch: a row admitting `broadcast_director`, for a session without `platform_admin` that holds `broadcast_director` → ask about `broadcast_director` → `403 BROADCAST_DIRECTOR_REQUIRED`.

The matrix validator (`authz.matrix.ts`) accepts a live / step-up row whose roles include `superadmin` or `broadcast_director`. Revalidation still only chooses which grant is asked about; the route `roles` check decides admission (A1). The rule is recorded as ADR-0001 amendment A4 by the Issue that ships the guard change, in the shape of A1/A3, with the admin console mapping both `403` codes to no-access and `503 IDP_REVALIDATION_UNAVAILABLE` to retry.

## «Доступы» under `superadmin` (EARS-3…EARS-5)

| Route                                     | Before                                   | After                                |
| ----------------------------------------- | ---------------------------------------- | ------------------------------------ |
| `GET /v1/admin/staff-access`              | `[platform_admin]`, live                 | `[superadmin]`, live                 |
| `POST /v1/admin/staff-access/grants`      | `[platform_admin]`, live, `stepUp: true` | `[superadmin]`, live, `stepUp: true` |
| `POST /v1/admin/staff-access/revocations` | `[platform_admin]`, live, `stepUp: true` | `[superadmin]`, live, `stepUp: true` |

- **Grant.** `GRANTABLE_STAFF_ROLES` = `platform_admin`, `event-registrar`, `congress-program-committee`, `broadcast_director`. The Zod enum refuses `superadmin` (`400`) before the cascade. A director grant is the 047 `platform_admin` path — no event, no binding row; completeness reads the IdP grant, password, `users` row and the latest ledger row exactly as 047 «Completeness and retry».
- **List.** The IdP grant search widens from «roleKeys ∩ GRANTABLE_STAFF_ROLES» to «roleKeys ∩ (GRANTABLE_STAFF_ROLES ∪ {superadmin})». A `superadmin` row and a `broadcast_director` row are one row per person with an empty event. The list row contract carries a `revocable: boolean` (false for `superadmin`, for the caller's own `platform_admin` and for the `platform_admin` of any account that holds `superadmin`); the admin draws «Отозвать» only when `revocable`. The row's `role` enum is the listed set (grantable ∪ `superadmin`), not the grantable set.
- **Revoke.** The revocation enum stays `GRANTABLE_STAFF_ROLES`, so `superadmin` is `400`. The 047 self-revocation refusal of `platform_admin` stands for the superadministrator. A revocation of `platform_admin` from an account whose IdP grant still holds `superadmin` is refused before any IdP write, with `409 STAFF_REVOKE_SUPERADMIN_HOLDER`, shown as «Это суперадминистратор: роль «Администратор платформы» у него не отзывается. Сначала оператор снимает роль суперадминистратора.», and nothing changed: no IdP write, no session ended, no ledger row. Once the operator command has removed `superadmin`, the same revocation takes the 047 path. A director revocation is the 047 `platform_admin` path: IdP role removal, `forceLogout` + pending-sign-in purge, `auth.role.revoked`.
- **Chrome.** `ADMIN_SECTION_NAV`'s «Доступы» entry is drawn only when `session.roles` include `superadmin`; `canAccessPath("/access")` and `canAccessResource("staff-access")` require it. A platform administrator without it gets the existing refusal page on `/access`.

047's e2e fixtures and its `@feature:047` scenarios sign in as a platform administrator; they move to the superadmin fixture in the same Issue.

## Operator command (EARS-6)

`apps/api/scripts/superadmin.ts` (`pnpm --filter @ds/api superadmin -- grant|remove --email <e> --by-admin <sub>`), on the shape of `break-glass-cli.ts`: a boot half that opens an HTTP-less Nest context, and a run half testable with a context double.

- **It writes through the staff-access service**, not around it: the same IdP adapter calls (find by email, read grant, `PUT` grant), the same `users` mirror upsert and the same ledger writer, so its `auth.role.granted` / `auth.role.revoked` rows are shape-identical to a «Доступы» row with `by_admin` = the operator subject passed. No step-up — the operator has shell access to the API host, which is the trust root ADR-0001 §8 gives staff-account creation; the compensating control is the runbook note.
- **`--by-admin`** — before any write, both verbs look up the subject in the IdP (user by id). When it is missing, malformed or resolves to no user, the command refuses with a reason and changes nothing. The subject must be an existing account; the command does not check that account's roles.
- **grant** — refuse an unknown, unverified or ambiguous email (047 EARS-3 rules; the command creates no account and sets no password — the person signs in with their own password and has, or enrols, TOTP); add `superadmin` and `platform_admin` to the existing grant, each only when absent; append one `auth.role.granted` per role added. Running it again finds both present and writes nothing.
- **remove** — refuse when the IdP project grant search finds no other holder of `superadmin`; otherwise remove `superadmin` only (`platform_admin` stays; once `superadmin` is gone, a superadministrator may revoke it in «Доступы»), end every admin session and pending sign-in (`forceLogout` + purge, as 047 EARS-7), append `auth.role.revoked`.
- **First holder.** For the very first run there is no superadministrator to name; `--by-admin` is the operator's own subject (for the owner's account, the account itself), the same as a break-glass run.
- **Runbook.** `apps/docs/content/operations/admin-onboarding.md` gains «Superadministrator» — when to run it, the exact command, and the post-action note on the tracking Issue (operator, target, why).

## Admin chrome (EARS-3, EARS-8)

`apps/admin/lib/admin-access.ts`:

- `AdminAccess` gains `superadmin: boolean` and `director: boolean`. `full` stays «holds `platform_admin`».
- `adminNavItems`: `full` → `ADMIN_SECTION_NAV` minus «Доступы» unless `superadmin`; a director without `full` → `[{ href: "/events", … "app.nav.events" }]` followed by the registrar / committee links it also holds.
- `canAccessPath` for a director without `full`: `/events`, `/events/create`, `/events/<id>` only (not `/events/<id>/roster|submissions|congress-intake`); `canAccessResource`: `events`, `event-kinds`, `projects`, `experts`, `directions` and the three event-link resources. For `projects` and `experts` this covers the list and the detail read. For `event-kinds` and `directions` it covers the list read, as the table allows. `/access` requires `superadmin`.
- **No superadmin-only state.** By the invariant in «Role keys», every `superadmin` session is also `full`. The chrome therefore has no superadmin-only branch, and there is no empty-nav case: a superadministrator gets `ADMIN_SECTION_NAV` with «Доступы», and `landingRedirect` behaves as for any `full` session.
- `landingRedirect` needs no change: `/events` is the director's first link and is accessible.
- Event card and create form (`app/events/[id]/page.tsx`, `app/events/create/page.tsx`, `components/event-form.tsx`): the roster / intake / submissions links, `RecordingsPanel`, the legacy toggle of the create form and the legacy action buttons are drawn only when `access.full`. The rest — the form, `StreamConfigForm`, `LifecycleActions`, the experts / projects / directions panels — is drawn as for a platform administrator.

No new screen and no new composition: the director sees a subset of today's admin, the superadministrator today's «Доступы» with two more role labels. Admin screens are the lead's call (AGENTS.md §7) — no Stage A.

## Release order

The release that ships the «Доступы» move leaves the section with no holder until the operator command runs, because no account holds `superadmin` yet. The prod deploy's IdP converge (`provision.sh`, run by `tools/deploy/prod.mjs`) seeds the two role keys, so the command can run right after the release; the operator runs it for the owner's account and records the post-action note on the parent Issue. Nothing else in the admin changes for any existing account in that window. The step is a deferred prod action, tracked by its own Issue (repo-conventions → «Deferred prod action»).
