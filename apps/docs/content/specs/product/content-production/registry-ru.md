### Правила модели

| Правило                                    | Содержание                                                                                                                                                                                                                                                                    |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1. Давность                               | При конфликте источников действует более поздний: ответы владельца 2026-10-01 > интервью 2026-09-30 > встречи 09 > 08 > … Внутри одной встречи — более поздняя реплика. Вытесненное значение фиксируется пометкой «Заменено», а не открытым вопросом                          |
| R2. Роли — не люди                         | Функции и роли закрепляются только за абстрактными ролями. Имена допустимы лишь как свидетельство интервью (лучше — ссылка на строку). Совмещения, наблюдаемые сегодня, — AS-IS-наблюдение, не модельная роль. Процесс должен масштабироваться без персонального узкого места |
| R3. Состав ролей — результат моделирования | Какие DS-роли существуют (PO и продюсер, маркетолог, роли мероприятийного контура из BPMN) и где их границы — выход моделирования. Такие роли помечены «роль-кандидат», это не вопросы владельцу                                                                              |
| R4. Глоссарий обязателен                   | Каждый доменный термин реестра определён в `glossary-ru.md` (с EN-слагом для переноса в глоссарий репозитория)                                                                                                                                                                |

## Объекты

Обозначения. Источники: черновик владельца «Процесс разработки образовательного контента» (2026-09-30) — строка черновика владельца; `A:/B:/C:` — ID в pass-A/B/C; `Ln` — строка транскрипта; `P:` — элемент AS-IS BPMN мероприятий DS (doctor_school_business_processes.bpmn: Task_/Gateway_/Event_ или lane); `M:дата-время` — встреча BBM из обзора продуктовой линейки; `static` — статические модели bbm-kb (decisions-log, VPC). ICOM: I — вход, C — управление, O — выход, M — механизм, `атрибут` — параметр, аннотирующий блок; `O→I` — выход одной функции становится входом другой (функции указаны). `ВЛ` — ответ владельца 2026-10-01; `AS` — механика авторской доли BBM finmodel (bbm decisions-log 2026-08-10). Колонка «Решение / вопрос»: «Решено» / «Заменено» (R1) с основанием; `→ОВn` — раздел «Открытые вопросы владельцу». Статусы: подтверждён, новый, неоднозначный, роль-кандидат (R3), объединён, исключён, только черновик.

## Роли

Роли — абстрактные позиции модели, не люди (R2): процесс должен масштабироваться без персонального узкого места. Совмещения, наблюдаемые сегодня («один человек — эксперт, рецензент и амбассадор»), приведены только как AS-IS-наблюдение в колонке «Примечание». Состав DS-ролей и их границы (PO и продюсер, маркетолог, роли мероприятийного контура) — результат моделирования (R3): такие роли помечены «роль-кандидат». «Сторона»: DS — команда Doctor.School; фарма — заказчик / спонсор; лидер — лидер мнений и его окружение; внешняя — прочие организации и аудитория. Источник P — дорожки AS-IS BPMN мероприятий.

### Сборка

- Производство стандартизуется снизу вверх: урок → модуль → курс; КП кастомизируется: «совсем разные пути входа в каждую компанию» (M:2026-09-08-0952). Договор и производство — стандартные (L3013-3029, L3075).
- Порядок: сначала договорённость с партнёром (стандартный договор DS — всегда первый шаг, L3329), потом производство (M:2026-07-07-0957).
- Один набор клинических случаев используется в нескольких курсах — стандартная база плюс сборка под партнёра (гипотеза, M:2026-06-09-0959).
- Пожелания компаний учитываются при создании курса (A:O137 → F-018).
