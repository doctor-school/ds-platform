# Cross-front capability ownership registry

This file is the operational form of the AGENTS.md §6 rule **«Cross-front capability reuse before invention»** and of ADR-0013 §A1: every cross-front behaviour has **one canonical core implementation** in a shared package (`packages/**`) or a shared service (`apps/api/**`), and each app adds only a thin host projection — defaults, authorization, response envelope, route, copy. App-to-app imports (`apps/doctor` → `apps/portal`), copied query/state logic and fork UI are forbidden; divergence needs an ADR-backed reason.

The registry exists because the rule kept being restated and kept being missed: a capability that already ships in Academy was re-described as new work for Doctor, and the owner reads that as «rebuilding what already works». Prose could not stop it — a checked-in row, a required Issue field and a CI marker can.

**How it is used.**

- **Before opening an Issue** on a `track:doctor` / `track:academy` deliverable: find the capability's row here (or grep `apps/portal`, `apps/doctor`, `packages/` and ADD the row), then fill the Issue's `Reuse:` field with one of `canon: <path>` / `extract-from: <path> (#N)` / `new: <reason>`. `pnpm issue:create` fails closed without it.
- **Before opening a PR** that adds or moves a file under `apps/portal/**` or `apps/doctor/**`: give it its row in [Host-file allowlist](#host-file-allowlist) or [Route-file registry](#route-file-registry) in the same PR. The BLOCK tree guards check the tree against this file: `pnpm lint:host-allowlist` (every host file has an exact-path row), `pnpm lint:route-mount` (every route file has a row, and a `mounted` route is mount + config, plus at most one sibling server-action binding) and `pnpm lint:import-boundary` (packages never import apps; host configs carry no host logic).
- **Row maintenance is not a separate chore.** The PR that moves a capability — extracts it, adds the second consumer, or lands the shared unit — **updates its row in the same commit**. A row that disagrees with the tree is a review finding, not a follow-up.

`Kind` is one of **shared package** (`packages/**` — design-system block/primitive, schema, codec), **shared API** (`apps/api/**` service/repository + a `packages/schemas` contract), or **host-only** (a file listed in the [Host-file allowlist](#host-file-allowlist) below, with the reason recorded there). There is no «app-local» kind: a helper under `apps/<host>/{lib,components}` whose sibling exists on the other host is a violation, not a licence (ADR-0013 §A1). Every row also carries **Owner package** — the one package that owns the capability's behaviour («shared already» when the canonical location is that owner; «net-new» when no second host consumes it yet) (ADR-0013 §A1); a host adds only a route file and host-config fields over it.

## Route-file registry

This table is the checked-in answer key for every Next.js composition route file of the two storefronts and of the sign-in host — every `apps/portal/app/**/{page,layout}.tsx`, `apps/doctor/app/**/{page,layout}.tsx` and `apps/login/app/**/{page,layout}.tsx`. It is the second of the three tree checks of [#2002](https://github.com/doctor-school/ds-platform/issues/2002) (tech spec §3 rule 3, «Route mount»): the host-file allowlist above deliberately skips route files, so `page.tsx` is the one place a storefront could still grow host logic unobserved. **A new route file needs a row here in the same PR** — `pnpm lint:route-mount` reads this table and fails a route it cannot find (WARN until wave 1 lands, BLOCK after, per #2074). Rows are exact repo-relative paths, never globs, sorted by path, and a row naming a file that no longer exists fails too.

`package` is the `@ds/<name>` the route mounts or will mount; a `permanent` row carries `—` plus the reason it is host-only. `until` is one of three recorded states:

- **`wave N (#Issue)`** — the page still carries inline host logic until that wave extracts it into the package. Its body is **not** read by the guard; a PR diff touching it is a WARN with the row quoted (the honest limit), so growth of a doomed route file stays visible.
- **`mounted`** — the page is a thin projection **now**, and the guard enforces mount-only: the only imports allowed are the package (and its subpaths), the route's own host-config module and `import type … from "next"`; the only body allowed is Next segment config (`dynamic = "<literal>"`, `metadata` of string literals and package-import reads) plus one default export returning the package mount with its config, optionally preceded by `await` of the route props; the mount's attributes are string literals or bare identifiers naming the host config, the binding, a route prop or an awaited name.
- **`permanent`** — a genuinely host-only route (brand frame, host-only surface) that no wave replaces.

Out of scope, as in the allowlist: `loading` / `error` / `not-found` / `template` / `default` / `route` files — presentational shells and API stubs, not the composition surface a wave extracts.
