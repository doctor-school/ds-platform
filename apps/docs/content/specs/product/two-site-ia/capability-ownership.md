# Cross-front capability ownership registry

This file is the operational form of the AGENTS.md §6 rule **«Cross-front capability reuse before invention»** and of ADR-0013 §A1: every cross-front behaviour has **one canonical core implementation** in a shared package (`packages/**`) or a shared service (`apps/api/**`), and each app adds only a thin host projection — defaults, authorization, response envelope, route, copy. App-to-app imports (`apps/doctor` → `apps/portal`), copied query/state logic and fork UI are forbidden; divergence needs an ADR-backed reason.

The registry exists because the rule kept being restated and kept being missed: a capability that already ships in Academy was re-described as new work for Doctor, and the owner reads that as «rebuilding what already works». Prose could not stop it — a checked-in row, a required Issue field and a CI marker can.

**How it is used.**

- **Before opening an Issue** on a `track:doctor` / `track:academy` deliverable: find the capability's row here (or grep `apps/portal`, `apps/doctor`, `packages/` and ADD the row), then fill the Issue's `Reuse:` field with one of `canon: <path>` / `extract-from: <path> (#N)` / `new: <reason>`. `pnpm issue:create` fails closed without it.
- **Before opening a PR** that touches `apps/portal/{app,components,lib}/**` or `apps/doctor/{app,components,lib}/**`: put a `cross-front reuse:` line in the PR body naming the canonical path you consumed, or stating `new` / `bespoke` with a rationale. The `cross-front-reuse` guard (`tools/lint/cross-front-reuse-lint.ts`, WARN posture per ADR-0007 §2.6) checks it.
- **Row maintenance is not a separate chore.** The PR that moves a capability — extracts it, adds the second consumer, or lands the shared unit — **updates its row in the same commit**. A row that disagrees with the tree is a review finding, not a follow-up.

`Kind` is one of **shared package** (`packages/**` — design-system block/primitive, schema, codec), **shared API** (`apps/api/**` service/repository + a `packages/schemas` contract), or **app-local** (host composition that has not earned extraction yet; the `Extraction / debt` column then says what would trigger it).

Thin host projections are intentional: Academy and Doctor have different targeting, envelopes and copy, but both delegate to the same services and contracts. What the registry forbids is the other thing — a second implementation of the core.

[`019-design.md`](../../features/019-doctor-events-feed/019-design.md) §1.1 (EARS-15) defers to this file: the 019 matrix was the first, spec-scoped version of this table and is now a pointer, so one registry serves every doctor/academy spec instead of one per feature.
