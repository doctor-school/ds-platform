## 2. Decision — feature packages (the architecture)

**Decision.** A capability used by both storefronts lives in one **feature package** under `packages/` that exports the complete behaviour: page-level components, hooks, URL-state codecs, routing after actions (`returnTo`, replay, entry policy), error dictionaries, default copy and the tests that came with the Academy implementation. A storefront contributes exactly two things per capability: a **route file** (the Next.js `page.tsx` that mounts the package component) and a **host-config object**. Nothing else about that capability may exist under `apps/<host>/`.

**Host config (the only legitimate divergence).** Route table (paths on this host), copy source (a messages object; the Academy passes `next-intl` messages, the doctor host its RU literals until unified), data endpoint / adapter (`/v1/public/events` vs `/v1/storefront/doctor/events` with specialty targeting), filter defaults, brand assets, consent list, feature flags the product owner has decided per host. A divergence that is not expressible as config needs an ADR-backed product reason recorded before implementation (ADR-0013 §A1 unchanged).

**Package contract (what «complete behaviour» means).** A feature package ships two entry points: `@ds/<pkg>` (client components, hooks, URL-state codecs, error dictionaries) and `@ds/<pkg>/server` (server components, `generateMetadata` builders, server actions, the `middleware.ts` / `proxy.ts` helpers such as `returnTo` parking and session forwarding, cache-tag / `revalidate` policy). A package imports `@ds/schemas`, `@ds/design-system`, another feature package only in the direction fixed in §4 («Dependency graph»), and never `apps/*`. Cross-cutting host files — `middleware.ts` / `proxy.ts`, `layout.tsx` metadata, server actions, the session cookie / `ForwardedSession` shape, caching — keep the decision in the package as an exported helper; the host file is one call with its config. The `returnTo` parking rule in `apps/portal/middleware.ts` is the first such case and moves with wave 1.

**Host-config type (where adaptation ends and business logic begins).** Every package exports `HostConfig` and the host module ends with `satisfies HostConfig`. Allowed field kinds are closed:

- **data** — route table (path strings), copy source (messages object), endpoint paths, consent list, brand assets, filter defaults, per-host product flags (`boolean` / string enum) the owner has decided;
- **adapters** — pure `(dto) => model` mappers over the response of the configured endpoint, and a `(key) => string` copy resolver. An adapter reads only its argument: no session, no URL, no branching on user or event state.

Forbidden in a host config: lifecycle callbacks (`onSuccess`, `onError`, `beforeSubmit`), landing / redirect resolvers (`resolveLanding`, `nextRoute`), predicates deciding whether an action is allowed, any function that reads host state. A behaviour that differs between hosts is a named flag whose **every branch lives in the package with a test per branch**, or a product divergence recorded per ADR-0013 §A1 before implementation. The doctor host's own decisions that exist today — landing selection by specialty (`registration-landing`), the stale-`returnTo` explanation (`return-context-card`), the extra confirmation / consent states, the `/verify` THROW-branch divergence (DEBT 2026-09-07) — are the first entries of the wave-1 behaviour matrix (§4), each either a flag with both branches in the package, a recorded product divergence, or a convergence the owner has approved.

**Layering after the change.**

| Layer                                                                                                                                                                     | Owner       | Holds                                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/api` + `packages/schemas`                                                                                                                                           | one backend | domain, contracts, server policies (CTA, room entry, rate limits)                                                                                       |
| `packages/design-system`                                                                                                                                                  | shared      | primitives and blocks — presentation only, no transport, no routing                                                                                     |
| **feature packages** (`packages/auth-flow`, `packages/events-storefront`, `packages/account`, existing `packages/room`, `packages/legal-content`; names settled per wave) | shared      | pages, hooks, URL state, post-action routing, error maps, default copy, tests                                                                           |
| `apps/portal`, `apps/doctor`                                                                                                                                              | per host    | route files, chrome (header/footer/theme mount), host-config objects, host-only pages (doctor: specialties, hero; Academy: projects, experts, partners) |

**Rejected: multi-tenant single app** (one Next.js app, host-based middleware, Vercel Platforms pattern). It yields the same sharing plus a shared shell, but couples the two tracks into one deploy unit and one release train, while the tracks ship on separate milestones with different IA, and `apps/doctor` already runs as its own container (#1860). Feature packages keep separate release trains **possible** without forcing them: today `pnpm deploy:prod` ships both containers from one SHA and one service set, so a shared package does not by itself make either host releasable alone — the argument is about not closing that door, not about a benefit realised now. The option can be revisited if the shells converge.

**Rejected: «copy the file».** A copy is a fork the same day — the six twin files above are the evidence. The correct form of «copy» in a monorepo is an import. The one bounded exception is stage 0 below: a marked (`// mirror-of:`), DEBT-tracked, branch-by-branch copy that the named wave deletes — never an unmarked copy, never past the wave its marker names (lifetime and marker format: stage 0 below).

## 3. Rules that change (stage 1, docs only)

1. **ADR-0013 §A1** — inline rewrite of «thin host projection»: a route file plus a host-config object. A helper under `apps/<host>/{lib,components}` whose sibling exists on the other host is a violation, not «app-local». The same rewrite moves §A1's closing sentence — ownership of the auth shell and the login / recovery / confirmation **compositions** — from `@ds/design-system` blocks to `packages/auth-flow`; design-system keeps the cards (presentation), the package owns the compositions (behaviour).
2. **Registry `capability-ownership.md`** — new column «Target package / wave»; new section «Host-file allowlist» listing every file permitted under `apps/{portal,doctor}/{lib,components}` with its reason; delete the wording «the two host compositions stay app-local» (row 35) and «extract on a third host or a behavioural divergence» (row 44) — they license duplication; rows 45–46 (`theme-toggle` copy, msk «extract on the next touch») get a target package and wave instead of a DEBT pointer.
3. **Guard** — #2002 is rewritten: replace the PR-body string check with three tree checks, each with negative fixtures for the bypass it closes (BLOCK after wave 1; WARN until then; the `cross-front-reuse` PR-body marker is retired when the guard turns BLOCK; #1874 / #1907 / #1564 folded in):
   - **Allowlist** over every `apps/{portal,doctor}/**/*.{ts,tsx}` except Next.js route files (`page`, `layout`, `loading`, `error`, `not-found`, `template`, `default`, `route`, `middleware` / `proxy`), tests and `e2e/**` — a new file anywhere else (a `hooks/` directory, an `app/**/*-client.tsx`, a renamed directory) needs its registry row in the same PR. Negative fixtures: a helper under `hooks/`, a client component beside `page.tsx`.
   - **Route mount** — a route file whose path the registry assigns to a package imports that package's page export and, from the host, only its host-config module; any other import or a body beyond mount + config fails. Negative fixture: fetch-and-branch logic written straight into `page.tsx`.
   - **Import boundary** — `packages/**` never import `apps/*` or another package against the §4 dependency direction (ESLint `local/package-import-boundary` in `tools/lint/eslint-rules`, run as the promotable `pnpm lint:import-boundary`); a host-config module — recognised by the file convention `host-config.{ts,tsx}` / `*.host-config.{ts,tsx}` under `apps/{portal,doctor}` — imports nothing from `apps/<host>/{lib,components}` and type-checks against the package's `HostConfig` (`satisfies`), which rejects function-valued fields outside the closed adapter list. Negative fixtures: a package importing `apps/portal/lib/*`, a config with an `onSuccess` callback.
   - **Honest limit.** A file already on the allowlist can still grow. A diff touching a row whose `until` names a wave is WARN with the row quoted, so growth of a doomed file is visible; beyond that, allowlisted files remain reviewer territory (rule 5), and the guard's claim is «no _new_ host logic without a registry event», not «no duplication».
4. **Specs** — a storefront spec for a capability already live on the other host is one boundary line «projection of `packages/<x>`; host-config diff: …», never a re-specified EARS list. 021 stays as the recorded counter-example. `author-ears-spec` and `open-ears-issues` 2b get this rule; an EARS Issue whose behaviour the other host already ships is closed as a duplicate of the extraction wave, not implemented. **No requirement is lost in the collapse**: the wave Issue that absorbs or closes an EARS Issue carries a disposition table — every shall-clause of the absorbed Issue is one of **covered** (package test id), **host difference** (config flag + the test of that branch), or **cancelled** (owner decision, quoted) — and the projection line in the storefront spec links the source EARS it stands for. First instance: 021's «a disabled submit always states its reason» (#1548) has no Academy precedent and is an open owner question on #2027, not an implicit drop.
5. **Briefs** — an extraction brief names both halves (storage/helper AND every call-site decision rule) with `file:line`, lists every behaviour branch (missing / success / failure) the package must reproduce, and forbids a host-local substitute («if the rule does not fit the host, STOP and return the question»). `request-mode-a-review` asks «does the host mount the package, and is every divergence a config field?».
6. **Design canvases** — section 6 below.

## 5. Guard shape (why an allowlist, not a marker)

A PR-body marker is a field the author fills after the code exists; it verifies attention, not structure. The allowlist inverts the default: a file under a storefront's `lib/` or `components/` exists only because the registry says why. Adding host logic then requires a registry edit in the same PR, which is the review event the current rule lacks. The allowlist alone is necessary, not sufficient: logic written into `page.tsx`, a new `hooks/` directory or a callback smuggled through host config all pass a `{lib,components}` allowlist — hence the route-mount and import-boundary checks of §3 rule 3 travel with it, and #2002 is not done until the three checks and their negative fixtures are green. Severity path per ADR-0007 §2.6: WARN until wave 1 lands, BLOCK after.

## 6. Design canon — one canvas per capability

The same duplication exists in `design-source/` and confuses vendoring (tokens and artboards are pulled per file). Consolidating a capability drawn twice is a **wave-ENTRY condition** (owner 2026-09-08) — the §4 gate names the drawing Issue and its `blocked_by` edge on the wave; the archive moves and the duplicate sets no wave touches are stage-3 cleanup, owned by #2075. A wave needs one owning package per component, the approved variants of both hosts preserved, and a parity check of the package against the canvases both hosts were built from — not a single physical file. Merging two canvases is an owner drawing action; a visible difference discovered while merging is a Stage-A question, never something the merge resolves on its own, so a consolidation can never quietly become a redesign.

Rules (land in `design-source/README.md`, stage 1):

1. **One canvas per capability, host as a prop.** A capability both storefronts render has one `.dc.html`; host differences are props / fork panels, never a second `doctor-*` / `academy-*` file. Host-only screens (`doctor-feed`, `doctor-school`, `academy-invest`, …) keep their host prefix.
2. **Tokens only in `design-system.dc.html`.** No canvas redefines a colour, radius or type step; a canvas that does is a vendoring defect, not a design decision.
3. **Superseded and decision canvases move to `design-source/archive/`** in the PR that vendors the successor or records the decision; the README table lists only canon.
4. **Vendoring writes the registry row.** The PR that vendors a canvas names the feature package (not the host) that will build it; the registry row and the canvas table stay in sync.
5. **Owner draws once.** When a doctor screen equals an Academy screen, the request to the owner is «add the host prop / fork panel to `<canon>.dc.html`», never «draw the doctor version».
6. **Stage A for a shared capability is the host-switched canvas.** A capability both storefronts render is designed once, in one canvas whose `host` prop shows/hides the host-specific blocks (e.g. the 021 medical-worker declaration on `витрина врача`, absent on `Академия`); a canvas drawn for one host is not Stage-A approval for the other, and the wave that builds the package does not start until that canvas exists (#2076 events feed, #2080 auth).
