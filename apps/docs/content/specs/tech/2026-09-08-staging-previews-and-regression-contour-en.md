# Staging box, per-PR previews and the end-to-end regression contour

Issue: [#2056](https://github.com/doctor-school/ds-platform/issues/2056). Owner request of 2026-09-08: «пересматриваем систему и среду разработки … сделать надёжнее, сильнее и устойчивее, а не добавлять точки отказа, хрупкость или переусложнять … многие вещи, если можно, лучше сделать детерминированно, убрав генеративный элемент», and «Я бы наоборот пошёл от минимального набора, чтобы не плодить точки отказа. Но сама механика со стейджингом мне нравится.» This document is the single place the plan lives between sessions; a session working on it reads this file first and updates §8 and §10 here, never a parallel note.

Related canon it changes or narrows: AGENTS.md §6 («Verify UI live before done», «Worktree-per-session», «PR lifecycle runs to completion»), AGENTS.md §9 and `.claude/rules/dev-stand.md` (local stand, ports, branch databases), skill `build-ui-from-design-system` → Stage B (owner stand on the lead's machine), `tools/deploy/release-gate.mjs` (release gate inputs), the release-cycle spec §10 (`2026-07-15-release-cycle-context-freshness-design-en.md`). Related open Issues it absorbs: #1490, #1510, #1530, #1554, #1778 (the five «Integration: NNN-scenarios.feature Playwright-BDD journey against the real stack» Issues), #2012 (standalone-boot probes), #1943 (dev-stand seed), #1692 — its «live-stand axe leg has no CI home» half only: the `shell-axe` suite (008 EARS-12) runs on every slot (§6.6); the `.origin-bottom` contrast defect it reports stays a product fix on Issue #1692 itself (hotfix-pr), a prerequisite of §8 step 6 — the axe bar is never armed on a slot while the defect is known red.

## 1. Finding (why this exists)

Release `release-2026.09.08-1` (SHA `b9ca3371`) shipped regressions that every local and CI tier had passed. They belong to one class: **the production artifact was never executed with the full stack before it reached production.** Verified against `origin/main` of 2026-09-08:

- **No tier runs the browser → Next.js → api junction automatically.** `api-e2e` and `admin-e2e` in `ci.yml` boot real Postgres + Zitadel and test the NestJS api over HTTP. The Playwright jobs for `@ds/portal` and `@ds/doctor` boot `next start` with **no api behind it**: `apps/doctor/playwright.ci.config.ts` `testIgnore`s 13 of the 35 doctor e2e specs (the «return-context tier» that needs a live api); `apps/portal/playwright.ci.config.ts` pins CI to the backend-free axe scan. Every session-dependent page (account, my events, registration state, event page) is verified only by hand.
- **No tier runs the production artifact.** The Playwright tiers run a full `.next` build; production ships `.next/standalone` inside an image built on the box (`apps/{portal,doctor}/Dockerfile`, `tools/deploy/prod.mjs` «on-box builds, no registry»). `tools/ci/standalone-boot-check.mjs` is the one tier that boots the standalone server, and it probes `/` only, accepting any status below 500 (#2012). `tools/deploy/smoke-prod.mjs` probes a fixed list of cold pages **after** the switch.
- **The regression check is a manual, generative step.** The owner's Stage-B drive on a stand served from the lead's machine (`build-ui-from-design-system` → Stage B) is the only place a whole journey is exercised; it is exploratory and unrepeatable, and by canon it is _acceptance_, not QA (memory `feedback_prestageb_exploratory_acceptance_drive`). The five «Integration: … journey against the real stack» Issues that would make the journeys repeatable are all open; the `.feature` files exist (19 under `specs/features/*/`, 4 more under `apps/portal/e2e/features/`) and are executed nowhere automatically.
- **The local-stand discipline is the largest rule family in the repo and the one that breaks most.** `.claude/rules/dev-stand.md` «Parallel sessions» (port probing, «never kill a listener you did not start», foreign-holder teardown refusal, branch databases, coordination-gated rollback) and the Stage-B stand-survival rules exist because several sessions share one developer machine and one personal TrueNAS stand. Memories `reference_lander_needs_main_tree_session`, `reference_stage_b_stand_survival_and_peer_merge`, `feedback_worktree_discipline` record the failures. None of these rules protect production; they protect one machine from its own concurrency.

A per-route or per-link probe list (the first proposal in the session) was rejected by the owner as a point fix: «А что если в новом релизе добавится ещё десяток ссылок? Опять менять составы команд?» — and it would not have caught a `200` that renders the wrong page. The decision below contains **no hand-maintained lists**: every verified set is derived from an artifact that changes together with the code.

## 2. Decision

One always-on **staging box** runs the same compose files as production and hosts two kinds of slots: a persistent **`main` slot** (the release candidate) and ephemeral **`pr-<N>` preview slots**, one per open pull request, each on a **cloned golden database**. A **spec-derived end-to-end suite** (`playwright-bdd` over the spec's `NNN-scenarios.feature` files plus two artifact-derived walks) runs on every preview and on every `main` deploy; its result is a head-pinned GitHub check-run. The **release gate reads only recorded state**: a green `main`-slot run for the exact SHA. **Local stands leave the delivery discipline**: the owner's Stage-B acceptance happens on the preview URL, the regression evidence is the suite, and the lead never serves a stand from a developer machine again.

Minimal component set, nothing beyond it (owner: «от минимального набора»):

## 3. Topology

**Box.** One VPS (`stage-1`) sized for concurrent on-box image builds plus 3–5 live previews; the size is an owner decision recorded in §10, the working assumption is ≥8 vCPU / 16 GB / 160 GB NVMe. It is provisioned by the same Terraform module shapes as `api-prod` (`api-prod.tf` → `stage-1.tf`), with the same public firewall model (22 from the operator allowlist, 80/443 public) — but in its **own VPC** (`twc_vpc.stage`, its own CIDR), not in `twc_vpc.ds`. The Timeweb rule model is allow-only and the production VPC firewall does not filter the private interface (`infra/deploy/terraform/network.tf`, DSO-125 note: the existing rules already open 5432/6379/22 to the whole `var.vpc_cidr`), so a deny rule cannot isolate a box that runs arbitrary PR code; the absence of a network path can. It is the **only** new machine.

**Shared infrastructure project** `stg-infra` (compose project name), started once and kept up: Postgres 17 (the `data-prod` image with pgvector + pg_partman), Redis, Zitadel + `zitadel-login`, Centrifugo, Cerbos, MinIO, Mailpit, sms-sink, `sms-aero-adapter` pointed at the sink, Caddy. This is the service list of the TrueNAS dev stand today (`infra/dev-stand/compose.core.yml`) — the stand moves from a personal box to a project box; `infra/dev-stand/` stays the portable contract and gains the staging recipe as its reference recipe (§7).

**Slots.** A slot is one compose project (`main` or `pr-<N>`) running exactly the product services: `api`, `portal`, `doctor`, `admin`, and the `migrate` one-shot, built from the slot's git tree with the production Dockerfiles (`docker compose build`, image tag = the slot's head SHA, no registry — identical to `tools/deploy/prod.mjs`). Each slot joins the `stg-infra` network; nothing in a slot publishes a host port. Caddy resolves slot containers by compose DNS name (`pr-2034-portal`), so **there is no port allocation anywhere** — the port-pair discipline of `dev-stand.md` has no counterpart here.

**Hostnames.** `*.stage.doctor.school` wildcard `A` record in the DNS zone (owner-managed, like the production records). Per slot: `academy-<slot>.stage.doctor.school` → portal, `doctor-<slot>.stage.doctor.school` → doctor, `api-<slot>.stage.doctor.school` → api, `admin-<slot>.stage.doctor.school` → admin; `<slot>` is `main` or `pr-<N>`. TLS via Caddy on-demand issuing with an `ask` endpoint served by C3 that answers 200 only for hosts of currently registered slots (bounds certificate issuance to real slots). Every staging host is behind Caddy basic auth (one credential pair in the box env, known to the owner and to the suite runner) and sends `X-Robots-Tag: noindex`.

**Identity.** One Zitadel instance for all slots, one project, provisioned by the existing `provision.sh` converge on `stg-infra` start; every slot's api uses the same IdP project and client. Consequence recorded as a rule, not a hope: **a PR that changes IdP provisioning (`provision.sh`, `idp-policy.mjs`) is serialized like a migration** — one in flight repo-wide, its preview runs the converge against the shared IdP and the change is visible to every other slot; the PR body names this. Per-PR Zitadel instances are a non-goal.

**Secrets and side effects.** The box has its own `.env` set (never production values); SMS and email terminate in the sinks; SmartCaptcha uses the vendor's test keys; egress otherwise follows production (`ADR-0011`). A staging slot can never reach production Postgres, Redis, S3 or Zitadel — `stage-1` has no route into `twc_vpc.ds` (separate VPC, §3 Box), verified as part of C1 acceptance; production S3 and Zitadel are additionally guarded by the box holding no production credentials.

## 4. Data — golden dataset, template database, clones

**Golden dataset (C5).** A deterministic seed in `packages/db/src/seed/golden/` with fixed UUIDs and fixed timestamps relative to a pinned «now» (so an «upcoming» event stays upcoming): doctor accounts in every state the specs distinguish (unverified, verified, MFA-enrolled, deleted), an admin account, experts, projects, events in every lifecycle state (draft, published upcoming, live, hidden, past with recording), registrations, the legal documents. Doctor and admin accounts also exist in the shared Zitadel with credentials read from the box env; the seed asserts they exist and refuses to run otherwise (no silent creation with generated passwords). The dataset is **the only test data**; a scenario that needs data the golden set lacks extends the golden set in the same PR. `#1943` (seed an expert on the seeded event) is absorbed here.

**Template database.** `ds_golden` is rebuilt by the `main` slot deploy whenever `apps/api/drizzle/**` (the Drizzle output directory, `packages/db/drizzle.config.ts`) or `packages/db/src/seed/golden/**` changed at the deployed SHA: `CREATE DATABASE ds_golden_next` → migrate to the `main` head → seed → rename old to `ds_golden_prev`, new to `ds_golden` (one `_prev` kept). It is never migrated in place, so it is always «main head + golden seed» and nothing else.

**Clones.** `slot up pr-<N>` runs `CREATE DATABASE ds_pr_<N> TEMPLATE ds_golden` (seconds), then the slot's own `migrate` one-shot on the clone. `slot sync` (a new push) re-clones from scratch rather than migrating forward — a preview always reflects «main golden + this branch's migrations», never an accumulation. `slot down` drops the database. `dev:db:branch` on TrueNAS becomes unnecessary for delivery (§7).

**`main` slot database.** `ds_main` persists across `main` deploys and is migrated forward by the slot's `migrate` one-shot exactly as production is — this is the pre-production proof that the migration set applies to a live database with data. `slot reset main` rebuilds it from `ds_golden` (operator command, logged).

**Production data** never reaches the box (doctors' personal data, 152-ФЗ). The realistic shape of the golden set is the substitute, and its realism is a spec responsibility (§6.1: a scenario's `Given` names golden entities).

## 5. Pipeline

**PR lifecycle (C4 → C3).**

1. `opened` / `reopened` / `synchronize`: the workflow (GitHub-hosted runner, SSH to the box with a deploy key held as a repository secret — the same shape `deploy:prod` uses from the operator machine, moved to CI for staging only) runs `slot up|sync pr-<N> <head-sha>`: `git archive` of the head into `/srv/slots/pr-<N>/`, `docker compose build`, clone database, `migrate`, `up -d`, register the four hostnames with the `ask` endpoint, wait for `/v1/health` of the slot to report the head SHA (the existing `version` field). Then it runs the regression suite (§6) against the slot from the runner and uploads the Playwright HTML report as the workflow artifact.
2. It posts **one sticky PR comment** (edited in place, marker `<!-- preview -->`): the four URLs, the head SHA, the suite verdict with per-`@EARS-N` failures, and the artifact link. The suite result is also a check-run named `preview-e2e` on the head SHA.
3. `closed` (merged or not): `slot down pr-<N>` — compose down with volumes, drop `ds_pr_<N>`, deregister hostnames, prune the slot's images. A nightly `slot gc` on the box removes any slot whose PR is not open (`gh pr view` state) and any image not referenced by an open slot — the safety net for a missed `closed` event.
4. Concurrency: one workflow run per PR at a time (`concurrency: preview-${{ github.event.number }}`, cancel-in-progress); slots of different PRs run concurrently and are independent by construction (own project, own database, own image tags). The two repo-wide serial resources stay what they are today: the Drizzle journal and the shared IdP (§3).

**Stage-B on the preview.** The owner opens the sticky comment's URL; `build-ui-from-design-system` → Stage B keeps its evidence contract (recorded-at, head pin, GO/NO-GO in the PR or the Issue) and loses its stand-serving half: no `next start` on the lead's machine, no port record, no relaunch recipe, no liveness re-check. The lead's exploratory Playwright MCP drive, when a brief calls for one, targets the preview URL.

**Merge gate.** `pnpm merge:gate <N>` (skill `merge-when-green`) already pins check-runs to the head SHA; `preview-e2e` joins the required set for every PR that gets a slot (every non-draft PR; a `docs`-only PR is detected by the existing `changes` job filter and gets no slot and no `preview-e2e` requirement). A `user-facing` PR therefore merges on: Mode (a) APPROVE at head + green CI + green `preview-e2e` at head + the recorded Stage-B GO. No `--mode-a-exempt`-style bypass exists for `preview-e2e`; a red suite is either a product bug (fix in the PR) or a wrong scenario (fix the scenario in the PR, reviewed by Mode (a) as a spec change).

**`main` slot.** On every push to `main` (squash merge), the `push` job of the same workflow runs `slot sync main <sha>` (persistent database, forward migration, template rebuild when needed), then the same suite, and records the result as check-run `main-e2e` on the merge SHA plus a GitHub Deployment `staging` with `success`/`failure`. The `main` slot always shows the newest merged SHA; there is no manual «deploy to staging». Because the slot runs the standalone image, this run is the tier that executes the production artifact (§1, second bullet).

**Release gate (C7).** `release-gate.mjs` gains check 3: the `main-e2e` check-run for the SHA `deploy:prod` is about to ship is `success`; anything else — missing, pending, failure — refuses. A `failure` result is never exemptable (memory `feedback_close_stage_b_gates_before_deploy_not_exempt`: the gate reads state only). A **missing or pending** check-run — the box is down or the run has not finished — is the one case the existing mandatory-reason hatch `--release-gate-exempt "<reason>"` (`tools/deploy/release-gate.mjs`, same contract as `--mode-a-exempt`) also covers for check 3, so a staging outage cannot hold a production hotfix (`deploy:prod --ref <sha>`, #1886) hostage — owner constraint §10 «не плодить точки отказа». The reason lands in the release record; the exempt is logged as a §9 event, never a routine. The hotfix SHA is on `main` by construction, so the ordinary path is covered identically. The existing post-switch `deploy:smoke` stays as the «did the switch happen» probe; it is not extended with route lists.

## 6. Regression contract (C6)

The contract has five rules. Each is enforced by a tool with an exit code; none is enforced by a reviewer's memory.

### 6.1 The spec's feature file is the suite

`apps/docs/content/specs/features/NNN-<slug>/NNN-scenarios.feature` is the **only** source of end-to-end scenarios for a feature. `playwright-bdd` (`bddgen`, already a dependency of `apps/portal`) is configured with `features: [<repo>/apps/docs/content/specs/features/**/NNN-scenarios.feature]` and the host projects select by tag: `@host:academy`, `@host:doctor`, `@host:both`. The four journey files under `apps/portal/e2e/features/` are folded into their specs' feature files in the backfill waves (§8) and the directory is removed; `author-ears-spec` step 7 already produces the feature file, so a new feature costs nothing extra.

Every scenario carries `@EARS-N` tags for the handlers it exercises and a `Given` clause that names golden entities by their seed name (`Given the golden doctor "verified-cardiologist" is signed in`), never by hand-typed data. Step definitions live in `packages/e2e/steps/` (one shared package for both hosts; a host-specific step reads a `HostConfig` field of the step package, mirroring the feature-package rule of the one-code-two-storefronts plan §2) and are ordinary TypeScript reviewed by Mode (a).

Generation policy for agents: an implementer may use the Playwright **planner/generator** agents (Playwright ≥ 1.56, output = ordinary spec/step files) to draft step definitions; the draft is committed and reviewed like hand-written code. The scenario text itself is authored from EARS, never generated from a crawl.

### 6.2 A navigation step asserts the destination, not the address

Rule for step definitions (enforced by `tools/lint/scenario-step-lint.ts`, BLOCK): a step whose text matches `navigates to|opens|lands on` must also name the landing evidence — the page's `h1` text or its `data-surface` marker — and the step implementation asserts both the pathname **and** the evidence. The bare form `Then the shell navigates to "/account/events"` (today in `shell-journey.feature`) is rejected; the accepted form is `Then the shell lands on "/account/events" showing "Мои события"`. This is the rule that turns «200 but the wrong page» into a red check.

### 6.3 Two derived walks, no lists

Both are Playwright specs under `packages/e2e/derived/` that read their inputs from artifacts:

- **Navigation walk.** Each host exports its navigation model from the module that renders it (`apps/portal/components/app-shell-header.tsx` today hard-codes `DISCOVERY_HREF`, `MY_EVENTS_HREF`, `LOGIN_HREF`; the export becomes a typed array `{ label, href, landing: { h1 }, audience: 'guest' | 'doctor' | 'both' }` that the header renders **from**, so the model and the render cannot diverge). The walk visits every item as a guest and as the golden signed-in doctor and asserts status 200, pathname, and `h1`. A guest item that redirects to `/login` asserts the login `h1` and the `returnTo` value.
- **Route walk.** For each host the walk reads the route manifest of the slot's build (`.next/server/app-paths-manifest.json`, exported at image build time to a fixed path the walk fetches from the slot), skips API and internal routes by a fixed pattern, resolves dynamic segments from `packages/e2e/route-params.ts` — a typed map `'/webinars/[slug]' → golden.events.upcoming.slug` — and asserts 200 + a non-empty `h1` (or the route's declared `landing` when the page module exports one). A dynamic route with **no** entry in `route-params.ts` fails the walk naming the route: adding a route forces the author to say which golden entity renders it. This walk on the `main` slot is what makes #2012's blind spot (`/documents/[slug]` served from runtime files missing in the standalone image) structurally visible, because the slot runs the standalone image.

Ten new links in a release enter both walks with zero edits to any list.

### 6.4 Coverage is a lint, not a review comment

`tools/lint/scenario-coverage-lint.ts`: for every feature spec whose `NNN-requirements.md` frontmatter says `surface: user-facing`, every `EARS-N` handler id in the requirements file must appear as an `@EARS-N` tag in that spec's `NNN-scenarios.feature`, on a scenario that is not `@quarantine`. Severity: BLOCK for a spec created or modified in the PR, WARN (report row) for untouched specs until the backfill waves close (§8) — the ADR-0007 §2.6 WARN→BLOCK promotion applies. Backend-only specs are exempt by their own frontmatter (they own Vitest e2e per F-22).

### 6.5 Flake and quarantine

The gate runs with `retries: 0`. A scenario that fails without a product cause is a bug in the scenario, fixed in a PR. Quarantine is `@quarantine(#N)` on the scenario, where `#N` is an OPEN Issue naming the scenario; `scenario-coverage-lint` treats a quarantined scenario as absent for coverage (so a quarantined `@EARS-N` shows as uncovered) and BLOCKs a `@quarantine` without an open Issue. The Playwright **healer** agent never runs in CI or in a slot: a test that rewrites its own assertion on failure hides the regression this contour exists to catch. It may be used by an implementer locally on a PR, and the resulting change is a reviewed diff.

### 6.6 The live-stand axe leg runs on every slot

The existing `shell-axe` / live-stand a11y suites (008 EARS-12; today skipped in CI because `E2E_PORTAL_URL` is unset) run inside `preview-e2e` and `main-e2e` with the slot URL as `E2E_PORTAL_URL` / `E2E_DOCTOR_URL`, under the `playwright-axe` BLOCK bar. This is the CI home #1692 asks for. The a11y defect #1692 reports is a product fix outside this plan and a **prerequisite of §8 step 6**: the suites join the slot check-runs only once the fix is on `main`, so the BLOCK bar never arms against a known-red page (there is no quarantine route for `*.e2e.spec.ts` files by design — §6.5 quarantine is for `.feature` scenarios, and a11y defects are fixed, not parked).

## 8. Execution plan

Order is dependency order. Each line becomes one engineering-task Issue (`track:platform`, milestone «Platform ops & hardening») opened **after** this spec lands, as sub-issues of #2056; sizes are the lead's estimate for one Opus implementer session each.

1. **C1 box + `stg-infra`** — Terraform `stage-1.tf` (owner runs `apply`; provider write actions are owner-gated per the AGENTS.md §6 live-infra rule), box bootstrap from the existing `infra/deploy/cloud-init`, `stg-infra` compose (the `data-prod` + dev-sink services), Zitadel provisioned by `provision.sh`, `twc_vpc.stage` with no route to `twc_vpc.ds` verified. Acceptance: `docker compose -p stg-infra ps` all healthy; a connection from the box to the production Postgres private address is unroutable (no route, not a timeout on an open path).
2. **C2 edge** — wildcard record (owner, DNS provider), Caddy on-demand TLS with the `ask` endpoint stub, basic auth, `noindex`. Acceptance: `https://academy-main.stage.doctor.school` answers 401 without credentials and presents a valid certificate.

## 9. Failure modes and recovery

| Failure                                       | Visible as                                                                                                                                 | Recovery                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Box down / unreachable                        | `preview-e2e` and `main-e2e` never appear on the head; `merge:gate` and `release-gate` refuse (zero registered runs = FAIL, existing rule) | Nothing merges until the box is back (no bypass for `preview-e2e`); a production hotfix ships through `--release-gate-exempt "<reason>"` on the missing `main-e2e` run only (§5). The box is a Terraform resource: `apply` recreates it, `stg-infra` and `ds_golden` rebuild from the repo (no state on the box is unique) |
| Wildcard certificate / DNS issue              | Slot URLs fail TLS; suite red on connection                                                                                                | Caddy on-demand issuance retries; the `ask` endpoint log names the host                                                                                                                                                                                                                                                    |
| Two PRs each carrying a migration             | The second preview's `migrate` fails on its clone (journal conflict) — the same conflict the PR would hit at merge                         | Existing rule: one migration in flight; the losing PR rebases                                                                                                                                                                                                                                                              |
| A PR changes `provision.sh`                   | Its preview converges the shared IdP; other slots see the change                                                                           | Serialized like a migration (§3); the PR body names it; the converge is idempotent by design (#1997)                                                                                                                                                                                                                       |
| Golden seed drift (a scenario needs new data) | Coverage lint green, scenario red on `Given`                                                                                               | The PR extends the golden set; `ds_golden` rebuilds on the `main` deploy                                                                                                                                                                                                                                                   |
| Flaky scenario                                | Red gate with no product cause                                                                                                             | `@quarantine(#N)` + Issue (§6.5); never `retries`                                                                                                                                                                                                                                                                          |
| Disk pressure from images                     | `slot gc` report; build failures                                                                                                           | Nightly gc; `docker buildx prune` with the same reserved-space policy as `prod.mjs`                                                                                                                                                                                                                                        |
| A preview leaks to the internet               | —                                                                                                                                          | Basic auth on every host, `noindex`, test-key captcha, sinks for SMS/email; no production secrets on the box by construction                                                                                                                                                                                               |
