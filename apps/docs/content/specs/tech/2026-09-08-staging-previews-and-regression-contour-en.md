# Staging box, per-PR previews and the end-to-end regression contour

Issue: [#2056](https://github.com/doctor-school/ds-platform/issues/2056). Owner request of 2026-09-08: «пересматриваем систему и среду разработки … сделать надёжнее, сильнее и устойчивее, а не добавлять точки отказа, хрупкость или переусложнять … многие вещи, если можно, лучше сделать детерминированно, убрав генеративный элемент», and «Я бы наоборот пошёл от минимального набора, чтобы не плодить точки отказа. Related canon it changes or narrows: AGENTS.md §6 («Verify UI live before done», «Worktree-per-session», «PR lifecycle runs to completion»), AGENTS.md §9 and `.claude/rules/dev-stand.md` (local stand, ports, branch databases), skill `build-ui-from-design-system` → Stage B (owner stand on the lead's machine), the release runbook (skill `run-prod-deploy`, `tools/deploy/README.md`), the release-cycle spec §10 (`2026-07-15-release-cycle-context-freshness-design-en.md`). ## 1. Finding (why this exists)

Release `release-2026.09.08-1` (SHA `b9ca3371`) shipped regressions that every local and CI tier had passed. They belong to one class: **the production artifact was never executed with the full stack before it reached production.** Verified against `origin/main` of 2026-09-08:

- **No tier runs the browser → Next.js → api junction automatically.** `api-e2e` and `admin-e2e` in `ci.yml` boot real Postgres + Zitadel and test the NestJS api over HTTP. The Playwright jobs for `@ds/portal` and `@ds/doctor` boot `next start` with **no api behind it**: `apps/doctor/playwright.ci.config.ts` `testIgnore`s 13 of the 35 doctor e2e specs (the «return-context tier» that needs a live api); `apps/portal/playwright.ci.config.ts` pins CI to the backend-free axe scan. Every session-dependent page (account, my events, registration state, event page) is verified only by hand.
- **No tier runs the production artifact.** The Playwright tiers run a full `.next` build; production ships `.next/standalone` inside an image built on the box (`apps/{portal,doctor}/Dockerfile`, `tools/deploy/prod.mjs` «on-box builds, no registry»). `tools/ci/standalone-boot-check.mjs` is the one tier that boots the standalone server, and it probes `/` only, accepting any status below 500 (#2012). `tools/deploy/smoke-prod.mjs` probes a fixed list of cold pages **after** the switch.
- **The regression check is a manual, generative step.** The owner's Stage-B drive on a stand served from the lead's machine (`build-ui-from-design-system` → Stage B) is the only place a whole journey is exercised; it is exploratory and unrepeatable, and by canon it is _acceptance_, not QA (memory `feedback_prestageb_exploratory_acceptance_drive`). The five «Integration: … journey against the real stack» Issues that would make the journeys repeatable are all open; the `.feature` files exist (19 under `specs/features/*/`, 4 more under `apps/portal/e2e/features/`) and are executed nowhere automatically.
- **The local-stand discipline is the largest rule family in the repo and the one that breaks most.** `.claude/rules/dev-stand.md` «Parallel sessions» (port probing, «never kill a listener you did not start», foreign-holder teardown refusal, branch databases, coordination-gated rollback) and the Stage-B stand-survival rules exist because several sessions share one developer machine and one personal TrueNAS stand. Memories `reference_lander_needs_main_tree_session`, `reference_stage_b_stand_survival_and_peer_merge`, `feedback_worktree_discipline` record the failures. None of these rules protect production; they protect one machine from its own concurrency.

A per-route or per-link probe list (the first proposal in the session) was rejected by the owner as a point fix: «А что если в новом релизе добавится ещё десяток ссылок? Опять менять составы команд?» — and it would not have caught a `200` that renders the wrong page. The decision below contains **no hand-maintained lists**: every verified set is derived from an artifact that changes together with the code.

## 2. Decision

One always-on **staging box** runs the same compose files as production and hosts two kinds of slots: a persistent **`main` slot** (the release candidate) and ephemeral **`pr-<N>` preview slots**, one per open pull request, each on a **cloned golden database**. A **spec-derived end-to-end suite** (`playwright-bdd` over the spec's `NNN-scenarios.feature` files plus two artifact-derived walks) is run **by the agent, from its own machine, against a slot** — on the preview before Stage-B, on the `main` slot before a release — and its log is recorded where the evidence of that step already lives (the PR body for a preview, the release record for `main`). **Nothing runs on a schedule, on a webhook or in a workflow**: the stand is operated exactly the way production is deployed — one operator, one foreground command at a time, and the box does nothing between commands. **Local stands leave the delivery discipline**: the owner's Stage-B acceptance happens on the preview URL, the regression evidence is the suite, and the lead never serves a stand from a developer machine again.

Minimal component set, nothing beyond it (owner: «от минимального набора»):

## 3. Topology

**Box.** One VPS (`stage-1`), Timeweb preset `4805` — 8 vCPU / 12 GB / 100 GB NVMe in ru-3, 2 900 ₽/мес plus the public IPv4 (owner decision 2026-09-09, §10). RAM is the binding constraint and it is spoken for: `stg-infra` ≈ 4 GB, idle slots ≈ 1.5 GB each — four of them (`main` plus three previews) ≈ 6 GB — leaving ≈ 2 GB of headroom. The 1.5 GB figure is an **estimate**, not a measurement: api ≈ 400 MB, three Next.js standalone servers ≈ 250 MB each, centrifugo ≈ 50 MB. It is measured for real at Phase B acceptance (an acceptance criterion of #2095, with four slots up), and the preset is revisited if an idle slot exceeds 2 GB — at 2 GB the budget is 4 + 4 × 2 = 12 of 12 GB, i.e. no headroom at all, so this is the number the sizing hangs on. The host itself runs no application runtime of ours (below). Image builds do run here, as they do on production: `stage-1` measures 8 vCPU / 11 GB RAM / 91 GB free disk, against `ds-api-prod`'s 4 vCPU / 7 GB / 59 GB free, and production builds every one of its images on that smaller box. A build is transient — it holds CPU and BuildKit cache, not the resident RAM the slot budget above accounts for — and `slot up` is one foreground command at a time. What does **not** run here is the Playwright suite: the browsers run on the operator's machine (§5). The one consequence that stays a rule is **the preview cap is 3** concurrent slots (`slot up` refuses the fourth). Provisioned by the same Terraform module shapes as `api-prod` (`api-prod.tf` → `stage-1.tf`), with the same public firewall model (22 from the operator allowlist, 80/443 public) — but in its **own VPC** (`twc_vpc.stage`, its own CIDR), not in `twc_vpc.ds`. The Timeweb rule model is allow-only and the production VPC firewall does not filter the private interface (`infra/deploy/terraform/network.tf`, DSO-125 note: the existing rules already open 5432/6379/22 to the whole `var.vpc_cidr`), so a deny rule cannot isolate a box that runs arbitrary PR code; the absence of a network path can. It is the **only** new machine.

**Shared infrastructure project** `stg-infra` (compose project name), started once and kept up: Postgres 17 (the `data-prod` image with pgvector + pg_partman), Redis, Zitadel + `zitadel-login`, Cerbos, MinIO, Mailpit, sms-sink, `sms-aero-adapter` pointed at the sink, and Caddy. Centrifugo is **not** shared: it is part of the `api-prod` service set and runs inside every slot. This is the service list of the TrueNAS dev stand today (`infra/dev-stand/compose.core.yml`) — the stand moves from a personal box to a project box; `infra/dev-stand/` stays the portable contract and gains the staging recipe as its reference recipe (§7).

**Host runtime.** The box runs **no application runtime of ours outside a container**. There is no Node on the host, no `pnpm`, no workspace checkout and no long-lived process of this repository: `command -v node` and `command -v pnpm` are both empty. The only thing the box executes on our behalf is `docker`, driven over SSH by the operator's machine. This is strictly production's host contract (`tools/deploy/prod.mjs` ships a tree and then only ever runs `docker compose` on the far side), and no third-party apt repository is added to the box. Everything that needs the workspace — the `slot.mjs` logic itself, migrations, the golden seed — runs either on the operator's machine or inside the slot's own `migrate` image (§4).

**Slots.** A slot is one compose project (`main` or `pr-<N>`) running exactly the product services: `api`, `portal`, `doctor`, `admin`, `centrifugo`, and the `migrate` one-shot, running images the box itself built, with the production Dockerfiles, from the committed tree `slot up` shipped it — tagged `ds-<app>:<sha>` in the box's local Docker, exactly as production tags its own (§5). No image is ever pulled from a registry, because none is published. **Network isolation per slot:** every slot has its own compose network (the project default network); the frontends and `centrifugo` are attached to it only, so the production upstream `API_PROXY_TARGET=http://api:3000` (`infra/deploy/compose/api-prod/compose.yml`) resolves to the slot's own `api` and cannot resolve to another slot's — the shared-network alias collision of two projects both naming a service `api` (Compose does not define which alias wins) is impossible by construction. Only `api` additionally joins the external `stg-infra` network (Postgres, Redis, Zitadel, Cerbos, MinIO, sinks). `slot up` connects the shared Caddy container to the slot network and `slot down` disconnects it, so Caddy resolves slot containers by compose DNS name (`pr-42-portal`, §3 «Hostnames») and **there is no port allocation anywhere** — the port-pair discipline of `dev-stand.md` has no counterpart here; nothing in a slot publishes a host port. **Redis isolation per slot:** each slot's `api` gets its own Redis logical database (`REDIS_URL=redis://redis:6379/<db>`, `<db>` allocated by `slot up` from the slot name, `main` = 0), so OTP challenges, session revocation by subject and rate-limit keys of one slot never touch another; the Redis `databases` setting on the box is raised to cover the slot budget. **Object-storage isolation per slot:** each slot's `api` gets its own MinIO bucket (`S3_BUCKET_UPLOADS=ds-<slot>`, created `ensure-present` by `slot up` before migrate and dropped by a preview's `slot down`; `main`'s bucket is persistent like `ds_main`), reached over the one public host `S3_ENDPOINT=https://s3.<base domain>` because a presigned SigV4 GET is bound to the host it was signed for. Acceptance for both: from a slot's frontend, the proxied `/v1/health` reports the slot's own SHA; a `SCAN` on another slot's Redis database after a login on the first shows nothing.

**Hostnames.** `*.stage.doctor.school` wildcard `A` record in the DNS zone (owner-managed, like the production records). Every consumer — Caddy, `slot.mjs`, the suite — derives its names from one convention, and nothing keeps a list of them:

| Thing                     | Form                                                                          | Example (`pr-42`)                   |
| ------------------------- | ----------------------------------------------------------------------------- | ----------------------------------- |
| Public host               | `<app>-<slot>.stage.doctor.school`, `app ∈ academy \| doctor \| admin \| api` | `academy-pr-42.stage.doctor.school` |
| Slot name                 | `main` \| `pr-<N>`, `N` = the PR number                                       | `pr-42`                             |
| Container                 | `<slot>-<service>` (`academy` → the `portal` service)                         | `pr-42-portal`                      |
| Compose project / network | `slot-<slot>`                                                                 | `slot-pr-42`                        |
| Database                  | `ds_main` \| `ds_pr_<N>`, cloned from `ds_golden`                             | `ds_pr_42`                          |
| Mail sender local part    | `no-reply+<slot>@`                                                            | `no-reply+pr-42@`                   |
| Slot tree on the box      | `$HOME/ds-platform.slots/<slot>`                                              | —                                   |

`academy` naming the portal is the one non-obvious mapping: the public `academy-<slot>` host is served by the `portal` service, so the container behind it is `<slot>-portal`. `main` and `pr-<N>` are the **only** slot names (`SLOT_NAME_RE`, `tools/staging/slot.mjs`), so a reserved smoke slot such as `pr-0` is not a slot at all: a smoke check uses a real open PR number or the `main` slot.

The edge derives the upstream from the matched name instead of from generated state: **one** host-regexp block over the convention above maps `<app>-<slot>` to `<slot>-<service>` on the service's port, with the two Centrifugo path families of the production vhost (`/connection/websocket` and `/api/*`, `infra/deploy/compose/api-prod/Caddyfile`) routed to the slot's own `centrifugo` — the api derives both the browser websocket URL and its server-side publish base from the one `CENTRIFUGO_URL` (`apps/api/src/room/chat.gateway.ts`), so a slot's `CENTRIFUGO_URL` is its `api-<slot>` host and the staging Caddy carries the same two `handle` blocks. TLS is Caddy on-demand issuance whose `ask` endpoint answers 200 for any host matching that same regexp, plus the shared IdP host, and refuses everything else: certificate issuance is bounded by the convention rather than by an allow list, and a slot coming up or going down never reloads Caddy. A wildcard certificate was considered and rejected — DNS-01 at the owner's DNS provider would require a custom Caddy build carrying a provider plugin, a heavier standing dependency than the regexp it would replace. Every staging host is behind Caddy basic auth (one credential pair in the box env, known to the owner and to the suite runner) and sends `X-Robots-Tag: noindex`, with exactly two exemptions. Browsers cache basic-auth per host and every slot is a new set of hosts, so the challenge is answered ONCE per browser: a basic-auth success on any slot host sets a stand-wide gate cookie on the parent domain (`Domain=stage.doctor.school`, `Secure; HttpOnly; SameSite=Lax`, one year) whose value is a stand secret in the box env, and a request carrying it skips the challenge on every current and future slot host; the cookie is issued only after `basic_auth` succeeds, never on the 401, and non-browser callers (the suite runner, the slot tool's health leg) keep plain basic-auth. Rotation is a new value in the box env plus a recreate of the edge container. (1) The two Centrifugo path families on `api-<slot>` are not basic-auth-challenged, because the browser websocket upgrade carries no credentials and the api's publish call carries only `X-API-Key`; they stay protected by Centrifugo's own connection token (HMAC) and API key, exactly as in production. (2) The shared IdP host `id.stage.doctor.school` is not challenged as a whole, because every slot api reaches the IdP machine-to-machine through the PUBLIC issuer origin (`IDP_ISSUER` is the public URL in production too, `infra/deploy/api.env.example`) and so does the Zitadel converge; a challenge there breaks OIDC discovery and token exchange while protecting nothing, since Zitadel authenticates every caller on its own. `X-Robots-Tag: noindex` still applies to `id`. Acceptance (step 2): an unauthenticated `GET https://api-main.stage.doctor.school/v1/health` answers 401, an unauthenticated websocket handshake on `/connection/websocket` of the same host reaches Centrifugo (a Centrifugo error frame or a 502 while no `main` slot is up, never a Caddy 401). The `pr-<N>` form of the same check is testable from step 2 as well, because the `ask` regexp does not depend on a slot existing: a well-formed name with nothing behind it gets its certificate and then a 502 behind the challenge, while a malformed name is refused before any ACME order starts.

**Identity.** One Zitadel instance for all slots, one project, provisioned by the existing `provision.sh` converge on `stg-infra` start; every slot's api uses the same IdP project and client. Consequence recorded as a rule, not a hope: **a PR that changes IdP provisioning (`provision.sh`, `idp-policy.mjs`) is serialized like a migration** — one in flight repo-wide, its preview runs the converge against the shared IdP and the change is visible to every other slot; the PR body names this. Per-PR Zitadel instances are a non-goal. **What the shared IdP does not isolate — and how the plan copes:** golden identities are shared, so scenarios that mutate identity state (password change, email/phone verification, MFA enrolment — spec 003) would race across slots. Rule: **one suite run at a time, repo-wide** — an operator rule, not a queue: the run is a foreground command on the operator's machine, and a second operator waits for it — while slots themselves stay up in parallel for manual acceptance; and the golden identities are reset **by the operator, on the operator's machine, as the last stage of every `slot up`** (§5 step 1) — an idempotent converge of the golden accounts to their seeded state (password, verification flags, MFA factors) through the same Zitadel management API `provision.sh` uses, which also flushes the slot's own Redis database; `pnpm stage:slot reset-identities <slot>` runs that same converge on its own when only the identities need putting back. The reset and the suite run are two commands of the same operator session, and only one suite runs at a time, so the reset that precedes a run is still the state that run observes. Manual use of two previews with the same golden account at the same time is allowed for read paths and is the operator's own conflict on write paths; the suite never depends on it.

**Secrets and side effects.** The box has its own `.env` set (never production values; the names are `infra/deploy/stage.env.example`); SMS and email terminate in the sinks; SmartCaptcha uses the vendor's test keys; egress otherwise follows production (`ADR-0011`). A staging slot can never reach production Postgres or Redis — `stage-1` has no route into `twc_vpc.ds` (separate VPC, §3 Box), verified as part of C1 acceptance. The stand's own object storage is the box's MinIO: `S3_ACCESS_KEY` is its root user and `MINIO_ROOT_PASSWORD` is the S3 secret key, interpolated into a slot's `api` and `migrate` as `S3_SECRET_KEY` by `infra/deploy/compose/slot/compose.yml` so the box keeps exactly one copy of it, while the slot env file carries only the derived addressing keys. Production S3 and Zitadel are public endpoints; the box cannot be kept from resolving them, so the control there is authorization: the box holds no production credential of any kind (C1 acceptance greps the box env against the production secret names), and the staging Zitadel is the only issuer any slot is configured with.

**Sink partitioning across slots.** Mailpit and sms-sink stay **single instances**; slots are separated by **recipient/sender namespace**, not by another container per slot. Mail a slot's own `api` sends carries a slot-tagged sender local part (`no-reply+<slot>@stage.doctor.school`), so the suite selects its own mail with one Mailpit search query and a slot never reads another's. Mail and SMS that the **shared Zitadel** originates (OTP, verification) cannot be tagged — one instance, one template set, one SMTP/HTTP provider — so the control there is the serialization that §3 «Identity» already imposes for the shared IdP: one suite runs at a time, and a run reads the newest message for its recipient. This is why a second Mailpit per slot would buy nothing: the messages that actually race are the ones no per-slot instance would receive.

**Trust boundary.** The repository `doctor-school/ds-platform` is **PUBLIC**, and that half of the boundary is unchanged: anyone may open a pull request from a fork, so **no CI job of this repository ever executes on the staging box**, the box runs no GitHub Actions agent, and no self-hosted runner is ever added. What the production delivery shape changes is the positive half — how code legitimately reaches the box. It reaches it exactly one way: **an authorized operator ships a committed SHA over SSH** (`git archive` → `ssh` → staged extract → atomic swap → `docker compose build`). That is production's boundary verbatim (`tools/deploy/prod.mjs`), and it needs no inbound CI path, no deploy key, no port 22 open to GitHub and no long-lived GitHub credential on the box.

Consequence to state as a rule: a **fork** PR gets a preview only after a maintainer has read its diff. Shipping a fork head to the box is the same act as checking that branch out and running it on your own machine — the operator performs it and owns it. Nothing withholds a fork preview automatically, and nothing should: the maintainer's read is the control, and it is the only one an operator-driven delivery can honestly claim.

The box runs nothing of ours outside a container (§3 «Host runtime»). Between two `slot` commands it is a Docker daemon with containers on it and no process of this repository at all.

In reach of the box: the box env (`/etc/ds-platform/stage.env` — sinks, vendor test keys, secrets generated on this box; by construction no production credential) and the box's Docker daemon, which is full control of the box and of every live slot. What can put code inside that reach: only a committed tree an operator shipped over SSH. Out of reach: production Postgres and Redis (no route — separate VPC) and every repository secret — nothing of this stand runs in GitHub Actions, so no workflow ever carries a staging credential; the basic-auth password the suite needs is read from the box over the operator's own SSH session (`tools/staging/README.md`).

## 4. Data — golden dataset, template database, clones

**Golden dataset (C5).** A deterministic seed in `packages/db/src/seed/golden/` with fixed UUIDs and timestamps relative to the seed run time, so an «upcoming» event is genuinely upcoming on a stand whose apps read the real clock, and every re-seed moves the schedule forward — except the set-once publication instants (`first_published_at`, guarded by the `taxonomy_first_published_at_set_once` trigger), which a re-run leaves as first written (`GOLDEN_NOW` pins the instant explicitly for the unit suite and for the drift check).

The set has two halves, built by the same pure builder at the same pin. The **named catalogue** is what the scenarios compile against: a handful of rows with stable names (`golden.events.upcoming`, `golden.doctors.verifiedCardiologist`, …) that a `Given` addresses directly — doctor accounts in every state the specs distinguish (unverified, verified, MFA-enrolled, deleted), an admin account, experts, projects, events in every lifecycle state, registrations, the legal documents. Its ids and offsets never move. The **volume half** (ordinals ≥ 1000 in every id group, `packages/db/src/seed/golden/volume.ts`) is what makes the stand look like the product: dozens of events from six months back to four months forward, every entity family present in every state with a multiplicity.

**Production shape.** Production data never reaches the box, so the _shape_ of the golden set is the only substitute for it — and a one-row-per-state fixture hides exactly the defects a walk is looking for: pagination, an empty cell in a week view, a month view with a single point, a list that sorts fine at n=1. The design target is the **production shape**, not a floor: an operator opening a preview slot should not be able to tell it from the real catalogue. That covers **every** admin family, not the ones a walk happened to open first: the taxonomy (directions, their partition of the Минздрав specialty book, the weighted adjacency graph between them), the partners with their generated wordmarks, and the targeting links that carry an эфир to a doctor — because a specialty that resolves to no direction, or a direction that leads to no upcoming эфир, is an empty feed behind a dataset whose every count looks healthy.

doctor.school runs эфиры **every day**, so the dataset lays out a real season rather than a sample of one. The calendar is anchored on the pin's own Monday and runs from six months behind the run instant to four months ahead of it: two or three эфиров on every weekday, one on every Saturday, a long-format «школа» on one Sunday a month, plus the two live rooms and the эфир later today that no grid cell can supply. The number of events is an **output** of that cadence — around 670 at any run date — never a knob, and because the grid is anchored on weeks rather than on days the season holds the same cells in the same order whatever weekday the seed runs on; what the pin moves is which of them have already happened.

Every эфир reads like a real one — a title from a curated Russian programme, a description of three to five paragraphs assembled from per-specialty prose banks, a duration that is the sum of its own programme — and carries the people and the artefacts the page renders: two to four experts, most panels with a Модератор among them, each expert with a portrait, a bio, credentials and an affiliation; one or two sponsoring projects with their own descriptions; and a downloadable programme PDF generated from the эфир's own rows, absent on a deliberate minority of upcoming эфиры so the «программа готовится» plaque stays walkable. Every verified doctor carries fifteen to forty registrations spread over past and future эфиры with about a tenth of them cancelled, so «мои эфиры» paginates and a seat count is something an operator can check. Speaker portraits and programmes are objects, not rows, so the seed writes them to the slot's bucket as part of the same idempotent run (`packages/db/src/seed/golden/README.md` → «Media»); the portraits are synthetic faces, because production photographs of real experts are exactly the data that must not reach the box. A fixture where the prose was one line, the programme empty and the schedule a handful of rows was rejected on the Stage-B walk of PR #2216, which is why «≥N» is never the goal.

The unit suite (`golden.spec.ts`, `#2213:` titles) pins **floors under that shape** rather than describing it: the daily cadence itself, the weekly and monthly coverage, the roster sizes, the registration and cancellation ranges, every lifecycle state with a walkable multiplicity, more than one page of both the archive and the admin list, recordings in every kind and status, and a doctor in every verification and lifecycle state. Those floors are asserted at **several pins** — both month ends, a leap day, a year boundary, a run minutes before a month rolls over — because a floor proven at one mid-month pin is a property of that pin, not of the dataset. A new floor is raised by adding rows and the assertion in the same PR — never by relaxing one.

**Only shapes the product can produce.** The set substitutes for production data, so it never contains a row the platform itself would refuse to write: an `in_archive` эфир carries a published recording (the `hidden -> in_archive` transition is offered only then), `recording_expected_by` is written on exactly the ended эфиры with no published recording — the rows where the dated «запись готовится» plaque is actually projected, some dates ahead of the pin and some already overdue — and a registration exists only on an эфир that was registrable, with `registered_at` before both the эфир and «now». A shape the product cannot reach teaches the operator nothing and hides the defect it imitates.

**Determinism at volume.** No random source and no faker dependency: the volume rows are index-driven plans over curated Russian literal lists — product-like titles and names on purpose, because a generated «Event 17» makes an operator walk unreadable and hides the text-length problems a real catalogue has — and every instant is `shiftFromNow(now, …)`. Same pin ⇒ same bytes.

Doctor and admin accounts of the named catalogue also exist in the shared Zitadel with credentials read from the box env; the seed asserts they exist and refuses to run otherwise (no silent creation with generated passwords). The volume doctors are deliberately **not** IdP-backed — they carry a synthetic subject and exist to give the lists, rosters and admin tables their population; an IdP account is provisioned only for a doctor a scenario signs in as. The dataset is **the only test data**; a scenario that needs data the golden set lacks extends the golden set in the same PR. `#1943` (seed an expert on the seeded event) is absorbed here.

**Template database.** `ds_golden` is rebuilt by the `main` slot deploy whenever `apps/api/drizzle/**` (the Drizzle output directory, `packages/db/drizzle.config.ts`) or `packages/db/src/seed/golden/**` changed at the deployed SHA: `CREATE DATABASE ds_golden_next` → migrate to the `main` head → seed → rename old to `ds_golden_prev`, new to `ds_golden` (one `_prev` kept). It is never migrated in place, so it is always «main head + golden seed» and nothing else. **Both steps run through the containerized entry points** — `docker compose --profile migrate run --build --rm migrate` in the `main` slot's own project, the same one-shot production runs (`tools/deploy/prod.mjs`), and the seed as a `run --rm migrate pnpm seed:golden` one-shot in the same image — **never a host `pnpm`**. This is stated explicitly because the box has no `pnpm` and no workspace checkout to run one with (§3 «Host runtime»): `tools/staging/golden-db.mjs` runs both through the slot's `migrate` one-shot, and a command array in it that shells `pnpm` directly is a bug.

**Clones.** `slot up pr-<N>` runs `CREATE DATABASE ds_pr_<N> TEMPLATE ds_golden` (seconds), then the slot's own `migrate` one-shot on the clone, then **the branch's own golden seed** — an idempotent upsert keyed on the fixed UUIDs, so a PR that extends the golden set sees its new entities on its own preview before merge, and an unchanged seed rewrites only the time-derived columns it may move (the set-once publication instants excepted) while the entity set stays exactly the same. The seed is **not run on the host**: `slot.mjs` executes it as a one-shot container in the slot's own image at the branch SHA, `docker compose run --rm migrate pnpm seed:golden` — the `migrate` target of `apps/api/Dockerfile` is the full workspace install (its `deps` stage), so `packages/db` and its seed are already inside the image. Same shape as the `migrate` one-shot itself, which is why the host needs no `pnpm` and no checkout (§3 «Host runtime»). `slot sync` (a new push) re-clones from scratch rather than migrating forward — a preview always reflects «main golden + this branch's migrations + this branch's seed», never an accumulation. `slot down` drops the database. `dev:db:branch` on TrueNAS becomes unnecessary for delivery (§7).

**`main` slot database.** `ds_main` persists across `main` deploys and is migrated forward by the slot's `migrate` one-shot exactly as production is — this is the pre-production proof that the migration set applies to a live database with data — followed by the golden seed upsert at the deployed SHA through the same `docker compose run --rm migrate pnpm seed:golden` one-shot, which is how a merged golden extension reaches `ds_main` (production runs no seed; the upsert is a staging-only step declared in `slot.mjs`, never in `prod.mjs`). `slot reset main` rebuilds it from `ds_golden` (operator command, logged).

**Production data** never reaches the box (doctors' personal data, 152-ФЗ). The realistic shape of the golden set is the substitute — the production shape above is the target, and realism beyond it is a spec responsibility (§6.1: a scenario's `Given` names golden entities).

## 5. Pipeline

**PR lifecycle (C3 → C4).**

1. An agent driving the PR's session runs `pnpm stage:slot up pr-<N> --ref <head sha>` **on its own machine**. The command is foreground and ssh-drives the box in production's order (`tools/deploy/prod.mjs`): `git archive` of the committed head SHA → `ssh` → staged extract and atomic swap into `$HOME/ds-platform.slots/pr-<N>` → `docker compose build` in project `slot-pr-<N>` → the pre-swap boot verify of the images just built → `CREATE DATABASE ds_pr_<N> TEMPLATE ds_golden` → the containerized `migrate` one-shot → the branch's own golden seed (§4) → `up -d` → running-SHA verify (`docker inspect` of the running containers over ssh, `verifyRunningSha` in `tools/deploy/prod.mjs`; a slot has a public host, so it also reads `/v1/health` behind the edge — the probe `prod.mjs` uses at preflight) → image retention (the last N SHA tags per repo kept, then `docker buildx prune -f --reserved-space`). Nothing is pulled: images are local and SHA-tagged, `ds-<app>:<sha>`, as production's are. A failure fails the command on the operator's terminal naming the stage it died in, and a re-run is idempotent.

   The golden-identity reset is the LAST STAGE OF THAT SAME COMMAND, not a second one: every `slot up` ends by converging the golden Zitadel accounts to their seeded state and flushing the slot's Redis database (§3 «Identity»), so a command that reports success has reported a fully converged slot. The converge is idempotent, including a re-run against a live slot, which is what makes folding it in safe. `pnpm stage:slot reset-identities <slot>` remains a subcommand of its own for the case where only the identities need putting back. Either way it belongs on the operator's machine and nowhere else — it ssh-drives the box and reads `/etc/ds-platform/golden-subjects.env` — which is also where the suite run of step 2 happens.

2. Once step 1 reports the slot converged and its golden identities reset, the agent runs the suite **from the same machine**: `pnpm e2e:stage pr-<N>` (C4/C6, step 7). It targets the slot's public hostnames — `E2E_PORTAL_URL` / `E2E_DOCTOR_URL` / `E2E_ADMIN_URL` derived from the §3 convention and the slot name — with the basic-auth pair read from the box exactly as `slot up` reads it (`STAGE_BASIC_AUTH_PASS`, `tools/staging/README.md`). Playwright browsers are the operator machine's own. One suite run at a time repo-wide (§3 Identity); the golden-identity reset it depends on happened at the end of step 1 in the same session. The Playwright HTML report stays on the operator's machine as the run artifact. Nothing is dispatched anywhere and nothing waits: the slot was converged synchronously, before the run.

3. The agent records the run in the **PR body**, in the same evidence block the Stage-B fields already occupy (`design-approval.md`): the four URLs, the head SHA the slot runs, the run's timestamp and its verdict with per-`@EARS-N` failures. Mode (a) reads that block and refuses a `user-facing` PR whose recorded run is missing, red, or pinned to a SHA that is no longer the head — the reviewer is the check, and the record is a body line a human can read, not a status an automation writes.

4. The slot is torn down in the **PR closeout tail**, where the Stage-B stand teardown already lives: `pnpm stage:slot down pr-<N>` — compose down with volumes, drop `ds_pr_<N>`, remove the slot tree and its SHA-tagged images. A stand lives until the acceptance verdict and not longer, and that verdict is the thing that ends it — no timer, no poller and no webhook decides it. `pnpm stage:slot gc` is an operator-run subcommand like every other and reclaims Docker disk down to a free-space floor, never a live slot; a slot whose PR turned out to be closed is taken down with `slot down` in the closeout re-sweep the tail already performs (`gh pr list` + `pnpm stage:slot status`). There is no timer on the box: the box carries no Node and no unit of ours, so a sweep could not run there even if one were wanted.

5. Concurrency: `slot up` is a foreground operator command, so two runs against one slot cannot interleave, and slots of different PRs are independent by construction (own compose project, own tree, own database, own image tags). The repo-wide serial resources stay what they are today: the Drizzle journal (one migration in flight), the shared IdP (`provision.sh` changes serialized like a migration, §3), and one suite run at a time over the shared IdP (§3 Identity).

**Stage-B on the preview.** The owner opens the slot URL the lead posts with the Stage-B request; `build-ui-from-design-system` → Stage B keeps its evidence contract (recorded-at, head pin, GO/NO-GO in the PR or the Issue) and loses its stand-serving half: no `next start` on the lead's machine, no port record, no relaunch recipe, no liveness re-check. The lead's exploratory Playwright MCP drive, when a brief calls for one, targets the preview URL.

**Merge gate.** `pnpm merge:gate <N>` (skill `merge-when-green`) is unchanged: Mode (a) APPROVE at head + green CI + the recorded Stage-B GO. The regression run is part of what Mode (a) approves (§5 step 3), not a separate required check: a red suite is either a product bug (fix in the PR) or a wrong scenario (fix the scenario in the PR, reviewed by Mode (a) as a spec change), and a `docs`-only PR neither gets a slot nor records a run.

**`main` slot.** The `main` slot is converged **by hand, when a release is being prepared** — not on every merge. The release runbook (`run-prod-deploy`, C7) runs `pnpm stage:slot up main --ref <sha>` on the SHA about to ship — the same command as a preview, against the persistent `ds_main` database: forward migration through the containerized `migrate` one-shot exactly as production runs it, the golden-seed upsert, and the `ds_golden` template rebuild when the deployed SHA changed `apps/api/drizzle/**` or the golden seed (§4), with the golden-identity converge folded into that same command — then `pnpm e2e:stage main` and the log into the release record. A **cherry-pick hotfix ref** (release-cycle spec §10.11, `deploy:prod --ref <sha>`) takes the identical pair on that SHA. Between releases the `main` slot shows whatever the last release rehearsal shipped; an operator may re-converge it at any time, and nothing does so on its own. Because the slot runs the standalone image the box built from the shipped tree, this run is the tier that executes the production artifact (§1, second bullet).

**Release runbook (C7).** `release-gate.mjs` is unchanged: it keeps reading the recorded state it reads today (release-blocker, batched Stage-B) and gains no staging input. The `main`-slot converge + suite run is a **pre-flight item of the release runbook** the agent performs and records, next to the existing items (skill `run-prod-deploy`, `tools/deploy/README.md`). A red or missing run holds the deploy the way any other failed pre-flight item does — the owner's release «go» is given on a runbook that shows the run, and the reason for shipping without one (a staging outage during a hotfix) is written into the release record, never a routine. The existing post-switch `deploy:smoke` stays as the «did the switch happen» probe; it is not extended with route lists.

## 6. Regression contract (C6)

The contract has five rules. Each is enforced by a tool with an exit code; none is enforced by a reviewer's memory.

### 6.1 The spec's feature file is the suite

`apps/docs/content/specs/features/NNN-<slug>/NNN-scenarios.feature` is the **only** source of end-to-end scenarios for a feature. `playwright-bdd` (`bddgen`, already a dependency of `apps/portal`) is configured with `features: [<repo>/apps/docs/content/specs/features/**/NNN-scenarios.feature]` and the host projects select POSITIVELY by a Feature-level tag: the `academy` project takes `@host:academy or @host:both`, the `doctor` project `@host:doctor or @host:both`. The vocabulary also carries `@host:admin`, selected by NO storefront project — an admin-surface or API-internal journey belongs to the admin suite in `apps/admin`, and running it on a storefront would only report false reds. Positive selection makes the tag structural rather than optional: a feature file carrying no host tag would be selected by neither project, so `bddgen` fails and names the file (`packages/e2e/bin/check-host-tags.ts`) before generation. Adding or retargeting that tag is a suite-selection edit, not authorship, so it does not make the annotating PR inherit the spec's §8 backfill debt under the §6.4/§6.5 severity split. The four journey files under `apps/portal/e2e/features/` are folded into their specs' feature files in the backfill waves (§8) and the directory is removed; `author-ears-spec` step 7 already produces the feature file, so a new feature costs nothing extra.

Every scenario carries `@EARS-N` tags for the handlers it exercises and a `Given` clause that names golden entities by their seed name (`Given the golden doctor "verified-cardiologist" is signed in`), never by hand-typed data. Step definitions live in `packages/e2e/steps/` (one shared package for both hosts; a host-specific step reads a `HostConfig` field of the step package, mirroring the feature-package rule of the one-code-two-storefronts plan §2) and are ordinary TypeScript reviewed by Mode (a).

Generation policy for agents: an implementer may use the Playwright **planner/generator** agents (Playwright ≥ 1.56, output = ordinary spec/step files) to draft step definitions; the draft is committed and reviewed like hand-written code. The scenario text itself is authored from EARS, never generated from a crawl.

### 6.2 A navigation step asserts the destination, not the address

Rule for scenarios and step definitions, enforced by `tools/lint/scenario-step-lint.ts`: an **outcome** step that asserts an ADDRESS must also name the landing evidence — the page's `h1` text or its `data-surface` marker — and the step implementation asserts the pathname **and** the evidence. An outcome step is a `Then` step and the `And`/`But` steps continuing a `Then` block in a feature file, and a `Then(...)` binding in a step file. The bare form `Then the shell navigates to "/account/events"` is rejected; the accepted form is `Then the shell lands on "/account/events" showing "Мои события"`, and `showing data-surface "documents"` is the accepted alternative for a page that owns no `h1`. This is the rule that turns «200 but the wrong page» into a red check.

The scope is the outcome step, not the verb: a `When the doctor opens the ≡ navigation` is an action the person performs, and a rule keyed on the literal verb would flag non-navigation «opens» actions that assert nothing about where anyone landed — teaching authors to reword the verb rather than to name the evidence. A step asserting the ABSENCE of a destination is likewise out of scope: there is no landing whose evidence could be named.

Severity follows the §6.4 model: BLOCK for a step in a file the PR touches, a reported WARN row for untouched files, until the step-8 backfill ([#2068](https://github.com/doctor-school/ds-platform/issues/2068)) rewords the nine pre-contract rows (the 008 and 013 scenarios and `apps/portal/e2e/features/shell-journey.feature`) together with their step implementations. A `@quarantine` without an open Issue is BLOCK everywhere (§6.5) — a parked scenario is the one case where silence is indistinguishable from deletion.

### 6.3 Two derived walks, no lists

Both are Playwright specs under `packages/e2e/derived/` that read their inputs from artifacts:

- **Navigation walk.** Each host exports its navigation model from a React-free module next to its shell configuration (`apps/portal/lib/navigation-model.ts`, `apps/doctor/lib/navigation-model.ts`): a typed array `{ id, label, href, landing: { h1 }, audience: 'guest' | 'doctor' | 'both' }`. Since #2180 the chrome itself is the shared `@ds/storefront-shell` and each host supplies only VALUES, so `apps/<host>/lib/shell-config.ts` **derives** the wordmark's target and the nav from that array and the host's auth-cluster mapping derives `loginHref` / `profileHref` from it — the model and the rendered bar cannot diverge, because there is one list rather than a list plus a render. A destination the chrome does not paint has no row, so the walk never asserts a link the UI does not offer. The walk visits every item as a guest and as the golden signed-in doctor and asserts status 200, pathname, and `h1`. A guest item that redirects to `/login` asserts the login `h1` and the `returnTo` value.
- **Route walk.** For each host the walk reads the route manifest of the slot's build (`.next/server/app-paths-manifest.json`, exported at image build time to a fixed path the walk fetches from the slot — SLOT IMAGES ONLY, behind the `CONTOUR_MANIFEST` build arg that defaults to off and that only `infra/deploy/compose/slot/compose.yml` passes, so production serves no `/__contour/*`), skips API and internal routes by a fixed pattern, resolves dynamic segments from `packages/e2e/route-params.ts` — a typed map `'/webinars/[slug]' → golden.events.upcoming.slug` — and asserts 200 + a non-empty `h1` (or the route's declared `landing` when the page module exports one). A dynamic route with **no** entry in `route-params.ts` fails the walk naming the route: adding a route forces the author to say which golden entity renders it. This walk on the `main` slot is what makes #2012's blind spot (`/documents/[slug]` served from runtime files missing in the standalone image) structurally visible, because the slot runs the standalone image.

Ten new links in a release enter both walks with zero edits to any list.

### 6.4 Coverage is a lint, not a review comment

`tools/lint/scenario-coverage-lint.ts`: for every feature spec whose `NNN-requirements.md` frontmatter says `surface: user-facing`, every `EARS-N` handler id in the requirements file must appear as an `@EARS-N` tag in that spec's `NNN-scenarios.feature`, on a scenario that is not `@quarantine`. Severity: BLOCK for a spec created or modified in the PR, WARN (report row) for untouched specs until the backfill waves close (§8) — the ADR-0007 §2.6 WARN→BLOCK promotion applies. Backend-only specs are exempt by their own frontmatter (they own Vitest e2e per F-22).

### 6.5 Flake and quarantine

The gate runs with `retries: 0`. A scenario that fails without a product cause is a bug in the scenario, fixed in a PR. Quarantine is `@quarantine(#N)` on the scenario, where `#N` is an OPEN Issue naming the scenario; `scenario-coverage-lint` treats a quarantined scenario as absent for coverage (so a quarantined `@EARS-N` shows as uncovered) and BLOCKs a `@quarantine` without an open Issue. The Playwright **healer** agent never runs in CI or in a slot: a test that rewrites its own assertion on failure hides the regression this contour exists to catch. It may be used by an implementer locally on a PR, and the resulting change is a reviewed diff.

### 6.6 The live-stand axe leg runs on every slot

The existing `shell-axe` / live-stand a11y suites (008 EARS-12; today skipped in CI because `E2E_PORTAL_URL` is unset) run inside the operator's suite run against a slot, with the slot URL as `E2E_PORTAL_URL` / `E2E_DOCTOR_URL`, and a violation fails that run. This is the live home #1692 asks for. The a11y defect #1692 reports is a product fix outside this plan and a **prerequisite of §8 step 7**: the suites join the slot run only once the fix is on `main`, so the run never fails against a known-red page (there is no quarantine route for `*.e2e.spec.ts` files by design — §6.5 quarantine is for `.feature` scenarios, and a11y defects are fixed, not parked).

The box is a Terraform resource: `apply` recreates it, `stg-infra` and `ds_golden` rebuild from the repo (no state on the box is unique)                                                                                                                                                                                                                                                                                                                                           |
