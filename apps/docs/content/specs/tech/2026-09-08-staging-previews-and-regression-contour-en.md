## 1. Finding (why this exists)

Release `release-2026.09.08-1` (SHA `b9ca3371`) shipped regressions that every local and CI tier had passed. They belong to one class: **the production artifact was never executed with the full stack before it reached production.** Verified against `origin/main` of 2026-09-08:

- **No tier runs the browser → Next.js → api junction automatically.** `api-e2e` and `admin-e2e` in `ci.yml` boot real Postgres + Zitadel and test the NestJS api over HTTP. The Playwright jobs for `@ds/portal` and `@ds/doctor` boot `next start` with **no api behind it**: `apps/doctor/playwright.ci.config.ts` `testIgnore`s 13 of the 35 doctor e2e specs (the «return-context tier» that needs a live api); `apps/portal/playwright.ci.config.ts` pins CI to the backend-free axe scan. Every session-dependent page (account, my events, registration state, event page) is verified only by hand.
- **No tier runs the production artifact.** The Playwright tiers run a full `.next` build; production ships `.next/standalone` inside an image built on the box (`apps/{portal,doctor}/Dockerfile`, `tools/deploy/prod.mjs` «on-box builds, no registry»). `tools/ci/standalone-boot-check.mjs` is the one tier that boots the standalone server, and it probes `/` only, accepting any status below 500 (#2012). `tools/deploy/smoke-prod.mjs` probes a fixed list of cold pages **after** the switch.
- **The regression check is a manual, generative step.** The owner's Stage-B drive on a stand served from the lead's machine (`build-ui-from-design-system` → Stage B) is the only place a whole journey is exercised; it is exploratory and unrepeatable, and by canon it is _acceptance_, not QA (memory `feedback_prestageb_exploratory_acceptance_drive`). The five «Integration: … journey against the real stack» Issues that would make the journeys repeatable are all open; the `.feature` files exist (19 under `specs/features/*/`, 4 more under `apps/portal/e2e/features/`) and are executed nowhere automatically.
- **The local-stand discipline is the largest rule family in the repo and the one that breaks most.** `.claude/rules/dev-stand.md` «Parallel sessions» (port probing, «never kill a listener you did not start», foreign-holder teardown refusal, branch databases, coordination-gated rollback) and the Stage-B stand-survival rules exist because several sessions share one developer machine and one personal TrueNAS stand. Memories `reference_lander_needs_main_tree_session`, `reference_stage_b_stand_survival_and_peer_merge`, `feedback_worktree_discipline` record the failures. None of these rules protect production; they protect one machine from its own concurrency.

A per-route or per-link probe list (the first proposal in the session) was rejected by the owner as a point fix: «А что если в новом релизе добавится ещё десяток ссылок? Опять менять составы команд?» — and it would not have caught a `200` that renders the wrong page. The decision below contains **no hand-maintained lists**: every verified set is derived from an artifact that changes together with the code.

## 2. Decision

One always-on **staging box** runs the same compose files as production and hosts two kinds of slots: a persistent **`main` slot** (the release candidate) and ephemeral **`pr-<N>` preview slots**, one per open pull request, each on a **cloned golden database**. A **spec-derived end-to-end suite** (`playwright-bdd` over the spec's `NNN-scenarios.feature` files plus two artifact-derived walks) runs on every preview and on every `main` deploy; its result is a head-pinned GitHub check-run. The **release gate reads only recorded state**: a green `main`-slot run for the exact SHA. **Local stands leave the delivery discipline**: the owner's Stage-B acceptance happens on the preview URL, the regression evidence is the suite, and the lead never serves a stand from a developer machine again.

Minimal component set, nothing beyond it (owner: «от минимального набора»):

## 3. Topology

**Box.** One VPS (`stage-1`), Timeweb preset `4805` — 8 vCPU / 12 GB / 100 GB NVMe in ru-3, 2 900 ₽/мес plus the public IPv4 (owner decision 2026-09-09, §10). RAM is the binding constraint and it is spoken for: `stg-infra` ≈ 4 GB, idle slots ≈ 1.5 GB each — four of them (`main` plus three previews) ≈ 6 GB — leaving ≈ 2 GB of headroom. The 1.5 GB figure is an **estimate**, not a measurement: api ≈ 400 MB, three Next.js standalone servers ≈ 250 MB each, centrifugo ≈ 50 MB. It is measured for real at Phase B acceptance (an acceptance criterion of #2095, with four slots up), and the preset is revisited if an idle slot exceeds 2 GB — at 2 GB the budget is 4 + 4 × 2 = 12 of 12 GB, i.e. no headroom at all, so this is the number the sizing hangs on. The host itself adds no application runtime beyond a pinned Node LTS (below). That budget closes only because neither image builds nor the Playwright suite run here (§5): the preview workflow builds on GitHub-hosted runners and pushes to GHCR, the box pulls, and the browsers run on the hosted runner. The one consequence that stays a rule is **the preview cap is 3** concurrent slots (`slot up` refuses the fourth). Provisioned by the same Terraform module shapes as `api-prod` (`api-prod.tf` → `stage-1.tf`), with the same public firewall model (22 from the operator allowlist, 80/443 public) — but in its **own VPC** (`twc_vpc.stage`, its own CIDR), not in `twc_vpc.ds`. The Timeweb rule model is allow-only and the production VPC firewall does not filter the private interface (`infra/deploy/terraform/network.tf`, DSO-125 note: the existing rules already open 5432/6379/22 to the whole `var.vpc_cidr`), so a deny rule cannot isolate a box that runs arbitrary PR code; the absence of a network path can. It is the **only** new machine.

**Shared infrastructure project** `stg-infra` (compose project name), started once and kept up: Postgres 17 (the `data-prod` image with pgvector + pg_partman), Redis, Zitadel + `zitadel-login`, Cerbos, MinIO, Mailpit, sms-sink, `sms-aero-adapter` pointed at the sink, and Caddy. Centrifugo is **not** shared: it is part of the `api-prod` service set and runs inside every slot. This is the service list of the TrueNAS dev stand today (`infra/dev-stand/compose.core.yml`) — the stand moves from a personal box to a project box; `infra/dev-stand/` stays the portable contract and gains the staging recipe as its reference recipe (§7).

**Host runtime.** Outside Docker the box carries exactly one application runtime: a **pinned Node LTS**, unpacked from the official `nodejs.org` tarball (version and SHA-256 pinned in the install script) under `/opt/node` and symlinked into `/usr/local/bin`. It is installed **by step 4 over SSH**, in the same idempotent script that lands `slot.mjs` and the deployer units — not by `cloud-init`, which stays prod-length because of the provider's first-boot reset (#2121, §8 step 1). No third-party apt repository is added to the box. That runtime exists only so `slot.mjs` and `ds-slot-deployer` can run: there is **no `pnpm` and no workspace checkout on the host** (`command -v pnpm` is empty), and everything that needs the workspace — migrations, the golden seed — runs inside the slot's own `migrate` image (§4).

**Slots.** A slot is one compose project (`main` or `pr-<N>`) running exactly the product services: `api`, `portal`, `doctor`, `admin`, `centrifugo`, and the `migrate` one-shot, running the images the preview workflow built from the slot's head with the production Dockerfiles (`ghcr.io/doctor-school/ds-platform/<app>:pr-<N>-<sha7>` / `:main-<sha7>`, §5); the box pulls them and never builds. **Network isolation per slot:** every slot has its own compose network (the project default network); the frontends and `centrifugo` are attached to it only, so the production upstream `API_PROXY_TARGET=http://api:3000` (`infra/deploy/compose/api-prod/compose.yml`) resolves to the slot's own `api` and cannot resolve to another slot's — the shared-network alias collision of two projects both naming a service `api` (Compose does not define which alias wins) is impossible by construction. Only `api` additionally joins the external `stg-infra` network (Postgres, Redis, Zitadel, Cerbos, MinIO, sinks). `slot up` connects the shared Caddy container to the slot network and `slot down` disconnects it, so Caddy resolves slot containers by compose DNS name (`pr-2034-portal`) and **there is no port allocation anywhere** — the port-pair discipline of `dev-stand.md` has no counterpart here; nothing in a slot publishes a host port. **Redis isolation per slot:** each slot's `api` gets its own Redis logical database (`REDIS_URL=redis://redis:6379/<db>`, `<db>` allocated by `slot up` from the slot name, `main` = 0), so OTP challenges, session revocation by subject and rate-limit keys of one slot never touch another; the Redis `databases` setting on the box is raised to cover the slot budget. Acceptance for both: from a slot's frontend, the proxied `/v1/health` reports the slot's own SHA; a `SCAN` on another slot's Redis database after a login on the first shows nothing.

**Hostnames.** `*.stage.doctor.school` wildcard `A` record in the DNS zone (owner-managed, like the production records). Per slot: `academy-<slot>.stage.doctor.school` → portal, `doctor-<slot>.stage.doctor.school` → doctor, `api-<slot>.stage.doctor.school` → api, with the two Centrifugo path families of the production vhost (`/connection/websocket` and `/api/*`, `infra/deploy/compose/api-prod/Caddyfile`) routed to the slot's own `centrifugo` — the api derives both the browser websocket URL and its server-side publish base from the one `CENTRIFUGO_URL` (`apps/api/src/room/chat.gateway.ts`), so a slot's `CENTRIFUGO_URL` is its `api-<slot>` host and the staging Caddy carries the same two `handle` blocks per slot vhost —, `admin-<slot>.stage.doctor.school` → admin; `<slot>` is `main` or `pr-<N>`. TLS via Caddy on-demand issuing with an `ask` endpoint served by C3 that answers 200 only for hosts of currently registered slots (bounds certificate issuance to real slots). Every staging host is behind Caddy basic auth (one credential pair in the box env, known to the owner and to the suite runner) and sends `X-Robots-Tag: noindex`, with exactly two exemptions. (1) The two Centrifugo path families on `api-<slot>` are not basic-auth-challenged, because the browser websocket upgrade carries no credentials and the api's publish call carries only `X-API-Key`; they stay protected by Centrifugo's own connection token (HMAC) and API key, exactly as in production. (2) The shared IdP host `id.stage.doctor.school` is not challenged as a whole, because every slot api reaches the IdP machine-to-machine through the PUBLIC issuer origin (`IDP_ISSUER` is the public URL in production too, `infra/deploy/api.env.example`) and so does the Zitadel converge; a challenge there breaks OIDC discovery and token exchange while protecting nothing, since Zitadel authenticates every caller on its own. `X-Robots-Tag: noindex` still applies to `id`. Acceptance (step 2): an unauthenticated `GET https://api-main.stage.doctor.school/v1/health` answers 401, an unauthenticated websocket handshake on `/connection/websocket` of the same host reaches Centrifugo (a Centrifugo error frame or a 502 while no `main` slot is up, never a Caddy 401). The `pr-<N>` form of the same check becomes testable at step 4, once the `ask` registry knows preview slots; probing an unregistered host before that starts a doomed ACME order (README «Edge»).

**Identity.** One Zitadel instance for all slots, one project, provisioned by the existing `provision.sh` converge on `stg-infra` start; every slot's api uses the same IdP project and client. Consequence recorded as a rule, not a hope: **a PR that changes IdP provisioning (`provision.sh`, `idp-policy.mjs`) is serialized like a migration** — one in flight repo-wide, its preview runs the converge against the shared IdP and the change is visible to every other slot; the PR body names this. Per-PR Zitadel instances are a non-goal. **What the shared IdP does not isolate — and how the plan copes:** golden identities are shared, so scenarios that mutate identity state (password change, email/phone verification, MFA enrolment — spec 003) would race across slots. Rule: **suite runs are serialized repo-wide** (`concurrency: staging-e2e`, no cancel), while slots themselves stay up in parallel for manual acceptance; every suite run starts with `slot reset-identities <slot>` — an idempotent converge of the golden accounts to their seeded state (password, verification flags, MFA factors) through the same Zitadel management API `provision.sh` uses — and flushes the slot's own Redis database. Manual use of two previews with the same golden account at the same time is allowed for read paths and is the operator's own conflict on write paths; the suite never depends on it.

**Secrets and side effects.** The box has its own `.env` set (never production values; the names are `infra/deploy/stage.env.example`); SMS and email terminate in the sinks; SmartCaptcha uses the vendor's test keys; egress otherwise follows production (`ADR-0011`). A staging slot can never reach production Postgres or Redis — `stage-1` has no route into `twc_vpc.ds` (separate VPC, §3 Box), verified as part of C1 acceptance. Production S3 and Zitadel are public endpoints; the box cannot be kept from resolving them, so the control there is authorization: the box holds no production credential of any kind (C1 acceptance greps the box env against the production secret names), and the staging Zitadel is the only issuer any slot is configured with.

**Sink partitioning across slots.** Mailpit and sms-sink stay **single instances**; slots are separated by **recipient/sender namespace**, not by another container per slot. Mail a slot's own `api` sends carries a slot-tagged sender local part (`no-reply+<slot>@stage.doctor.school`), so the suite selects its own mail with one Mailpit search query and a slot never reads another's. Mail and SMS that the **shared Zitadel** originates (OTP, verification) cannot be tagged — one instance, one template set, one SMTP/HTTP provider — so the control there is the serialization that §3 «Identity» already imposes for the shared IdP: suite runs are serialized repo-wide, and a run reads the newest message for its recipient. This is why a second Mailpit per slot would buy nothing: the messages that actually race are the ones no per-slot instance would receive.

**Deployer trust boundary.** The repository `doctor-school/ds-platform` is **PUBLIC**. That is the fact the whole boundary is built on: anyone may open a pull request from a fork, so **no CI job of this repository ever executes on the staging box**, and the box runs no GitHub Actions agent at all. What runs on the box is one thing the repository does not control from the outside: the **slot deployer** (§5), a systemd timer that polls GitHub read-only, pulls the images the workflow published, and converges slots. It is **outbound only** — the box exposes no inbound CI path and needs neither a deploy key nor a CI-facing port 22.

The only code the box runs outside a container is that deployer and `slot.mjs`, on the pinned host Node LTS described above (§3 «Host runtime») — both from this repository, installed by step 4 over SSH; no branch code and no workspace tooling is ever installed on the host.

In reach of the box: the box env (`/etc/ds-platform/stage.env` — sinks, vendor test keys, secrets generated on this box; by construction no production credential) and the box's Docker daemon, which is full control of the box and of every live slot. What can put code inside that reach: only container images the preview workflow built from a branch of **this** repository and pushed to GHCR. A fork PR's `GITHUB_TOKEN` is read-only, so it cannot push an image, so it gets no slot — by construction, not by a maintainer remembering to withhold approval. The deployer's own credential is a fine-grained **read-only** token (`STAGE_GH_READ_TOKEN`, «Pull requests: read» + «Metadata: read»); it can read nothing an anonymous visitor of a public repository cannot, and exists only to lift the unauthenticated rate limit. Out of reach: production Postgres and Redis (no route — separate VPC) and every repository secret, which never leaves GitHub-hosted runners — the workflow-side half of this contract (permissions block, no `pull_request_target`, the fork branch, staging basic-auth credentials injected only into non-fork suite jobs) is step 6.

## 4. Data — golden dataset, template database, clones

**Golden dataset (C5).** A deterministic seed in `packages/db/src/seed/golden/` with fixed UUIDs and fixed timestamps relative to a pinned «now» (so an «upcoming» event stays upcoming): doctor accounts in every state the specs distinguish (unverified, verified, MFA-enrolled, deleted), an admin account, experts, projects, events in every lifecycle state (draft, published upcoming, live, hidden, past with recording), registrations, the legal documents. Doctor and admin accounts also exist in the shared Zitadel with credentials read from the box env; the seed asserts they exist and refuses to run otherwise (no silent creation with generated passwords). The dataset is **the only test data**; a scenario that needs data the golden set lacks extends the golden set in the same PR. `#1943` (seed an expert on the seeded event) is absorbed here.

**Template database.** `ds_golden` is rebuilt by the `main` slot deploy whenever `apps/api/drizzle/**` (the Drizzle output directory, `packages/db/drizzle.config.ts`) or `packages/db/src/seed/golden/**` changed at the deployed SHA: `CREATE DATABASE ds_golden_next` → migrate to the `main` head → seed → rename old to `ds_golden_prev`, new to `ds_golden` (one `_prev` kept). It is never migrated in place, so it is always «main head + golden seed» and nothing else.

**Clones.** `slot up pr-<N>` runs `CREATE DATABASE ds_pr_<N> TEMPLATE ds_golden` (seconds), then the slot's own `migrate` one-shot on the clone, then **the branch's own golden seed** — an idempotent upsert keyed on the fixed UUIDs, so a PR that extends the golden set sees its new entities on its own preview before merge, and an unchanged seed is a no-op. The seed is **not run on the host**: `slot.mjs` executes it as a one-shot container in the slot's own image at the branch SHA, `docker compose run --rm migrate pnpm seed:golden` — the `migrate` target of `apps/api/Dockerfile` is the full workspace install (its `deps` stage), so `packages/db` and its seed are already inside the image. Same shape as the `migrate` one-shot itself, which is why the host needs no `pnpm` and no checkout (§3 «Host runtime»). `slot sync` (a new push) re-clones from scratch rather than migrating forward — a preview always reflects «main golden + this branch's migrations + this branch's seed», never an accumulation. `slot down` drops the database. `dev:db:branch` on TrueNAS becomes unnecessary for delivery (§7).

**`main` slot database.** `ds_main` persists across `main` deploys and is migrated forward by the slot's `migrate` one-shot exactly as production is — this is the pre-production proof that the migration set applies to a live database with data — followed by the golden seed upsert at the deployed SHA through the same `docker compose run --rm migrate pnpm seed:golden` one-shot, which is how a merged golden extension reaches `ds_main` (production runs no seed; the upsert is a staging-only step declared in `slot.mjs`, never in `prod.mjs`). `slot reset main` rebuilds it from `ds_golden` (operator command, logged).

**Production data** never reaches the box (doctors' personal data, 152-ФЗ). The realistic shape of the golden set is the substitute, and its realism is a spec responsibility (§6.1: a scenario's `Given` names golden entities).

## 5. Pipeline

**PR lifecycle (C4 → C3).**

1. `opened` / `reopened` / `synchronize`: the workflow runs entirely on **GitHub-hosted runners** (`runs-on: ubuntu-latest`); nothing of it executes on the box. It has three parts.

   **Build.** It builds the four product images (`api`, `portal`, `doctor`, `admin`) from the same Dockerfiles `tools/deploy/prod.mjs` builds on production and pushes them to GHCR as `ghcr.io/doctor-school/ds-platform/<app>:pr-<N>-<sha7>` (public packages, `permissions: packages: write` on the job's own `GITHUB_TOKEN`). This is the fork gate: a fork PR's `GITHUB_TOKEN` is read-only, the push cannot happen, and therefore no slot can exist for it. The workflow detects `github.event.pull_request.head.repo.fork` up front and posts the sticky comment «no preview for fork PRs — a maintainer re-opens the change from a branch of this repository» instead of a red job.

   **Converge (pull-based, on the box).** A systemd timer `ds-slot-deployer.timer` (unit + script delivered by step 4 with `slot.mjs`; not installed by `cloud-init`) fires every 60 s. It reads desired state from GitHub over the REST API with `STAGE_GH_READ_TOKEN` from `/etc/ds-platform/stage.env` — a fine-grained **read-only** token («Pull requests: read», «Metadata: read»), owner-minted; it grants nothing a visitor of a public repository lacks and exists only to lift the unauthenticated rate limit — takes the open non-draft PRs plus the `main` head as the desired slot set, checks that the tagged images exist in GHCR, and converges: `slot up|sync pr-<N> <sha>` **pulls** the images (no build on the box), clones the database, runs `migrate`, seeds the clone through the `migrate` one-shot at the branch SHA (§4), `up -d`, registers the four hostnames with the `ask` endpoint; `slot down pr-<N>` for a PR that is closed or back to draft. Traffic is outbound only: no inbound port, no deploy key, no repository secret on the box, and no third-party code executing outside a slot's own containers.

   **Suite.** The workflow then polls `https://api-pr-<N>.stage.doctor.school/v1/health` (basic auth) until the reported `version` equals the head SHA — 15 minutes, after which `preview-e2e` is red with «the slot deployer did not converge» (§9) — and runs the regression suite (§6) from the hosted runner against the slot's public hostnames, with `E2E_PORTAL_URL` / `E2E_DOCTOR_URL` / `E2E_ADMIN_URL` set to them and `STAGE_BASIC_AUTH_USER` / `STAGE_BASIC_AUTH_PASS` from repository secrets (staging-only credentials, and unavailable to a fork PR by GitHub's own rule). Playwright browsers install on the hosted runner (`npx playwright install --with-deps`), never on the box. Runs stay serialized repo-wide (§3 Identity). The Playwright HTML report is uploaded as the workflow artifact.

2. It posts **one sticky PR comment** (edited in place, marker `<!-- preview -->`): the four URLs, the head SHA, the suite verdict with per-`@EARS-N` failures, and the artifact link. The suite result is also a check-run named `preview-e2e` on the head SHA.
3. `ready_for_review` runs the same job as `synchronize` (a draft turned ready without a push gets its slot and its check-run). `converted_to_draft` and `closed` (merged or not) need **no** job at all: the PR leaves the deployer's desired set on its next 60-second tick and the deployer runs `slot down pr-<N>` — compose down with volumes, drop `ds_pr_<N>`, deregister hostnames, prune the slot's images. Teardown is therefore state-driven, not event-driven, and a missed webhook cannot leak a slot; the nightly `slot gc` on the box stays as the belt to that braces, removing any slot whose PR is not open and any image not referenced by an open slot.
4. Concurrency: one workflow run per PR at a time (`concurrency: preview-${{ github.event.number }}`, cancel-in-progress); slots of different PRs run concurrently and are independent by construction (own project, own database, own image tags). The two repo-wide serial resources stay what they are today: the Drizzle journal and the shared IdP (§3).

**Stage-B on the preview.** The owner opens the sticky comment's URL; `build-ui-from-design-system` → Stage B keeps its evidence contract (recorded-at, head pin, GO/NO-GO in the PR or the Issue) and loses its stand-serving half: no `next start` on the lead's machine, no port record, no relaunch recipe, no liveness re-check. The lead's exploratory Playwright MCP drive, when a brief calls for one, targets the preview URL.

**Merge gate.** `pnpm merge:gate <N>` (skill `merge-when-green`) already pins check-runs to the head SHA; `preview-e2e` joins the required set for every PR that gets a slot (every non-draft PR; a `docs`-only PR is detected by the existing `changes` job filter and gets no slot and no `preview-e2e` requirement). A `user-facing` PR therefore merges on: Mode (a) APPROVE at head + green CI + green `preview-e2e` at head + the recorded Stage-B GO. No `--mode-a-exempt`-style bypass exists for `preview-e2e`; a red suite is either a product bug (fix in the PR) or a wrong scenario (fix the scenario in the PR, reviewed by Mode (a) as a spec change).

**`main` slot.** On every push to `main` (squash merge), the `push` job of the same workflow builds and pushes the four `:main-<sha7>` images, waits for the deployer to converge the `main` slot on that SHA (persistent database, forward migration, template rebuild when needed — the deployer treats the `main` head as one more desired slot), then runs the same suite from the hosted runner and records the result as check-run `main-e2e` on the merge SHA plus a GitHub Deployment `staging` with `success`/`failure`. The same job is reachable by `workflow_dispatch` with a `ref` input (a full commit SHA; the job checks out, builds and reports on exactly that SHA, and records it as the `main` slot's pinned desired SHA, which the deployer honours over the `main` head until the next push to `main`): this is how a **cherry-pick hotfix ref** (release-cycle spec §10.11, `tools/deploy/prod.mjs` — a SHA that is patch-equivalent to `main` but not on it) gets its `main-e2e`: `deploy:prod --ref <sha>` dispatches it, waits for the check-run, and only then reaches the release gate. The `main` slot therefore shows the newest merged SHA or the hotfix ref under release; there is no manual «deploy to staging». Because the slot runs the standalone image, this run is the tier that executes the production artifact (§1, second bullet).

**Release gate (C7).** `release-gate.mjs` gains check 3: the `main-e2e` check-run for the SHA `deploy:prod` is about to ship is `success`; anything else — missing, pending, failure — refuses. A `failure` result is never exemptable (memory `feedback_close_stage_b_gates_before_deploy_not_exempt`: the gate reads state only). A **missing or pending** check-run — the box is down or the run has not finished — is the one case the existing mandatory-reason hatch `--release-gate-exempt "<reason>"` (`tools/deploy/release-gate.mjs`, same contract as `--mode-a-exempt`) also covers for check 3, so a staging outage cannot hold a production hotfix (`deploy:prod --ref <sha>`, #1886) hostage — owner constraint §10 «не плодить точки отказа». The reason lands in the release record; the exempt is logged as a §9 event, never a routine. A hotfix ref is not on `main` — it gets its own `main-e2e` through the `workflow_dispatch` route above, so the hatch is never the routine hotfix path. The existing post-switch `deploy:smoke` stays as the «did the switch happen» probe; it is not extended with route lists.

## 6. Regression contract (C6)

The contract has five rules. Each is enforced by a tool with an exit code; none is enforced by a reviewer's memory.

### 6.1 The spec's feature file is the suite

`apps/docs/content/specs/features/NNN-<slug>/NNN-scenarios.feature` is the **only** source of end-to-end scenarios for a feature. `playwright-bdd` (`bddgen`, already a dependency of `apps/portal`) is configured with `features: [<repo>/apps/docs/content/specs/features/**/NNN-scenarios.feature]` and the host projects select by tag: `@host:academy`, `@host:doctor`, `@host:both`. The four journey files under `apps/portal/e2e/features/` are folded into their specs' feature files in the backfill waves (§8) and the directory is removed; `author-ears-spec` step 7 already produces the feature file, so a new feature costs nothing extra.

Every scenario carries `@EARS-N` tags for the handlers it exercises and a `Given` clause that names golden entities by their seed name (`Given the golden doctor "verified-cardiologist" is signed in`), never by hand-typed data. Step definitions live in `packages/e2e/steps/` (one shared package for both hosts; a host-specific step reads a `HostConfig` field of the step package, mirroring the feature-package rule of the one-code-two-storefronts plan §2) and are ordinary TypeScript reviewed by Mode (a).

Generation policy for agents: an implementer may use the Playwright **planner/generator** agents (Playwright ≥ 1.56, output = ordinary spec/step files) to draft step definitions; the draft is committed and reviewed like hand-written code. The scenario text itself is authored from EARS, never generated from a crawl.

### 6.2 A navigation step asserts the destination, not the address

Rule for step definitions (enforced by `tools/lint/scenario-step-lint.ts`, BLOCK): a step whose text matches `navigates to|opens|lands on` must also name the landing evidence — the page's `h1` text or its `data-surface` marker — and the step implementation asserts both the pathname **and** the evidence. The bare form `Then the shell navigates to "/account/events"` (today in `shell-journey.feature`) is rejected; the accepted form is `Then the shell lands on "/account/events" showing "Мои события"`. This is the rule that turns «200 but the wrong page» into a red check.

### 6.3 Two derived walks, no lists

Both are Playwright specs under `packages/e2e/derived/` that read their inputs from artifacts:

- **Navigation walk.** Each host exports its navigation model from the module that renders it (`apps/portal/components/app-shell-header.tsx` today hard-codes `DISCOVERY_HREF`, `MY_EVENTS_HREF`, `LOGIN_HREF`; the export becomes a typed array `{ label, href, landing: { h1 }, audience: 'guest' | 'doctor' | 'both' }` that the header renders **from**, so the model and the render cannot diverge). The walk visits every item as a guest and as the golden signed-in doctor and asserts status 200, pathname, and `h1`. A guest item that redirects to `/login` asserts the login `h1` and the `returnTo` value.
- **Route walk.** For each host the walk reads the route manifest of the slot's build (`.next/server/app-paths-manifest.json`, exported at image build time to a fixed path the walk fetches from the slot), skips API and internal routes by a fixed pattern, resolves dynamic segments from `packages/e2e/route-params.ts` — a typed map `'/webinars/[slug]' → golden.events.upcoming.slug` — and asserts 200 + a non-empty `h1` (or the route's declared `landing` when the page module exports one). A dynamic route with **no** entry in `route-params.ts` fails the walk naming the route: adding a route forces the author to say which golden entity renders it. This walk on the `main` slot is what makes #2012's blind spot (`/documents/[slug]` served from runtime files missing in the standalone image) structurally visible, because the slot runs the standalone image.

Ten new links in a release enter both walks with zero edits to any list.

### 6.4 Coverage is a lint, not a review comment

`tools/lint/scenario-coverage-lint.ts`: for every feature spec whose `NNN-requirements.md` frontmatter says `surface: user-facing`, every `EARS-N` handler id in the requirements file must appear as an `@EARS-N` tag in that spec's `NNN-scenarios.feature`, on a scenario that is not `@quarantine`. Severity: BLOCK for a spec created or modified in the PR, WARN (report row) for untouched specs until the backfill waves close (§8) — the ADR-0007 §2.6 WARN→BLOCK promotion applies. Backend-only specs are exempt by their own frontmatter (they own Vitest e2e per F-22).

### 6.5 Flake and quarantine

The gate runs with `retries: 0`. A scenario that fails without a product cause is a bug in the scenario, fixed in a PR. Quarantine is `@quarantine(#N)` on the scenario, where `#N` is an OPEN Issue naming the scenario; `scenario-coverage-lint` treats a quarantined scenario as absent for coverage (so a quarantined `@EARS-N` shows as uncovered) and BLOCKs a `@quarantine` without an open Issue. The Playwright **healer** agent never runs in CI or in a slot: a test that rewrites its own assertion on failure hides the regression this contour exists to catch. It may be used by an implementer locally on a PR, and the resulting change is a reviewed diff.

### 6.6 The live-stand axe leg runs on every slot

The existing `shell-axe` / live-stand a11y suites (008 EARS-12; today skipped in CI because `E2E_PORTAL_URL` is unset) run inside `preview-e2e` and `main-e2e` with the slot URL as `E2E_PORTAL_URL` / `E2E_DOCTOR_URL`, under the `playwright-axe` BLOCK bar. This is the CI home #1692 asks for. The a11y defect #1692 reports is a product fix outside this plan and a **prerequisite of §8 step 6**: the suites join the slot check-runs only once the fix is on `main`, so the BLOCK bar never arms against a known-red page (there is no quarantine route for `*.e2e.spec.ts` files by design — §6.5 quarantine is for `.feature` scenarios, and a11y defects are fixed, not parked).
