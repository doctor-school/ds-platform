# Миграция нативного SMTP-профиля Postbox

[EN](./2026-09-10-postbox-native-smtp-profile-design-en.md) · [003 §14.5](../features/003-user-authentication/003-design.md#145-activation-evidence-and-ramp-10592116-microsoft-1120) · [#2116](https://github.com/doctor-school/ds-platform/issues/2116)

**Включение в production ожидает разрешения:** владелец разрешил подготовку, тестирование, ревизию контракта и реализацию. Дизайн задаёт будущую реализацию; выбор миграции production-профиля и применимое разрешение на релиз фиксируются до записи в production. #2144/#2145 независимы. Новый аккаунт или ключ Yandex не требуется.

## Контракт

Существующий ID mail.ru и описание `real transactional sender` сохраняются без изменений. Для Postbox создаётся ровно один профиль `real transactional sender:postbox` с теми же выбранными credentials Postbox, что использует BFF через `IDP_SMTP_REAL_*`. ID стабилен **внутри каждого провайдера**: единый ID не переписывается при смене провайдера. Intercept сохраняет `dev-stand mailpit`.

Провижининг и runtime находят ровно один профиль явно выбранного провайдера и сверяют ID, host:port, TLS, username, адрес и имя отправителя. Несовпадение — ошибка, а не разрешение обновлять credentials, переименовывать, удалять/пересоздавать профиль или создавать новое поколение. Ротация credentials требует отдельной проверенной миграции; публичные метаданные не доказывают равенство пароля.

## API и исходники запиненной версии

Последовательность поддерживается [Admin proto v4.15.0](https://github.com/zitadel/zitadel/blob/v4.15.0/proto/zitadel/admin.proto). Deprecated SMTP-маршруты присутствуют в этой версии; новый маршрут не исправляет общий command/reducer.

| Операция         | HTTP-путь относительно `/admin/v1`          | Проверка                                                                                                   |
| ---------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Инвентаризация   | `POST /smtp/_search` с пагинацией           | Полный список; сохранить исходный активный ID и публичные метаданные                                       |
| Создание         | `POST /smtp`                                | `senderAddress`, `senderName`, `tls`, `host`, `user`, `password`, `description`; сохранить возвращённый ID |
| Чтение кандидата | `GET /smtp/{id}`                            | Точные метаданные, неактивное состояние, тот же ID в списке                                                |
| Тест кандидата   | `POST /smtp/{id}/_test` с `receiverAddress` | Реальная тестовая отправка только контролируемому получателю                                               |
| Включение        | `POST /smtp/{id}/_activate`                 | Прочитать `GET /smtp` и полный список; активен ровно один ID                                               |
| Нативный откат   | `POST /smtp/{originalId}/_activate`         | Исходные метаданные и настоящее нативное уведомление через mail.ru                                         |

[AddSMTPConfig](https://github.com/zitadel/zitadel/blob/v4.15.0/internal/command/smtp.go) создаёт событие Added; [проекция](https://github.com/zitadel/zitadel/blob/v4.15.0/internal/query/projection/smtp.go) создаёт профиль с непустым ID неактивным. Активация меняет состояния, а не credentials SMTP, и деактивирует другие активные профили инстанса. Предварительно деактивировать старый профиль не нужно.

После ошибочного обновления пароля event write model старого ID отличается от query-проекции. `TestSMTPConfigById` читает **write model**: успешный тест этого ID не доказывает откат на mail.ru. Настоящие нативные уведомления используют [GetActiveEmailConfig → SMTPConfigActive](https://github.com/zitadel/zitadel/blob/v4.15.0/internal/notification/handlers/config_email.go), включая пароль из проекции. Поэтому сохранённый профиль — **условная цель отката**, требующая доказательства реальной нативной отправки; история событий не считается исправленной. Replay, reset проекции, password-only PUT, переключение метаданных и слепой upgrade IdP не входят в миграцию.

## Идемпотентность и ограниченная готовность

Одновременно работает одна миграция под сериализацией deploy. До CREATE прочитать все страницы. Ноль совпадений допускает один CREATE; один точный кандидат переиспользуется без PUT; дубликаты/несовпадения останавливают процесс до активации. Несекретный возвращённый ID фиксируется в доказательствах активации до продолжения. После таймаута CREATE сверяются список и события/проекция; автоматически повторять CREATE при неопределённом результате нельзя. Невидимый ошибочный CREATE не доказывает отсутствие профиля.

Готовность проверяется в пределах **абсолютного срока 120 секунд**, с интервалом 1 секунда и лимитом запроса 5 секунд (каждый запрос ограничивается также остатком общего срока). Требуются точные метаданные и ожидаемое состояние; при отказе старый выбор сохраняется или восстанавливается. Этот ограниченный бюджет учитывает [настройки проекции запиненной версии](https://github.com/zitadel/zitadel/blob/v4.15.0/cmd/defaults.yaml): `RequeueEvery: 60s`, `RetryFailedAfter: 1s`, `MaxFailureCount: 5`; он не гарантирует convergence. Успешная HTTP-мутация, обработанный sequence или отсутствие новых failed events сами по себе недостаточны. `_test` не доказывает доставку production-получателю или равенство двух моделей ранее повреждённого профиля.

## Выкладка и откат

Используются существующие provisioner, runtime-reconciler и канонический `pnpm deploy:prod`. `IDP_SMTP_REAL_PROVIDER` выбирает одного провайдера для BFF и нативного reconciler. Синхронизация флагов runtime, intercept вне production и SMS сохраняют поведение. Для добавления Postbox нужен выбор профиля провайдера в этих существующих путях; режим владения, совместимый промежуточный релиз, supervisor, журнал фаз и отдельный framework репетиций не требуются.

До изменения конфигурации выкладки сохраняются полное защищённое окружение mail.ru и исходный нативный ID. Неактивный кандидат готовится и тестируется до включения. Существующая проверка нативного readback до замены приложения (#2151) сохраняется; после старта и reconcile нового приложения активный ID проверяется снова. Во время замены старый BFF может ещё использовать mail.ru, а его reconciler — повторно выбрать mail.ru; операция не атомарна и завершена лишь после согласования нового приложения и нативного выбора.

При неудачной или неопределённой активации/выкладке до новой попытки проверяется фактическое состояние приложения и нативного выбора. Согласованное старое окружение BFF восстанавливается до канонического отката на предыдущее приложение; сохранённый ID mail.ru повторно активируется с проверкой метаданных проекции. Подтверждается фактическое получение нативного и BFF-письма через mail.ru. Незавершённое восстановление остаётся неуспешной активацией, а не успешным релизом. Оба профиля сохраняются; восстановление не обновляет credentials и не удаляет профили.

## Проверка и приёмка

Целевой TDD покрывает явный выбор провайдера в reconciler, сохранение mail.ru, создание/переиспользование кандидата, отказ при дубликатах или несовпадении идентичности, неопределённый CREATE и исчерпание ограниченного readback. Сохраняются существующие тесты защиты deploy и поведение intercept вне production. Зафиксированная проверка запиненной версии уже подтверждает применимость create/activate/reactivate; повторение всей инфраструктурной fixture не является предпосылкой добавления провайдера.

Production-приёмка в #2116 использует реальных провайдеров и существующие продуктовые шаблоны: контролируемые register/resend/reset и login OTP верифицированного аккаунта с отдельной фиксацией SMTP-принятия, полученных заголовков и размещения в ящике. By-ID тест не доказывает получение письма. Содержание писем и поток аутентификации не меняются. Готовность квот требуется до массового запуска; доказательства Microsoft остаются в #1120, а прежнее исключение для релиза одноразовое.

## Существующие доказательства API провайдера

Изолированная проверка Zitadel v4.15.0 от 2026-09-10 воспроизвела SQLSTATE 42601 при обновлении пароля, задержку видимости query, успешную нативную доставку через новый профиль после readback и возврат нативной доставки на сохранённый исходный ID. Повторный CREATE вернул другой ID. GET-by-ID использовал неактивное состояние `3`, список — `SMTP_CONFIG_INACTIVE`. Доказательства сохранены вне git в `2116-smtp-rehearsal.json`, `2116-smtp-rehearsal-idp.log` и `stand-ops-2116-rehearsal.log`. Тестовые приёмники доказывают только маршрут, а не credentials реального провайдера, TLS или доставку.
