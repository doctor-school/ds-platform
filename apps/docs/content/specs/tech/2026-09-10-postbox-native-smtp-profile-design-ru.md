# Миграция нативного SMTP-профиля Postbox

[EN](./2026-09-10-postbox-native-smtp-profile-design-en.md) · [003 §14.5](../features/003-user-authentication/003-design.md#145-activation-evidence-and-ramp-10592116-microsoft-1120) · [#2116](https://github.com/doctor-school/ds-platform/issues/2116)

**Включение в production ожидает разрешения:** владелец разрешил подготовку, тестирование, ревизию контракта и реализацию. Дизайн задаёт будущую реализацию; выбор миграции production-профиля и применимое разрешение на релиз фиксируются до записи в production. #2144/#2145 независимы. Новый аккаунт или ключ Yandex не требуется.

## Контракт

Существующий ID mail.ru и описание `real transactional sender` сохраняются без изменений. Для Postbox создаётся ровно один профиль `real transactional sender:postbox` с теми же выбранными credentials Postbox, что использует BFF через `IDP_SMTP_REAL_*`. ID стабилен **внутри каждого провайдера**: единый ID не переписывается при смене провайдера. Intercept сохраняет `dev-stand mailpit`.

Провижининг и runtime находят ровно один профиль явно выбранного провайдера и сверяют ID, host:port, TLS, username, адрес и имя отправителя. Несовпадение — ошибка, а не разрешение обновлять credentials, переименовывать, удалять/пересоздавать профиль или создавать новое поколение. Ротация credentials требует отдельной проверенной миграции; публичные метаданные не доказывают равенство пароля.

## API и исходники запиненной версии

Последовательность поддерживается [Admin proto v4.15.0](https://github.com/zitadel/zitadel/blob/v4.15.0/proto/zitadel/admin.proto). Deprecated SMTP-маршруты присутствуют в этой версии; новый маршрут не исправляет общий command/reducer.

| Операция         | HTTP-путь относительно `/admin/v1`          | Проверка                                                                                                   |
| ---------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Инвентаризация   | `POST /smtp/_search` с пагинацией           | Полный список; сохранить исходный активный ID и публичные метаданные                                       |
| Создание         | `POST /smtp`                                | `senderAddress`, `senderName`, `tls`, `host`, `user`, `password`, `description`; сохранить возвращённый ID |
| Чтение кандидата | `GET /smtp/{id}`                            | Точные метаданные, неактивное состояние, тот же ID в списке                                                |
| Тест кандидата   | `POST /smtp/{id}/_test` с `receiverAddress` | Реальная тестовая отправка только контролируемому получателю                                               |
| Включение        | `POST /smtp/{id}/_activate`                 | Прочитать `GET /smtp` и полный список; активен ровно один ID                                               |
| Нативный откат   | `POST /smtp/{originalId}/_activate`         | Исходные метаданные и настоящее нативное уведомление через mail.ru                                         |

[AddSMTPConfig](https://github.com/zitadel/zitadel/blob/v4.15.0/internal/command/smtp.go) создаёт событие Added; [проекция](https://github.com/zitadel/zitadel/blob/v4.15.0/internal/query/projection/smtp.go) создаёт профиль с непустым ID неактивным. Активация меняет состояния, а не credentials SMTP, и деактивирует другие активные профили инстанса. Предварительно деактивировать старый профиль не нужно.

После ошибочного обновления пароля event write model старого ID отличается от query-проекции. `TestSMTPConfigById` читает **write model**: успешный тест этого ID не доказывает откат на mail.ru. Настоящие нативные уведомления используют [GetActiveEmailConfig → SMTPConfigActive](https://github.com/zitadel/zitadel/blob/v4.15.0/internal/notification/handlers/config_email.go), включая пароль из проекции. Поэтому сохранённый профиль — **условная цель отката**, требующая репетиции на запиненной версии и доказательства реальной нативной отправки; история событий не считается исправленной. Replay, reset проекции, password-only PUT, переключение метаданных и слепой upgrade IdP не входят в миграцию.

## Идемпотентность и ограниченная готовность

Одновременно работает одна миграция под сериализацией deploy. До CREATE прочитать все страницы. Ноль совпадений допускает один CREATE; один точный кандидат переиспользуется без PUT; дубликаты/несовпадения останавливают процесс до активации. Несекретный возвращённый ID сохраняется до продолжения. После таймаута CREATE сверяются список и события/проекция; автоматически повторять CREATE при неопределённом результате нельзя. Невидимый ошибочный CREATE не доказывает отсутствие профиля.

Готовность проверяется в пределах **абсолютного срока 120 секунд**, с интервалом 1 секунда и лимитом запроса 5 секунд (каждый запрос ограничивается также остатком общего срока). Требуются точные метаданные и ожидаемое состояние; при отказе старый выбор сохраняется или восстанавливается. Этот ограниченный бюджет учитывает [настройки проекции запиненной версии](https://github.com/zitadel/zitadel/blob/v4.15.0/cmd/defaults.yaml): `RequeueEvery: 60s`, `RetryFailedAfter: 1s`, `MaxFailureCount: 5`; он не гарантирует convergence. Успешная HTTP-мутация, обработанный sequence или отсутствие новых failed events сами по себе недостаточны. `_test` не доказывает доставку production-получателю или равенство двух моделей ранее повреждённого профиля.

## Владение deploy и откат

Существующий API реагирует на **любое** изменение флага и первую синхронизацию SDK. Он способен повторно активировать старый профиль после включения Postbox деплоем. Заморозки только email-флага недостаточно.

Сначала совместимый релиз с выбранным mail.ru передаёт управление нативным SMTP production **деплою**. Runtime production только проверяет выбранный профиль и активное состояние, не активируя SMTP; управление intercept флагом вне production сохраняется явно. В production обязателен real-режим email: false email-real флаг — ошибка конфигурации, не активирующая Mailpit; BFF-отправки завершаются внутренней ошибкой без изменения enumeration-safe ответов. Независимо поставленные в очередь нативные отправки проверка BFF остановить не может. При старте неверные владение/режим отклоняются; поздние сигналы дают очищенную диагностику без мутаций. SMS-reconcile не меняется. Режим владения обязателен в production-конфигурации и проверяется до миграции. Это предпосылка реализации внутри #2116, а не ручная остановка/патч процесса и не зависимость от #2144/#2145.

Затем канонический deploy готовит build/preboot-проверки, сохраняет согласованное старое окружение и исходный ID, создаёт/тестирует неактивного кандидата, активирует его и требует convergence до миграции/замены приложения (#2151). До замены совместимый API продолжает обслуживать BFF через явно выбранный mail.ru, нативные отправки идут через Postbox. Переход ограничен **абсолютным сроком 300 секунд от первой попытки активации**, включая convergence, миграцию, замену и readiness; вывод логов срок не продлевает. Истечение срока или отмена watchdog запускает откат с отдельным **абсолютным бюджетом 180 секунд**; превышение бюджета отката — инцидент. Существующий watchdog отсутствия вывода сам по себе не реализует этот контракт. После готовности приложения активный ID проверяется снова; переход не считается завершённым включением.

Любой отказ после **первой попытки активации**, включая потерю/таймаут ответа, отказ до замены, истечение срока или отмену, сверяет активное состояние и восстанавливает исходный ID с проверенным readback. Неопределённая активация означает возможное изменение выбора, а не доказательство ненужности отката. До старта/перезапуска предыдущего приложения восстанавливается согласованная старая BFF-конфигурация, затем доказывается настоящая нативная и BFF-доставка. Отказ отката — инцидент релиза; нельзя возвращать успех или откатывать только образы, оставляя изменённый нативный выбор. Оба профиля сохраняются после успеха/отката; очистка и исправление истории провайдера требуют отдельного объёма.

Один удалённый supervisor владеет автоматом прямого перехода/отката и устойчивым несекретным журналом фаз. Отмена сначала останавливает прямой actuator и дожидается завершения либо передаёт завершение тому же удалённому supervisor; откат не должен гоняться с продолжающейся удалённой активацией. Убить только локальный SSH-канал недостаточно. Неустановленное состояние удалённого actuator или прерванный журнал означает заблокированное восстановление/инцидент, а не разрешение второму процессу миграции. Журнал хранит исходный/новый ID и фазу, без credentials.

## Проверка и приёмка

Изолированная fixture использует точную версию IdP, собственные PostgreSQL, сеть и два SMTP-приёмника с синтетическими credentials. Она воспроизводит ошибочный PUT пароля исходного ID; показывает расхождение query/write model; создаёт неактивного кандидата Postbox; тестирует, активирует и отправляет настоящее нативное уведомление; повторно активирует исходный ID и проверяет фактический приёмник. Она доказывает сохранение исходного ID и повторяет CREATE, показывая отсутствие уникальности на стороне провайдера. Запрет дубликатов должна обеспечить реализация; fixture не утверждает, что это поведение уже реализовано. Чтение исходников не заменяет успешную репетицию.

Runtime TDD покрывает выбор профиля, дубликаты/несовпадения/неизвестный профиль, потерю ответа CREATE, таймаут готовности, отклонённую мутацию, production-reconcile без записей при каждом сигнале флагов, откат при отказе до замены, повторный active-check после замены и отсутствие секретов в диагностике. Тест защиты до замены из #2151 сохраняется. Production-приёмка отдельно проверяет контролируемые register/resend/reset и login OTP верифицированного аккаунта, различает принятие провайдером и полученные заголовки/размещение, фиксирует готовность квот. Microsoft остаётся #1120; прежнее исключение для релиза одноразовое.

## Проверка перекрёстных ссылок

### Зафиксированная репетиция API провайдера — 2026-09-10 UTC

Две изолированные fixture использовали PostgreSQL 17, два Mailpit-приёмника и `ghcr.io/zitadel/zitadel:v4.15.0`, image `sha256:f4ab88245b0d619c533edf68d82e554c66a0b9015c2cc91d52b0a4d79deecb21`. SHA-256 экспериментального runner: `1ac9b317db5399b9953a256b1d395a47761f1be61e3f5fa1848d88fe98b63982`. Привязанный к машине исходник и хронологические доказательства сохранены вне git: `2116-smtp-rehearsal.mjs`, `2116-smtp-rehearsal.json`, `2116-smtp-rehearsal-idp.log`, `stand-ops-2116-rehearsal.log`. Запись доказывает применимость API провайдера, а не проверенную закоммиченную production-реализацию.

1. Исходный профиль активен на sequence 108; PUT со сменой пароля принят на 109, но query остаётся на 108 с SQLSTATE 42601. By-ID тест использовал изменённый маршрут write model.
2. CREATE принят на 110, GET кандидата отсутствует. Немедленная активация 111 и нативное уведомление оставили доставку на исходном приёмнике. Ошибка события 109 достигла count 5 в 03:29:26; query затем продвинулась автоматически, без ручного skip/replay.
3. После readback кандидата активация 113 доставила настоящее нативное уведомление верификации в Postbox-приёмник в 03:30:03; активация исходного ID 114 — в mail.ru-приёмник в 03:30:08. Триггер: `POST /v2/users/human` с синтетическими `username`, `profile:{givenName,familyName}`, `email:{email}`, без `returnCode`; из приёмника читаются только метаданные маршрута/auth.
4. Чистый сравнительный прогон: кандидат сразу неактивен, нативная активация и откат успешны. Повторный идентичный CREATE дал другой ID. GET-by-ID кодирует неактивное состояние числом `3`, список — `SMTP_CONFIG_INACTIVE`; поддерживаемые wire-формы нормализуются.

Приёмники принимали любой пароль и фиксировали username аутентификации; TLS был false. Это доказывает маршрут/сохранённый ID, **не** валидность пароля, TLS, доставку Yandex или содержание native login OTP. Настоящие Postbox test/auth и production login OTP остаются гейтами релиза. Все собственные контейнеры/сети удалены; shared-сервисы, production, тома и host-порты не менялись.
