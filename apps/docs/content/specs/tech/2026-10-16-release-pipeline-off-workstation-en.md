## 1. Finding (why this exists)

**A release today depends on one personal Windows workstation staying alive, reachable and correctly configured for 20–90 minutes.** Verified in code on 2026-10-15:

- `pnpm deploy:prod` (`tools/deploy/prod.mjs`) is one foreground Node process on the owner's PC. In order, it:
  1. checks stage prerequisites (`STAGE_BASIC_AUTH_PASS`, `ssh ds-stage-1 true`), a clean tree, fetch, green CI and the release gate;
  2. runs the stage `main` check (`tools/deploy/stage-main-check.mjs`): a temporary worktree, `pnpm install`, then `slot.mjs up main`, which ships the tree and builds images on ds-stage-1, then `tools/staging/e2e-stage.mjs`, which runs the Playwright suite **on the PC** against `*.stage.doctor.school`;
  3. runs read-only prod checks;
  4. ships the tree to ds-api-prod and ds-data-prod (`git archive` piped over ssh, `tools/deploy/lib/remote.mjs` `shipTree`);
  5. takes a pgbackrest backup;
  6. runs `docker compose build` **on ds-api-prod** (~192 s);
  7. verifies boot, updates the IdP, migrates and runs `up -d` (~246 s);
  8. verifies SHA, retention and smoke;
  9. writes `gh release create` and a GitHub Deployment record (`tools/deploy/deployment-record.mjs`), **on success only**.
- Nothing detaches remote work: there is no `nohup`, `setsid`, `systemd-run` or `tmux`, no lock and no state file. When the client dies mid-step, the code can only report that the remote work «MAY have completed» (`tools/deploy/lib/remote.mjs:78`).
- Port 22 on ds-api-prod and ds-stage-1 admits only the owner PC's `/32` (`infra/deploy/terraform/network.tf:97-103`, `stage-1.tf:132-138`). None of the seven GitHub Actions workflows (all `ubuntu-latest`) reaches a Timeweb host. `.github/workflows/release-digest.yml` already listens to `deployment_status`.
- The PC is the only holder of four credentials: the ssh keys to the three boxes; the GitHub token (in the OS keyring); `TWC_TOKEN` (the full Timeweb account) together with the local `terraform.tfstate`; and `STAGE_BASIC_AUTH_PASS`, exported by hand. Stage and prod runtime secrets already live on the boxes.
- The agent's `gh` runs under the owner's own GitHub account (`sidorovanthon`). GitHub therefore cannot tell an action the agent takes from one the owner takes. §3 item 3 is built around this fact.

## 2. Target picture

Owner-confirmed 2026-10-16 (chat): «Да, всё так.» The design is measured against these ten properties:

| #   | Property                                                                                                                     |
| --- | ---------------------------------------------------------------------------------------------------------------------------- |
| P1  | No personal machine in the release path                                                                                      |
| P2  | The owner decides when: the agent dispatches, only the owner approves the production deployment, and both are recorded       |
| P3  | A durable, clean executor: client death never kills a box step                                                               |
| P4  | An automatic stage check whose results are stored                                                                            |
| P5  | Prod is protected: one release at a time, idempotent steps, a rollback floor                                                 |
| P6  | No secrets on personal machines; least privilege for each credential                                                         |
| P7  | Visible status, failures included, without exposing logs or data in a public repository                                      |
| P8  | The agent prepares, dispatches and observes a release; it never approves the production deployment and never holds prod keys |
| P9  | Proportionate cost                                                                                                           |
| P10 | A defined fallback when the normal path is unavailable                                                                       |

## 3. Decision

1. **Build once, in Actions, into the Timeweb registry.** (P1, P3, P5, P9)
   - On merge to `main`, a GitHub-hosted runner builds each first-party image once, tags it with the full commit SHA and pushes it to `ds-platform.registry.twcstorage.ru`.
   - The build job records each image's digest for that SHA as a job output and an uploaded manifest.
   - Stage and prod pull the **same** image by that recorded digest. A release never re-resolves a tag.
   - PR-head images go under a separate `pr/` repository prefix, and a release accepts only digests recorded by a `main` or `hotfix/*` build; `pr/` digests never reach production.
   - No box builds an image.
   - Images are environment-agnostic: a build bakes no per-environment value. Per-environment values (the SmartCaptcha site key `SMARTCAPTCHA_SITE_KEY`, the staging-contour flag `CONTOUR_MANIFEST`) are runtime env. Only a build-time value identical in every environment stays a build arg — `API_PROXY_TARGET=http://api:3000`, because Next freezes `rewrites()` at build (DSO-100).
2. **Stage `main` converges automatically.** (P4, P7)
   - After the build, an Actions job converges the stage `main` slot to those images. It sends one forced command, `release stage-main <sha>`, with that run's `images-<sha>.json` manifest on stdin; the job runs on pushes to `main` only (never a PR build), and a `hotfix/*` SHA is not converged on stage by this path: the driver refuses any SHA that is not on `main`. On the box the release driver (§5) runs the operator's own converge — `tools/staging/slot.mjs up main` — from the codeload tarball of exactly that SHA, through the box-local executor, in a unit that outlives the job. The job then polls `status stage-main <sha>` until the driver unit ends.
   - The stage suite then runs against `*.stage.doctor.school` over HTTPS, and its verdict becomes a check on the commit.
   - The report is handled under the public-log rules in §4.
3. **Release = `workflow_dispatch` + owner-only Environment approval.** (P2, P5, P7, P8)
   - The agent, on the owner's word, or the owner dispatches the release workflow for a SHA. The workflow refuses a SHA without a green stage-suite check.
   - The workflow then waits on Environment `production`. Its deployment branches are restricted to `main`, and its required reviewer is the owner.
   - After approval it runs the deploy job and then smoke. It writes a GitHub Deployment record for **success and failure** alike. The existing Mattermost digest (`release-digest.yml`) fires on success.
   - A workflow `concurrency` group allows one release at a time.
   - **Approving the deployment is owner-only, but GitHub cannot enforce that today.** The agent's `gh` runs under the owner's account (§1), so GitHub cannot distinguish an approval the agent sends from one the owner sends.
     - **Current control (agent-side).** The Claude Code and Codex permission configurations deny the pending-deployments approval call: a `POST` to `repos/*/actions/runs/*/pending_deployments` through `gh api`, and every `gh run` approval-style subcommand. The agent may dispatch and observe only. This is a structural deny rule, not a discipline note (§8 step (e)).
     - **Target state.** The agent operates under its own GitHub identity (a machine user or a GitHub App with `actions:write`). That identity is not a reviewer and no owner token sits in the agent harness. It must exist before step (e) goes live (§10). Prevent-self-review stays **off** while the owner is the single human reviewer: with it on, a release the owner dispatched could never be approved. The protection comes from the agent identity not being a reviewer, plus the agent-side deny rule.
4. **Box access: GitHub-hosted runners push over hardened ssh.** (P1, P6, P8)
   - Port 22 opens to the internet with the hardening set in §4.
   - The prod key is released only inside Environment `production`, after approval. The stage key is released only inside Environment `stage`.
   - ds-data-prod stays private: it is reached through ds-api-prod as a jump host.
   - This retires the owner-`/32` rule and its IP-drift failures.
5. **Every long box step is a detached, locked, observable unit** (§5). The runner starts the unit and polls its status file, and a fresh runner can reattach. (P3, P5)
6. **Secrets live where they are used** (§4). The normal path needs no secret on any personal machine. (P6)
7. **Break-glass.** The same box entrypoints can be run by hand from any machine that holds the owner's offline break-glass key (§4). (P10)
8. **PR slots keep the agent-driven lifecycle and the Stage-B rules unchanged.** The difference is that their images also come from the registry, built by Actions for the PR head under the `pr/` prefix, instead of being built on the box. Slot mechanics stay in the staging spec. (P3, P9)

```text
merge to main
   │
   ▼
[Actions: build]  GitHub-hosted runner, push token (Environment `build`)
   │  docker build ×N ──push──▶ ds-platform.registry.twcstorage.ru/<image>:<full-sha>
   │  records digests for <sha> (job output + manifest)
   ▼
[Actions: stage-converge]  Environment `stage` (stage ssh key)
   │  ssh ds-stage-1 → forced command → systemd-run ds-stage-main-<sha12> (pull by digest, migrate, up)
   ▼
[Actions: stage-suite]  Environment `stage` (STAGE_BASIC_AUTH_PASS, test tokens)
   │  Playwright → https://*.stage.doctor.school ──▶ commit check (summary only) · full report → ds-stage-1 over ssh
   ▼
(agent on the owner's word, or the owner) workflow_dispatch release <sha>
   │  refuse unless the stage-suite check on <sha> is green
   ▼
[Environment `production` approval]  branches: main only · required reviewer: owner
   │  agent-side deny rule: the agent never calls the approval API
   ▼
[Actions: deploy]  concurrency: release; prod ssh key released now
   │  ssh ds-api-prod → forced command → systemd-run ds-prod-<sha12>
   │     (pull recorded digests · pgbackrest backup · migrate · up -d · verify · prune)
   │  runner polls the status file; job log = status lines only; a fresh runner may reattach
   ▼
[Actions: smoke + record]  GitHub Deployment success|failure ──▶ release-digest.yml → Mattermost
```

## 4. Secrets and access

| Secret                                                   | Holder                                                      | Released when                                          |
| -------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------ |
| Registry push token (push + pull)                        | Environment secret of the build job                         | every build on `main` / PR head (internal PRs only)    |
| Registry pull token (pull only)                          | each box, `/etc/ds-platform/registry-pull-token` (600 root) | read by the box unit on pull                           |
| Prod ssh key (`deploy` user, forced command)             | Environment `production` (deployment branches: `main`)      | only after the owner approves the release              |
| Stage ssh key (`deploy` user, forced command)            | Environment `stage` (deployment branches: `main`)           | stage converge and slot jobs                           |
| `STAGE_BASIC_AUTH_PASS`, suite test tokens               | Environment `stage`                                         | stage-suite job                                        |
| Break-glass ssh key                                      | owner, offline                                              | by hand, only when the normal path is unavailable (§9) |
| `TWC_TOKEN` (full Timeweb account) + `terraform.tfstate` | owner-side admin credential                                 | never on a box, never in GitHub                        |
| Stage / prod runtime secrets                             | the boxes (unchanged)                                       | read by compose on the box                             |

Today the push token is stored only on ds-stage-1 (`/etc/ds-platform/registry-push-token`). §8 step (a) moves it into the build Environment and removes it from the box.

**ssh hardening on ds-api-prod and ds-stage-1** (§8 step (c)) — the standard set for a key-only admin port open to the internet:

- key-only authentication (already in place: `PasswordAuthentication no`);
- `PermitRootLogin no` (today it is `yes`);
- a dedicated `deploy` user. The CI keys in its `authorized_keys` carry `command="/usr/local/bin/ds-deploy-entrypoint",no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding`. The entrypoint (`infra/deploy/bin/ds-deploy-entrypoint`, installed beside `ds-release` by every operator run) splits `SSH_ORIGINAL_COMMAND` on single spaces, never through a shell, and matches it against a strict allowlist with exact arity and the `ds-release` argument checks: `status <env> <sha>` (→ `ds-release status`), `release <env> <sha>` (→ the box-side release driver of steps (d)/(e); refused with exit 3 while none is installed) and, on ds-stage-1 only, `upload-report <sha>` (the report tar stream of the paragraph below; absolute paths, `..` and links are refused) and `observe <name>` (one named read-only observation of the stage `main` slot for the stage suite, §5). Anything else exits 2 and is logged to the auth journal, so a CI key never reaches a shell;
- the existing operator key of `deploy` keeps its current sudo until step (f), so `pnpm deploy:prod` and `slot.mjs` keep working unchanged; once the workstation path is retired to break-glass, `deploy`'s sudo is narrowed from NOPASSWD-all to the entrypoint alone;
- break-glass uses a separate admin user `breakglass`. Its key is held offline by the owner, carries no forced command, and has full sudo; it is the only interactive admin path once root login is off, and root holds no key;
- connection rate limiting: `MaxStartups 10:30:60` plus fail2ban on the sshd journal;
- `unattended-upgrades` for security patches;
- ds-data-prod keeps no public ssh; it is reached through ds-api-prod as a jump host. It gets the same `PermitRootLogin no`, break-glass user and root-key removal, and no CI key.

The settings live in the drop-in `/etc/ssh/sshd_config.d/10-ds-hardening.conf` (read before the main `sshd_config`, whose image-default `PermitRootLogin yes` is commented out; sshd takes the first value it reads). A new box gets this end state from its cloud-init file; a running box converges to it with `infra/deploy/bin/harden-ssh.sh` (idempotent, `sshd -t` before the reload).

**Public logs and artifacts (ADR-0011 channel 3).** The repository is public. ADR-0011 channel 3 allows build, test and deploy automation in Actions only with no runtime personal data in logs. Under that rule:

- **Prod jobs print status lines only:** unit name, phase, exit code, SHA and duration. They never print `journalctl` output, compose logs, migration output or backup output. The full logs stay on the box (the journal of the unit) and are read over ssh by the operator.
- **Nothing from the stage suite that can carry credentials goes to GitHub.** Stage holds only the deterministic golden synthetic dataset, and production data never reaches the box (staging spec §4), but a Playwright trace keeps the `Authorization: Basic` header of the stage gate and the passwords a test types (`packages/e2e/playwright.config.ts:160-161`: `trace: "retain-on-failure"`, `httpCredentials`). So the public check shows only a machine-readable summary: test title, status, duration and retry count — no traces, screenshots, videos, HTML report or error bodies. The full Playwright report, traces included, is copied over ssh to ds-stage-1 `/var/lib/ds-platform/e2e-reports/<sha>/` (root-readable, 14-day retention enforced by the next run's cleanup) and read there by the operator. The public check's console is `packages/e2e/reporters/summary.ts`, selected by `E2E_PUBLIC_LOG=1`, which only `.github/workflows/stage.yml` sets.

**Rejected for now: a pull agent.** This is the OpenGitOps «pulled automatically» principle: an agent on each box polls for a desired state, and port 22 stays closed. It changes only who initiates the deploy; the images, registry and approval stay identical, so switching later is cheap. Revisit trigger: a regulatory requirement (152-ФЗ / ФСТЭК) to keep admin ports closed, or log evidence of attempts beating the controls above.

## 5. Durable box steps

A release spans two production boxes plus operator-side steps (the IdP converge over HTTPS, the smoke, the release cut and the Deployment record), so no single unit on one box can run it whole. Instead every long box step (pull, backup, migrate, up, prune) runs inside its own transient systemd unit on the box it changes, driven by the entrypoint `/usr/local/bin/ds-release`. The caller's death — a cancelled runner, a network cut, a killed workstation — never kills the step. Operator-side steps and the short read-only probes (boot verify, running-SHA verify) stay where they are.

- **Entrypoint.** `ds-release release [--retry-failed] <env> <sha> <step> <script-file>`, `status <env> <sha>`, `finish <env> <sha> succeeded|failed`, `check <env>`, `lease <env> <sha>` (read-only: refused while another SHA holds the env), `supersede <env> [<script-file>]` and `forget <env>`, where `<env>` is one of `prod`, `stage-main` or `stage-pr-<N>`. It lives in the tree (`infra/deploy/bin/ds-release`) and every operator run installs it with `sudo install -m 0755` before its first `ds-release` call: a forward run from the tree it has just shipped, right after the ship and before any box step; the rollback, which ships no tree, from the operator checkout's committed file, streamed over ssh and checked against its sha256, before its first `check`. cloud-init creates its state directory on a new box.
- **Stage suite box reads.** The stage suite reads the box only through the CI key's `observe <name>`, its parameters one JSON object (≤ 4 KiB) on stdin. The entrypoint runs only the named observations defined in the tree (`OBSERVATIONS` in `ds-deploy-entrypoint`): the configured academy host, the IdP password-complexity policy (the box reads the IdP token and calls the IdP itself; only the policy flags leave it), and one SELECT per test-owned-row read of `packages/e2e/lib/` (the owned mirror count, consent snapshot, phone account count, congress snapshot and wrong-verification snapshot). No SQL or shell comes from the client: each parameter is checked against its own pattern box-side (the journey's synthetic address shape, a numeric subject, a UUID, `+1999` test phones) and reaches psql as a psql variable (`:'name'`), never spliced into the SQL text. The SQL runs against the `main` slot database only, inside `BEGIN READ ONLY` with a 5 s statement timeout, and its answer is checked to come from that database in a read-only transaction before it is printed. The client receives only what the suite parses (a count or a fingerprinted snapshot of its own rows); an unknown name or a bad parameter exits 2, any other box exits 3, a failed read exits 1 with one fixed short reason (§4, public logs). The operator path is unchanged: run from the workstation, the same libs read the box with the operator's ssh.
- **Stage `main` release driver.** The CI key's forced command `ds-deploy-entrypoint` execs `/usr/local/lib/ds-platform/release-driver <env> <sha>` for `release`, with the client's stdin; every operator run installs it beside `ds-release` (0755 root). On the box whose `/etc/ds-platform/box-role` is `stage` it accepts only `stage-main` (`stage-pr-<N>` is refused: PR slots stay operator-driven, §3 item 8; a prod box refuses until the prod driver lands with #2986). It validates the stdin manifest (exactly `sha`, `ref`, `images`; `sha` equal to the argument; a `main` or `hotfix/*` ref; each of the recorded images a `sha256` digest reference of its own name), then, unless a unit of the same SHA is already running (it answers `attached` before any provenance check, since that unit started only after both passed, so a GitHub rate limit or a registry outage never fails a running converge), checks both provenances on the box, from no client data, and refuses with exit 3 on any failure: the tree — GitHub serves a fork-network commit through this repository's codeload URL, so the unauthenticated `GET https://api.github.com/repos/doctor-school/ds-platform/compare/main...<sha>` must answer `status` `behind` or `identical` (anything else, a 404, a rate limit or a network error included, refuses); and the images — logged in with the box's pull credential (`/etc/ds-platform/registry-pull-token`, inside root's shell under a docker config dir of its own — `DOCKER_CONFIG=$(mktemp -d)`, root-only, removed on exit — so it never touches root's shared docker login that concurrent pulls use), every manifest digest must equal the digest the registry serves for `<registry>/<image>:<sha>` in the release namespace (no `pr/`), which only the build Environment's push token writes. It then asks `ds-release lease` and refuses on another SHA's lease, saves the manifest root-only (removing the saved manifests of other SHAs, whose units read theirs at start) and starts `systemd-run --unit=ds-stage-main-<sha12>-driver --remain-after-exit -p KillMode=mixed` as the deploy user, with the manifest as the unit's stdin. It answers within seconds with one line: `started <unit>`, `attached <unit>` (the unit runs), or `already-succeeded` (the unit exited 0 and the release record closed `succeeded`); any other finished unit of the SHA is reset and started again, and ds-release's attempt semantics above decide what re-runs. The unit downloads `https://codeload.github.com/doctor-school/ds-platform/tar.gz/<sha>` (it honours `export-ignore` exactly as `git archive` does), extracts it and runs `node <tree>/tools/staging/slot.mjs up main --ref <sha> --local --images-file -`, where `-` reads the inherited stdin (fd 0) without opening a path, so the root-only manifest needs no permission check against the deploy user. `--local` swaps only the transport: every ssh script, capture and ship of the plan runs through a local `bash -c` with the same stdin and watchdog, the ship installs that extracted tree as the slot tree, the digests come from the manifest instead of `gh`, and the health check's basic-auth plaintext from `/etc/ds-platform/stage-basic-auth.txt`; the plan, its steps and its ds-release units are the operator's. Node is the box's pinned runtime (`infra/deploy/bin/install-node.sh`, a post-boot provisioning step). `status <env> <sha>` through the entrypoint adds the unit as `"driver": {"unit", "active": "activating|active|inactive|failed|absent", "rc"}`, where `active` describes the unit's process, not systemd's ActiveState (a finished `--remain-after-exit` unit stays `active (exited)` there): a running process is `active` (`activating` while starting), an exit with status 0 is `inactive` with `rc` 0, a non-zero exit or systemd's `failed` is `failed` with `rc` = ExecMainStatus, and no unit is `absent` with `rc` null; the caller's run is terminal when `active` is `inactive`, `failed` or `absent`, and succeeded only when `rc` is 0 and the release record is `succeeded`. Nothing of the converge reaches the client; its log stays in the unit's journal.
- **Unit name.** `systemd-run --unit=ds-<env>-<sha12>-<step> --remain-after-exit -p KillMode=mixed`, which runs the step script as the calling operator user. A second start under the same name fails fast, so the name itself deduplicates. Finished units of the env are stopped and reset by a later call for that env: only after it has taken the lock, and only for units no longer running.
- **Lock and lease.** Every mutating call holds `flock -n /run/lock/ds-<env>.lock` for its whole (short) life. A release stays open from its first step until `finish`; while one SHA's release is open for an env, `release` for a different SHA of the same env is refused and names the open SHA. Any start is also refused while a step unit of another SHA of the env is still running (`activating`, or `active` with sub-state `running` — not the `active (exited)` every finished `--remain-after-exit` unit shows), and the error names that unit. The operator closes every run explicitly: `finish … succeeded` at the end of the deploy or the slot converge, `finish … failed` on any failure exit. One that cannot (the box is unreachable) leaves the exact `finish` command in its output. The workflow `concurrency` group is the first line of defence and the lease the last.
- **Status file — the authority.** Each box keeps `/var/lib/ds-platform/release/<env>/<sha>.json` for the current attempt of each SHA it ran steps for; a closed attempt is archived beside it as `<sha>.<startedAt>.json`. The entrypoint writes the file atomically (write to a unique temp file in the same directory, `fsync`, `rename`, `fsync` of the directory) at every step boundary, so even a verdict recorded without the lock never shares a temp file with another write. A file that does not parse stops every call that reads it with `ds-release: corrupt status file <path>` and a non-zero exit, and the poller reports it as such, never as lost contact:

  ```json
  {
    "env": "prod",
    "sha": "<full sha>",
    "unit": "ds-prod-<sha12>-<step>",
    "state": "running | succeeded | failed | superseded",
    "step": "pull | backup | migrate | up | verify | prune",
    "steps": [
      {
        "name": "pull",
        "unit": "ds-prod-<sha12>-pull",
        "startedAt": "…",
        "endedAt": "…",
        "rc": 0
      }
    ],
    "startedAt": "…",
    "updatedAt": "…",
    "error": null
  }
  ```

  `state` is the release-level record. It is `running` while the attempt is open — a failed step records its error but leaves the attempt open — and `succeeded` or `failed` only through `finish`, whose `succeeded` refuses while any step lacks a success verdict. `superseded` marks an attempt the env has moved off: starting a new SHA marks the env's previous closed attempt `superseded`, and so does the app-only rollback (below).

- **Reattach.** The runner never streams a step: it starts the unit, then polls `status <env> <sha>`, which reads the status file and reports whether the running step's unit is still alive. Each poll prints one status line into the job log (§4); it never tails the journal. Recorded verdicts answer only within the attempt that recorded them. `release` for SHA X reads X's record first:
  - record `running` (the attempt was never closed — its client died): X resumes in that attempt, step by step:
    - step `succeeded`: it returns that verdict without starting a unit, so a resumed attempt never repeats backup or migrate.
    - step `failed`: it returns `failed`. Only an explicit `--retry-failed` re-runs a failed step; nothing re-runs a succeeded one.
    - step `running`: it attaches to the existing unit by name. A unit that died without recording a verdict (a reboot) is recorded as `failed`.
    - step absent: it starts the unit.
  - record `succeeded`, `failed` or `superseded`: the closed attempt is archived and a fresh attempt starts, running every step again. This is what makes deploy B → rollback A → deploy B again, and stage B → C → B, converge for real.
  - record absent: a fresh attempt starts.

  Losing the box while polling ends only the wait: the unit keeps running, and a re-run of the same SHA reattaches. The poller tolerates a few consecutive polls that read the step's unit as gone (a transient `systemctl` failure on the box) before it asks `release` to settle it; when the box then answers that the unit still runs, the unit is left running and the reattach command printed. Every step stays idempotent, as the `pnpm deploy:prod` steps are today. A stage slot's verdicts are dropped (`forget`) when what they describe is gone: on `down`, and on `reset main` before the re-cloned database is migrated again.

- **Rollback floor.** This is unchanged from today: the pre-migrate pgbackrest backup and the app-only rollback to the previous image digest (`run-prod-deploy` → rollback). The rollback takes no lease, so it never waits on the release it reverts, but a step outlives its operator session: before its first state change the rollback installs `ds-release` on both boxes (the one write that precedes it, which leaves the release state untouched) and runs the read-only `check prod` on both and refuses, naming the unit, while any `ds-prod-*` step unit still runs (a still-running `migrate` would otherwise reach its `up -d` and put the rolled-off SHA back). Its `up -d` then runs through `supersede prod` on api-prod — under the env lock, refused while a step unit runs — which marks the recorded attempts `superseded`; data-prod's records are superseded the same way. With registry images, the rollback becomes a pull of the previous SHA's recorded digest instead of a rebuild.

## 7. Rejected alternatives

- **Workstation hardening only** (keep-awake, IP pinning, a watchdog): it fails P1, «no personal machine».
- **GHCR:** private packages on Free include only 1 GB transfer/month, which one release exceeds. Pulls to RU boxes run at ~1.8 MB/s, and making the packages public needs an org setting change.
- **S3 tarballs via `docker save` / `docker load`:** no layer dedup, and it would need its own versioning and GC. It is kept only as the emergency fallback (§9).
- **Self-hosted `registry:2` on S3:** one more service to run and patch.
- **Timeweb App Platform for the core stack:** compose apps forbid `volumes` and proxy only the first service. There are no stands for compose apps, no pre-deploy or migration step and no approval, so orchestration would still be needed.
- **Kubernetes + GitOps:** overkill for one prod box and one operator.
- **Self-hosted CI inside Russia:** GitLab CE needs 8 vCPU / 16 GB, and pull-mirroring is a Premium feature. Forgejo and Gitea lack environments with reviewers and would become a second source of truth.
- **Self-hosted GitHub runner:** fork PRs would run on our box, because the repo is public (owner 2026-09-09).
- **Larger GitHub runners with a static IP:** they require a paid plan.

| Failure                                  | Effect                                                                                                    | Recovery                                                                                                                                                       |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Timeweb registry down                    | no new pulls; running containers are unaffected                                                           | emergency fallback: the build job writes a `docker save` of the built images to S3, and the box loads it with `docker load` through the break-glass entrypoint |
