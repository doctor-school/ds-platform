## 1. Finding (why this exists)

**A release today depends on one personal Windows workstation staying alive, reachable and correctly configured for 20–90 minutes.** Verified in code on 2026-10-15:

- `pnpm deploy:prod` (`tools/deploy/prod.mjs`) is one foreground Node process on the owner's PC. In order, it:
  1. checks stage prerequisites (`STAGE_BASIC_AUTH_PASS`, `ssh ds-stage-1 true`), a clean tree, fetch, green CI and the release gate;
  2. runs the stage `main` check (`tools/deploy/stage-main-check.mjs`): a temporary worktree, `pnpm install`, then `slot.mjs up main`, which ships the tree and builds images on ds-stage-1, then `tools/staging/e2e-stage.mjs`, which runs the Playwright suite **on the PC** against `*.stage.doctor.school`;
  3. runs read-only prod checks;
  4. ships the tree to ds-api-prod and ds-data-prod (`git archive` piped over ssh, `tools/deploy/lib/remote.mjs` `shipTree`);
  5. takes a pgbackrest backup;
  6. runs `docker compose build` **on ds-api-prod** (~192 s);
  7. verifies boot, updates the IdP, migrates and runs `up -d` (~246 s);
  8. verifies SHA, retention and smoke;
  9. writes `gh release create` and a GitHub Deployment record (`tools/deploy/deployment-record.mjs`), **on success only**.
- Nothing detaches remote work: there is no `nohup`, `setsid`, `systemd-run` or `tmux`, no lock and no state file. When the client dies mid-step, the code can only report that the remote work «MAY have completed» (`tools/deploy/lib/remote.mjs:78`).
- Port 22 on ds-api-prod and ds-stage-1 admitted only the owner PC's `/32` (the Terraform firewall rules `api_ssh` and `stage_1_ssh`). None of the seven GitHub Actions workflows (all `ubuntu-latest`) reaches a Timeweb host. `.github/workflows/release-digest.yml` already listens to `deployment_status`.
- The PC is the only holder of four credentials: the ssh keys to the three boxes; the GitHub token (in the OS keyring); `TWC_TOKEN` (the full Timeweb account) together with the local `terraform.tfstate`; and `STAGE_BASIC_AUTH_PASS`, exported by hand. Stage and prod runtime secrets already live on the boxes.
- The agent's `gh` runs under the owner's own GitHub account (`sidorovanthon`). GitHub therefore cannot tell an action the agent takes from one the owner takes. §3 item 3 is built around this fact.

## 2. Target picture

Owner-confirmed 2026-10-16 (chat): «Да, всё так.» The design is measured against these ten properties:

| #   | Property                                                                                                                                     |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | No personal machine in the release path                                                                                                      |
| P2  | The owner decides when: every production release needs the owner's word in chat: it triggers the agent's dispatch, and the quote is recorded |
| P3  | A durable, clean executor: client death never kills a box step                                                                               |
| P4  | An automatic stage check whose results are stored                                                                                            |
| P5  | Prod is protected: one release at a time, idempotent steps, a rollback floor                                                                 |
| P6  | No secrets on personal machines; least privilege for each credential                                                                         |
| P7  | Visible status, failures included, without exposing logs or data in a public repository                                                      |
| P8  | The agent prepares, dispatches and observes a release; it never holds prod keys                                                              |
| P9  | Proportionate cost                                                                                                                           |
| P10 | A defined fallback when the normal path is unavailable                                                                                       |

## 3. Decision

1. **Build once, in Actions, into the Timeweb registry.** (P1, P3, P5, P9)
   - On merge to `main`, a GitHub-hosted runner builds each first-party image once, tags it with the full commit SHA and pushes it to `ds-platform.registry.twcstorage.ru`.
   - The build job records each image's digest for that SHA as a job output and an uploaded manifest.
   - Stage and prod pull the **same** image by that recorded digest. A release never re-resolves a tag.
   - PR-head images go under a separate `pr/` repository prefix, and a release accepts only digests recorded by a `main` or `hotfix/*` build; `pr/` digests never reach production.
   - No box builds an image.
   - Images are environment-agnostic: a build bakes no per-environment value. Per-environment values (the SmartCaptcha site key `SMARTCAPTCHA_SITE_KEY`, the staging-contour flag `CONTOUR_MANIFEST`) are runtime env. Only a build-time value identical in every environment stays a build arg — `API_PROXY_TARGET=http://api:3000`, because Next freezes `rewrites()` at build (DSO-100).
2. **Stage `main` converges automatically.** (P4, P7)
   - After the build, an Actions job converges the stage `main` slot to those images. It sends one forced command, `release stage-main <sha>`, with that run's `images-<sha>.json` manifest on stdin; the job runs on pushes to `main` only (never a PR build), and a `hotfix/*` SHA is not converged on stage by this path: the driver refuses any SHA that is not on `main`. On the box the release driver (§5) runs the operator's own converge — `tools/staging/slot.mjs up main` — from the codeload tarball of exactly that SHA, through the box-local executor, in a unit that outlives the job. The job then polls `status stage-main <sha>` until the driver unit ends.
   - The stage suite then runs against `*.stage.doctor.school` over HTTPS, and its verdict becomes a check on the commit.
   - The report is handled under the public-log rules in §4.
3. **Release = `workflow_dispatch` + the owner's word in chat.** (P2, P5, P7, P8)
   - Every production release needs the owner's word in chat. On it the agent dispatches the release workflow `deploy-prod.yml` (`workflow_dispatch` inputs `sha` and `owner_quote`, both required). The workflow refuses an empty or whitespace-only `owner_quote` before any other step. The quote reaches the steps only through `env:`, never by `${{ }}` interpolation into `run:`.
   - The deploy job runs with `environment: { name: production, deployment: false }`: Environment `production` releases its secrets (the prod CI key and known_hosts) with deployment branches restricted to `main` and **no required reviewer**, but GitHub creates no Deployment of its own. A workflow `concurrency` group `deploy-prod` allows one release at a time and cancels none; it is not the changesets workflow's `release` group, so a push to `main` never cancels a waiting release. Job permissions: `contents: write` (release cut), `deployments: write`, `statuses: read`, `checks: read`, `actions: read` (images artifact), `issues: read` and `pull-requests: read` (the release gate and the release notes); the pre-flight job holds only read scopes.
   - Runner-side pre-flight, from the repo checkout and `GITHUB_TOKEN`, before the box is touched: the SHA is contained in `main`; the `stage-suite` status on the SHA is `success` (this replaces the PC stage check; a red or missing check refuses the release). The workstation path reads the same status for a target from `main` (`readStageSuiteProblem`, shared with `tools/deploy/release-runner.mjs`); a hotfix `--ref` target keeps the PC stage check, because Actions runs the stage suite only on `main` pushes; CI is green (the check-runs of `deploy-prod.yml` itself are not CI and are dropped by workflow path); the release gate (`release-gate.mjs`) passes; the live-broadcast gate passes; the recorded `images-<sha>.json` manifest exists. The workflow exposes no escape hatches: no `--skip-ci-check`, `--release-gate-exempt` or hotfix `--ref`; those stay on the workstation path (break-glass).
   - The deploy job then sends `release prod <sha>` to ds-api-prod with the manifest on stdin and polls `status prod <sha>`, status lines only (§4). Every box step, smoke included, runs in the prod release driver (§5).
   - After a terminal status, runner-side: on success the release cut (its own base selection: the newest release tag that is an ancestor of the SHA), and the ONE explicit GitHub Deployment record for **success and failure** alike, written with `GITHUB_TOKEN` with the owner quote in its description and payload — a failure record's status description reads `release failed @ <sha12> in <phase>: <reason>` (`redeploy failed @ …` alike) from `driver.failure` (§4 «Public logs»), and its payload keeps the note as `failure` (a runner that lost contact with the driver — ssh down, or its 60-min poll limit — records `error` instead, and a re-dispatch of the same SHA records the verdict; a success already recorded for the SHA is never recorded twice); its release notes are based on `previousSha`, which `status prod <sha>` adds to its `driver` object, so the runner needs no box access to read it. Events created by `GITHUB_TOKEN` start no workflows, so `deploy-prod.yml` calls the Mattermost digest itself after a success: `release-digest.yml` gains an `on: workflow_call` trigger, and keeps its `deployment_status` trigger for the Deployment record the break-glass `pnpm deploy:prod` writes.
   - **Rollback mode.** `deploy-prod.yml` has a third input, `mode` (`release` by default | `rollback` | `redeploy`). In `rollback` mode `owner_quote` is not required: a required non-empty `reason` replaces it (refused when empty or whitespace-only, and reaching the steps only through `env:`, like the quote), because a release that visibly broke production is rolled off by the agent without an owner word (§10). The runner pre-flight is its own and smaller: the SHA is the target of one of the latest 3 `release-*` Releases (the registry keeps the images of exactly those, §8 (a)), is a strict ancestor of the live SHA (the latest successful production Deployment's SHA) and is not the live SHA; its `images-<sha>.json` manifest is recorded. The migration floor is not checked here: it needs data-prod and runs box-side (§5, «Prod rollback»); the box repeats the ancestry and release checks as the boundary. It runs no stage-suite, release-gate or live-broadcast check: the target passed them when it shipped, and production is broken now. The job then sends `rollback prod <sha>` to ds-api-prod with the manifest on stdin and polls `rollback-status prod <sha>` (§5) (§5, «Prod rollback»). An ssh drop during that start call continues into the poll, which counts only a record that ended after the call; no such record and no running unit is a start still in flight for 8 polls (2 min), then the verdict is unknown because no rollback of this run was seen; an earlier attempt's `succeeded` record while the box names the target as its live SHA is recorded as a recovered success instead. After a terminal status it cuts no release and writes the ONE GitHub Deployment record (`success` or `failure`; `error` when the verdict is unknown, its status naming lost contact, the 30-min time-out or a lost start with no rollback seen) with `rollback to <sha12> — <reason>` as its description; a re-dispatch after lost contact whose rollback succeeded meanwhile is answered `already-succeeded` by the box (§5) and recorded `success` once; `deploy-prod.yml` itself posts a Mattermost notice «откат прода на <sha12>: <reason>» (not a release digest, which belongs to `release-digest.yml`). The workflow `concurrency` group and the environment are the release's.
   - **Redeploy mode.** The containers must be recreated at the SHA production already runs, with the box's current env: either an env file on the box changed (the SmartCaptcha toggle in `api.env` and the compose `.env`, a rotated key), or production is down on a red prod health probe and the live SHA must be brought back up (incident recovery, runbook `apps/docs/content/operations/prod-incident-response.md`). In `redeploy` mode `owner_quote` is required exactly as for a release (refused when blank, reaching the steps only through `env:`). An env-change redeploy needs the owner's word in chat; an incident-recovery redeploy of the live SHA runs under the owner's standing authorization for that case, which `owner_quote` carries together with the incident reference, and the agent reports the cause to the owner afterwards. The runner pre-flight checks only that the SHA has a production Deployment with a `success` status (it really was released) and that its `images-<sha>.json` manifest is recorded: the SHA passed the stage-suite, CI, release and live-broadcast gates when it was released, and it ships no new code. The job then sends `redeploy prod <sha>` to ds-api-prod with the manifest on stdin and polls `status prod <sha>` exactly as a release does (§5, «Prod release driver.»). After a terminal status it cuts no release, posts no digest, and writes a new GitHub Deployment record of the run (`success`, `failure`, or `error` on lost contact) described `redeploy @ <sha12> — «<quote>»` with `kind: redeploy` in its payload, even though the SHA's release record exists. The workflow `concurrency` group and the environment are the release's.
   - Why no GitHub approval: the agent's `gh` runs under the owner's account (§1), so a GitHub approval would not separate the agent from the owner, and the workstation path already grants the agent the same reach. The control is the recorded owner quote, not a second click.
4. **Box access: GitHub-hosted runners push over hardened ssh.** (P1, P6, P8)
   - Port 22 opens to the internet with the hardening set in §4.
   - The prod key is released only to the release workflow's deploy job inside Environment `production` (deployment branches `main`). The stage key is released only inside Environment `stage`.
   - ds-data-prod stays private: it is reached through ds-api-prod as a jump host.
   - This retires the owner-`/32` rule and its IP-drift failures.
5. **Every long box step is a detached, locked, observable unit** (§5). The runner starts the unit and polls its status file, and a fresh runner can reattach. (P3, P5)
6. **Secrets live where they are used** (§4). The normal path needs no secret on any personal machine. (P6)
7. **Break-glass.** The same box entrypoints can be run by hand from any machine that holds the owner's offline break-glass key (§4). (P10)
8. **PR slots keep the agent-driven lifecycle and the Stage-B rules unchanged.** The difference is that their images also come from the registry, built by Actions for the PR head under the `pr/` prefix, instead of being built on the box. Slot mechanics stay in the staging spec. (P3, P9)
9. **The prod read path: the agent reads prod through named verbs, never a shell or a query of its own.** (P6, P7, P8) A separate read key in Environment `production-read` (§4) reaches its own forced-command entrypoint on ds-api-prod, `ds-read-entrypoint`: a `schema` snapshot, named aggregate `observe` reads, and a `rehearse` of a SHA's migrations on a throw-away restore of prod on ds-data-prod (§5 «Prod read verbs.», «Migration rehearsal.»). The box encrypts every answer to the operator's result key before it leaves, so the public job carries ciphertext and status lines only (§4). The release runs the same rehearsal as a gate before its backup and migrate. Owner decision 2026-11-04 (§10).

```text
merge to main
   │
   ▼
[Actions: build]  GitHub-hosted runner, push token (Environment `build`)
   │  docker build ×N ──push──▶ ds-platform.registry.twcstorage.ru/<image>:<full-sha>

```

Today the push token is stored only on ds-stage-1 (`/etc/ds-platform/registry-push-token`). §8 step (a) moves it into the build Environment and removes it from the box.

**Actions that receive these secrets are pinned.** Every `uses:` in the workflows, first-party `actions/*` included, is pinned to the commit its floating major tag ran when pinned, with that exact release tag as a comment; bumps come only through Renovate's `github-actions` manager (`renovate.json`, the repository's single dependency-update owner), and the `action-pin` guard enforces the pin (`tools/lint/action-pin-lint.ts`); a tag can be repointed upstream, a SHA cannot.

**ssh hardening on ds-api-prod and ds-stage-1** (§8 step (c)) — the standard set for a key-only admin port open to the internet:

- key-only authentication (already in place: `PasswordAuthentication no`);
- `PermitRootLogin no` (today it is `yes`);
- a dedicated `deploy` user. The CI keys in its `authorized_keys` carry `command="/usr/local/bin/ds-deploy-entrypoint",no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding`. The entrypoint (`infra/deploy/bin/ds-deploy-entrypoint`, installed beside `ds-release` under the install rule of §5 «Entrypoint.») splits `SSH_ORIGINAL_COMMAND` on single spaces, never through a shell, and matches it against a strict allowlist with exact arity and the `ds-release` argument checks: `status <env> <sha>` (→ `ds-release status`), `rollback prod <sha>` (→ the prod rollback path of the release driver, §5; ds-api-prod only, the manifest on stdin), `rollback-status prod <sha>` (→ the rollback record and the `-rollback` unit state, §5), `redeploy prod <sha>` (→ the prod redeploy path of the release driver, §5; ds-api-prod only, the manifest on stdin), `release <env> <sha>` (→ the box-side release driver of steps (d)/(e); refused with exit 3 while none is installed) and, on ds-stage-1 only, `upload-report <sha>` (the report tar stream of the paragraph below; absolute paths, `..` and links are refused) and `observe <name>` (one named read-only observation of the stage `main` slot for the stage suite, §5). Anything else exits 2 and is logged to the auth journal, so a CI key never reaches a shell;
- on ds-stage-1 the operator key of `deploy` keeps its full sudo, so `slot.mjs` keeps working unchanged; on the prod boxes `deploy` holds no operator key («sudo on prod», below), and the break-glass `pnpm deploy:prod` runs as `breakglass`;
- **sudo on prod** (step (f)). On ds-api-prod `deploy` holds one sudo right, `/etc/sudoers.d/90-ds-deploy`: `deploy ALL=(root) NOPASSWD: /usr/local/bin/ds-deploy-entrypoint ""` (no argument) with `Defaults!/usr/local/bin/ds-deploy-entrypoint env_keep += "SSH_ORIGINAL_COMMAND"`, so the request survives sudo's environment reset. The prod CI keys carry `command="sudo -n /usr/local/bin/ds-deploy-entrypoint",…,no-user-rc` (no deploy-owned `~/.ssh/rc` runs before the sudo); the entrypoint and the release driver's `-driver` and `-rollback` units run as root, and their per-call `sudo` is a no-op there, so one code path serves both boxes. Root runs only code from root-owned files: the entrypoints in `/usr/local/bin` and `/usr/local/lib/ds-platform`, and the installed tooling tree (§5 «Two trees»), a root-owned, not group/other-writable directory per SHA under `/usr/local/lib/ds-platform/trees/`, refused when a symlink in it resolves outside it, and reached through a `tree` symlink switched by one rename; and the target tree the `-driver` unit downloads itself as root from codeload. The hop to ds-data-prod names `deploy`'s `known_hosts` explicitly, since root's does not pin data-prod. The live tree on both prod boxes stays at the fixed `/home/deploy/ds-platform`, with `compose/api-prod/.env` inside it, never a `~`-relative path: the root units (HOME=/root) and the break-glass operator `breakglass`, which connects to ds-api-prod as itself and runs every script it sends ds-api-prod as root (`sudo -n bash`, the tree included), address the same tree; data-prod is reached by the hop as `deploy` and by the break-glass operator as `breakglass`. `deploy` has no other rule, is in neither group `sudo` nor `docker` (docker is root-equivalent; the Actions path runs as root and needs neither), and has no key but the CI keys behind the forced command: the operator key is removed, and the operator path on ds-api-prod is break-glass; `harden-ssh.sh --role prod` removes nothing of deploy's unless it runs from a `breakglass` session (`SUDO_USER=breakglass`), the proof that the break-glass login works. ds-stage-1 keeps the `deploy` operator key with full sudo, because the PR slots keep their agent-driven `slot.mjs` lifecycle (§3 item 8). ds-data-prod is narrowed after ds-api-prod (step (f), «Order») to the same shape: the same `/etc/sudoers.d/90-ds-deploy`, `deploy` in neither group, and one key, the hop key, behind `command="sudo -n /usr/local/bin/ds-deploy-entrypoint",restrict,from="<api-prod VPC IP>"`; the prod release converges it itself (§5 «Data-prod verbs.», «Converge.»): every release runs the installed root-owned `harden-ssh.sh --role data --from-release` through the `converge` verb over the hop, so the box, not the release, tells when the narrowing is complete. That run takes the place of the breakglass-session proof with box-side checks that the break-glass path is in place and usable: user `breakglass` exists and is not locked (a login shell, no expired account), its `authorized_keys` holds at least one key, its sudoers drop-in grants it NOPASSWD sudo (`breakglass ALL=(ALL) NOPASSWD:ALL`) and passes `visudo -c`, and `sshd -t` passes with the new config; any check failing refuses the run and changes nothing. `--role prod` keeps the breakglass-session proof;
- **The read key on ds-api-prod** (§3 item 9). One more CI line in `deploy`'s `authorized_keys`: the read key behind `command="sudo -n /usr/local/bin/ds-read-entrypoint",restrict`. `ds-read-entrypoint` is its own binary, not a mode argument of `ds-deploy-entrypoint`, because an older `ds-deploy-entrypoint`, put back by any install of a tree that predates the read path (a box-side rollback's hotfix `--ref`, a break-glass run from an old checkout), ignores its arguments and would serve the read key every deploy verb. Old trees never write `/usr/local/bin/ds-read-entrypoint`; it is self-contained for the read verbs and never execs or sources `ds-deploy-entrypoint`, so whatever `ds-deploy-entrypoint` is installed, the read key reaches only the read verbs. `/etc/sudoers.d/90-ds-deploy` gains the one matching right, `deploy ALL=(root) NOPASSWD: /usr/local/bin/ds-read-entrypoint ""` (no argument, as for `ds-deploy-entrypoint`), and its own `env_keep += "SSH_ORIGINAL_COMMAND"` default. `ds-read-entrypoint` admits only the read verbs of §5 «Prod read verbs.» and refuses everything else with exit 2, `release`, `rollback`, `redeploy` and `status` included; `ds-deploy-entrypoint` serves none of the read verbs. The same release install step that installs `ds-release` and `ds-deploy-entrypoint` installs it on ds-api-prod; the data verb `install` on ds-data-prod leaves it out (`DATA_INSTALL` of `ds-deploy-entrypoint`), since only ds-api-prod serves the read verbs. The prod sudoers content of `harden-ssh.sh` (`PROD_DEPLOY_SUDOERS_CONTENT`, and the cloud-init `api-prod.yaml` copy pinned byte-equal to it) gains the right; the `--role data` content (`DATA_DEPLOY_SUDOERS_CONTENT`) does not, and every `--role prod` run, the full breakglass run included, writes the right instead of dropping it. The release installs the line and the right itself, as it converges ds-data-prod (§5 «Converge.»): right after its `install` step the prod release driver runs the installed root-owned `harden-ssh.sh --role prod --from-release`, which converges exactly these two — the read line rewritten from the shipped `prod-read.pub` (a rotation replaces the old body; a missing or malformed file refuses the run and changes nothing; the release skips the call, with a status line, while the tree carries no `prod-read.pub`), the sudoers file checked with `visudo -cf` before its rename — removes no other line and runs first the box-side break-glass checks of `--role data --from-release`. The full `--role prod` run from a `breakglass` session keeps the read line as a prod CI line, and refuses the read key passed as a `--ci-pubkey`. Two changes to the script follow, each an explicit test case of S1: `--from-release` is admitted for `--role prod` as well as `--role data`, and the prod CI line pattern (`PROD_CI_RE`) matches the `ds-read-entrypoint` line too, so the prod-run sweep of non-CI lines does not delete the read line. A rotation is the owner's key step (§10) plus the PR that commits the new `prod-read.pub`; the next release converges the line.
- break-glass uses a separate admin user `breakglass`. Its key is held offline by the owner, carries no forced command, and has full sudo; it is the only interactive admin path once root login is off, and root holds no key;
- connection rate limiting: `MaxStartups 10:30:60` plus fail2ban on the sshd journal;
- `unattended-upgrades` for security patches;
- ds-data-prod keeps no public ssh; it is reached through ds-api-prod as a jump host. It gets the same `PermitRootLogin no`, break-glass user and root-key removal, and no CI key. Besides the break-glass key it accepts only the api-prod hop key: the `deploy` `authorized_keys` entry for `/home/deploy/.ssh/data-prod-hop` is `command="sudo -n /usr/local/bin/ds-deploy-entrypoint",restrict,from="<api-prod VPC IP>"` (no pty, no forwarding, no user rc), so the key reaches only the data-prod verbs of the entrypoint (§5 «Data-prod verbs.»): no shell, no other sudo. The workstation break-glass path reaches ds-data-prod as `breakglass` through the `ds-data-prod` alias (ProxyJump via ds-api-prod) and calls the same verbs through `sudo -n`.
- **Accepted risk: the data-prod hop key.** ds-api-prod is internet-facing, and the key reaches root-run verbs on data-prod. But ds-api-prod already holds the database owner credentials (`/etc/ds-platform/api.env` `DATABASE_URL`), so a compromised ds-api-prod already reaches all the data; ds-data-prod therefore does not re-check the provenance of the tree it is shipped. The forced command is therefore not a privilege boundary against the key's holder: `ship`, `install` and `data-up` put a tree, root entrypoints and a compose file of the holder's choosing on ds-data-prod and run them, so the key stays root-equivalent there, and no signature or provenance check is added. What the forced command buys is narrower: no interactive shell and no ad-hoc command — every call is one allowlisted verb, its parameters checked box-side and its refusals logged, every script a root-owned file installed on the box, never text from the client — and `deploy` loses its general sudo for every other key.
- **Accepted risk: a release runs as root on ds-api-prod.** A holder of a prod CI key can release an arbitrary tree, which then runs as root. Releasing is code execution already: the prod containers hold the database credentials. The boundary is the release of the key by Environment `production` (deployment branches `main` only), not the box.
- **Least privilege: the read key.** The read path never rides Environment `production`, whose key reaches `release`, `rollback` and `redeploy`: a job that only reads holds a key that cannot change prod. On ds-api-prod `ds-read-entrypoint` is a real narrowing, unlike the hop key's forced command: the `authorized_keys` line fixes the binary, no install of an older tree can widen it (§4 «The read key on ds-api-prod»), and no read verb takes a tree, a script, SQL or a recipient from the client — its words and its JSON parameters are checked box-side, and every SQL text and the recipient certificate are root-owned installed files. `ds-read-entrypoint` reaches ds-data-prod through the existing hop key by the read data verbs (§5 «Prod read verbs.»); a holder of the hop key is already root-equivalent there (the accepted risk above), so the narrowing that matters is the read key's on ds-api-prod. What a holder of the read key gets: ciphertext it cannot open, because the recipient is fixed box-side, and the load of one rehearsal on ds-data-prod, bounded by its headroom check, its lock, its runtime cap and its refusal while a release step runs (§5 «Migration rehearsal.»). The one SHA input, `rehearse <sha>`, is refused unless the SHA is contained in `main`, so the migration SQL a rehearsal runs is reviewed code.
- **Accepted risk: the read-result key on the workstation.** P6 keeps credentials off personal machines; the result key is not a prod credential: it opens nothing on a box and changes nothing, it only decrypts answers the operator asked for, whose plaintext is read on the workstation anyway, where the agent reads it. Its loss exposes at most the artifacts still retained (one day, below) and is closed by committing a new recipient certificate, which the next release installs. No prod access key moves to the workstation.

The settings live in the drop-in `/etc/ssh/sshd_config.d/10-ds-hardening.conf` (read before the main `sshd_config`, whose image-default `PermitRootLogin yes` is commented out; sshd takes the first value it reads). A new box gets this end state from its cloud-init file; a running box converges to it with `infra/deploy/bin/harden-ssh.sh` (idempotent, `sshd -t` before the reload).

**Public logs and artifacts (ADR-0011 channel 3).** The repository is public. ADR-0011 channel 3 allows build, test and deploy automation in Actions only with no runtime personal data in logs. Under that rule:

- **Prod jobs print status lines only:** unit name, phase, exit code, SHA and duration, and for a failed run the phase it failed in plus one bounded refusal reason — the failure note below. They never print `journalctl` output, compose logs, migration output or backup output. The full logs stay on the box (the journal of the unit) and are read over ssh by the operator.
- **The failure note.** A failed driver-unit run records `{"phase", "reason"}`: `phase` is the deploy-plan phase `prod.mjs` was in (a strict id `[a-z][a-z0-9-]{0,39}`, `download` for a failed codeload download, null before the first phase or when unknown), `reason` one line of at most 160 characters, control characters stripped. The reason is an allow-list: only a refusal `prod.mjs` authors — marked as such at its `die()` call, its first line interpolating no Error message, stderr or box output — gives its first line; every other failure (the catch-all, a wrapped child-process error, a JSON.parse or network error) reads `unexpected error — see the box journal`, its phase still named, so no foreign text reaches the public log; a red smoke names only its failing probe labels, and a run that exits without a note reads `exited <rc> without a failure note`. `prod.mjs` writes it to the file the unit hands it (`DS_RELEASE_FAILURE_FILE`); the unit bounds it again and records it root-only (0600 in the 0700 driver dir) as `<sha>.failure` beside the saved manifest, dropped at the start of every attempt of the SHA and with the other SHAs' manifests at lease time. `status <env> <sha>` reports it as `driver.failure` (null, or absent from an older driver, means none); the runner bounds it a third time, prints it in the poll's terminal line and the `::error::` annotation, and writes it into the failure Deployment record.
- **Nothing from the stage suite that can carry credentials goes to GitHub.** Stage holds only the deterministic golden synthetic dataset, and production data never reaches the box (staging spec §4), but a Playwright trace keeps the `Authorization: Basic` header of the stage gate and the passwords a test types (`packages/e2e/playwright.config.ts:160-161`: `trace: "retain-on-failure"`, `httpCredentials`). So the public check shows only a machine-readable summary: test title, status, duration and retry count — no traces, screenshots, videos, HTML report or error bodies. The full Playwright report, traces included, is copied over ssh to ds-stage-1 `/var/lib/ds-platform/e2e-reports/<sha>/` (root-readable, 14-day retention enforced by the next run's cleanup) and read there by the operator. The public check's console is `packages/e2e/reporters/summary.ts`, selected by `E2E_PUBLIC_LOG=1`, which only `.github/workflows/stage.yml` sets.
- **Prod read results leave only encrypted.** Everything the read path returns is treated as business data, the schema snapshot included: it is low-sensitivity, since the schema is in the repository, but one rule for every verb is the rule that holds. `ds-read-entrypoint` on ds-api-prod encrypts the verb's whole answer to the recipient certificate it has installed (`openssl cms -encrypt -binary -aes-256-gcm -outform DER`, CMS AuthEnvelopedData, OpenSSL ≥ 3.0, which both prod boxes have: they run Ubuntu 24.04 (`var.ubuntu_2404_os_id`, `infra/deploy/terraform/api-prod.tf`, `data-prod.tf`), which ships OpenSSL 3.0; a box whose `openssl` cannot produce it refuses the verb with exit 3) and writes only the ciphertext to stdout, so plaintext never reaches the runner. `prod-observe.yml` uploads that ciphertext as its one artifact `prod-read-<run_id>` (`result.cms`, retention 1 day) and prints status lines only: verb, exit code, ciphertext size and sha256, and for a failure the fixed reason of §5; the job summary carries the same lines. Counts, distributions, rehearsal row counts and error text exist only inside the ciphertext. The operator decrypts on the workstation with `pnpm prod:read <run-id>` (`gh run download`, then `openssl cms -decrypt` with the result key) into `~/.ds-platform/prod-read/<run-id>.json`, outside the repository; a figure from it never goes into a commit, an Issue, a PR or any other public place.

**Rejected for now: a pull agent.** This is the OpenGitOps «pulled automatically» principle: an agent on each box polls for a desired state, and port 22 stays closed. It changes only who initiates the deploy; the images, registry and approval stay identical, so switching later is cheap. Revisit trigger: a regulatory requirement (152-ФЗ / ФСТЭК) to keep admin ports closed, or log evidence of attempts beating the controls above.

## 5. Durable box steps

A release spans two production boxes plus runner-side steps (the pre-flight, the release cut and the Deployment record), so no single unit on one box can run it whole. The IdP converge already runs on ds-api-prod with the box's PAT file. Instead every long box step (pull, backup, migrate, up, prune) runs inside its own transient systemd unit on the box it changes, driven by the entrypoint `/usr/local/bin/ds-release`. The caller's death — a cancelled runner, a network cut, a killed workstation — never kills the step. The short read-only probes (boot verify, running-SHA verify) stay in the driver unit's plan.

- **Entrypoint.** `ds-release release [--retry-failed] <env> <sha> <step> <script-file>`, `status <env> <sha>`, `finish <env> <sha> succeeded|failed`, `check <env>`, `lease <env> <sha>` (read-only: refused while another SHA holds the env), `supersede <env> [<script-file>]` and `forget <env>`, where `<env>` is one of `prod`, `stage-main` or `stage-pr-<N>`. It lives in the tree (`infra/deploy/bin/ds-release`) and is installed with `sudo install -m 0755`, together with the entrypoint and the release driver, by a run allowed to write these box-global files: a prod run always (it ships only `main` / `hotfix/*` SHAs); on ds-stage-1 only the stage `main` converge of a SHA contained in `main` — the operator's `up main` / `reset main` after `git fetch origin main` and `git merge-base --is-ancestor <sha> origin/main`, the release driver's unit on its own provenance check below, without a second network check. A PR slot run and a `main` converge at a hotfix ref install nothing and use what the box has, so the last writer is always a `main` tree. A forward run installs from the tree it has just shipped, right after the ship and before any box step; the box-side rollback ships no tree and installs nothing: it runs the entrypoints already installed. Each forward install records the SHA and tree path it installed from in `/usr/local/lib/ds-platform/installed-tree` and keeps that tree until a newer install replaces it; the workstation `--rollback` (break-glass) still installs from the operator checkout's committed file, streamed over ssh and checked against its sha256, before its first `check`. cloud-init creates its state directory on a new box.
- **Stage suite box reads.** The stage suite reads the box only through the CI key's `observe <name>`, its parameters one JSON object (≤ 4 KiB) on stdin. The entrypoint runs only the named observations defined in the tree (`OBSERVATIONS` in `ds-deploy-entrypoint`): the configured academy host, the IdP password-complexity policy (the box reads the IdP token and calls the IdP itself; only the policy flags leave it), and one SELECT per test-owned-row read of `packages/e2e/lib/` (the owned mirror count, consent snapshot, phone account count, congress snapshot and wrong-verification snapshot). No SQL or shell comes from the client: each parameter is checked against its own pattern box-side (the journey's synthetic address shape, a numeric subject, a UUID, `+1999` test phones) and reaches psql as a psql variable (`:'name'`), never spliced into the SQL text. The SQL runs against the `main` slot database only, inside `BEGIN READ ONLY` with a 5 s statement timeout, and its answer is checked to come from that database in a read-only transaction before it is printed. The client receives only what the suite parses (a count or a fingerprinted snapshot of its own rows); an unknown name or a bad parameter exits 2, any other box exits 3, a failed read exits 1 with one fixed short reason (§4, public logs). The operator path is unchanged: run from the workstation, the same libs read the box with the operator's ssh.
- **Data-prod verbs.** ds-data-prod (`/etc/ds-platform/box-role` `data`) is reached only through `ds-deploy-entrypoint`, which serves these verbs there and refuses them on any other box (exit 3). Exact arity, single-space words, no shell; `<sha>` is the full 40-hex id, `<unit>` a rollback unit `ds-prod-<sha12>-rollback`. A stdin payload is one JSON object (≤ 64 KiB) checked box-side field by field, or the tree archive; never script text. The checks keep each call to its verb; they are not a privilege boundary against the hop key's holder, who stays root-equivalent through `ship` + `install` + `data-up` (§4 accepted risk): what the verbs buy is no shell and no ad-hoc command, every call allowlisted and logged, and no general sudo for `deploy`.
  - `capabilities` → `{"role":"data","verbs":[…]}`: what the client asks first (transport below).
  - `postgres-probe` (stdin `{target, sourceHash, preferRecordedImages, paths}`: mount targets absolute paths, image references `sha256:<64 hex>` or a `name:tag` reference, `paths` relative paths without `..`) → runs the installed `/usr/local/lib/ds-platform/postgres-artifact-probe.py` (a box entrypoint, installed like the others) with `HOME=/home/deploy`; its read-only evidence JSON on stdout.
  - `postgres-checkpoint` (stdin `{schema: 1, hashVersion?: 2, sourceHash: <64 hex>, systemId: <15–20 digits>, images: {postgres, pgbackrest: sha256:<64 hex>}}`; `hashVersion: 2` marks a v2 source hash, absent = a v1 record — `tools/deploy/README.md` → PostgreSQL deployment guard) → `/home/deploy/ds-platform-postgres-state.json`, written whole and renamed into place; then one `log bound: /<name> log=<driver> max-size=… max-file=…` line per container of the compose projects `ds-data-prod` and `ds-glitchtip`, listed by their `com.docker.compose.project` label (no compose file, no `.env`), never its env. It is the non-durable verb that closes the release's `data-prod-up` phase on every run, so the release output carries the log bound the `up` unit applied. The report is evidence only: any docker error prints one `log bounds: unavailable — <reason>` line and the verb still exits 0, so the pre-ship checkpoint never blocks the ship that repairs a tree.
  - `ship <sha>` (stdin the gzip tar of the tree, ≤ 256 MiB, ≤ 2 GiB unpacked, ≤ 100 000 members) → the archive is checked member by member like `upload-report` (no absolute or `..` path, no hard link or special file; a symlink only when it resolves inside the tree), extracted under a sibling staging directory with root as owner, then swapped with `/home/deploy/ds-platform` by rename.
  - `install <sha>` → the box entrypoints (`BOX_ENTRYPOINTS`) installed from that live tree; ds-data-prod keeps no tooling tree (the box-side rollback runs on ds-api-prod).
  - `data-env` (stdin `{vpcIp: <IPv4>, images: {postgres, pgbackrest: sha256:<64 hex>}}`) → `compose/data-prod/.env` (`VPC_IP`) and `.postgres-artifacts.json`.
  - `data-up <sha> [retry-failed]`, `backup <sha> [retry-failed]` → `ds-release release [--retry-failed] prod <sha> up|backup` with the fixed step script of the entrypoint (compose `up` of postgres + pgbackrest on the recorded image ids, then redis, then GlitchTip — `compose/data-prod/glitchtip/compose.yml` with the `.env` `data-env` wrote, `--pull missing --wait --wait-timeout 300`, so a changed GlitchTip compose file recreates its containers every release; `backup.sh incr`); `data-up` refuses with exit 3 before it starts the unit when `/etc/ds-platform/glitchtip.env` is absent or unreadable, naming the file and never reading it; the client polls `status prod <sha>`.
  - `backup-info` → the first 20 lines of `pgbackrest --stanza=ds info`. `rollback-floor` → `ABSENT` or `PRESENT`, the fixed 0036 presence read of `event_speakers` in `ds_prod`.
  - `finish <sha> succeeded|failed`, `check [<unit>]`, `supersede [<unit>]` → `ds-release finish|check|supersede [--except <unit>] prod`; `status prod <sha>` as on every box.
  - `converge <sha>` → the box entrypoints installed from that live tree as `install <sha>` does, then `/usr/local/lib/ds-platform/harden-ssh.sh --role data --from-release` (root-owned, this release's copy); its output streams back and its exit is the verb's. Idempotent: on a converged box it prints `nothing to change`.
  - **Transport.** The release driver on ds-api-prod sends the verb as the ssh command (the forced command hands it to the entrypoint as `SSH_ORIGINAL_COMMAND`). The workstation break-glass path logs in as `breakglass`, a shell login, and runs the same verb as `sudo -n env SSH_ORIGINAL_COMMAND='<verb>' /usr/local/bin/ds-deploy-entrypoint`. One code path (`tools/deploy/lib/data-prod.mjs`) with the form fixed by the run mode: the Actions `--local` run uses the forced form only, the workstation path the `sudo -n` form; per run the client asks `capabilities` once in that form, and a form that does not answer refuses the run — the other form is never tried.
  - **Converge.** No owner server step is in the path: every release takes the same steps, and the box state decides which of them change anything. Every Actions release converges ds-data-prod right after its `install` step and before the first data-prod state change (`data-prod-env`, `data-prod-up`, `backup`): it calls `converge <sha>` through the hop's forced command, then asks `capabilities` again and goes on only when the verb exited 0 and the forced command answers; a failed converge fails the release before any swap. The forced command answering is not proof of a converged box: harden-ssh.sh puts the hop line behind the forced command first, so a run that stops after it (a failing later step, or a lost hop session) leaves the forced command answering while `deploy` still holds other rights; the next release's `converge` finishes the narrowing, and from a release harden-ssh.sh reloads ssh on every run, so sshd files a stopped run wrote take effect. On a converged box the verb prints `nothing to change`. After a failed converge the client asks `capabilities` again before it rethrows, so the run's `finish … failed` reaches ds-data-prod while the forced command still answers; when it does not, no further verb runs. `capabilities` must name every data verb, `converge` included. The workstation break-glass path reaches ds-data-prod as `breakglass`, a shell login, so only the Actions `--local` run converges.
- **Prod read verbs.** The read key (§4 «The read key on ds-api-prod») reaches `ds-read-entrypoint` on ds-api-prod (`/etc/ds-platform/box-role` `prod`; any other box refuses the read verbs with exit 3). Exact arity, single-space words, no shell; `<sha>` is the full 40-hex id, `<name>` an entry of the prod catalogue, the parameters one JSON object (≤ 4 KiB) on stdin, checked field by field box-side. Every answer leaves encrypted (§4 «Prod read results leave only encrypted.»); the shapes below are the plaintext `pnpm prod:read` recovers. Exit codes, as for the stage `observe`: 0 the answer; 1 a failed read, with one fixed short reason on stderr (`a release step is running`, `a rehearsal is running`, `the read-only transaction check failed`, `the read timed out`, `insufficient headroom (disk)`, `insufficient headroom (memory)`, `copy behind prod`, `archive check failed`, `the read failed`); 2 an unknown verb, a bad arity or a bad parameter, logged to the auth journal; 3 the wrong box, a verb or file not installed, or an `openssl` that cannot encrypt. A read never runs beside a release, a rollback or a redeploy, so its `ACCESS SHARE` locks never queue a migration's `ALTER TABLE`, and live queries behind it. The box-side check holds that for every release path: `schema`, `observe` and `rehearse` first run the read-only `ds-release check prod` locally on ds-api-prod — where the `migrate` step and the `-driver` and `-rollback` units run — and then `check prod` on ds-data-prod (its `up` and `backup` units), and refuse (1, `a release step is running`) while any `ds-prod-*` unit is active on either box, the `ds-prod-<sha12>-driver` and `-rollback` units included; an Actions release, rollback or redeploy keeps its `-driver` or `-rollback` unit live for the whole run, and a break-glass `pnpm deploy:prod` runs its steps as the same `ds-prod-*` units. The reads do not share the `deploy-prod` concurrency group, because a GitHub concurrency group keeps one pending run and a newer pending run cancels the older one, so a read could cancel a queued release or rollback. A release started while a read already runs waits at most that read's statement timeout (30 s) at its first lock; that residual is accepted. `capabilities` and `rehearsal-status` read no database and always answer.
  - `capabilities` → `{"role":"prod","mode":"read","verbs":[…]}`, in plaintext (it names verbs only). `prod-observe.yml` asks it first and refuses when the verb it was dispatched for is absent.
  - `schema` (no stdin) → the data verb `read-schema` over the hop. Answer: `{"verb":"schema","database":"ds_prod","takenAt","serverVersion","migrations":[{"id","hash","created_at"}],"dumpSha256","catalogue":{"tables":[{"schema","name","columns":[{"name","type","notNull","default","identity","generated"}],"indexes":[{"name","definition"}],"constraints":[{"name","kind","definition"}]}],"enums":[{"schema","name","values"}],"sequences":[{"schema","name"}]}}`. `migrations` are the rows of the api migrator's `__drizzle_migrations` table in apply order. `dumpSha256` is the sha256 of `pg_dump --schema-only --no-comments --no-owner --no-privileges ds_prod`, the change detector between two snapshots (an equal hash means no schema change), never compared with a local dump. The catalogue covers every non-system schema (not `pg_catalog`, `information_schema`, `pg_toast*`) and is read from `pg_catalog` with `format_type`, `pg_get_expr`, `pg_get_indexdef` and `pg_get_constraintdef`. No row data and no `COMMENT` text leave the box: the catalogue SQL reads only catalog relations, and the dump text never leaves, only its hash.
  - `observe <name>` (stdin the parameters) → the data verb `read-observe <name>`: one named aggregate read from `PROD_OBSERVATIONS` in `ds-deploy-entrypoint`, the prod counterpart of the stage `OBSERVATIONS` (§5 «Stage suite box reads.»). Each entry fixes its SQL, its parameters and its result columns. A parameter is either a value checked against its own pattern and passed as a psql variable (`:'name'`) — never a person-identifying value (an email, a phone, a name, a person's id): a filter on one would make any count a membership oracle for one person, so value patterns are enumerations, dates or ids of non-person objects — or an identifier taken from the entry's own enumerated list and passed as `:"name"`; neither is ever spliced into the SQL text, and no entry reaches a table or column outside its list. Result columns are declared aggregate kinds only — `count`, `distinct`, or `bucket` rows `{bucket, count}` — with integer counts. A bucket of fewer than 10 rows is folded into one `suppressed` bucket, itself reported as `"<10"` when under 10, and a `count` or `distinct` under 10 is reported as `"<10"` too, so no single person is identifiable. Answer: `{"verb":"observe","name","takenAt","result":{…}}`. The catalogue grows only by a reviewed PR; a test in `tools/deploy/ds-deploy-entrypoint.test.mjs` runs every entry against a fixture database and fails on an undeclared column, a non-integer value, an unsuppressed small bucket, an unsuppressed `count` or `distinct` under 10, or a value parameter whose pattern admits an email or a phone.

- **Migration rehearsal.** `rehearse <sha>` answers «what will the migrations of `<sha>` do to prod» on a throw-away restore of prod on ds-data-prod; prod data never leaves ds-data-prod and its backup repository.

The release gate below sends the same archive from the target tree it has already downloaded.
  - **Durable unit.** `rehearse <sha>` takes `flock -n /run/ds-platform/ds-rehearsal.lock` and refuses (1) while another rehearsal or any `ds-prod-*` step unit runs; under the lock, on every call (the no-pending path below included), it removes any leftover of an earlier rehearsal (a `ds-rehearse-*` container, a directory under `/var/lib/ds-platform/rehearsal/scratch/`), then — unless nothing is pending (below) — starts `systemd-run --unit=ds-rehearse-<sha12> -p RuntimeMaxSec=900 -p ExecStopPost=/usr/local/lib/ds-platform/rehearse-cleanup` and returns `started`, or `running` when that unit already runs. The unit runs the installed root-owned `/usr/local/lib/ds-platform/rehearse-migration.py` (a box entrypoint, installed like the others). `ExecStopPost` runs on success, failure, a kill and the runtime cap. A reboot leaves no unit, and its scratch (about one database size on the prod cluster's filesystem) is removed at boot by the installed `/etc/tmpfiles.d/ds-rehearsal.conf` entry `R! /var/lib/ds-platform/rehearsal/scratch`, which leaves the reports one level up; a container it left is removed by the next `rehearse` call. Teardown never depends on the client.
  - **Runtime budget.** The 15-min cap bounds the release gate phase too: with it a release keeps at least 45 min of the runner's 60-min poll limit (§3 item 3) and of the deploy job's `timeout-minutes: 75` (`deploy-prod.yml`); a rehearsal that hits the cap fails the gate like any failed rehearsal.
  - **Headroom check, before any restore.** The latest backup's database size comes from `pgbackrest --stanza=ds info --output=json`. The run refuses (1, `insufficient headroom (disk)`) unless the scratch filesystem of `/var/lib/ds-platform/rehearsal/` has at least 1.5 × that size + 2 GiB free — on the prod cluster's own filesystem this margin is also what keeps the prod cluster writable — and (1, `insufficient headroom (memory)`) unless `MemAvailable` is at least 1 GiB. A refusal creates nothing.
  - **Restore target.** A separate throw-away cluster: `pgbackrest restore` of the latest backup into a fresh `/var/lib/ds-platform/rehearsal/scratch/<sha12>/pgdata`, run in the recorded pgbackrest image with `--type=default --archive-mode=off` (recover to the end of the archive stream, then promote; pgBackRest admits `--target-action` only with a target type — `build/config.yaml` `target-action` `depend: type [immediate, lsn, name, time, xid]` — so none is passed. Right after a release the latest backup is that release's pre-migrate `incr`, which `--type=immediate` would stop at, replaying migrations prod already has and missing newer data). Prod sets no `archive_timeout`, so the open WAL segment, which can hold the last migrate, is not yet archived; the restore is therefore preceded by `pgbackrest --stanza=ds check` against the live cluster in the recorded pgbackrest image, which calls `pg_switch_wal()` on the primary and waits up to `archive-timeout` until that segment is in the repository (pgBackRest `src/command/check/check.c`, `dbWalSwitch` + `walSegmentFindOne`); a failed check refuses (1, `archive check failed`) and restores nothing. The live `postgresql.conf` is not changed. After the restore comes a container `ds-rehearse-<sha12>` of the recorded postgres image (`ds-platform-postgres-state.json` `images`) on that directory, with `--rm`, no restart policy, `--network none`, `--memory 768m --memory-swap 768m --oom-score-adj 1000` (so an index build in a migration hits its own cap, and under pressure the kernel's OOM killer picks the copy, never the prod postgres; the restore container gets the same cap and score), `listen_addresses=''` (socket only), `archive_mode=off` and small memory settings (`shared_buffers=128MB`, `max_connections=10`). It never joins the prod compose project, never publishes a port and never archives WAL into the prod stanza; the prod cluster is not touched. The restore takes ≈ 23 s today plus the WAL replay since the latest backup.
  - **Apply, as the migrator does.** The pending migrations are the journal entries whose `when` is newer than the newest `drizzle.__drizzle_migrations.created_at` (the row with the greatest `created_at`), the rule of the api migrator (`drizzle-kit migrate`, the `ds-api-migrate` image's `drizzle:migrate:ci`; `drizzle-orm/pg-core/dialect.js` `migrate`, drizzle-orm 0.45.2). Before any restore, `rehearse` reads that newest `created_at` from live `ds_prod` with the read transaction below (`BEGIN READ ONLY`, 5 s statement timeout, 2 s lock timeout); when no journal entry is newer, it answers `no pending migrations`, records a report with `"pending":0` and restores nothing. After the restore it reads the copy's newest `created_at` and refuses (1, `copy behind prod`) when it differs from the live value read before, tearing the copy down, so a rehearsal never runs on a copy that lacks a migration prod has. The harness applies them through the copy's `psql` in one transaction, as that migrator does (its `migrate` wraps the whole pending loop in one `session.transaction`), statements split on `--> statement-breakpoint`, and writes each migration's `__drizzle_migrations` row (`hash` the file's sha256, `created_at` its `when`). After each migration it reads, inside the same transaction: the elapsed time (`clock_timestamp()`), the rows inserted, updated and deleted per table (`pg_stat_xact_user_tables`, the difference from the previous migration), and the locks the backend holds (`pg_locks` of `pg_backend_pid()` joined to `pg_class`, those new since the previous migration, with their mode). A failing statement ends the run with that migration's tag, SQLSTATE and message and rolls the copy back; otherwise the harness commits and reads the `schema` catalogue of the copy.
  - **Report.** `{"verb":"rehearse","sha","backup":{"label","stopAt"},"recoveredTo","pending","migrations":[{"tag","ms","rows":{"<schema.table>":{"inserted","updated","deleted"}},"locks":[{"relation","mode"}],"error":null|{"sqlstate","message"}}],"catalogueAfter":{…},"state":"succeeded|failed"}`, `recoveredTo` the commit time of the last replayed transaction (`pg_last_xact_replay_timestamp()` after promotion; it stays fixed at the last transaction recovery replayed), so the report states how current the copy was; recorded root-only (0600) as `/var/lib/ds-platform/rehearsal/<sha>.json` (the newest 10 kept) and returned by `rehearsal-status <sha>`, encrypted on ds-api-prod. The plaintext state word (`running`, `succeeded`, `failed` or `absent`) is the one line `prod-observe.yml` prints; an error message, which can quote a row value, stays inside the ciphertext. Durations are indicative: the copy runs with less memory and without prod's concurrent load. `pnpm prod:schema-drift` compares a report's `catalogueAfter` with the snapshot of `<sha>`, so a migration chain that does not produce the schema its tree declares shows before the release.
  - **Release gate.** In `release` mode the prod release driver runs the rehearsal as its own phase, `rehearse`, after `install` and `converge` and before the first data-prod state change (`data-prod-env`, `data-prod-up`, `backup`) and the `migrate` step, through the hop's data verb with the target tree it has downloaded. With no pending migration — the live read of «Apply, as the migrator does.» above finds no journal entry of the target tree newer than prod's newest `created_at` — the phase prints `rehearsal: no pending migrations` and restores nothing. A failed rehearsal, a refused headroom check or a rehearsal that cannot run fails the release in phase `rehearse` before any prod state change; its failure note (§4) reads `migration <tag> failed (SQLSTATE <code>)` or the fixed refusal reason, nothing more, and the report waits on the box for `rehearsal-status`. So `deploy-prod.yml` refuses on the rehearsal instead of on prod, with no new input and no second key in the `production` job. `rollback` and `redeploy` modes rehearse nothing: they apply no migration. Break-glass is the one exception: `pnpm deploy:prod` takes `--skip-rehearsal "<reason>"`, recorded like its other gate exceptions; the Actions path has no skip input.

On the box whose `/etc/ds-platform/box-role` is `stage` it accepts only `stage-main` (`stage-pr-<N>` is refused: PR slots stay operator-driven, §3 item 8; a prod box is served by the prod driver below). It validates the stdin manifest (exactly `sha`, `ref`, `images`; `sha` equal to the argument; a `main` or `hotfix/*` ref; every required recorded image present; each image — a recorded one or one a newer tree added, which the driver does not know yet — named by a strict image name and a `sha256` digest reference of its own name; a newer image is accepted because the driver is installed from the tree a release ships, so refusing it would dead-end every release past the addition, and the shipped tree's `slot.mjs` / `prod.mjs` judge the image set before they pull), then, unless a unit of the same SHA is already running (it answers `attached` before any provenance check, since that unit started only after both passed, so a GitHub rate limit or a registry outage never fails a running converge), checks both provenances on the box, from no client data, and refuses with exit 3 on any failure: the tree — GitHub serves a fork-network commit through this repository's codeload URL, so the unauthenticated `GET https://api.github.com/repos/doctor-school/ds-platform/compare/main...<sha>` must answer `status` `behind` or `identical` (anything else, a 404, a rate limit or a network error included, refuses); and the images — logged in with the box's pull credential (`/etc/ds-platform/registry-pull-token`, inside root's shell under a docker config dir of its own — `DOCKER_CONFIG=$(mktemp -d)`, root-only, removed on exit — so it never touches root's shared docker login that concurrent pulls use), every manifest digest, of each image the manifest names, must equal the digest the registry serves for `<registry>/<image>:<sha>` in the release namespace (no `pr/`), which only the build Environment's push token writes. It then asks `ds-release lease` and refuses on another SHA's lease, saves the manifest root-only (removing the saved manifests of other SHAs, whose units read theirs at start) and starts `systemd-run --unit=ds-stage-main-<sha12>-driver --remain-after-exit -p KillMode=mixed` as the deploy user, with the manifest as the unit's stdin. The unit downloads `https://codeload.github.com/doctor-school/ds-platform/tar.gz/<sha>` (it honours `export-ignore` exactly as `git archive` does), extracts it and runs `node <tree>/tools/staging/slot.mjs up main --ref <sha> --local --images-file -`, where `-` reads the inherited stdin (fd 0) without opening a path, so the root-only manifest needs no permission check against the deploy user. `--local` swaps only the transport: every ssh script, capture and ship of the plan runs through a local `bash -c` with the same stdin and watchdog, the ship installs that extracted tree as the slot tree, the digests come from the manifest instead of `gh`, and the health check's basic-auth plaintext from `/etc/ds-platform/stage-basic-auth.txt`; the plan, its steps and its ds-release units are the operator's. Node is the box's pinned runtime (`infra/deploy/bin/install-node.sh`, a post-boot provisioning step). `status <env> <sha>` through the entrypoint adds the unit as `"driver": {"unit", "active": "activating|active|inactive|failed|absent", "rc", "failure"}`, where `active` describes the unit's process, not systemd's ActiveState (a finished `--remain-after-exit` unit stays `active (exited)` there): a running process is `active` (`activating` while starting), an exit with status 0 is `inactive` with `rc` 0, a non-zero exit or systemd's `failed` is `failed` with `rc` = ExecMainStatus, and no unit is `absent` with `rc` null; the caller's run is terminal when `active` is `inactive`, `failed` or `absent`, and succeeded only when `rc` is 0 and the release record is `succeeded`; `failure` is the failure note of §4 «Public logs» (stage's `slot.mjs` writes none, so a failed stage run reads `exited <rc> without a failure note`).   - **Own unit and record.** A rollback is its own unit and record kind: unit `ds-prod-<sha12>-rollback`, its own status file (kind `rollback`), never the release record of that SHA and never a `finish` on a release record. It takes no lease and is refused while any release step runs. A `rollback prod <sha>` whose target is already live because this SHA's own `-rollback` unit finished rc 0 with its record `succeeded` answers `already-succeeded` without the lock, a new record or a unit run — the runner's re-dispatch after lost contact; any other live target stays refused by the ancestry check. At its end it supersedes the prod release records, so a later release of the rolled-off SHA re-runs every step and `cmd_release`'s `already-succeeded` path cannot short-circuit it. `ds-release supersede prod` likewise excludes the rollback's own unit. The runner polls `rollback-status prod <sha>` (§4), never `status prod <sha>`: it returns the rollback record and the `-rollback` unit state, with the `driver` object of a release's.
- **Unit name.** `systemd-run --unit=ds-<env>-<sha12>-<step> --remain-after-exit -p KillMode=mixed`, which runs the step script as the calling operator user. A second start under the same name fails fast, so the name itself deduplicates. Finished units of the env are stopped and reset by a later call for that env: only after it has taken the lock, and only for units no longer running.
- **Lock and lease.** Every mutating call holds `flock -n /run/ds-platform/ds-<env>.lock` for its whole (short) life. `ds-release` runs as root on every box, so its lock directory is root-owned 0755, never the world-writable sticky `/run/lock`, where any uid could create the lock file first and block every release and rollback (with `fs.protected_regular`, root's own open of a lock file another uid created there is denied). The release driver takes its per-env lock `ds-release-driver-<env>.lock` in the same directory when it runs as root (ds-api-prod); as `deploy` on ds-stage-1 it cannot write there and locks in its own `/run/lock/ds-platform-deploy`. `/run` is tmpfs, so every call (re)creates its lock directory 0755 and refuses (exit 3) one that is a symlink, is not owned by the caller or is group- or other-writable; a lock path that exists but cannot be opened is refused the same way, naming the path and its owner. A release stays open from its first step until `finish`; while one SHA's release is open for an env, `release` for a different SHA of the same env is refused and names the open SHA. Any start is also refused while a step unit of another SHA of the env is still running (`activating`, or `active` with sub-state `running` — not the `active (exited)` every finished `--remain-after-exit` unit shows), and the error names that unit. The operator closes every run explicitly: `finish … succeeded` at the end of the deploy or the slot converge, `finish … failed` on any failure exit. One that cannot (the box is unreachable) leaves the exact `finish` command in its output. The workflow `concurrency` group is the first line of defence and the lease the last.
- **Status file — the authority.** Each box keeps `/var/lib/ds-platform/release/<env>/<sha>.json` for the current attempt of each SHA it ran steps for; a closed attempt is archived beside it as `<sha>.<startedAt>.json`. The entrypoint writes the file atomically (write to a unique temp file in the same directory, `fsync`, `rename`, `fsync` of the directory) at every step boundary, so even a verdict recorded without the lock never shares a temp file with another write. A file that does not parse stops every call that reads it with `ds-release: corrupt status file <path>` and a non-zero exit, and the poller reports it as such, never as lost contact:

  ```json
  {
    "env": "prod",
    "sha": "<full sha>",
    "unit": "ds-prod-<sha12>-<step>",
    "state": "running | succeeded | failed | superseded",
    "step": "pull | backup | migrate | up | verify | prune",
    "steps": [
      {
        "name": "pull",
        "unit": "ds-prod-<sha12>-pull",
        "startedAt": "…",
        "endedAt": "…",
        "rc": 0
      }
    ],
    "startedAt": "…",
    "updatedAt": "…",
    "error": null
  }
  ```

  `state` is the release-level record. It is `running` while the attempt is open — a failed step records its error but leaves the attempt open — and `succeeded` or `failed` only through `finish`, whose `succeeded` refuses while any step lacks a success verdict. `superseded` marks an attempt the env has moved off: starting a new SHA marks the env's previous closed attempt `superseded`, and so does the app-only rollback (below).

- **Reattach.** The runner never streams a step: it starts the unit, then polls `status <env> <sha>`, which reads the status file and reports whether the running step's unit is still alive. Each poll prints one status line into the job log (§4); it never tails the journal. Recorded verdicts answer only within the attempt that recorded them. `release` for SHA X reads X's record first:
  - record `running` (the attempt was never closed — its client died): X resumes in that attempt, step by step:
    - step `succeeded`: it returns that verdict without starting a unit, so a resumed attempt never repeats backup or migrate.
    - step `failed`: it returns `failed`. Only an explicit `--retry-failed` re-runs a failed step; nothing re-runs a succeeded one.
    - step `running`: it attaches to the existing unit by name. A unit that died without recording a verdict (a reboot) is recorded as `failed`.
    - step absent: it starts the unit.
  - record `succeeded`, `failed` or `superseded`: the closed attempt is archived and a fresh attempt starts, running every step again. This is what makes deploy B → rollback A → deploy B again, and stage B → C → B, converge for real.
  - record absent: a fresh attempt starts.

  Losing the box while polling ends only the wait: the unit keeps running, and a re-run of the same SHA reattaches. The poller tolerates a few consecutive polls that read the step's unit as gone (a transient `systemctl` failure on the box) before it asks `release` to settle it; when the box then answers that the unit still runs, the unit is left running and the reattach command printed. Every step stays idempotent, as the `pnpm deploy:prod` steps are today. A stage slot's verdicts are dropped (`forget`) when what they describe is gone: on `down`, and on `reset main` before the re-cloned database is migrated again.

- **Edge config.** The ship replaces the live tree, so before it the release keeps the `Caddyfile` and `centrifugo/config.json` the running containers serve in `/var/lib/ds-platform/runtime-config/previous/` (root 0700/0600), tagged with the SHA it was taken for: a re-entered run of that SHA keeps the backup, the next SHA retakes it, and a rollback keys its backup apart from the forward release of its target. Right after the boot verify, before IdP, `migrate` and `up`, the shipped `Caddyfile` is validated (`caddy validate`) on the caddy image the shipped compose pins, and the shipped `centrifugo/config.json` must parse as a JSON object. An invalid config puts the kept configs back on disk and fails the release before any swap: production still serves the previous config. A failed runtime-config apply puts the kept configs back, restarts caddy and centrifugo onto them and fails the release naming that restore. The rollback applies the same controls to the target's configs («Prod rollback», Steps).
- **Rollback floor.** This is unchanged from today: the pre-migrate pgbackrest backup and the app-only rollback to the previous image digest (`run-prod-deploy` → rollback). The rollback takes no lease, so it never waits on the release it reverts, but a step outlives its operator session: before its first state change the rollback runs the read-only `check prod` on both boxes, its own unit excluded, and refuses, naming the unit, while any other `ds-prod-*` step unit still runs; the box-side rollback installs nothing, only the workstation `--rollback` installs `ds-release` from the operator checkout (a still-running `migrate` would otherwise reach its `up -d` and put the rolled-off SHA back). Its `up -d` then runs through `supersede prod` on api-prod — under the env lock, refused while a step unit runs — which marks the recorded attempts `superseded`; data-prod's records are superseded the same way. With registry images, the rollback becomes a pull of the previous SHA's recorded digest instead of a rebuild.

## 7. Rejected alternatives

- **Workstation hardening only** (keep-awake, IP pinning, a watchdog): it fails P1, «no personal machine».
- **GHCR:** private packages on Free include only 1 GB transfer/month, which one release exceeds. Pulls to RU boxes run at ~1.8 MB/s, and making the packages public needs an org setting change.
- **S3 tarballs via `docker save` / `docker load`:** no layer dedup, and it would need its own versioning and GC. It is kept only as the emergency fallback (§9).
- **Self-hosted `registry:2` on S3:** one more service to run and patch.
- **Timeweb App Platform for the core stack:** compose apps forbid `volumes` and proxy only the first service. There are no stands for compose apps, no pre-deploy or migration step and no approval, so orchestration would still be needed.
- **Kubernetes + GitOps:** overkill for one prod box and one operator.
- **Self-hosted CI inside Russia:** GitLab CE needs 8 vCPU / 16 GB, and pull-mirroring is a Premium feature. Forgejo and Gitea lack environments with reviewers and would become a second source of truth.
- **Self-hosted GitHub runner:** fork PRs would run on our box, because the repo is public (owner 2026-09-09).
- **Larger GitHub runners with a static IP:** they require a paid plan.
- **Free-form SQL on the prod read path, read-only or not:** any query reaches any row, and its output cannot be reviewed before it runs. Reads are named verbs and named aggregate entries in the tree, grown by reviewed PRs (§5 «Prod read verbs.»). Owner 2026-11-04 (§10).
- **A Postgres login role for the agent, read-only included:** it needs a network path to the database from outside (a new listener or a tunnel) and a database credential on the workstation, and a read-only role still reads every row. The read-only transaction inside a named verb is the guard instead. Owner 2026-11-04.
- **Rehearsing on a copy outside ds-data-prod (stage, a runner, the workstation):** prod personal data would leave the prod box and its backup repository (staging spec §4: production data never reaches stage). The rehearsal restores on ds-data-prod itself. Owner 2026-11-04.
- **New inbound ports, a VPN or a bastion for the read path:** owner decision #1384 stands; the read path rides the existing hardened ssh and the existing hop.
- **Plaintext read results in the job log, summary or an artifact:** the repository is public, so every job log and artifact is world-readable (§4 public logs). Results leave only as ciphertext to a recipient fixed box-side.
- **Decrypting in Actions, or a recipient chosen by the client:** a decrypting job would print plaintext into a public run, and a client-chosen recipient would let a holder of the read key encrypt to itself. The recipient certificate is a root-owned installed file; the private key stays on the workstation (§4 accepted risk).
- **`age` for the result encryption:** a new package on ds-api-prod; `openssl` is already on the box and on the workstation and gives CMS AuthEnvelopedData with AES-256-GCM.
- **Reusing the `production` key and Environment for reads:** that key reaches `release`, `rollback` and `redeploy`, so every read would hold a key that changes prod (P6, least privilege).
- **The release gate as a runner step of `deploy-prod.yml`:** it would need the read key, a second prod key, in the `production` job, and the runner is not durable. The rehearsal is a phase of the box-side release driver, which already holds the hop (§5 «Migration rehearsal.»).
- **One transaction per migration in the rehearsal:** the api migrator applies the pending set in one transaction, so per-migration transactions would understate how long locks are held. The harness keeps the migrator's single transaction and takes per-migration readings inside it.
