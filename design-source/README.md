# `design-source/` — imported Claude Design canvas (single source of truth)

This folder holds the **actual design source** for the Doctor.School neo-brutalist visual language, imported verbatim from the Claude Design project **«Doctor.School визуальный язык»** (`8cc2f39a-d58e-4491-b539-4337881ced4f`).

> **Build to these files, NOT to issue-body prose.** The `.dc.html` inline styles carry the exact values — px, border widths, colors (light + dark), states, and placeholder copy. Issue descriptions are a lossy transcription and a coverage checklist, **not** the fidelity spec. Where prose and this source disagree, **the source wins**. (The neo-brutalist re-skin diverged the first time precisely because it was built from prose instead of this HTML.)
>
> **Vendor EVERY canvas the surface renders — not only the headline one.** If a demo/composition renders a unit whose spec lives in a separate canvas (a card, a block, a screen fragment), that canvas must land here BEFORE building. The #514 rhythm demo repeated the founding error one layer down: its event card was built from §09 prose while `unit-event-card.dc.html` sat unimported.

## Naming convention

**The canvas title in Claude Design IS the vendored file name** — kebab-case English, no extension (title `event-page` → `design-source/event-page.dc.html`). There is no name map and no transliteration step: if the two ever disagree, the canvas title is renamed, never the file.

The group prefix answers one question — «do both storefronts render it?»: **`ds-*`** = system canvases, the visual language itself rather than a product screen · **no prefix + a `host` prop** = a shared capability both storefronts render from one canvas (`event-page`, `events-feed`, `room`, `document`, `auth`) · **`unit-*`** = a block other canvases `dc-import` (card, column, filter), never a standalone screen · **`doctor-*`** / **`academy-*`** = host-only screens, only that storefront renders them · **`archive-*`** = superseded canvases and decision mockups, which in the repo live in `design-source/archive/`.

**In the project, not vendored:** `ds-responsive-preview` — a utility preview canvas, not a build reference · `archive-design-directions` — the «three directions of the visual language» exploration that preceded `ds-foundation` · `archive-event-page-v1` — the 2026-08 single-storefront event page superseded by `event-page` · `archive-academy-project-v1` / `archive-academy-expert-v1` — the pre-relaunch Academy project / expert pages superseded by `academy-project` / `academy-expert` · `archive-events-feed-v1` — the pre-relaunch copy of the drift-re-pulled `events-feed`. Their bytes are the previous git revision of the corresponding file here, not a second source.

## Canon rules

One capability, one canvas — the same rule the code follows (ADR-0013 §A1: a capability both storefronts render lives in one feature package, hosts contribute a route file and a host-config object).

1. **One canvas per capability, host as a prop.** A capability both storefronts render has one `.dc.html`; host differences are props / fork panels, never a second `doctor-*` / `academy-*` file. `event-page.dc.html` (`header` prop) and `document.dc.html` (`shell` prop) are the model. Host-only screens (`doctor-feed`, `doctor-school`, `academy-invest`, …) keep their host prefix.
2. **Tokens only in `ds-foundation.dc.html`.** No other canvas redefines a colour, radius or type step; a canvas that does is a vendoring defect, not a design decision.
3. **Superseded and decision canvases move to `design-source/archive/`** in the PR that vendors the successor or records the decision. The «Files» tables above list canon only.
4. **Vendoring writes the registry row.** The PR that vendors a canvas names in `specs/product/two-site-ia/capability-ownership.md` the **feature package** (not the host) that will build it; the registry row and the canvas tables stay in sync.
5. **The owner draws once.** When a doctor screen equals an Academy screen, the request to the owner is «add the host prop / fork panel to `<canon>.dc.html`» — never «draw the doctor version». The same applies in the other direction: when the doctor canvas is the one vendored (auth), the request is «add the host prop and bring the Academy screens into `auth.dc.html`».

## Provenance & how to refresh

- **Project:** <https://claude.ai/design/p/8cc2f39a-d58e-4491-b539-4337881ced4f>
- **Canvas names are ASCII since 2026-09-09** (#2150): the canvas title equals the file base name, so there is no name map to consult — the «Naming convention» section above is the whole rule. A canvas whose title still reads in Cyrillic is a canvas to rename, not a file to transliterate.
- **Re-pull the exact bytes:** `DesignSync get_file` against project `8cc2f39a` with the canvas title (= the file base name, e.g. `ds-foundation`); write the bytes verbatim.
- **Never re-type a canvas.** `get_file` returns the content as a JSON tool result; write the file from that result programmatically (a large result is persisted to the session's `tool-results/` directory, a small one lands in the session transcript — both are parseable JSON). A hand-retyped copy is not the source (the first #1450 attempt injected a stray line into `doctor-home.dc.html` before the bytes were re-pulled properly).
- **Drift check on every vendoring pass:** re-pull every canvas a new screen `dc-import`s or that has an `archive-*-v1` sibling in the project. On 2026-08-24 five canvases had moved without any prompt targeting them (`ds-foundation`, `unit-event-card`, `academy-experts`, `academy-projects`, `events-feed`). On **2026-09-09** (#2150) five more were re-pulled the same way: `doctor-home`, `event-page-recording`, `account-my-events`, `account-profile`, `events-feed-month`.
- **`ds-shell` vendored 2026-09-10** (#2150): the owner drew the shared shell, it was pulled byte-exact, wired to render `props.children`, and the 27 screens that carried their own header/footer were swapped to `dc-import` it. The swapped screens were pushed back to the project the same day, so repo and project are byte-equal.
- **View it live:** open the Claude Design link above. The DC runtime (`support.js`) that renders the `<x-dc>` template is not vendored here — re-pull it via `DesignSync get_file` on `support.js` if you ever need to render locally (it expects `window.React` / `window.ReactDOM` globals).
